## 00 · 先给六条结论

读正文之前先有个底，这六条是整份文档的骨架：

1. **Redis 不是"更快的数据库"，它是"内存里的数据结构服务器"。**
   它解决的不是"存得下"，是"**取一次要多快**"。你的 Hive 解决的是"存得下 + 算得出"，两者不在一个问题上。

2. **它快的原因不是"因为用内存"这一句。** 是三条叠加：
   内存随机读比磁盘快 1000 倍（物理）、单线程省掉了锁和上下文切换（架构）、数据结构是按场景定制的（设计）。
   **只答"因为内存"的，面试官会继续问，然后你就没词了。**

3. **单线程是它的设计选择，不是它的缺陷**，但有三条硬代价：
   一条慢命令（`KEYS *`、大 `DEL`）会卡住**所有**客户端；CPU 只能用满一个核；单个 value 不能太大（建议 < 10KB）。

4. **Redis 的持久化不等于数据库的可靠性。** RDB 会丢最后一次快照之后的数据；
   AOF `everysec` 最多丢 1 秒。**把它当"缓存"用，别当"账本"用。**

5. **★★ 你现在的项目其实用不上 Redis。** 大屏读的是离线导出的静态 JS，打开就是毫秒级 —— 这已经等价于"预计算 + 缓存"了。
   真正需要 Redis 的是**三个还没做的场景**（在线查询 / 实时链路 / 实时大屏），第 08 章讲。
   **不知道这一点，你在面试里说"我项目用了 Redis"，一被追问就会露。**

6. **这一行最容易被忽略**：Redis 的瓶颈**几乎永远不是 CPU，是网络和内存**。
   所以"单线程能不能扛住"这个问题，正确答案是"能，因为它压根不用 CPU 干活"。

## 01 · Redis 到底是什么，插在你项目的哪个位置

### 1.1 先看一条延迟阶梯（这张图比任何定义都有用）

你项目里所有的"慢"，本质都是**数据在哪个物理介质上**决定的：

```
   1 纳秒    │ CPU 执行一条指令
 100 纳秒    │ ★ 内存随机读一次              ← Redis 在这里
 100 微秒    │ SSD 随机读一次（比内存慢 1000 倍）
  10 毫秒    │ 机械硬盘随机读一次（比内存慢 10 万倍）
   1 秒      │ 一个网络来回（跨机房）
  35 秒      │ ★ Spark 起一次会话查一次 ADS   ← 你现在的路
  54 分钟    │ ★ 你整条 gmall_evt_pipeline 跑一遍
```

**这张表要背下来，因为它是所有 Redis 面试题的物理依据。**

> **名词**：**随机读**指"直接跳到某个位置拿一条数据"，磁盘要先寻道再读，内存不用找，直接按地址取。
> 这就是为什么 100 纳秒 vs 10 毫秒 —— 差的是"要不要动机械部件 / 要不要发指令给闪存控制器"。

**你项目里的现实**：大屏要展示 `ads_trade_day` 那 31 行数据。
- 走 Hive：一次查询几秒到几十秒（HiveServer2 排队 + 编译 + 起 MR/Spark 作业）
- 走 Redis：一次查询 **0.1 毫秒**，快了 **5 个数量级以上**

差别不在"数据量小"，而在"**这 31 行数据是不是已经算好、放在内存里等着**"。

### 1.2 三个坐标：Redis 到底站在哪

很多人把 Redis 理解成"另一种 MySQL"，这是错的。用三个问题定位它：

| 问题 | MySQL / Hive | Redis |
|---|---|---|
| **数据在哪** | 磁盘（Hive 在 HDFS，MySQL 在本地文件） | **内存**（磁盘只做备份） |
| **一次查询多快** | 毫秒 ~ 分钟级 | **亚毫秒级**（0.1 ms 量级） |
| **能装多少** | TB ~ PB | **GB 级**（受内存限制，这是它的天花板） |
| **数据会不会丢** | 不会（有事务、有 WAL） | **可能丢**（取决于持久化配置） |
| **怎么查** | SQL（声明式，"我要什么"） | **命令**（"你对这个 key 做什么"） |

**一句话**：**Redis 是拿"能装多少"和"会不会丢"换"取一次有多快"。**

> 这三个词要一起记：**内存 → 快 → 但小且可能丢**。
> 面试官问"Redis 有什么缺点"，答"容量受内存限制、持久化有丢失窗口、单线程怕慢命令"，就是这三样。

### 1.3 那它到底是个什么"服务器"

Redis 的全名是 **REmote DIctionary Server（远程字典服务器）**。名字已经说明白了：

> **它是一个"你通过网络去操作的、装在内存里的字典（key → value）"。**

它是**独立进程**，跟你的 Hive 一样要单独启动、单独占端口（默认 **6379**）。
你的程序（Python / Java）连上它，发命令，它回结果。**它不会替你算数** —— 它只负责"存取"。

```
   你的程序  ──TCP 6379──▶  ┌────────────────────┐
                            │   redis-server     │
                            │   一个进程          │
                            │   数据全在内存里     │  ← 断电就没了（除非配持久化）
                            └────────────────────┘
                                      │
                                      └── 定时/按策略 落盘 ──▶ dump.rdb / appendonly.aof
```

**关键认知**：Redis 里**没有表、没有 SQL、没有 JOIN**。
它的数据模型是 **key → value**，value 可以是五种结构（第 03 章）。
所以"用 Redis 做数仓"这种想法从根上就不成立 —— 它没有能力做聚合和关联。

### 1.4 什么该进 Redis，什么绝对不该进（★ 这条比"是什么"更重要）

| 该进 | 为什么 | 你的项目里的例子 |
|---|---|---|
| **算好了、短时间内反复读的结果** | 一次算、一万次读 | ADS 层那 6 张表的查询结果 |
| **热点维表**（小、经常被查） | 查询次数远超更新次数 | `dim_product`（14 万行）、`dim_date`（365 行） |
| **需要原子计数的东西** | `INCR` 是原子的，不用加锁 | 页面 PV 计数、接口限流 |
| **需要排序 / 去重的集合** | ZSet / Set 就是为这个设计的 | 实时 GMV 排行榜（ZSet） |
| **短命的会话状态** | TTL 自动过期，不用写清理任务 | 登录 token、DS 任务锁 |

| 绝对不该进 | 为什么 | 会怎样 |
|---|---|---|
| **原始明细数据** | 1063 万行行为日志，内存装不起 | 内存打满 → 触发淘汰 → 缓存疯狂失效 → 比不用还慢 |
| **需要复杂查询的数据** | 没 SQL、没 JOIN、没 GROUP BY | 你得在应用层自己写循环，代码爆炸 |
| **不能丢的账** | 持久化有丢失窗口 | 财务数据丢了就是事故 |
| **超大 value**（>10MB） | 单线程读它一次要几十毫秒 | 卡住所有其他客户端 |

> ★ **判断口诀**：**"这份数据是不是"算好之后要被反复读很多次、而且丢了也能重算"？**
> 是 → 适合 Redis。否 → 不适合。
> 这句话能挡住 90% 的"乱用 Redis"。

### 1.5 一句话把它挂到你项目上

```
   ┌──────────── HDFS（存得下）────────────┐
   │  ODS → DWD → DWS → ADS（算得出）       │
   │          ↑ 这一步花 54 分钟            │
   └────────────────┬───────────────────────┘
                    │ ADS 结果（约 2000 行 / 不到 1 MB）
                    ▼
        ┌───────────────────────────┐
        │  Redis（取得快，0.1 毫秒） │  ← 你要学的东西在这
        └───────────────────────────┘
                    │
                    ▼
              大屏 / 接口 / 另一个程序
```

**Hive 负责"算一次"，Redis 负责"被读一万次"。** 这是它们唯一的关系。

## 02 · 凭什么快：三个机制 + 单线程的三个代价

这一章是面试的主战场。要能一层一层往下答，而不是停在"因为内存"。

### 2.1 机制一：数据在内存（物理层）

**物理上是什么**：内存（DRAM）是电容阵列，按地址直接访问，**不需要移动任何机械部件、不需要等控制器寻道**；
磁盘（HDD/SSD）要先发指令、排队、寻址，才能拿到一个块。

| 介质 | 随机读耗时 | 相对内存 | 你项目里的对应 |
|---|---|---|---|
| 内存 | ~100 ns | 1× | Redis 的数据 |
| NVMe SSD | ~100 μs | 慢 1000× | 集群系统盘 |
| 机械盘 | ~10 ms | 慢 10 万× | （本项目未用） |
| HDFS 一次查询 | 秒 ~ 分钟 | — | 因为有作业调度开销，不只是 IO |

> ⚠️ **只答到这一层是不够的**。因为面试官会接着问："那 Memcached 也在内存里，为什么 Redis 单线程还比它快/不比它慢？"
> 所以要往下讲两层。

### 2.2 机制二：单线程 + 事件循环（架构层）

**先纠正一个很多人都答错的细节**：

> **Redis 6.0 之后，"网络读写"是多线程的，但"命令执行"仍然是单线程。**
> 也就是说：多个线程负责从 socket 里把数据读出来、把结果写回去；
> **但真正去改内存里那个 key 的，永远只有一个线程。**

为什么敢这么做？因为**命令执行本身极快**（内存操作，几微秒），瓶颈在网络上。
把网络 IO 拆出去做多线程，等于"多雇几个人搬货，但仓库还是一个人管"——管仓库的那个人根本忙不过来。

**那单线程为什么反而快？三条原因：**

| 原因 | 具体表现 | 物理上是什么 |
|---|---|---|
| **① 没有锁** | 所有命令天然串行，不用 `lock` / `unlock` | 省掉了加锁解锁的原子指令，也省掉了"等锁"的时间 |
| **② 没有上下文切换** | 一个线程跑到底，CPU 缓存不会被打散 | 切换线程要保存/恢复寄存器、刷新 TLB，**每次约 1~10 微秒**，比一条 Redis 命令还贵 |
| **③ 没有多线程调试的坑** | 不存在"两个线程同时改一个 key" | 所有操作的原子性天然成立（`INCR` 就是原子的） |

> **名词**：**上下文切换**指 CPU 从一个线程换到另一个线程时，要把当前的状态（寄存器、栈指针）存起来、把另一个的恢复回来。
> 这个动作本身不干任何活，纯开销。线程越多、切换越频繁，浪费越大。

**一个线程怎么同时服务 1000 个客户端？靠 IO 多路复用（I/O multiplexing）。**

> **名词**：**IO 多路复用**指"一个线程同时盯着多个连接，谁有数据来了就处理谁"。
> Linux 上的实现叫 **epoll**。你不需要记 API，但要能讲清这个顺序：

```
① 客户端发来数据
      ↓
② 网卡收到 → 硬件中断 → 内核把数据放进这个 socket 的接收缓冲区
      ↓
③ 内核把这个 socket 标记为"就绪"，放进 epoll 的就绪列表
      ↓
④ Redis 主线程问 epoll："哪些连接有活了？"（一次系统调用，不是 1000 次）
      ↓
⑤ 拿到就绪列表，逐个执行命令（内存操作，几微秒）→ 写回结果
      ↓
⑥ 回到 ④，继续等
```

**对比传统的"一连接一线程"**：1000 个连接 = 1000 个线程，即使全都没数据，内核也要在这 1000 个线程之间不停切换 —— **全是在空转**。
epoll 把"检查谁有数据"这件事交给内核做，一次返回所有就绪的，**一个线程就够了**。

| 方式 | 1000 连接时的线程数 | 空闲时的开销 |
|---|---|---|
| 一连接一线程 | 1000 | 巨大的上下文切换（纯浪费） |
| **epoll 事件循环** | **1**（+ 几个 IO 线程） | 几乎为 0 |

### 2.3 机制三：数据结构是按场景定制的（设计层）

这一点最容易被忽略，但它解释了"为什么 Redis 快得不像单线程"。

**Redis 没有用通用的 B+ 树 / 哈希表一把梭**，而是给每种需求配了一个专门的底层结构：

| 你用的类型 | 底层结构 | 为什么这样设计 |
|---|---|---|
| String | **SDS**（简单动态字符串） | 自带长度字段 → 取长度 O(1)；预留空间 → 追加不用每次扩容 |
| Hash | **listpack**（小）/ **hashtable**（大） | 小的时候用连续内存（缓存友好），大了才转哈希表 |
| List | **quicklist**（listpack 组成的双向链表） | 兼顾"两端插入快"和"内存连续" |
| Set | **intset**（纯整数）/ **listpack** / **hashtable** | 纯整数时用有序数组，二分查找，省内存 |
| ZSet | **listpack**（小）/ **skiplist**（跳表） | 见 2.4 |

> **名词**：**listpack / ziplist** 是"把多个小元素紧凑地塞进一块连续内存"的结构。
> 好处是一次内存访问就能拿到多个元素（CPU 缓存命中率高），坏处是插入要挪动内存，所以**只在小数据量时用**。
> Redis 7.0 之后 `ziplist` 基本被 `listpack` 取代。

### 2.4 补一个高频追问：ZSet 为什么用跳表，不用红黑树？

**先说什么叫跳表（skiplist）**：在有序链表上面**叠几层"索引链表"**，查找时从最高层往下跳，跳过大量节点。

```
   第 3 层：  1 ──────────────────▶ 40 ─────────────▶ 90
   第 2 层：  1 ──────▶ 15 ───────▶ 40 ──────▶ 66 ──▶ 90
   第 1 层：  1 ─▶ 7 ─▶ 15 ─▶ 22 ─▶ 40 ─▶ 55 ─▶ 66 ─▶ 78 ─▶ 90
   第 0 层（全量有序链表）：1 → 7 → 15 → 22 → 40 → 55 → 66 → 78 → 90
```

查 66：第 3 层 1→40，第 2 层 40→66，**两步就到**。平均查找 O(log n)。

**为什么不用红黑树（平衡二叉搜索树）？三条理由：**

| 理由 | 具体 | 你的场景里意味着什么 |
|---|---|---|
| **① 范围查询更自然** | 跳表底层就是一条有序链表，`ZRANGEBYSCORE` 找到起点后**沿链表往后走就行**；红黑树要中序遍历，指针跳来跳去 | 排行榜"取第 10~20 名"是跳表的强项 |
| **② 实现简单、好维护** | 跳表插入/删除就是改几个指针；红黑树要处理一堆旋转和颜色 | 代码少 → bug 少 |
| **③ 内存访问更顺序** | 底层链表连续走，CPU 缓存命中率高；树的节点散落在堆里 | 快 |

> ⚠️ 注意：**"跳表比红黑树快"这个说法不严谨**。理论上都是 O(log n)。
> 准确的说法是：**在"范围查询 + 实现简单 + 缓存友好"这三点上跳表更合适**。这样答才经得起追问。

### 2.5 ★ 单线程的三条硬代价（必须知道，否则就是只报喜不报忧）

| 代价 | 现象 | 怎么避免 | 你的项目里要注意什么 |
|---|---|---|---|
| **① 慢命令阻塞全局** | 执行 `KEYS *`（全库扫）、`FLUSHALL`（清空）、大 key 的 `DEL` 时，**所有客户端一起卡住** | 用 `SCAN` 代替 `KEYS`；大 key 用 `UNLINK`（异步删）；禁用危险命令 | `KEYS gmall:ads:*` 这种写法**绝对不要**在上线代码里出现 |
| **② CPU 只能用满一个核** | 这台机器的其他核闲着，Redis 也上不去 | 单机单实例 → 多开几个实例分片 | 你只有一台 4GB 的小机器，无所谓 |
| **③ 大 value 灾难** | 一个 1MB 的 String，读一次要几毫秒，等于卡了全局几毫秒 | value 控制在 **10KB 以内**；大对象拆开 | 千万别把 1063 万行明细塞一个 key |

> ★ **这条要主动讲**：面试时"Redis 有什么缺点"答出"单线程怕慢命令 / 大 key"，比答"内存有限"更能证明你真用过。

### 2.6 本章小结（背这段就够）

> Redis 快，是因为：**① 数据在内存（物理上快 1000 倍）；② 单线程执行 + epoll 事件循环（省掉锁和上下文切换）；③ 底层结构按场景定制（跳表 / listpack / SDS）**。
> 单线程不是缺陷，但代价是：**一条慢命令卡住所有人、只能用满一个核、大 value 会拖垮它**。
> 而且 6.0 起**网络 IO 已经多线程，命令执行仍是单线程** —— 这个区分能直接区分"背过的"和"懂的"。

## 03 · 五种数据结构：什么时候用哪个

Redis 的 value 只有五种基本类型（外加几个扩展）。**面试考的不是"有哪五种"，是"这个场景你选哪个、为什么"。**

### 3.1 一张选型表（先记这张）

| 类型 | 一句话 | 你的场景能干嘛 | 常用命令 |
|---|---|---|---|
| **String** | 一个 key 对一个值（字符串/数字/二进制） | 缓存 JSON、计数器、分布式锁 | `SET` `GET` `INCR` `SETNX` |
| **Hash** | 一个 key 下挂很多"字段 → 值" | 存一个对象（如一个商品的所有属性） | `HSET` `HGET` `HGETALL` |
| **List** | 有序、可重复、两端进出 | 消息队列（简易）、最近 N 条记录 | `LPUSH` `RPOP` `LRANGE` |
| **Set** | 无序、**自动去重** | 去重统计、求交集/差集 | `SADD` `SISMEMBER` `SINTER` |
| **ZSet** | 每个元素带一个**分数**，按分数自动排序 | **排行榜**、延时队列 | `ZADD` `ZREVRANGE` `ZINCRBY` |

> **名词**：**ZSet（Sorted Set，有序集合）** 是 Redis 最有辨识度的结构 ——
> 它同时做到"按成员查分数 O(1)"和"按分数取排名 O(log n)"，别的结构做不到。

### 3.2 String：最常用，也最容易被用错

```bash
SET gmall:ads:trade_day '{"order_cnt":186059,"gmv":57575996.50}'   # 存
GET gmall:ads:trade_day                                             # 取
SETEX gmall:ads:trade_day 3600 '...'                                # 存 + 3600 秒后自动删
INCR  gmall:stat:pv                                                 # 原子自增（不存在会当成 0）
```

**底层**：SDS（简单动态字符串）。相比 C 原生字符串，它**自带长度**（取长度 O(1)，不用像 C 那样数到 `\0`）、
**预留空间**（追加时不用每次重新分配）、**二进制安全**（能存任意字节，包括 `\0`）。

**三个必须知道的能力**：

| 能力 | 命令 | 为什么重要 |
|---|---|---|
| 原子自增 | `INCR` / `INCRBY` | 不用"读出来 + 加 1 + 写回去"，**天然不会算错**（并发下这一点是致命的） |
| 不存在才写 | `SET key val NX` | **分布式锁的地基** |
| 带过期时间写 | `SET key val EX 60` / `SETEX` | 一条命令搞定"存 + 过期"，不会忘记设 TTL |

> ⚠️ **陷阱**：`SET k v NX EX 30` 和 "先 `SETNX` 再 `EXPIRE`" 不是一回事。
> 后者如果中间进程挂了，key 就**永远不过期**（死锁）。**要写就必须写成一条命令。**

### 3.3 Hash：存"对象"用，别拿它当表

```bash
HSET product:1004856 name "连衣裙" category_l1 "apparel" brand "unknown"
HGET product:1004856 name
HGETALL product:1004856
```

**什么时候用 Hash 而不是 String 存 JSON？**

| | String 存整个 JSON | Hash 存字段 |
|---|---|---|
| 改一个字段 | 读出整个 JSON → 改 → 写回（**非原子**） | `HSET key field val`（**原子**） |
| 只取一个字段 | 要反序列化整个 JSON | `HGET key field`（只传这一个值） |
| 网络传输 | 每次都传整个对象 | 只传需要的字段 |

> **判断**：**如果一个对象你经常"只改其中一两个字段"或"只取一两个字段" → 用 Hash。**
> 如果永远是整体读、整体写 → 用 String 存 JSON 更省事（也更好压缩）。

**注意**：Hash **不是表**。你没法"查所有 category_l1 = apparel 的商品" —— 那需要遍历所有 key。**这是 Redis 的边界，别硬来。**

### 3.4 List：能当队列，但别当正经消息队列

```bash
LPUSH queue:task "job1"     # 左边进
RPOP  queue:task            # 右边出（FIFO）
LRANGE queue:task 0 9       # 看前 10 个（不删除）
```

**底层**：quicklist（一串 listpack 组成的双向链表）。**两端插入删除 O(1)，中间访问 O(n)。**

> ⚠️ **这条要主动说**：**List 不适合做生产级消息队列**。
> 因为 `RPOP` 之后如果消费者崩了，消息就**丢了**（没有 ACK 机制）。
> Redis 后来专门加了 `Stream` 类型（带消费者组 + ACK），但**正经的消息队列还是 Kafka / RocketMQ**。
> 面试答"我用 List 做消息队列"是减分项，答"List 只能做简易队列，可靠性不够，生产上用 Kafka"是加分项。

### 3.5 Set：去重和"集合运算"

```bash
SADD uv:2019-10-01 513781527 513781528 513781527   # 加了 3 次，只有 2 个成员
SCARD uv:2019-10-01                                 # 2（自动去重）
SISMEMBER uv:2019-10-01 513781527                   # 1（在不在）
SINTER uv:2019-10-01 uv:2019-10-02                  # 两天的交集（连续两天都来的用户）
```

**底层**：元素全是整数且数量少 → `intset`（有序数组，二分查找）；
数量少且是字符串 → `listpack`；都超了 → `hashtable`。

> ★ **这个用法能直接对上你的项目**：`dws_user_event_day` 里有 `user_id × dt`。
> 如果要做"某天有多少独立访客"，用 `SADD uv:<dt> <user_id>` 然后 `SCARD` 就是答案，**而且天然去重**。
> 但注意 —— 你已经有 Hive 在做这件事了，**不要为了用 Redis 而用 Redis**（第 08 章会讲这个边界）。

### 3.6 ZSet：排行榜的唯一正解

```bash
ZADD   rank:gmv:2019-10-01 8106.42 1004856          # 商品 1004856 的分数是 8106.42
ZINCRBY rank:gmv:2019-10-01 120.5 1004856           # 分数再加 120.5（原子）
ZREVRANGE rank:gmv:2019-10-01 0 9 WITHSCORES        # 取分数最高的前 10 名
ZRANK   rank:gmv:2019-10-01 1004856                 # 这个商品排第几
```

**底层**：小数据量用 listpack；大了转 **skiplist + dict** 双结构（dict 用来 O(1) 查分数，skiplist 用来按分数排序）。

> **对照你的项目**：`ads_top_product_day` 是"31 天 × 每天 Top 50 = 1550 行"，这是 Hive 离线算出来的。
> 如果要做"**实时榜单**"（用户下单立刻反映到排行榜），ZSet 的 `ZINCRBY` 就是标准做法 ——
> **因为它是原子的，两个人同时加分会正确地累加，不会互相覆盖。**

### 3.7 三种"看着像"但容易选错的场景

| 需求 | 错误选法 | 正确选法 | 为什么 |
|---|---|---|---|
| 统计一篇文章的阅读量 | 用 Set 存每个用户 ID | **String + `INCR`** | 只关心数字，不用记谁看过；Set 会白占内存 |
| 判断用户是否点过赞 | 用 String 存 "1" | **Set + `SISMEMBER`**（或 Bitmap） | 要判断"这个人有没有"，Set 是 O(1)，String 也行但不好扩展 |
| 取最近 100 条操作记录 | 用 Set | **List + `LPUSH` + `LTRIM`** | Set 无序，拿不到"最近" |

## 04 · 持久化：内存里的东西怎么不丢

### 4.1 先明确一件事：Redis 有两种落盘方式，各有各的丢数据窗口

| 方式 | 干什么 | 什么时候落盘 | 最多丢多少 |
|---|---|---|---|
| **RDB** | 把内存**全量快照**写成一个二进制文件 `dump.rdb` | 按规则（如"900 秒内改了 1 次"）或手动 `BGSAVE` | **上一次快照之后的所有写入** |
| **AOF** | 把每条**写命令**追加到日志 `appendonly.aof` | 按 `appendfsync` 配置 | 见 4.3 |

> ★ **一个必须自己说出来的判断**：**如果你的数据"丢了能重算"（比如 ADS 表结果），那就该关掉持久化，或者只开 RDB。**
> 持久化是有成本的（fork 阻塞、写盘 IO），**为了一份能重算的数据付这个成本是浪费**。

### 4.2 RDB 的机制：fork + 写时复制（COW）

**这是本章最值钱的部分**，因为它能同时回答"fork 会不会卡"和"内存为什么会翻倍"两个追问。

执行 `BGSAVE` 时发生了什么（**按顺序**）：

```
① 主进程 fork 出一个子进程
      ↓ 物理上：复制页表（虚拟地址 → 物理地址的映射表），
      ↓        不是复制数据！父子进程指向同一批物理内存页，并把这些页标成"只读"
      ↓ 所以此刻内存占用几乎没变
      ↓
② 子进程开始遍历内存，把数据写进 dump.rdb
      ↓ 物理上：子进程顺序读内存 → 顺序写磁盘。它读的是"共享的那批页"
      ↓
③ 与此同时，主进程继续处理客户端请求
      ↓ 一旦主进程要"写"某个共享页：
      ↓   触发缺页异常 → 内核复制一份这个页给主进程 → 主进程写新的那份
      ↓   （这就是"写时复制"：只有被写的页才复制）
      ↓
④ 子进程写完，退出；父进程用新文件替换旧的 dump.rdb
```

**由此得出三条结论，每条都是面试考点：**

| 结论 | 原因 | 你的场景里意味着什么 |
|---|---|---|
| **fork 会短暂阻塞主线程** | 复制页表要时间，内存越大页表越大 | 16GB 的实例 fork 可能卡 **几百毫秒**；你 4GB 的机器无所谓 |
| **COW 会让内存"膨胀"，最坏翻倍** | 主进程写入越猛，被复制的页越多 | 所以要留 **50% 空闲内存**，否则 OOM |
| **RDB 是"某个时刻"的快照** | 子进程遍历期间主进程的写入不在里面 | **快照之后的数据全会丢**，这点必须诚实 |

> **名词**：**COW（Copy-On-Write，写时复制）** 指"共享同一份数据，谁要改谁自己复制一份再改"。
> 它让 fork 的瞬间几乎零成本，代价是**后续的每次写入都可能触发一次内存复制**。

### 4.3 AOF 的三档 fsync

> **名词**：**fsync** 指"让操作系统把缓冲区里的数据真正刷到磁盘上"。
> 不 fsync 的话，数据只在操作系统的页缓存里，**断电就没了**（虽然进程还活着）。

| 配置 | 行为 | 最多丢 | 性能 |
|---|---|---|---|
| `appendfsync always` | 每条命令都 fsync | **几乎不丢**（最坏丢一条） | **最慢**（每条命令都要等磁盘） |
| `appendfsync everysec` | 每秒 fsync 一次（后台线程做） | **最多 1 秒** | **快**（默认值） |
| `appendfsync no` | 交给操作系统决定（通常 30 秒） | 最多 30 秒 | 最快，但不可控 |

**AOF 为什么会越来越大、怎么解决？**

因为它是"追加日志"——你改了同一个 key 一万次，日志里就有一万条命令。
Redis 用 **AOF 重写（rewrite）** 解决：fork 一个子进程，**只根据当前内存状态生成"最小命令集"**（比如 `SET k v` 一条），写成一个新文件。

> 注意：**重写也是 fork + COW** —— 跟 RDB 的机制一模一样。这也是为什么"fork 的代价"是 Redis 运维的核心话题。

### 4.4 混合持久化（4.0 之后的默认推荐）

问题：RDB 恢复快但丢得多；AOF 丢得少但文件大、恢复慢（要重放所有命令）。

**混合持久化（`aof-use-rdb-preamble yes`）**：AOF 文件的前半部分是 **RDB 格式的全量快照**，后半部分是**增量的 AOF 命令**。

- **恢复时**：先加载 RDB 部分（快），再重放增量命令（少）→ 又快又不丢
- **代价**：AOF 文件不再是纯文本，人看不懂了（但反正你也不该手改）

### 4.5 选型表（照这个答）

| 你的场景 | 建议 | 理由 |
|---|---|---|
| **纯缓存**（数据能重算） | **关持久化**，或只开 RDB | 挂了从 DB 重灌就行，不值得付 IO 成本 |
| 缓存 + 少量"丢了会疼"的状态（如分布式锁） | **RDB + AOF everysec** | 锁丢了会导致重复执行，值得多花点 |
| 当"主存储"用 | **不要这么干** | Redis 不是数据库，容量和可靠性都不够 |

> ★ **这是我最想让记住的一条**：**"Redis 持久化能把 Redis 当数据库用吗？" —— 不能。**
> 它只是"减少重启后的数据损失"，不是"保证不丢"。**能重算的进 Redis，不能丢的别只放在 Redis。**

## 05 · 内存满了怎么办：淘汰策略

### 5.1 两件事要分清：过期删除 vs 内存淘汰

| | 触发条件 | 干什么 |
|---|---|---|
| **过期删除** | key 到了 `EXPIRE` 设的时间 | 把这个 key 删掉 |
| **内存淘汰** | 内存用量 > `maxmemory` | 按策略**主动踢掉一些 key**（不管它们有没有过期） |

**过期删除是怎么做的？两种结合：**

1. **惰性删除**：你来读这个 key 的时候，发现它过期了，顺手删掉（不读就不删）
2. **定期删除**：每 100ms 随机抽 20 个设了过期时间的 key，删掉过期的；如果这 20 个里超过 25% 是过期的，就再来一轮

> 为什么这么设计？因为**遍历所有 key 太慢**（会阻塞主线程）。
> 代价是：**可能有一批过期 key 还占着内存**（没被抽到、也没人读）。这是"单线程 + 内存"的必然折中。

### 5.2 八种淘汰策略

| 策略 | 淘汰范围 | 淘汰规则 | 用在哪 |
|---|---|---|---|
| `noeviction`（**默认**） | — | **不淘汰**，写命令直接报错 | 当数据库用时（但别这么用） |
| `allkeys-lru` | 所有 key | 最近**最久没被访问**的 | **纯缓存的标准选择** |
| `allkeys-lfu` | 所有 key | **访问频率最低**的 | 有明显热点（少数 key 被疯狂访问） |
| `allkeys-random` | 所有 key | 随机 | 访问分布均匀时 |
| `volatile-lru` | 只淘汰**设了过期时间**的 | LRU | 缓存和持久数据混在一起 |
| `volatile-lfu` | 同上 | LFU | 同上 |
| `volatile-random` | 同上 | 随机 | 少见 |
| `volatile-ttl` | 同上 | **剩余存活时间最短**的 | 想让快过期的先走 |

### 5.3 ★ Redis 的 LRU 是"近似 LRU"，这点很多人不知道

**真正的 LRU** 要维护一条完整的访问顺序链表 —— 每次访问都要移动节点，内存和 CPU 成本都高。

**Redis 的做法**：`maxmemory-samples`（默认 5）—— **随机抽 5 个 key，从里面挑最久没被访问的淘汰**。

- 好处：不用维护链表，几乎零成本
- 代价：**可能淘汰掉"其实刚被访问过"的 key**（因为没抽到它）

> 把 `maxmemory-samples` 调到 10，命中率会更接近真 LRU，但 CPU 消耗也会上升。**默认 5 是权衡后的结果。**

### 5.4 你的场景该选哪个

你的 ADS 结果缓存：**所有 key 地位相同（都是 ADS 查询结果），丢了都能从 Hive 重算** →
**`allkeys-lru` + `maxmemory 512mb`** 就够了。

> ⚠️ 千万不要 `volatile-*` 系列，除非你能保证**所有**缓存 key 都设了 TTL。
> 如果有一批 key 没设 TTL，`volatile-lru` 会在"可淘汰的 key 用完"之后**直接开始报错**（行为等同于 `noeviction`）—— 这个坑很隐蔽。

## 06 · 缓存三大问题：穿透 / 击穿 / 雪崩

**这三个词的区分是面试第一道筛子**。先给一张对比表，把混淆点钉死：

| | 谁出问题 | 什么时候 | 后果 | 关键词 |
|---|---|---|---|---|
| **穿透**（penetration） | **数据本身不存在** | 查一个**数据库里也没有**的 key | 每次都打到 DB | "查不到" |
| **击穿**（breakdown） | **一个热点 key** | 这个 key **刚好过期**的瞬间 | 大量请求同时打 DB | "一个点塌了" |
| **雪崩**（avalanche） | **一大批 key** | 它们**同时过期**，或 Redis 整体挂了 | DB 瞬间被压垮 | "一片塌了" |

> 记忆法：**穿透 = 查的东西压根没有；击穿 = 一个洞被捅穿；雪崩 = 整片塌下来。**

### 6.1 缓存穿透：查一个不存在的东西

**现象**：攻击者用 `user_id = -1` 疯狂请求。缓存里没有 → 查 DB → DB 也没有 → 不写缓存 → 下次还查 DB。
**每次请求都穿透到 DB，缓存等于没起作用。**

**三种解法，代价各不相同：**

| 解法 | 怎么做 | 优点 | 代价 |
|---|---|---|---|
| **① 缓存空值** | DB 查不到也存一个 `null`，TTL 设短（如 60 秒） | 实现最简单 | 浪费内存；如果攻击者每次换随机 key，**照样穿透** |
| **② 布隆过滤器** | 把所有存在的 key 放进一个位数组，查询前先问它 | 内存极省（1 亿个 key 约 100MB） | **有假阳性**（说不存在的可能误判成存在），**没有假阴性**（说不存在就一定不存在）；**删除困难** |
| **③ 接口层校验** | 参数合法性先校验（ID 必须 > 0、格式必须对） | 成本最低，能挡掉一大部分 | 只能挡"明显非法"的 |

> **名词**：**布隆过滤器（Bloom Filter）** 是一个位数组 + 几个哈希函数。
> 存元素时把几个哈希位置置 1；查询时看这几个位置是不是全 1。
> 全是 1 → "可能存在"（可能是别人撞出来的）；有一个 0 → "**一定不存在**"。
> 所以它**只能用来"挡掉肯定不存在的"，不能用来"确认存在"**。

**落到你的项目**：大屏的日期参数是最典型的穿透入口 ——
`?dt=2019-13-45` 这种非法日期，如果不校验，会一路打到 Hive 上，**每次 35 秒**。
**这里最该做的是③（参数校验），而不是上布隆过滤器。** 别为了炫技加复杂度。

### 6.2 缓存击穿：一个热点 key 过期的那一瞬间

**现象**：`gmall:ads:trade_day` 是全站最热的 key，TTL 到期的**那一秒**，
1000 个并发请求同时发现"缓存没了"，**一起去查 Hive** → Hive 被压死（你的 Hive 一次查询 35 秒，1000 个并发直接排队到天荒地老）。

**两种解法：**

| 解法 | 怎么做 | 优点 | 代价 |
|---|---|---|---|
| **① 互斥锁（只让一个去查）** | 第一个发现缓存失效的请求 `SET lock NX EX 10` 抢锁，抢到的去查 DB 并回填；**没抢到的等一会儿再读缓存** | 保证只有一个请求打 DB | 没抢到的请求要**等待**（延迟变高）；锁本身要考虑超时和误删 |
| **② 逻辑过期（永不过期）** | 存的时候**不设 TTL**，而是在 value 里存一个 `expire_at` 字段；读到发现"逻辑上过期了"，就**异步起一个线程去刷新**，当前这个请求**先返回旧数据** | 请求永不阻塞，用户体验最好 | **会返回旧数据**（牺牲一致性）；实现更复杂 |

> ★ **这两个的取舍要能讲清**：
> **互斥锁 = 保一致性、牺牲可用性（有人要等）；逻辑过期 = 保可用性、牺牲一致性（返回旧值）。**
> 这不是技术选型，是业务选型 —— **面试答出这句话，比背实现细节值钱得多。**

### 6.3 缓存雪崩：一大片同时塌

**两种成因：**

| 成因 | 现象 | 解法 |
|---|---|---|
| **① 大量 key 同时过期** | 你在 00:00 一次性预热了 100 个 key，TTL 都设 24 小时 → **第二天 00:00 全部同时失效** | **TTL 加随机偏移**：`3600 + random(0, 600)` 秒 |
| **② Redis 整体挂掉** | 所有请求直接冲到 DB | **① 高可用**（主从 + 哨兵，第 07 章）；**② 限流降级**（Redis 挂了就返回缓存里的旧文件 / 直接拒绝，别让 DB 裸奔）；**③ 多级缓存**（本地缓存 + Redis） |

> ★ **这条对你有直接意义**：如果你给大屏做缓存预热，**千万别把 6 张 ADS 表的 TTL 都设成同一个值**。
> 加个随机偏移，成本是一行代码，收益是"不会在某个整点集体失效"。

### 6.4 还有第四个词：缓存一致性

面试常接着问："**更新数据的时候，是先删缓存还是先更 DB？**"

**标准答案（Cache Aside 模式）**：**先更新 DB，再删除缓存**（不是更新缓存）。

为什么是"删除"而不是"更新"？因为删除是**幂等**的（删两次和删一次结果一样），
而更新缓存要算新值，**并发下可能用旧值覆盖新值**。

为什么是"先 DB 后缓存"？反过来的话（先删缓存再更 DB），在"删完、DB 还没更"的窗口里，
别的请求会把**旧值**重新加载进缓存，然后一直错下去。

> ⚠️ 但"先 DB 后删缓存"也**不是绝对安全**：极端并发下仍有一瞬间的不一致。
> 所以更严谨的说法是：**缓存只能做到"最终一致"，做不到"强一致"。要强一致就别用缓存。**

## 07 · 主从 / 哨兵 / Cluster

这一章权重不高（★★），但三个名词必须能区分。

| 方案 | 解决什么 | 怎么工作 | 没解决什么 |
|---|---|---|---|
| **主从复制** | **读扩展 + 数据备份** | 从节点连上主节点，主节点把写命令传播给从节点 | **主挂了不会自动切换**（要人工） |
| **哨兵（Sentinel）** | **自动故障切换** | 独立的哨兵进程监控主节点，主挂了**投票选一个从节点升为主** | 容量还是单机的（一个主节点装不下就没办法） |
| **Cluster（集群）** | **容量横向扩展** | 把数据按 key 分到 **16384 个槽（slot）**，每个节点负责一部分槽 | 运维复杂；**跨槽的多 key 操作受限** |

### 7.1 为什么是 16384 个槽（这个数字面试爱问）

因为集群节点之间要**定期发心跳包**，心跳里要带"我负责哪些槽"的信息 —— 用**位图（bitmap）**表示。

- 16384 个槽 = 16384 bit = **2 KB**
- 如果是 65536 个槽 = 65536 bit = **8 KB**

节点几十个、每秒心跳好几次，**8KB 的心跳包纯属浪费带宽**。
而且 Redis 单机内存上限通常也就几十 GB，**16384 个槽（每个槽约几 MB~几百 MB）已经够用**。

> 结论：**16384 是"够用 + 心跳包别太肥"之间的折中**，不是随便定的。

### 7.2 你必须知道的：集群模式下多 key 操作会失败

```bash
# 如果 key1 和 key2 落在不同的槽 → 报 CROSSSLOT 错误
MGET key1 key2
```

解决：**用 hash tag** —— 把 key 里的一部分用 `{}` 括起来，Redis **只按 `{}` 里的内容算槽**，这几个 key 就必然同槽：

```bash
MGET {user:513781527}:name {user:513781527}:age    # 都按 "user:513781527" 算槽 → 同槽
```

### 7.3 你的项目需要哪个？

**都不需要。** 单机 Redis 足够 —— 你的数据量不到 1MB。
**但面试会问**，所以要能讲清"小项目单机够，需要高可用才上哨兵"这个判断。

## 08 · ★ 接进你的项目：一个诚实可行的方案

**这一章是整份文档的核心**，因为它回答"你为什么用它" —— 这才是面试官真正在意的。

### 8.1 先说一个不太好听的事实

**你现在的架构，Redis 是"用不上"的。**

```
gmall_evt_pipeline 跑完（54 分钟）
        ↓
export_dashboard_real.sh 导出
        ↓
dashboard_data_real.js（静态文件，约几十 KB）
        ↓
dashboard_real.html 双击打开 → 毫秒级渲染
```

**这条链路里，"打开快"是因为数据被预计算 + 预导出成静态文件了，不是因为有什么缓存。**
从原理上说，**这个静态 JS 文件本身就是一层"缓存"** —— 它已经做到了"算一次、读无数次"。

> ★ **这是一个必须自己意识到的判断**。如果你在简历上写"项目使用 Redis 做缓存优化"，
> 面试官问"优化前多慢、优化后多快、你怎么测的"，你答不出来，**这一条会成为整份简历的可信度黑洞**。
>
> **比"用上 Redis"更重要的是"知道什么时候不需要它"** —— 后者恰恰是更难的能力。

### 8.2 那它该插在哪：三个真实需要它的场景

| 场景 | 为什么现在没有 | 加了 Redis 解决什么 | 难度 |
|---|---|---|---|
| **A. 大屏改成在线查询** | 现在是静态导出，维度固定（不能按类目下钻、不能自由选日期） | 用户点一下换维度 → 后端查 Hive（35 秒）→ **必须加缓存，否则不可用** | 中 |
| **B. 实时链路**（Flink / Spark Streaming） | 全离线，没有流 | 流式 join 维表时，**必须用 Redis 存 `dim_product`**（14 万行），否则每条事件都去查 Hive 就废了 | 高 |
| **C. 实时大屏** | 大屏数据是"昨天的" | 最近 N 分钟的 GMV / DAU 存 Redis，**`ZINCRBY` / `INCR` 原子累加** | 中高 |

> **三个里 A 最容易落地、B 最能讲出深度、C 最有视觉冲击。**
> 但**都建立在一个前提上：你先把 Redis 跑起来，并且真的踩过至少一个坑。**

### 8.3 推荐路径：场景 A 的最小可行版（能在一晚上做完）

**目标**：给大屏加一个"在线查询接口"，用 Redis 做缓存，并且**保留静态文件作为降级方案**。

**架构**：

```
   dashboard_real.html
        │  ① 先试 fetch /api/ads/trade_day
        ▼
   Python Flask（新增，约 80 行）
        │  ② 先查 Redis
        ├──▶ 命中 → 直接返回 JSON（0.1 ms）
        └──▶ 未命中 → beeline 查 Hive ADS 表（35 s）→ 写回 Redis（TTL 24h + 随机偏移）→ 返回
                                    │
                                    └──▶ ③ 如果 Redis / 接口都挂了 → 大屏回退读本地 dashboard_data_real.js
```

**为什么这样设计（每条都是面试可讲的点）**：

| 设计 | 面试怎么讲 |
|---|---|
| **缓存 + 降级两个来源** | "缓存不可用时要保证页面还能打开，所以我保留静态文件做兜底 —— 这是可用性优先的设计" |
| **TTL 加随机偏移** | "6 张表的 key 如果同时过期会雪崩，所以 TTL 用 `86400 + random(0,3600)`" |
| **缓存空结果的 key**（TTL 60 秒） | "防止非法日期参数穿透到 Hive，一次 35 秒" |
| **只缓存 ADS，不缓存明细** | "ADS 只有 2108 行，全量不到 1MB;明细 1063 万行，进 Redis 就是自杀" |
| **不缓存 DWS** | "DWS 是 162 万 / 126 万行，体积大、访问频率低，缓存收益为负" |

**Key 设计（照抄即可）**：

```
gmall:ads:trade_day                 String(JSON)   TTL 86400 + rand(0,3600)
gmall:ads:active_user_day           String(JSON)   同上
gmall:ads:funnel_day                String(JSON)   同上
gmall:ads:repurchase_day            String(JSON)   同上
gmall:ads:category_day              String(JSON)   同上（434 行，约 60KB）
gmall:ads:top_product_day:<dt>      String(JSON)   每天一个 key，1550 行拆开更好
gmall:ads:__miss__:<参数hash>       String("1")    TTL 60，专治穿透
```

> **为什么 key 要带 `gmall:` 前缀**：一个 Redis 实例经常被多个应用共用，
> 前缀是"命名空间"，方便用 `SCAN gmall:ads:*` 单独清理，**也避免和别人的 `trade_day` 撞车**。

**容量估算（给面试官算一笔账）**：

| 表 | 行数 | 按 150 字节/行估 | 说明 |
|---|---|---|---|
| ads_trade_day | 31 | ~5 KB | |
| ads_active_user_day | 31 | ~5 KB | |
| ads_funnel_day | 31 | ~5 KB | |
| ads_repurchase_day | 31 | ~3 KB | |
| ads_category_day | 434 | ~65 KB | |
| ads_top_product_day | 1,550 | ~230 KB | |
| **合计** | **2,108** | **~310 KB** | 加上 Redis 自身开销，撑死 **1 MB** |

> **结论**：**整个 ADS 层进 Redis 只要 1MB。你的机器有 4GB，能装下 4000 个这样的项目。**
> 这句话很有说服力 —— 它同时说明了"为什么该缓存 ADS"和"为什么不该缓存明细"。
> ⚠️ 这里的 150 字节是**估算**，不是实测 —— 你跑完第 09 章实验 6 之后，把 `INFO memory` 的真实值填进来。

### 8.4 ★ 什么时候你才能说"我项目用了 Redis"

**只有做完下面三件事，这句话才是真的**：

1. **Redis 真的跑起来了**，你的程序真的连上了它（有 `redis-cli PING` → `PONG` 之外的证据：程序日志里有真实的命中/未命中）
2. **你真的测过"有缓存 vs 没缓存"的耗时差**（不是背"快 1000 倍"，是你自己测出来的两个数）
3. **你至少踩过一个坑并解决了**（比如大 key 阻塞、TTL 同时过期、或者 `KEYS *` 把服务卡住）

**第 3 条最重要** —— 面试官分辨"真做过"和"背过"，靠的就是你有没有踩过坑、怎么定位的。
**踩坑故事是编不出来的。**

## 09 · 动手实验：在你集群上跑一遍

> ⚠️ **写这份文档时你的集群是关机的**（SSH 连 192.168.87.131 超时）。
> 这一章的命令都是标准命令，但我**没有在你的机器上实测过**，所以每条都给了「预期结果」和「判据」——
> **跑出来不一样就说明有问题，别硬往下走**。

### 实验 0：装 Redis（在 lrh-1 上）

```bash
sudo apt update && sudo apt install -y redis-server
systemctl status redis-server --no-pager | head -5
```

**判据**（⚠️ 用外部判据，不要用 `systemctl is-active`，见 `CONTEXT.md` 陷阱 2）：

```bash
ss -lntp | grep 6379          # 必须有输出，说明端口在监听
redis-cli PING                # 必须回 PONG
redis-cli INFO server | grep redis_version    # 看版本
```

**预期**：`PONG`，版本 7.x（Ubuntu 24.04 默认源是 7.0 或 7.2）。

> ⚠️ **Ubuntu 的默认配置有个坑**：`bind 127.0.0.1 ::1` 只监听本机。
> 如果你要让 lrh-2/3 上的程序连过来，得改 `/etc/redis/redis.conf` 的 `bind`，
> **并且设 `requirepass`**（否则等于把数据库裸奔在局域网上）。**本项目单机用，不用改。**

### 实验 1：验证"内存里的读写有多快"

```bash
# 存 10 万个 key，看耗时
time redis-cli eval "
  for i=1,100000 do redis.call('SET','bench:'..i,'v'..i) end
  return redis.call('DBSIZE')
" 0
```

**预期**：10 万次 `SET` 在**几十毫秒到 1 秒**之间（取决于是否开了持久化、是否 pipelined）。
**判据**：平均下来**每次写入在微秒级** —— 这就是"内存比磁盘快 1000 倍"的体感来源。

> ⚠️ 这个写法是**在 Redis 内部执行 Lua 循环**，省掉了网络往返；
> 如果用 `redis-benchmark` 测，结果会低很多（因为网络往返也是成本）。
> **两种测法测的是不同的东西，别混着说。**

### 实验 2：验证"单线程会被慢命令卡住"（★ 最重要）

开**两个**终端：

```bash
# 终端 A：先塞 100 万个 key
redis-cli eval "for i=1,1000000 do redis.call('SET','k'..i,1) end" 0

# 终端 B：开一个持续 PING 的循环，观察延迟
while true; do redis-cli PING; done
```

然后**在终端 C**（或 A）执行：

```bash
redis-cli KEYS '*' | wc -l
```

**预期**：`KEYS *` 执行期间，**终端 B 的 `PING` 会明显停顿**（100 万 key 可能要几百毫秒到几秒）。

**判据**：`PING` 的输出出现了一段"空白间隔" —— **这就是"单线程被阻塞"的直接证据**。

> ★ **这个实验的价值**：它把"单线程怕慢命令"从一句背诵，变成你亲眼看到的现象。
> 面试时你可以说"我实测过，100 万 key 的 `KEYS *` 会让 PING 停顿 X 秒" —— **这个细节没人能背出来。**

### 实验 3：验证五种数据结构的行为

```bash
# String 的原子自增
redis-cli SET pv 0
redis-cli INCR pv          # 1
redis-cli INCRBY pv 10     # 11

# Set 自动去重（加 3 次同一个成员）
redis-cli DEL uv
redis-cli SADD uv u1 u2 u1
redis-cli SCARD uv         # 预期 2（不是 3）

# ZSet 自动排序（乱序插入）
redis-cli DEL rank
redis-cli ZADD rank 8106.42 p1 120.5 p2 50000 p3
redis-cli ZREVRANGE rank 0 -1 WITHSCORES
# 预期：p3(50000) → p1(8106.42) → p2(120.5)，按分数从高到低

# Hash
redis-cli DEL prod
redis-cli HSET prod name "连衣裙" brand "unknown"
redis-cli HGETALL prod

# 看每个 key 的底层编码（★★ 这条能验证第 03 章的"按大小切换结构"）
redis-cli OBJECT ENCODING uv      # 小整数集合 → intset 或 listpack
redis-cli OBJECT ENCODING rank    # 小 ZSet → listpack
redis-cli SADD big $(seq 1 200)   # 塞超过阈值
redis-cli OBJECT ENCODING big     # 预期变成 hashtable
```

**判据**：`OBJECT ENCODING` 的输出**从 `listpack` 变成 `hashtable`** ——
这是你亲眼看到"Redis 会按数据量自动换底层结构"，比背"listpack 转 hashtable"有说服力得多。

### 实验 4：看 RDB 快照生成与 fork

```bash
redis-cli CONFIG GET save            # 看自动快照规则
redis-cli INFO persistence | grep -E "rdb_last_bgsave|rdb_changes"
redis-cli BGSAVE                     # 手动触发一次
redis-cli INFO persistence | grep rdb_last_bgsave_status   # 预期 ok
ls -lh /var/lib/redis/dump.rdb       # 看文件大小
```

**判据**：`rdb_last_bgsave_status:ok` + `dump.rdb` 存在且大小 > 0。

**再验证 COW**：`BGSAVE` 之后立刻 `INFO memory` 看 `used_memory` 和
`used_memory_rss`（后者是操作系统实际给这个进程的物理内存）——
**RSS 会大于 used_memory**，差的那部分就是 COW 复制出来的页。

> **名词**：`used_memory` 是 Redis 自己统计的"数据占了多少"；
> `used_memory_rss` 是"操作系统实际分配了多少物理内存"。**两者不等是正常的**，差额包括内存碎片 + COW 副本。

### 实验 5：验证过期与淘汰

```bash
redis-cli SET tmp hello EX 3
redis-cli TTL tmp         # 3（或 2）
# 等 4 秒
redis-cli GET tmp         # (nil)
redis-cli TTL tmp         # -2（表示 key 不存在；-1 表示存在但没设过期）

# 淘汰策略（★ 先看清楚默认值，再做）
redis-cli CONFIG GET maxmemory-policy     # Ubuntu 默认可能是 noeviction
redis-cli CONFIG SET maxmemory 4mb
redis-cli CONFIG SET maxmemory-policy allkeys-lru
redis-cli INFO memory | grep used_memory_human
# 再塞大量 key 把它撑爆，观察 evicted_keys 增长
```

**判据**：`INFO stats | grep evicted_keys` 从 0 开始增长，**且写入不报错** —— 说明淘汰生效了。

> ⚠️ 如果 `maxmemory-policy` 是 `noeviction`，撑爆之后写命令会**直接报错**
> `OOM command not allowed when used memory > 'maxmemory'`。**这个报错你要亲眼看一次**，
> 因为线上最常见的 Redis 故障就是它。

### 实验 6：测你自己的 ADS 缓存容量（做完填回 8.3 的估算）

前提：集群里 `gmall` 库有数据（你的 ADS 6 张表）。

```bash
# 把 ads_trade_day 导出成 JSON，塞进 Redis，看真实占用
BEELINE=/opt/hive/apache-hive-3.1.3-bin/bin/beeline
$BEELINE -u jdbc:hive2://lrh-1:10000 --outputformat=csv2 \
  -e "SELECT * FROM gmall.ads_trade_day" > /tmp/trade_day.csv

redis-cli -x SET gmall:ads:trade_day < /tmp/trade_day.csv
redis-cli MEMORY USAGE gmall:ads:trade_day      # ★ 这个数字才是真的
redis-cli INFO memory | grep used_memory_human
```

**判据**：`MEMORY USAGE` 返回的字节数 —— **对比 8.3 里我估的 5KB，差多少？**

> ★ 这个实验的意义：**把"我估算 310KB"变成"我实测 XXX KB"**。
> 面试时说"我实测整个 ADS 层进 Redis 只占 X MB"，比说"应该不大"强一百倍。

### 实验 7：★ 制造一次"缓存击穿"，看它长什么样

这是**唯一一个能让你真正理解三大问题的实验**。

```bash
# 终端 A：模拟"热点 key 刚过期，100 个请求同时到达"
redis-cli SET hot v EX 1     # 1 秒后过期
sleep 2

# 终端 B：并发 100 个 GET
seq 100 | xargs -P 100 -I{} redis-cli GET hot
```

**你会看到什么**：全是 `(nil)` —— **100 个请求全部没命中，如果背后是 DB，这 100 个会全部打到 DB。**

**然后再做一次"加了互斥锁"的对照**：

```bash
# 用一个 key 模拟锁：只有抢到锁的那个才去"查 DB"
redis-cli SET hot v EX 1; sleep 2
for i in $(seq 1 5); do
  redis-cli SET lock:hot 1 NX EX 5   # NX = 只有不存在时才设成功
done
```

**预期**：5 次里只有 **1 次**返回 `OK`，其余 4 次返回 `(nil)`（抢锁失败）。

> ★ **这就是"互斥锁防击穿"的最小验证**：抢到锁的 1 个去查数据，其他的等待。
> 面试时你说"我用 `SET NX EX` 做过互斥锁，实测 5 个并发只有 1 个拿到锁"，**这是硬证据**。

> ⚠️ **分布式锁的两个必备细节**（面试必追问）：
> ① **value 必须唯一**（如 UUID），释放时用 Lua 比对"是不是我加的锁"，否则会误删别人的锁；
> ② **必须有超时**（`EX`），否则持锁进程崩了就是死锁。

## 10 · 面试 FAQ（22 问）+ 被证伪的常见说法

### 10.1 高频 22 问（每题给"能过关"的答法）

| # | 问题 | 答题要点（照这个结构说） |
|---|---|---|
| 1 | Redis 是什么 | 内存里的**数据结构服务器**，key-value，支持 5 种结构；解决"取一次多快"，不解决"存得下" |
| 2 | 为什么快 | 三条：**内存（快 1000×）+ 单线程免锁免切换 + 结构定制**。别只说内存 |
| 3 | 单线程还快？ | 命令执行是内存操作（微秒级），瓶颈在网络；**6.0 起 IO 多线程、命令执行仍单线程** |
| 4 | 单线程有什么问题 | 慢命令阻塞全局（`KEYS`/大 `DEL`）、只能用满一核、大 value 拖垮 |
| 5 | 五种结构 | String / Hash / List / Set / ZSet，**各配一个真实用法**（别只报名字） |
| 6 | ZSet 底层 | **跳表 + dict**。为什么不用红黑树：范围查询顺、实现简单、缓存友好 |
| 7 | 持久化方式 | RDB（快照，丢得多）/ AOF（日志，丢得少）/ 混合（推荐） |
| 8 | RDB 怎么做的 | `fork` + **COW**；fork 复制页表不复制数据；写时复制导致内存可能翻倍 |
| 9 | AOF 三档 | always（最安全最慢）/ **everysec（默认，丢 1 秒）** / no |
| 10 | 能不能当数据库 | **不能**。容量受内存限、持久化有丢失窗口。**能重算的才进 Redis** |
| 11 | 过期怎么删 | **惰性删除 + 定期删除**（每 100ms 抽 20 个，超 25% 过期就再来一轮） |
| 12 | 淘汰策略 | 8 种；缓存用 `allkeys-lru`；**注意 Redis 的 LRU 是采样近似，不是真 LRU** |
| 13 | 缓存穿透 | 查不存在的数据 → **缓存空值 / 布隆过滤器 / 参数校验** |
| 14 | 缓存击穿 | **单个热点 key 过期** → 互斥锁（牺牲可用性）/ 逻辑过期（牺牲一致性） |
| 15 | 缓存雪崩 | **大批 key 同时过期 或 Redis 挂了** → TTL 加随机 + 高可用 + 限流降级 |
| 16 | 三个怎么区分 | 穿透=查不到、击穿=一个点、雪崩=一片 |
| 17 | 缓存一致性 | **Cache Aside：先更 DB，再删缓存**（不是更新缓存）。只能做到最终一致 |
| 18 | 分布式锁怎么写 | `SET key uuid NX EX 30`；释放用 Lua 比对 value；**value 必须唯一、必须带超时** |
| 19 | 主从/哨兵/集群 | 主从=备份+读扩展；哨兵=自动切换；Cluster=分片（**16384 槽**） |
| 20 | 为什么 16384 槽 | 心跳包要带槽位图：16384 bit=**2KB**，65536 就是 8KB，**太浪费带宽** |
| 21 | 集群多 key 操作 | 会 `CROSSSLOT` 报错；用 **hash tag `{...}`** 让 key 落同槽 |
| 22 | 大 key 怎么处理 | 拆开（`hash` 分字段 / `list` 分页）；删除用 **`UNLINK`**（异步）不用 `DEL` |

### 10.2 ★ 被证伪的常见说法（这些"流行答案"其实是错的）

这一节是给你**避坑**的 —— 网上流传很广，但一深问就塌：

| 流行说法 | 为什么不对 | 正确的说法 |
|---|---|---|
| "Redis 是单线程的" | 6.0 起网络 IO 是多线程的 | "**命令执行**是单线程，网络读写是多线程的" |
| "Redis 快是因为数据在内存" | 只说对 1/3；Memcached 也在内存 | 内存 + 免锁 + 结构定制，**三条叠加** |
| "跳表比红黑树快" | 理论上都是 O(log n) | "**在范围查询场景下**跳表更合适，实现也更简单" |
| "Redis 可以做消息队列" | List 没 ACK，消费者崩了消息就丢 | "简易场景可以，**生产要用 Kafka**；Redis 有 Stream 但也别当主力" |
| "Redis 持久化保证数据不丢" | RDB 丢最后一次快照后的全部；AOF everysec 丢 1 秒 | "**只是减少损失**，不是保证不丢" |
| "用 Redis 就是做缓存" | 它还能做计数、排行榜、分布式锁、限流、去重 | "缓存是最常见用法，但它是**数据结构服务器**，用途更广" |
| "给所有 key 设一样的 TTL 就行" | 会雪崩 | "**TTL 必须加随机偏移**" |
| "先删缓存再更新 DB 也行" | 中间的窗口会被旧值回填 | "**先更新 DB，再删缓存**" |

## 11 · 名词对照表

| 英文 | 中文 | 一句话 |
|---|---|---|
| Redis | — | 内存里的 key-value 数据结构服务器 |
| key / value | 键 / 值 | Redis 里一切数据都是"名字 → 内容" |
| String | 字符串 | 最基础类型，能存文本/数字/二进制 |
| Hash | 哈希（散列） | 一个 key 下挂多个"字段→值"，像一个小对象 |
| List | 列表 | 有序、可重复，两端进出 |
| Set | 集合 | 无序、自动去重，支持交并差 |
| ZSet | 有序集合 | 每个成员带分数，按分数自动排序 |
| SDS | 简单动态字符串 | Redis 自己实现的字符串，自带长度 |
| listpack | 紧凑列表 | 把多个小元素塞进一块连续内存，省空间 |
| skiplist | 跳表 | 多层索引的有序链表，范围查询友好 |
| TTL | 存活时间 | key 多久后自动删除 |
| RDB | 快照文件 | 某一时刻的全量数据二进制副本 |
| AOF | 追加日志 | 每条写命令的日志，可重放恢复 |
| fork | 分叉 | 复制出一个子进程（复制页表，不复制数据） |
| COW | 写时复制 | 共享同一份内存，谁写谁复制 |
| fsync | 刷盘 | 强制把数据从系统缓存写到物理磁盘 |
| LRU | 最近最少使用 | 淘汰"最久没被访问"的 |
| LFU | 最不经常使用 | 淘汰"访问次数最少"的 |
| CROSSSLOT | 跨槽错误 | 集群模式下多个 key 不在同一槽，无法一起操作 |
| hash tag | 哈希标签 | 用 `{}` 指定按哪部分算槽，让 key 落同槽 |
| Cache Aside | 旁路缓存 | 应用自己管缓存：先更 DB 再删缓存 |

## 附录 A · 一页速查（贴墙用）

```bash
# ── 连接与体检 ──
redis-cli PING                              # PONG
redis-cli INFO server | grep redis_version
redis-cli INFO memory | grep -E "used_memory_human|maxmemory_human"
redis-cli INFO stats  | grep -E "keyspace_hits|keyspace_misses|evicted_keys"
redis-cli DBSIZE                            # 当前库 key 数量
redis-cli CONFIG GET maxmemory-policy

# ── 别用 KEYS，用 SCAN ──
redis-cli --scan --pattern 'gmall:ads:*' | head
redis-cli --bigkeys                         # 找出大 key（★ 上线前必跑一次）

# ── 常用 ──
redis-cli SET k v EX 3600
redis-cli TTL k                             # 剩余秒数；-1 无过期；-2 不存在
redis-cli TYPE k                            # 这个 key 是什么类型
redis-cli OBJECT ENCODING k                 # 底层编码（listpack / hashtable / skiplist）
redis-cli MEMORY USAGE k                    # 这个 key 占多少字节
redis-cli UNLINK k                          # 异步删除（大 key 用它，不用 DEL）
```

**命中率算法**（面试可能让你算）：

```
命中率 = keyspace_hits / (keyspace_hits + keyspace_misses)
```

如果命中率长期低于 80%，说明缓存设计有问题（key 太散、TTL 太短、或者数据量超出内存导致被淘汰）。
