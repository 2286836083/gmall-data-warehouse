# 03 · 怎么装：本项目的真实部署过程

> **这篇解决什么**：把 Spark 装到一套已有 Hadoop/Hive 的集群上，并且能读到 Hive 里的表。
>
> **这篇最大的价值不在"怎么装"**（装软件不难），而在**"为什么参数长成这样"**。
> 本项目所有参数都是**被环境约束逼出来的**，不是抄来的 —— 这才是能讲的价值。
>
> 📌 全部细节的原始记录见 `实验分析/实验10_Spark双引擎对比.md`（**证据**）；本篇是**教材**。

## 〇、先认识本篇会反复用到的几个词

按本套教程的约定，**每个名词第一次出现就解释**。这几个词在"装 Spark"的过程里会反复出现，先集中认一遍：

| 名词                              | 中文解释                                                                                                                                                   |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **元数据（metadata）**      | "**关于数据的数据**"——比如"这张表叫什么、有哪些列、数据存在 HDFS 哪个目录"。**它不存真实数据，只存"描述"**。就像图书馆的目录卡片，不是书本身 |
| **MetaStore（元数据服务）** | Hive 里**专门管元数据的那个后台服务**（一个独立进程，本项目跑在 lrh-1 的 9083 端口）。你用它问"表长什么样"                                           |
| **jar（Java Archive）**     | Java 的"**库文件包**"（类似 Python 的包、或者 Windows 里的 dll 文件）。Spark 自己依赖**几百个 jar**，运行时必须发给每个执行器                  |
| **vCore（虚拟核）**         | YARN 里**对 CPU 的计量单位**。一个 vCore ≈ 一个 CPU 线程的算力。本项目每个节点只配了 **2 个**                                                 |
| **sha512**                  | 一种"**文件指纹**"算法：按文件内容算出一串固定长度的字符。**文件被改动一个字节，指纹就完全不同** → 用来校验下载的安装包有没有损坏或被篡改     |
| **client / cluster 模式**   | Spark 提交作业的两种方式，区别在**Driver 跑在哪**（见 §3.2）：`client` = Driver 跑在你敲命令的那台机器；`cluster` = Driver 塞进 YARN 容器里跑   |

> 💡 后面遇到不认识的名词，先翻最后一篇的 **07 附录：名词对照表**。

## 一、先侦察环境（★ 这一步不能跳）

**为什么必须先侦察**：Spark 有几十个版本、配置项上百个。**不知道环境约束就选版本、配参数，等于蒙。**

本项目实测的约束（这一章是整套配置的全部依据）：

| 约束项                        | 实测值                                     | 怎么测的                                    | 逼出了什么决定                                                                  |
| ----------------------------- | ------------------------------------------ | ------------------------------------------- | ------------------------------------------------------------------------------- |
| **JDK 版本**            | 1.8.0_202                                  | `/opt/jdk/jdk1.8.0_202/bin/java -version` | **排除 Spark 4.x** → 只能用 3.5.x                                        |
| **Hadoop 版本**         | 3.3.6                                      | `hadoop version`                          | 必须选`-bin-hadoop3` 的发行包                                                 |
| **Hive 元数据服务版本** | 3.1.3（在 lrh-1:9083）                     | `ss -lnt \| grep 9083`                     | Spark 内置的 Hive 客户端是 2.3.9，**版本不匹配** → 必须手动指定 jar 路径 |
| **YARN 每节点容量**     | **2048 MB / 2 vCores**               | 见 §1.1（★ 最容易看错的地方）             | 决定了 Executor 内存**最多只能给到 2048MB**                               |
| **YARN 单容器上限**     | **2048 MB**                          | `cat yarn-site.xml`                       | `Executor 内存 + 额外开销 ≤ 2048`                                            |
| **YARN 总容量**         | **6144 MB / 6 核**（3 节点 × 2048） | 3 × 2048                                   | 决定了能起几个 Executor、并行度上限                                             |
| 集群能否上外网                | **能**（apache 官网与清华镜像都通）  | `wget -q --spider`                        | **可以直接在集群上下载**，不用先从本机传                                  |
| 磁盘剩余                      | lrh-1 5.5G / 2 号 9.7G / 3 号 9.8G         | `df -h /`                                 | 三台都装得下（Spark 解压后 429MB）                                              |

### 1.1 ⚠️ 一个真实的误读（值得单独讲）

看 YARN 容量时，命令输出里有**两组数字**，很容易看错：

```
Resource Utilization by Node :
  PMem:4860 MB,     VMEM:...      ← 这是【物理内存的使用量】，不是容量！
  ...
Configured Resources :
  memory:2048, vCores:2           ← ★ 这才是【YARN 容量】
```

**我当时就把 `PMem:4860` 当成了 lrh-1 的 YARN 容量**，差点推出"lrh-1 可以放两个大 Executor"的错误结论 ——
**按那个数配，作业会被 YARN 直接拒绝**。

**为什么会看错**：lrh-1 显示 4860MB 是因为它还扛着 NameNode / Hive / MySQL / 调度系统，
**物理内存用得多** ≠ **YARN 可用容量大**。

> ★ **教训（和第 11 章那条一脉相承）**：
> **看配置要看"配置"字段，不要看"使用"字段。**
> 判据本身错了，结论就全错，**而且不会报错** —— 你会一直以为自己是对的。

### 1.2 侦察的结论：这套集群很"寒酸"，但这反而更真实

YARN 总共只有 **6GB 内存 / 6 个核**。

所以本次对比的意义**不是**"Spark 能快多少倍"，而是
**"在同样紧张的资源下，两个引擎各自表现如何"** ——
这比 PPT 上的理想数字更接近真实生产里"资源不够用"的日常。

## 二、选版本：为什么是 3.5.9

**Spark 3.5.x 是最后一条支持 JDK 8 的版本线。**

| 选项        | 为什么不行 / 行                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Spark 4.x   | ❌ 要求**JDK 17+**。集群 JDK 是 8，升 JDK 意味着 Hadoop 3.3.6 / Hive 3.1.3 **全部面临重装** —— 风险和收益完全不成比例 |
| Spark 3.5.9 | ✅ JDK 8 能跑；且是 3.5 线的最新补丁版                                                                                              |

**不选 4.x 还有第二个理由（容易被忽略，但更危险）**：

> Spark 4.0 默认开启 `spark.sql.ansi.enabled=true`（**遵循 SQL 标准严格模式**）。
> 这会**改变 SQL 的语义**：除零变成报错、隐式类型转换变严格。
> 结果是**现有 SQL"跑得起来但结果不一样"** —— 这比"跑不起来"危险得多，
> 因为跑不起来你会立刻发现，结果不一样你可能几个月都不知道。

```
包名：spark-3.5.9-bin-hadoop3.tgz        （383MB）
       └─ "bin-hadoop3" 是为 Hadoop 3.x 预编译的版本
          选错了会出现 NoSuchMethodError 之类的兼容错误
```

**下载后必须校验完整性**（官方 sha512 与本地实测比对一致），确认包没被改坏或下载残缺。

## 三、部署模式：跑在 YARN 上，用 client 模式

Spark 有好几种"跑法"，本项目选的是 **Spark on YARN + client 模式**。名词先解释：

| 名词                   | 中文         | 含义                                                                          |
| ---------------------- | ------------ | ----------------------------------------------------------------------------- |
| **on YARN**      | 跑在 YARN 上 | 由 YARN 提供资源（容器），不另起一套 Spark 自己的集群                         |
| **client 模式**  | 客户端模式   | **Driver 跑在你敲命令的那台机器上**（本项目是 lrh-1），不在 YARN 容器里 |
| **cluster 模式** | 集群模式     | **Driver 也塞进 YARN 容器里**跑                                         |

### 3.1 为什么选 on YARN

- 这才是**生产形态**（面试可讲），而不是本地练手的 `local` 模式
- **复用现有 3 个 NodeManager**，不用额外起守护进程（省内存）

### 3.2 为什么选 client 模式（不是 cluster）

```
【client 模式】                          【cluster 模式】
  lrh-1（你敲命令的地方）                   YARN 容器里
  ├─ Driver ★ 就在这                       ├─ Driver ★ 在这
  └─ 你实时看得到日志                       └─ 日志在容器里，要绕一圈去捞
```

理由有两条：

1. **YARN 每节点只有 2048MB** —— cluster 模式下 Driver 会**抢走唯一的容器容量**，
   等于没资源跑 Executor 了
2. **client 模式能实时看 Driver 日志** —— 本项目强调"**进度必须可观测**"，
   cluster 模式的日志要去 YARN 里捞，不方便

### 3.3 jar 分发：把 Spark 自己的依赖提前放到 HDFS

**问题**：Spark 每次提交作业，都要把自己的一堆 jar 包（库文件）发给每个 Executor。

**做法**：把这 252 个 jar（338MB）**一次性放到 HDFS**，之后每次提交都从 HDFS 拿：

```
spark.yarn.jars = hdfs://lrh-1:8020/spark/jars/*
```

**收益**：一次性上传 18 秒，之后**每次提交省掉重复上传**。
（不配的话，每次提交都要从本地上传 338MB —— 在 6GB 小集群上是纯浪费。）

## 四、连上 Hive 的表（最容易踩坑的一步）★

**目标**：让 Spark 能读到 Hive 里的 `gmall` 库。这样同一个表，Hive 能查、Spark 也能查。

### 4.1 问题：两边版本不一致

```
Spark 3.5 自带的 Hive 客户端代码：2.3.9
集群实际运行的 Hive 元数据服务：  3.1.3
                    ↑ 版本号不一样
```

**为什么版本不一致会出问题**：

> **名词**：**Thrift（一种跨语言远程调用协议）** ——
> 你可以理解成"客户端和服务端之间约定的**通话格式**"。
> Hive 的元数据服务就是用 Thrift 对外提供接口的。
> **通话格式在 2.x → 3.x 之间改过**，所以老客户端不能直接和老版新服务对话。

表现：直连会报 `Invalid method name` 之类的错误。

### 4.2 解法：让 Spark 用集群自己的 Hive 库

官方给了两条路，本项目选第二条：

| 方案               | 做法                                              | 为什么不选 / 为什么选                                                          |
| ------------------ | ------------------------------------------------- | ------------------------------------------------------------------------------ |
| `maven`          | 从 Maven 中央仓库下载 3.1.3 的 jar                | ❌**每个 Executor 首次运行都要联网**，首次启动慢、不可离线、网络依赖点多 |
| **`path`** | **直接用集群已有的 Hive 3.1.3 的 lib 目录** | ✅**可控、可离线、版本严格一致**                                         |

配置（照抄可用）：

```properties
spark.sql.hive.metastore.version       3.1.3
spark.sql.hive.metastore.jars          path
spark.sql.hive.metastore.jars.path     file:///opt/hive/apache-hive-3.1.3-bin/lib/*
```

**另外**：把 Hive 的 `hive-site.xml` **拷一份**到 Spark 的 `conf/` 目录 ——
这样 Spark 才知道元数据服务的地址（`lrh-1:9083`）和 MySQL 连接信息。

> ⚠️ **是"拷副本"，不是"改原文件"**。原 Hive 配置一个字都没动 —— 这是安全边界。

### 4.3 一个可以省下的担心（本项目验证过）

一开始担心"Executor 是不是也得装 Hive 的那 277MB 库"。**实测不需要**：

- 与元数据的交互**只发生在 Driver 侧**（问表结构、问分区在哪）
- 真正干活时，Executor 只是按 Driver 给的 HDFS 路径**读文件**
- 实测：只在 lrh-1 保留 Hive 库、没分发到 2/3 号机，扫描 1063 万行**成功、无 ClassNotFound**

## 五、资源参数：为什么是 1408m 这种"怪数字"

先看最终配置，再解释每个数字的来路。

```properties
spark.executor.memory           1408m
spark.executor.memoryOverhead    384m
spark.executor.cores               2
spark.executor.instances           3
spark.driver.memory               1g
spark.sql.shuffle.partitions       6
```

### 5.1 Executor 内存 1408m —— 被 YARN 上限逼出来的

**先解释两个名词**：

| 名词                        | 中文                     | 含义                                                                                  |
| --------------------------- | ------------------------ | ------------------------------------------------------------------------------------- |
| `executor.memory`         | 执行器**堆内**内存 | Java 对象真正存放的地方（由 JVM 的`-Xmx` 控制）                                     |
| `executor.memoryOverhead` | 执行器**堆外**开销 | JVM 本身、字符串常量、网络缓冲等**堆外**部分。默认是 `max(384MB, 内存的 10%)` |

**YARN 的规矩**：一个容器申请多少内存，算的是**两者之和**：

```
   spark.executor.memory  +  spark.executor.memoryOverhead  ≤  YARN 单容器上限 2048MB
        （1408MB）                    （384MB）                        =  1792MB  ✅ 留了 256MB 余量
```

**如果按习惯写 `--executor-memory 2g` 会怎样**：
`2048 + 384 = 2432 > 2048` → **YARN 直接拒绝分配容器**，作业起不来。

> ★ **这就是"参数为什么长这么怪"的答案**：
> **不是拍脑袋，是被约束反推出来的。**
> 面试里被问"你的 Spark 参数怎么配的"，能答出这条推理链，比背默认值强得多。

### 5.2 其他几个数字的理由

| 参数                   | 值           | 为什么                                                                                               |
| ---------------------- | ------------ | ---------------------------------------------------------------------------------------------------- |
| `executor.cores`     | **2**  | 与每节点的 vCores（虚拟核）数一致 —— 一个 Executor 占满一个节点的核                                |
| `executor.instances` | **3**  | 三台机器各一个 → 总共 6 核，**与 Hive 侧的并行度对等**（对比才公平）                          |
| `driver.memory`      | **1g** | Driver 跑在 lrh-1，而这台机器可用物理内存只剩约 2.3G，**不能给它太多**                         |
| `shuffle.partitions` | **6**  | 默认值是**200**，在这套 6 核集群上是灾难（200 个任务排队等 6 个核）→ 对齐 Hive 侧的 reduce 数 |

> 📌 **对照：两个引擎的"每个任务能分到多少内存"其实不一样**
>
> - Hive：一个容器跑一个任务 → 1024MB / 堆上限 820MB，**一个任务独占**
> - Spark：一个 Executor 跑 2 个并发任务 → 1408MB 堆 / 2，**每个任务分到的更少**
>
> 这一点在后面验证"大基数聚合会不会内存不够"时是个看点。

## 六、一个必须显式设置的语义差异（★ 不设会静默出错）

同一个语句，两个引擎的行为**不一样**：

```sql
INSERT OVERWRITE TABLE t PARTITION (dt) SELECT ..., dt FROM ...
```

|                               | Hive                               | Spark（默认）                          |
| ----------------------------- | ---------------------------------- | -------------------------------------- |
| `INSERT OVERWRITE` 分区表时 | 只覆盖**本次数据涉及的分区** | **先清空整张表**，再把数据写进去 |

**Spark 侧必须显式加一行**：

```properties
spark.sql.sources.partitionOverwriteMode = dynamic
```

**不设会怎样**：全量跑的时候**看不出问题**（反正都要重写整表）。
但只要有一次"只补跑某一天的数据"，**其余日期的分区会被静默清空**：

```
你只想补 10-05 一天的数据：
  期望：其他 30 天还在
  实际：整张表被清空，只剩 10-05 一天   ← 数据"看起来写成功了"，但丢了 30 天
```

> ⚠️ 这属于"**跑得对、结果错**"的典型陷阱：**不报错，但数据悄悄没了**。
> 本项目专门做了验证：设了 `dynamic` 之后 `show partitions` 实测 **31 = 31**，
> 与 Hive 版完全一致 —— 这就是该参数**真正生效的证据**。

## 七、验收：三层判据（★ 不能只看"装完了没报错"）

装完必须**分层验证**，一层比一层硬：

| 层                      | 判据                                               | 期望结果                                         | 它证明了什么                           |
| ----------------------- | -------------------------------------------------- | ------------------------------------------------ | -------------------------------------- |
| **① 元数据可见** | `show databases` / 表数量                        | 3 个库；`gmall` 下 **27 张表**           | Spark 认得 Hive 的表                   |
| **② 数据可读**   | `select count(*) from gmall.ads_active_user_day` | **31**（与基线一致）                       | 能读到真实数据、数值对得上             |
| **③ 分布式可跑** | 在 YARN 模式扫 1063 万行                           | **10,630,245**（与基线**逐位一致**） | 真的在集群上跑起来了，不是本地模式假跑 |

**为什么必须分三层**：①过了②没过，说明"知道表在哪但读不到数据"（权限/路径问题）；
②过了③没过，说明"能读单机文件但上不了集群"（YARN 配置问题）。**三层都过才叫装好。**

### 7.1 一个必须诚实说明的数字

验证时单看一条 `count(*)`：**墙上时间是 51.5 秒**，而 Spark 自己报"执行耗时 15.9 秒"。

**差的约 35 秒是什么**：JVM 启动 + 连接元数据 + 向 YARN 提交应用的**固定开销**。

> → 这直接推出第 01 篇那个结论：**Spark 单发小查询不划算**，
> 优势只在"一个常驻会话里连着干很多活"时体现。
> 所以本项目的对比**只跑批处理，不比单条查询** —— 那对 Spark 不公平，也没有业务意义。

## 八、完整配置清单（可抄）

### 8.1 `spark-defaults.conf`

```properties
# ── 跑在 YARN 上 ──
spark.master                            yarn
spark.submit.deployMode                 client

# ── 连 Hive 元数据（版本必须与集群的 metastore 服务一致）──
spark.sql.hive.metastore.version        3.1.3
spark.sql.hive.metastore.jars           path
spark.sql.hive.metastore.jars.path      file:///opt/hive/apache-hive-3.1.3-bin/lib/*

# ── 写分区表的语义：必须 dynamic，否则会清空整表 ──
spark.sql.sources.partitionOverwriteMode dynamic

# ── 资源（每个数都被 YARN 上限逼出来）──
spark.executor.memory                   1408m
spark.executor.memoryOverhead            384m
spark.executor.cores                       2
spark.executor.instances                   3
spark.driver.memory                       1g

# ── 并行度（默认 200 在 6 核集群上是灾难）──
spark.sql.shuffle.partitions               6

# ── jar 走 HDFS，避免每次提交重传 338MB ──
spark.yarn.jars                  hdfs://lrh-1:8020/spark/jars/*

# ── 事件日志（给 History Server 回放用）──
spark.eventLog.enabled                  true
spark.eventLog.dir              hdfs://lrh-1:8020/spark/eventlogs
```

### 8.2 部署步骤（在本项目集群上的实际操作顺序）

```bash
# 1) 下载并校验（383MB，约 1 分钟）
cd /home/lrh/downloads && wget <apache 镜像地址>/spark-3.5.9-bin-hadoop3.tgz
sha512sum spark-3.5.9-bin-hadoop3.tgz     # 与官方值比对

# 2) 解压安装（三台都要）
sudo tar -xzf spark-3.5.9-bin-hadoop3.tgz -C /opt/
sudo chown -R lrh:lrh /opt/spark-3.5.9-bin-hadoop3

# 3) 分发 Spark 自己的 jar 到 HDFS（一次性，18 秒）
hdfs dfs -mkdir -p /spark/jars
hdfs dfs -put /opt/spark-3.5.9-bin-hadoop3/jars/* /spark/jars/

# 4) 建 event log 目录
hdfs dfs -mkdir -p /spark/eventlogs

# 5) 写配置 + 拷 Hive 配置副本
vim /opt/spark-3.5.9-bin-hadoop3/conf/spark-defaults.conf
cp /opt/hive/apache-hive-3.1.3-bin/conf/hive-site.xml /opt/spark-3.5.9-bin-hadoop3/conf/

# 6) 三层判据验证（见 §七）
```

> ⚠️ **只新增目录，不改任何既有配置** —— 这是本项目的安全边界，
> 意味着随时可以整个删掉 `/opt/spark-3.5.9-bin-hadoop3` 回滚，不影响 Hive/Hadoop。

1. 为什么选 Spark 3.5.9 而不是 4.x？（给两个理由）—— 对应 **§二**
2. 为什么用 client 模式而不是 cluster 模式？—— 对应 **§3.2**
3. 为什么要配 `metastore.jars=path`？`maven` 方案差在哪？—— 对应 **§4.2**
4. Executor 内存为什么是 1408m？如果用 `2g` 会怎样？—— 对应 **§5.1**
5. `partitionOverwriteMode` 不设会出什么问题？为什么这个错误特别危险？—— 对应 **§六**
6. 验收 Spark 装好了，你会怎么验证？（不能只看"没报错"）—— 对应 **§七**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 为什么不用 Spark 4**

- ① **集群 JDK 是 1.8**，Spark 4 要求 JDK 17+，升 JDK 会牵连 Hadoop/Hive 全部重装
- ② **Spark 4 默认开 ANSI 严格模式**（除零报错、隐式转换变严）→
  现有 SQL 可能"**跑得起来但结果不一样**"，这种错比跑不起来危险得多
- 补充：3.5.x 是最后支持 JDK 8 的版本线

**2. client vs cluster**

- YARN **每节点只有 2048MB** —— cluster 模式下 Driver 会**抢走唯一的容器容量**，Executor 就没资源了
- client 模式下 Driver 在 lrh-1，**日志实时可见**（本项目强调进度可观测）

**3. metastore jars=path**

- 原因：Spark 3.5 内置 Hive 客户端是 **2.3.9**，集群 metastore 服务是 **3.1.3**，
  Thrift 协议在 2.x→3.x 有变更 → 直连报错
- `maven` 的缺点：**每个 Executor 首次运行都要联网**下载 jar → 慢、不可离线、依赖点多
- `path` 的优点：直接用集群已有的 Hive lib，**版本严格一致、可离线、可控**

**4. 1408m 的来历**

- 算式：`executor.memory + memoryOverhead ≤ YARN 单容器上限 2048MB`
- `1408 + 384 = 1792 ≤ 2048`，还留 256MB 给 NodeManager
- 若写 `2g`：`2048 + 384 = 2432 > 2048` → **YARN 拒绝分配容器，作业起不来**
- 加分项：说出"memoryOverhead 是堆外开销，默认 `max(384MB, 10%)`"

**5. partitionOverwriteMode**

- 不设（默认 `STATIC`）= `INSERT OVERWRITE` 会**先清空整张表**再写
- 全量跑看不出问题；**只补跑某一天时，其余分区会被静默清空**
- 危险的原因：**不报错**，数据"看起来写成功了"，属于"跑得对、结果错"
- 验证方式：设 `dynamic` 后 `show partitions` 应为 31 = 31（本项目实测）

**6. 三层验收**

- ① **元数据可见**：`show databases` / `gmall` 27 张表
- ② **数据可读**：`count(*)` 与基线一致（31）
- ③ **分布式可跑**：YARN 模式扫 1063 万行 = 10,630,245（逐位一致）
- 关键：**"装完没报错"不算验收**，必须跑到"真实数据、真实集群、数值对得上"

</details>
