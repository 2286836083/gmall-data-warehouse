# 02 · 核心概念：一次 Spark 作业从头到尾

> **这篇解决什么**：Spark 的名词特别多（Driver、Executor、Job、Stage、Task、RDD、DataFrame、DAG…），
> 而且它们**有严格的父子层级**，不理解层级就会一直混。
>
> 本篇每个名词都给：**中文名 + 干什么 + 类比 + 物理上是什么**。
> 读完你应该能在脑子里"放一遍电影"：从敲下回车，到结果出来。

---

## 一、先看层级：谁包含谁（★ 最重要的一张图）

Spark 的名词之所以混，是因为它们**分四层套着**。先记住这个包含关系：

```
一个 应用 (Application)              ← 你提交的一次"活"，比如"跑完这 8 条 SQL"
  │
  ├─ 一个 Driver（驱动器）            ← 这个应用的"大脑"，只有一个
  │
  ├─ 若干个 Job（作业）               ← 一条 SQL 触发的计算 = 一个 Job
  │    └─ 若干个 Stage（阶段）         ← Job 内部按"要不要跨机器搬数据"切开的段
  │         └─ 若干个 Task（任务）     ← Stage 内部并行的最小单位，一个 Task 处理一片数据
  │
  └─ 若干个 Executor（执行器）         ← 常驻的"工人进程"，所有 Task 在它里面跑
```

**一句话**：**应用包含作业，作业包含阶段，阶段包含任务；Driver 指挥，Executor 干活。**

> ⚠️ **最容易混的三组**（先记住区别，后面再展开）：
>
> - **Driver ≠ Executor**：一个是"脑"，一个是"手"
> - **Job ≠ Stage**：Job 是"一次完整的计算"，Stage 是它内部被切开的段落
> - **Executor ≠ Task**：Executor 是**进程**（常驻），Task 是它内部的**线程**（临时）

## 二、四个"角色"：谁是谁

### 2.1 Driver（驱动器）

|                        |                                                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **中文名**       | 驱动器 / 驱动程序                                                                                                                         |
| **干什么**       | ① 解析你写的 SQL 或代码，生成执行计划；② 把计划拆成 Task，派给 Executor；③ 收集结果、监控进度、失败时重试                              |
| **类比**         | 工地的**项目经理**：不看图纸算不出工期，不动手搬砖，但所有决定都是他做的                                                            |
| **物理上是什么** | **一个 JVM 进程**。它跑在哪很关键 —— 本项目是 `client` 模式，**Driver 就跑在 lrh-1 这台机器上**（和你敲命令的地方在一起） |

> ⚠️ **Driver 挂了，整个应用就挂了**（它管着全局状态）。所以 Driver 的内存不能给太小。

### 2.2 Executor（执行器）

|                        |                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| **中文名**       | 执行器                                                                                                        |
| **干什么**       | 真正干活：在本地读数据、算、把结果写出去。**所有 Task 都在它内部以线程方式运行**                        |
| **类比**         | 工地上的**施工队**：一个队里有若干个工人（线程），队长（Executor）负责占地盘（内存）                    |
| **物理上是什么** | **一个 JVM 进程，跑在 YARN 的容器里**。Spark 应用启动时申请，之后**一直留着不退出**，直到应用结束 |

**这是 Spark 快的关键之一**：
MapReduce 是"**每个任务雇一个新工人**"（每个 task 起一个 JVM，跑完就销毁），
Spark 是"**工人先雇好，一直用**"（Executor 常驻，任务只是线程）。

### 2.3 SparkSession（会话）/ SparkContext（上下文）

|                        |                                                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **中文名**       | 会话 / 上下文                                                                                                        |
| **干什么**       | 你写代码/敲 SQL 的"**入口对象**"。通过它才能创建 DataFrame、执行 SQL、拿到配置                                 |
| **类比**         | 你去办事时的**工牌**——证明"我是这个应用的人"，有它才能叫得动 Executor                                        |
| **物理上是什么** | Driver 进程里的一个 Java 对象（`SparkSession`）。老版本里叫 `SparkContext`，现在 `SparkSession` 把它包在里面了 |

> 💡 **为什么要有"会话"这个概念**：它就是**那笔 35 秒固定开销的载体**。
> 建立会话 = 启动 Driver + 连元数据 + 向 YARN 申请 Executor。
> **会话建立一次、用好多次，那 35 秒就被摊薄了** —— 这正是第 01 篇讲的"收益来自会话复用"的机制层面解释。

### 2.4 ApplicationMaster（应用管理器，简称 AM）

> 这个名字你在一篇 YARN 里见过（`零基础教程/05`）。这里说明它和 Spark 的关系。

|                        |                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------- |
| **中文名**       | 应用管理器                                                                                            |
| **干什么**       | **YARN 那一侧的"项目经理"**：向 YARN 申请 Executor 容器、盯着它们别死                           |
| **物理上是什么** | 一个独立的 JVM 进程。**在 client 模式下，它和 Driver 是分开的**：Driver 在 lrh-1，AM 在 YARN 里 |

> ⚠️ **别把 Driver 和 AM 搞混**：**Driver 管计算，AM 管资源申请**。
> 在 `cluster` 模式下两者才跑在一起（本项目没用 cluster 模式，见第 03 篇）。

## 三、三层"任务"：Job、Stage、Task

这三个词都是"任务"的意思，但**粒度完全不同**。用"做一顿饭"来对照：

| 名词            | 中文名 | 粒度                                   | 做饭的类比                     |
| --------------- | ------ | -------------------------------------- | ------------------------------ |
| **Job**   | 作业   | **一条 SQL 触发的全部计算**      | "做这顿饭"                     |
| **Stage** | 阶段   | Job 内部按"要不要跨机器搬数据"切开的段 | "切菜"、"下锅炒"、"装盘"       |
| **Task**  | 任务   | Stage 内部并行执行的最小单位           | "切第一个土豆"、"切第二个土豆" |

### 3.1 Job（作业）

- **什么时候产生**：你执行一条 SQL，或者代码里调用了一个"**动作**"（Action）→ 触发一个 Job
- **物理上是什么**：不是一个进程，而是**Driver 里的一组调度记录**（"这批任务归这个 Job 管"）
- **注意**：一条 SQL 通常是 1 个 Job，但如果有多个"动作"也可能拆成多个 Job

### 3.2 Stage（阶段）

- **怎么切出来的**：**看有没有"跨机器搬数据"**（也就是 shuffle，见下）
  - 不搬 → 能连着做，**塞进同一个 Stage**
  - 要搬 → 必须切开，**前面一个 Stage 做完落盘，后面一个才能开始**
- **为什么必须切开**：因为搬数据要等**所有上游任务都把数据准备好**才能开始，
  这在物理上就是一个"**分界线**"（术语叫 shuffle boundary，洗牌边界）

### 3.3 Task（任务）

- **是什么**：Stage 内部**并行**执行的最小单位。
- **一个 Stage 有多少 Task**：取决于这个 Stage 要处理的数据被切成几片（**分片数**，见 §4.3）
- **物理上是什么**：**Executor 进程里的一个线程**（不是进程！这是 Spark 和 MapReduce 的关键区别）
- **一个 Task 的大小**：通常一个 Task 处理一个 HDFS 数据块（约 128MB）

```
        一个 Stage 里有 6 个 Task（可以并行跑的 6 个线程）
        ┌──────────────────────────────────────────┐
        │  Executor 进程（常驻）                     │
        │   ├─ 线程 1 → Task 1  ← 处理第 1 片数据    │
        │   ├─ 线程 2 → Task 2  ← 处理第 2 片数据    │
        │   └─ 线程 3 → Task 3                     │
        └──────────────────────────────────────────┘
        ┌──────────────────────────────────────────┐
        │  Executor 进程（另一台机器）                │
        │   ├─ 线程 1 → Task 4                     │
        │   ├─ 线程 2 → Task 5                     │
        │   └─ 线程 3 → Task 6                     │
        └──────────────────────────────────────────┘
```

## 四、三个"数据相关的名词"

### 4.1 Shuffle（洗牌）★ 全篇最重要的词

|                        |                                                                                                                            |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **中文名**       | 洗牌 / 数据重分布                                                                                                          |
| **干什么**       | 把**散落在不同机器上的同类数据，搬到同一台机器上**。比如 `GROUP BY dt`，得把同一个 `dt` 的数据都弄到一起才能统计 |
| **类比**         | 打牌时把牌重新分堆：所有红桃放一起、所有黑桃放一起                                                                         |
| **物理上是什么** | **数据跨网络传输 + 两端各读写一次磁盘**。这是 Spark **唯一必须落盘**的地方，也是**最贵的操作**           |

**为什么它是"分界线"**：shuffle 要等上游全部完成才能开始（因为要"收齐"同一类的数据），
所以它天然把计算切成两段 → **这就是 Stage 的划分依据**。

### 4.2 RDD（弹性分布式数据集）

|                        |                                                                                                                |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| **中文名**       | 弹性分布式数据集（Resilient Distributed Dataset）                                                              |
| **干什么**       | Spark 最早的数据抽象：一批"可以并行处理的数据"，且**记得自己是怎么算出来的**（所以一个分片丢了可以重算） |
| **类比**         | 一张**会记笔记的清单**：不光记内容，还记"我是从哪一步变来的"                                             |
| **物理上是什么** | 不是实体文件，而是**一组分片（partition）+ 一条"血统"记录（它是从哪个 RDD 经过什么操作变来的）**         |

> 💡 **"弹性"指什么**：某个分片所在机器挂了，Spark 不用重新跑全流程，
> 因为 RDD **记得计算过程**，可以只把丢的那一片算回来。这叫"**容错**"。

### 4.3 DataFrame（数据框）—— 现在最常用的抽象

|                        |                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| **中文名**       | 数据框                                                                                     |
| **干什么**       | **带列名的二维表**（就像一张 Excel 表），可以直接用 SQL 查                           |
| **类比**         | 一张**有表头的表**：比 RDD 那种"一堆没名字的对象"友好得多                            |
| **物理上是什么** | 逻辑上是一张表，**背后仍然是一组 RDD 分片 + 一份"表结构描述"（有哪些列、什么类型）** |

**RDD vs DataFrame 怎么选**（对数据开发岗位的实用结论）：

|              | RDD                                   | DataFrame                                  |
| ------------ | ------------------------------------- | ------------------------------------------ |
| 是什么       | 一堆数据对象，**没有列名**      | **有列名的表**                       |
| 怎么写       | 写代码（`map`/`filter` 这类函数） | **写 SQL**，或写链式调用             |
| 性能         | 差（引擎不知道你在干什么）            | **好**（引擎知道列名和类型，能优化） |
| 本项目用哪个 | ❌ 没用                               | ✅**全部用 DataFrame / SQL**         |

> **结论（省你时间）**：**做数仓 ETL，99% 的场景用 DataFrame / SQL。**
> RDD 现在主要用于极底层定制（比如自己控制分片方式），入门阶段可以先跳过。

### 4.4 Partition（分片）

|                        |                                                                             |
| ---------------------- | --------------------------------------------------------------------------- |
| **中文名**       | 分片 / 分区（注意：和 Hive 的"分区"不是一回事！）                           |
| **干什么**       | 把一份数据切成 N 片，每片交给一个 Task 处理 →**片数 = 并行度**       |
| **类比**         | 一叠考卷分给 6 个老师批改，就是 6 片                                        |
| **物理上是什么** | 内存里的一组数据块；读取时通常**一个 HDFS 数据块（128MB）= 一个分片** |

> ⚠️ **重名警告（必须分清）**：
>
> - **Hive 的"分区"**（partition）指**目录**，比如 `dt=2019-10-01/`，是用来**快速定位数据**的
> - **Spark 的"分片"**（partition）指**并行切分的份数**，是用来**决定并行度**的
> - 中文都翻译成"分区"，但完全是两件事。**看到 partition 先想：它在说目录还是说份数？**

## 五、两个"操作类型"：Transformation 和 Action

### 5.1 Transformation（转换）

|                    |                                                                                |
| ------------------ | ------------------------------------------------------------------------------ |
| **中文名**   | 转换                                                                           |
| **是什么**   | "**描述一个加工步骤**"，比如"过滤出 view 事件""按 dt 分组"               |
| **例子**     | `filter`（过滤）、`select`（选列）、`groupBy`（分组）、`join`（关联）  |
| **关键特性** | **惰性**——你写了它，**Spark 不会立刻执行**，只是记下"有这么一步" |

### 5.2 Action（动作）

|                  |                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| **中文名** | 动作                                                                                              |
| **是什么** | "**我现在就要结果**"，这才真正触发计算                                                      |
| **例子**   | `show()`（显示几行）、`count()`（数行数）、`collect()`（把结果收回来）、`write`（写出去） |

### 5.3 为什么要"惰性"？（这是 Spark 能优化的前提）

```
你写的：  读表 → 过滤 → 分组 → 计数
          （转换）（转换）（转换）↑ 都是"只记不做"

你说"要结果"（Action）的那一刻：
          Spark 才回头看整条链，发现"过滤条件可以提前一点、这个分组可以合并"
          → 生成最优的执行计划 → 才真正开跑
```

**物理上的意义**：如果不惰性（写一步执行一步），引擎就**没有机会看全局**，
只能老老实实按你写的顺序干 —— 这正是 MapReduce"一段段翻译"的局限。

> 💡 **一个实用推论**：**为什么你的 Spark 程序跑得慢、或者看起来"什么都没发生"？**
> 因为**没有 Action**。Spark 只在遇到 Action 时才真正执行。

## 六、把电影放一遍：一次作业从头到尾

现在把上面的名词串起来。场景：**你在 lrh-1 上执行一条 Spark SQL**。

```
① 【你敲下回车】
     spark-sql 启动 → 建立 SparkSession（会话）
     ↳ 这一步就开始付那 35 秒固定开销

② 【Driver 开始工作】
     解析 SQL → 生成执行计划（Catalyst 优化器先改写、化简）
     → 编译成一张 DAG（有向无环图）

③ 【Driver 向 YARN 要资源】
     通过 ApplicationMaster 向 YARN 申请 Executor 容器
     YARN 的 ResourceManager 在 lrh-1/2/3 各划出容器
     ↳ 容器里起 Executor 进程（JVM），一直留着

④ 【Driver 把 DAG 切成 Stage】
     凡是遇到 shuffle（要跨机器搬数据）就切一刀
     例如：读数据+过滤 = Stage 1；分组聚合 = Stage 2

⑤ 【Stage 内部并行跑 Task】
     Stage 1 有 6 个 Task（因为数据有 6 片）
     → Driver 把 6 个 Task 分给 3 个 Executor
     → 每个 Executor 内部用 2 个线程跑
     ★ Task 是线程，不会新建进程 —— 省掉了反复启 JVM

⑥ 【遇到 shuffle（Stage 边界）】
     Stage 1 的所有 Task 把结果按 key 写到自己机器的磁盘
     然后 Stage 2 的 Task 跨网络去各台机器"拉"属于自己的那份
     ↳ 全流程中最贵的一步：网络 + 磁盘

⑦ 【Stage 2 跑完，写结果】
     结果写回 HDFS（带副本），或返回给 Driver

⑧ 【应用结束】
     Executor 退出，会话关闭
     ↳ 如果又要跑第二条 SQL、且会话已关 → 那 35 秒要再付一次！
```

**这张图的三个要点**：

| 要点                                          | 说明                                                                    |
| --------------------------------------------- | ----------------------------------------------------------------------- |
| **Executor 是"提前雇好、一直用"的**     | 所以同一个会话里跑越多 SQL，这笔钱摊得越薄                              |
| **Task 是线程，不是进程**               | 这是 Spark 快于 MapReduce 的直接原因之一                                |
| **shuffle 是唯一的"必须落盘 + 走网络"** | 也是 Stage 的分界；**优化 Spark 作业，本质就是减少/优化 shuffle** |

> 📌 **本项目对照**：本项目的 8 段 SQL 单会话连跑，逐段耗时是
> `19.4 → 10.0 → 3.4 → 2.9 → 2.8 → 0.9 → 1.4 → 1.0` 秒，**前后差了 19 倍**。
> 而分段跑时只差 3 倍。为什么越跑越快？
> 推断（**未深入验证**）：Executor 常驻省掉了后续的 JVM 启动与类加载、
> JIT（即时编译）被预热、部分数据进了操作系统缓存。
> **这是"为什么 Spark 必须长跑才划算"的微观证据。**

**每题标了对应小节——答不出来就回去看那节。**

1. 一个应用里，Job、Stage、Task 各是什么？谁包含谁？—— 对应 **§一、§三**
2. Driver 和 Executor 的区别？各自物理上是什么？—— 对应 **§二**
3. Spark 的"分片（partition）"和 Hive 的"分区（partition）"有什么不同？—— 对应 **§4.4**
4. Transformation 和 Action 有什么区别？为什么这个区别很重要？—— 对应 **§五**
5. Stage 是**根据什么**切出来的？为什么必须在那里切？—— 对应 **§3.2、§4.1**
6. 为什么同一个会话里连跑多条 SQL，后面的会越来越快？—— 对应 **§六**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 三层任务的包含关系**

- **应用 > Job > Stage > Task**
- Job = 一条 SQL 触发的全部计算；Stage = Job 内部按"要不要跨机器搬数据"切开的段；
  Task = Stage 内部并行的最小单位
- 加分项：Task 是**线程**；一个 Stage 的 Task 数 = 数据分片数

**2. Driver vs Executor**

- **Driver（驱动器）= 大脑**：生成执行计划、切 Stage、派 Task、收结果、重试。物理上是一个 JVM 进程（本项目在 lrh-1）
- **Executor（执行器）= 手**：真正读数据、算、写结果。物理上是**跑在 YARN 容器里、常驻的 JVM 进程**
- 易错点：Driver 挂了整个应用就挂；Executor 挂了可以重起

**3. 两个"分区"**

- **Hive 的分区 = 目录**（`dt=2019-10-01/`），作用是**快速定位数据**（不用扫全表）
- **Spark 的分片 = 并行份数**，作用是**决定并行度**（几片就几个 Task）
- 中文都叫"分区"，但是两回事 —— 看到这个词先问"它在说目录还是份数"

**4. Transformation vs Action**

- **Transformation（转换）**：描述加工步骤（过滤、分组、关联），**惰性，不立刻执行**
- **Action（动作）**：要结果（`count`/`show`/`write`），**才真正触发计算**
- 为什么重要：惰性让 Spark 能看到**整条链**再优化（"过滤能不能提前"），
  这是它比 MapReduce"一段段翻译"强的机制；也解释了"为什么我写了半天没动静"—— 缺 Action

**5. Stage 怎么切**

- 依据：**有没有 shuffle（要跨机器搬数据）**
- 不搬 → 塞进同一个 Stage；要搬 → 必须切开
- 为什么必须切：shuffle 要等**上游所有任务都准备好**才能开始收集同类数据，
  这个"等待"就是天然的物理分界线

**6. 为什么越跑越快**

- Executor **常驻**：后续 SQL 不用重新启动进程、不用重新加载类
- **JIT（即时编译）预热**：热点代码被编译成机器码后越来越快
- 数据可能进了**操作系统缓存**
- ⚠️ 诚实标注：这三条是**推断，未深入验证**（本项目实测到"逐段递减 19 倍"这个现象，
  但没做对照实验证明是哪一条在起作用）
