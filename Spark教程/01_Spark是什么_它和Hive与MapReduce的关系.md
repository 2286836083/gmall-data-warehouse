# 01 · Spark 是什么：它和 Hive、MapReduce 是什么关系

> **这篇解决什么**：把"Spark 是什么"讲清楚——包括一个让很多人搞错的关系问题：
> **Hive 和 Spark 根本不是同一层的两个东西，它们不是竞争对手。**
>
> 先把关系理顺，后面才不会越学越乱。

---

## 一、先看全景：这三样东西各站一个位置

大数据离线处理，永远是三个问题：**存哪、谁分资源、谁来算**。

```
       ① 数据存在哪？               ② 谁来分配机器资源？          ③ 谁真正把活算了？
   ┌──────────────────┐        ┌────────────────────┐      ┌────────────────────┐
   │      HDFS        │        │       YARN          │      │   计算引擎          │
   │  分布式文件系统    │        │  资源调度器         │      │  MapReduce          │
   │  把数据切块存到     │        │  决定"这个活派给     │      │  或                 │
   │  多台机器上        │        │  哪台机器、给多大"   │      │  Spark              │
   └──────────────────┘        └────────────────────┘      └────────────────────┘
        数据在这                     资源在这                   算力在这
```

**关键认知**：**第 ③ 格是可以替换的。**

- 早些年：第 ③ 格填的是 **MapReduce**（Hadoop 自带的计算引擎）
- 现在：越来越多填 **Spark**

**换引擎，不用换存储、不用换调度。** 数据还在 HDFS 上，资源还是 YARN 分——
只是"干活的工人"从 MapReduce 换成了 Spark。

> 📌 **本项目对照**：Spark 装好之后，**YARN 一行配置都没改**，
> 就能把原来交给 MapReduce 的活交给 Spark 跑。这叫"**计算与资源解耦**"——
> YARN 只认"申请多少内存和 CPU"，不关心你要跑的是 MapReduce 还是 Spark。

---

## 二、Hive 站在哪一格？（这是最容易搞错的地方）

先给结论：**Hive 不是一个计算引擎，Spark 也不是 Hive 的替代品。**

Hive 实际由两部分组成：

| Hive 的组成                   | 干什么                                                       | 类比                         |
| ----------------------------- | ------------------------------------------------------------ | ---------------------------- |
| **元数据（MetaStore）** | 记住"表叫什么、有哪些字段、分区在哪、数据存在 HDFS 哪个目录" | 图书馆的**目录卡片柜** |
| **SQL 解析器**          | 把你写的 SQL 翻译成"能在集群上跑的任务"                      | **翻译官**             |

**注意第二行**："翻译成能在集群上跑的任务"——**翻译成什么任务，是可以换的**：

```
                  ┌──────────────────────────────┐
   你写 SQL  ───▶  │  Hive 的 SQL 解析器（翻译官） │
                  └──────────────┬───────────────┘
                                 │  翻译成……
                    ┌────────────┴────────────┐
                    ▼                         ▼
            ┌───────────────┐         ┌───────────────┐
            │  MapReduce    │         │    Spark      │
            │  （老引擎）    │         │  （新引擎）    │
            └───────────────┘         └───────────────┘
```

所以正确的说法是：

- **Hive 提供"表"和"SQL"这两件事**（元数据 + 翻译）
- **MapReduce 和 Spark 是两种可以替换的"执行方式"**
- 本项目里：**Spark 通过 Hive 的 MetaStore 拿到表定义**（所以 Spark 里 `show tables` 能看到一模一样的 27 张表），
  但**真正计算的是 Spark 自己，不再走 MapReduce**

> ⚠️ **一个常见误解**："Spark 取代了 Hive"。
> 不准确。准确的说法是：**Spark 取代了 MapReduce 作为执行引擎**；
> Hive 的元数据仍然在用（否则 Spark 不知道你的表长什么样）。

## 三、Spark 为什么快？先说三个机制

先说清楚：**MapReduce 慢在哪儿**（不然后面的话都是空的）。

MapReduce 的两个"原罪"：

| 原罪                                  | 具体表现                                                         | 物理上是什么                                         |
| ------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------- |
| **① 每一步之间都要落盘**       | map 写完先落本地磁盘，reduce 拉取时再落一次盘，最后结果写回 HDFS | 磁盘读写速度只有内存的**1/100 左右**（见下表） |
| **② 每个小任务都要起一个 JVM** | 一个 map 任务 = 一个新启动的 Java 进程，跑完就销毁               | 启动一个 JVM 要几秒，**这钱是白花的**          |

> **名词**：**JVM（Java 虚拟机）**——运行 Java 程序的"容器"。
> 你可以把它理解成一个"进程"：启动它要花时间（加载类、初始化），所以**反复启动是很贵的**。

硬件速度对照（这是"为什么落盘那么贵"的物理依据）：

| 层级               | 速度                | 相对内存            |
| ------------------ | ------------------- | ------------------- |
| 内存               | ~20 GB/s            | 1×                 |
| NVMe 固态          | ~3 GB/s             | 慢 7 倍             |
| SATA 固态          | ~500 MB/s           | 慢 40 倍            |
| **机械硬盘** | **~150 MB/s** | **慢 130 倍** |

**Spark 的三个对策**：

| # | Spark 的做法                          | 通俗说法                 | 物理上到底怎么实现的                                                                                                        |
| - | ------------------------------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 1 | **中间结果尽量留在内存**        | "不搬仓库，手递手"       | 一个阶段（Stage）内部，前一步的产出直接放在 Executor（干活进程）的内存里，下一步就地接着算；**只有跨阶段时才落盘**    |
| 2 | **Executor 常驻，任务用线程跑** | "工人不走，只换手里的活" | Spark 启动时会起若干个 Executor 进程并**一直留着**，每个任务只是它内部的一个线程——**没有反复启动 JVM 的开销** |
| 3 | **整条 SQL 一起优化**           | "先看完全图再派工"       | Spark 会把整个 SQL 编译成一张**有向无环图（DAG）**，先整体优化再执行；MapReduce 是"一段一段翻译"，看不到全局          |

> **名词**：**DAG（有向无环图，Directed Acyclic Graph）**——一种"带方向的流程图"：
> 每个点是一步计算，箭头表示"必须先做 A 才能做 B"，而且**不会绕回来**（无环）。
> 中文可以理解成"**带先后顺序的施工进度图**"。

### 3.1 三种优化，一句话总结

> MapReduce 把成本花在"**工序之间来回搬料 + 反复雇工人**"上；
> Spark 说：料尽量不搬仓库（留内存）、工人别走（Executor 常驻）、工期我整体排（DAG）。

## 四、但是——主流说法只说对了一半（本项目实测）

上面那三条听起来很有道理，**而且确实是 Spark 的设计目标**。本项目实测下来：

### 4.1 实测数据（同 SQL、同资源、同一时间窗口）

| 调用方式                             | Spark            | Hive / MapReduce | 快多少             |
| ------------------------------------ | ---------------- | ---------------- | ------------------ |
| **① 一个会话里连跑 8 段 SQL** | **75 秒**  | 389 秒           | **5.0 倍**   |
| **② 每段 SQL 各起一个会话**   | **381 秒** | 421 秒           | **只快 10%** |

**同一个 Spark、同一批 SQL，只是"怎么调用"不一样，结果从 5 倍掉到 1.1 倍。**

### 4.2 更反直觉的：轻作业上 Spark 反而更慢

| 作业                           | Spark | Hive            | 谁快                    |
| ------------------------------ | ----- | --------------- | ----------------------- |
| DWS 交易主题（只扫 18.6 万行） | 45 秒 | **26 秒** | **Hive 快 19 秒** |
| ADS 转化漏斗                   | 42 秒 | **38 秒** | Hive 快 4 秒            |
| ADS TopN 商品                  | 42 秒 | **35 秒** | Hive 快 7 秒            |

### 4.3 为什么？——"固定开销"这笔账

**Spark 每次启动一个会话（提交一个应用），都要付一笔固定成本：**

```
   启动 JVM（几十毫秒~几秒）
 + 连接 Hive 元数据服务
 + 向 YARN 申请 Executor 容器并等待分配
 ────────────────────────────────────
   合计约 35 秒   ← 还没开始算任何数据
```

算一下 8 段各起一个会话的情况：

```
35 秒 × 8 段 = 280 秒   占 Spark 总耗时 381 秒的 73%
```

也就是说：**Spark 把 73% 的时间花在了"准备工作"上。**

而 Hive 那边虽然也有启动开销，但它每个作业本身就要跑 20~80 秒（MapReduce 干活慢），
**启动开销占比小得多**。

### 4.4 修正后的正确说法（★ 这是本篇最重要的一句）

> ❌ 不准确的说法：**"Spark 比 Hive 快。"**
>
> ✅ 准确的说法：**"Spark 把成本从『每次作业』挪到了『每次会话』——
> 所以它只在会话被复用时才划算。"**

两个可以直接拿去用的判断：

1. **多个作业要合并进一个常驻会话**（生产做法：Spark ThriftServer 常驻服务，或者一个应用里跑多条 SQL）
2. **单条短查询不要用 Spark** —— 一次约 35 秒的启动成本，比很多查询本身还长

> ⚠️ **诚实标注**：那个"5.0 倍"是**这套集群、这套 SQL、这种调用方式下的实测比值**，
> 不宜外推成"Spark 普遍比 Hive 快 5 倍"。
> 另外要说明：Hive 一段 SQL 会编译成多个 MapReduce 作业串行跑，
> 而 Spark 的 8 条 INSERT 是 8 个 DAG —— 两者内部组织方式并不完全对等。

## 五、一张表看清两者的差别

| 对比项                      | Hive + MapReduce                                                   | Spark                                                                                      |
| --------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| **一句 SQL 变成什么** | 一个或多个**作业**，每个作业是一批**容器**（JVM 进程） | 一张**DAG**，切成若干**阶段**，由常驻进程里的**线程**执行                |
| **中间结果放哪**      | **每个作业之间必须落磁盘**                                   | **阶段内部尽量留内存**，只有跨阶段才落盘                                             |
| **进程模型**          | 一个容器一个任务，**反复启 JVM**                             | Executor 进程**一次启动、常驻**，任务是线程                                          |
| **谁来调度**          | YARN 按容器粒度调度                                                | Spark 先自己排出执行计划，再向 YARN 申请 Executor；**YARN 只看得到 Executor 这一层** |
| **谁来翻译 SQL**      | Hive 自己的解析器                                                  | Spark 的 Catalyst 优化器                                                                   |
| **启动开销**          | 每个作业几秒（但作业本身慢，占比小）                               | **每次会话约 35 秒**（所以怕短查询、怕反复起会话）                                   |
| **适合什么**          | 大规模、不着急的离线批处理；只写 SQL                               | 复杂多步计算、要反复复用中间结果、会话常驻的场景                                           |

> **名词**：**Catalyst（催化剂）**——Spark SQL 内部那个"**查询优化器**"。
> 你写的 SQL 先被它改写、化简（比如把能提前过滤的条件提前），再生成执行计划。

## 六、常见误解（这些说法都不准确）

| ❌ 不准确                         | ✅ 应该是                                                                                                |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| "Spark 取代了 Hive"               | Spark 取代的是**MapReduce 这个执行引擎**；Hive 的元数据还在用（本项目 Spark 就是连的 Hive 元数据） |
| "Spark 比 Hive 快 5 倍"           | 要看调用方式：会话复用 5 倍，各起会话只快 10%，轻作业反而更慢                                            |
| "Spark 快是因为用内存"            | 只说对一半。另一半是"**Executor 常驻省掉了反复启 JVM**"和"**整条 DAG 一起优化**"             |
| "Spark 什么都能干，Hive 该淘汰了" | 单条短查询、纯 SQL 报表，Hive/MapReduce 更省（不用付 35 秒启动费）                                       |
| "Spark 是数据库"                  | 不是。它不存数据（数据在 HDFS），也不管资源（资源是 YARN 给的）                                          |

## 七、自测

**每题标了对应小节——答不出来就回去看那节。**

1. "存、分资源、算"这三件事分别由谁负责？哪一格可以替换？—— 对应 **§一**
2. Hive 由哪两部分组成？为什么说 Hive 和 Spark 不是竞争关系？—— 对应 **§二**
3. MapReduce 慢的两个原因是什么？Spark 的三个对策分别对应哪个原因？—— 对应 **§三**
4. 为什么"每段 SQL 各起一个会话"时 Spark 只快 10%？—— 对应 **§4.3**
5. 用一句话说清"Spark 和 Hive 该怎么选"。—— 对应 **§4.4**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 三个位置**

- 存 → **HDFS**；分资源 → **YARN**；算 → **计算引擎**（MapReduce 或 Spark）
- **第三格可以替换**：换引擎不用改存储、不用改 YARN 配置
- 加分项：这叫"计算与资源解耦"；本项目装 Spark 后 YARN 一行配置都没改

**2. Hive 的两个组成 / 为什么不是竞争**

- Hive = **元数据（MetaStore，"表长什么样"）+ SQL 解析器（"翻译官"）**
- 翻译成什么任务**可以换**：可以是 MapReduce，也可以是 Spark
- 所以 Spark 和 Hive 不在同一层：**Hive 管"表 + SQL"，Spark 管"算"**
- 本项目 Spark 连的就是 Hive 的元数据 → `show tables` 能看到同样 27 张表

**3. MapReduce 慢 vs Spark 三对策**

| MapReduce 慢在                             | Spark 的对策                        |
| ------------------------------------------ | ----------------------------------- |
| 每一步之间都要落盘（磁盘比内存慢 ~130 倍） | ① 阶段内部结果留内存，跨阶段才落盘 |
| 每个任务都起一个 JVM（启动贵）             | ② Executor 常驻，任务用线程跑      |
| 一段段翻译，看不到全局                     | ③ 整条 SQL 编译成 DAG，整体优化    |

- 加分项：说出"JVM 反复启动"是白花的钱（任务本身只要几秒）

**4. 为什么各起会话只快 10%**

- Spark 每次提交要付约 **35 秒**固定开销（启 JVM + 连元数据 + 向 YARN 申请 Executor）
- 8 段 × 35 秒 = 280 秒，占 381 秒的 **73%**
- Hive 虽然也慢，但它每个作业本身要跑 20~80 秒，**启动开销占比小**

**5. 一句话说清怎么选**

- "**多作业进一个常驻会话，就用 Spark（收益来自会话复用）；单条短查询别用 Spark（35 秒启动费比查询还贵）**"
- 加分项：承认"5.0 倍"是特定条件下的实测值，不宜外推

</details>
