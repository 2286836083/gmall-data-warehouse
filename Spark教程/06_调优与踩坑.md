# 06 · 调优与踩坑

> **这篇解决什么**：Spark 作业跑得慢、跑挂了、或者"看起来跑完了但数据不对"，往哪个方向想。
>
> **调优的第一原则和 Hive 一样**（`零基础教程/11` 讲过）：
> **先找瓶颈，不要猜。** 不看数据就加内存、加并行度，是碰运气。

---

## 一、先建立"钱花在哪"的意识

Spark 作业的时间，基本花在这四件事上（按常见程度排）：

```
① shuffle（跨机器搬数据）        ← 最贵，也最该优化
② 读 HDFS / 写 HDFS（磁盘 + 网络）
③ 等资源（YARN 没有空闲容器）
④ 真正在算（CPU）
```

**和 Hive/MapReduce 的结论一样：CPU 很少是瓶颈。**

所以调优动作的优先级是：
**先看有没有能减少 shuffle 的写法** → 再看内存够不够 → 最后才看并行度。

---

## 二、内存：三个数字，必须分清

Spark 的 Executor 内存**不是一个数**，而是三层：

```
┌─────────────────────────────────────────────┐
│  YARN 容器（上限 2048MB，集群硬约束）          │
│  ┌───────────────────────────────────────┐  │
│  │ spark.executor.memory  = 1408MB       │  │ ← 堆内（Java 对象、数据、缓存）
│  │   （JVM 的 -Xmx 控制）                 │  │
│  ├───────────────────────────────────────┤  │
│  │ spark.executor.memoryOverhead = 384MB │  │ ← 堆外（JVM 自身、网络缓冲、字符串）
│  └───────────────────────────────────────┘  │
│                                              │
│              1408 + 384 = 1792MB ≤ 2048 ✅   │
└─────────────────────────────────────────────┘
```

**名词解释**：

| 名词 | 中文 | 装什么 |
|---|---|---|
| **堆内内存（heap）** | JVM 堆 | Java 对象、你的数据、缓存 —— 由 `-Xmx`（也就是 `executor.memory`）控制 |
| **堆外内存（off-heap / overhead）** | JVM 堆外 | JVM 自身的结构、字符串常量、网络传输缓冲 |
| **OOM（Out Of Memory）** | 内存溢出 | 内存不够导致崩溃。**分两种，处理方式不同（见下）** |

### 2.1 两种"内存不够"，症状不同

| 症状 | 是哪种 OOM | 怎么办 |
|---|---|---|
| 日志里出现 `java.lang.OutOfMemoryError: Java heap space` | **堆内不够** | 调大 `spark.executor.memory`（但要保证总和 ≤ 容器上限） |
| 容器被 YARN **直接杀掉**（`Container killed ... exceeding memory limits`） | **总容器超限**（堆内+堆外超了） | 调大 `memoryOverhead`，或减小 `executor.memory` |

> ⚠️ **这是两个不同的错，别混**：一个是"程序内部不够用"，一个是"你申请的额度被超了"。
> 前者的解法在 Spark 参数里，后者的解法是重新算"堆内+堆外 ≤ 容器上限"这笔账。

### 2.2 本项目的一个特别注意点

```
Hive  ：一个容器跑 1 个任务 → 1024MB 容器 / 堆上限 820MB，一个任务独占
Spark ：一个 Executor 跑 2 个任务 → 1408MB 堆 ÷ 2 ≈ 704MB 每个任务
```

**也就是说 Spark 里每个任务分到的内存，其实比 Hive 少。**
所以"大基数聚合会不会内存不够"这件事，在 Spark 侧更值得关注。

> 💡 **推论**：如果遇到"某个 Stage 反复失败、报堆内存不足"，
> 可以考虑**减少每个 Executor 的并发任务数**（`executor.cores` 调小），
> 相当于"让每个任务独占更多内存" —— 用并行度换内存。

## 三、并行度：`shuffle.partitions` 为什么必须改

**名词**：**`spark.sql.shuffle.partitions`** ——
shuffle 之后把数据切成**多少片**（也就是产生多少个并行任务）。

**它的默认值是 200。** 这在两边的极端都不好：

| 集群核数 | 默认 200 的后果 |
|---|---|
| **小集群（本项目：6 核）** | **灾难**：200 个任务排队等 6 个核 → 大量任务在等，还产生 200 个小文件 |
| 大集群（几百核） | 资源不够分：200 个任务摊不到每个核 |

**本项目的做法**：配成 **6**（与 6 个核对齐，也和 Hive 侧的 reduce 数对齐）。

**怎么定这个数**（经验规则）：

```
片数 ≈ 集群总核数 × 1~2        （太小：并行度不够；太大：任务调度开销 + 小文件）
或者：每个分片的目标数据量 ≈ 128MB~256MB（一个 HDFS 块大小）
```

> 💡 **一个直观判断**：打开 Spark UI 的 Stages 页面，
> 如果看到**几百个 task 各自只处理几十 KB**，就是分片设太大了（典型症状：默认 200 没改）。

## 四、数据倾斜（和 Hive 里是同一个病）

**名词**：**数据倾斜** —— 某个 key 的数据量特别大，
导致处理它的那**一个任务**要跑很久，其他任务早就跑完了，**整个 Stage 卡在等它**。

### 4.1 症状

- 大部分任务几秒完成，**个别任务跑几十分钟**
- Spark UI 的 Stages 页面：某个 task 的耗时远超其他（**看 Max 和 75 分位数的差距**）
- 或者：极少数分片的数据量比其他的大几十倍

### 4.2 定位

```sql
-- 先看哪个 key 大（和 Hive 里的做法一样）
SELECT category_l1, COUNT(1) AS cnt
FROM gmall.dwd_event_log_di
GROUP BY category_l1
ORDER BY cnt DESC
LIMIT 20;
```

本项目数据里 `category_l1 = 'unknown'` 占 **31.9%** —— 这类"空值/异常值集中"就是典型倾斜源。

### 4.3 解法（按优先级）

| 解法 | 做法 | 适用 |
|---|---|---|
| **① 过滤掉异常 key** | 分析时不看 `unknown`（或单列出来） | 脏数据造成的倾斜 |
| **② 两阶段聚合（加盐）** | 先给 key 加随机前缀做局部聚合，再去掉前缀做全局聚合 | 大基数聚合 |
| **③ 广播小表** | 小表直接发给每个任务，不做 shuffle 关联 | 大表关联小表 |
| **④ 拆分热点单独处理** | 热点 key 走一条路径，其余走另一条，最后合并 | 极少数超级热点 |

**加盐的写法**（和 Hive 版本思路一致）：

```sql
-- 本来会倾斜：GROUP BY key
-- 加盐后：
SELECT key, SUM(cnt) FROM (
  SELECT SUBSTR(salted_key, 1, INSTR(salted_key,'_')-1) AS key,
         COUNT(1) AS cnt
  FROM (
    SELECT CONCAT(key, '_', CAST(FLOOR(RAND()*10) AS STRING)) AS salted_key
    FROM t
  ) a
  GROUP BY salted_key
) b
GROUP BY key;
```

> ⚠️ **慎用 `rand()` 类函数做加盐**：它会让**结果不可重现**。
> 如果必须用，要清楚"每次跑出来的中间结果可能不同，但最终结果必须一致"。

## 五、AQE：Spark 3 的"自动调优"（知道有这回事）

**名词**：**AQE（Adaptive Query Execution，自适应查询执行）** ——
Spark 3 引入的能力：**边跑边看实际数据量，动态调整执行计划**。

它主要自动做三件事：

| 自动做什么 | 解决什么问题 |
|---|---|
| 合并过小的分片 | 分片数设太大导致的"几百个小任务" |
| 拆分过大的分片 | 分片不均衡 |
| 把大表关联小表**自动改成广播** | 避免不必要的 shuffle |

**默认是开启的**（`spark.sql.adaptive.enabled=true`）。

> 💡 **实用价值**：AQE 能自动缓解一部分"分片数拍脑袋"的问题，
> 但**它救不了数据倾斜**（那是数据本身的问题）。
> 所以别指望"开了 AQE 就不用管调优"。

## 六、小文件问题（两个引擎都要面对）

**现象**：`shuffle.partitions` 设太大、或者写入任务太多 → 每个分片输出一个文件 →
**一个分区目录下几百个小文件**。

**后果**：
- 下次读的时候，**每个小文件都成为一个任务** → 任务数爆炸、调度开销大于计算
- HDFS 上 **NameNode 元数据压力**（第 04 章讲过：文件数决定 Namenode 内存）

**解法**：

| 解法 | 怎么做 |
|---|---|
| 减少分片数 | 调小 `shuffle.partitions` |
| 写入前合并 | `repartition(n)` / `coalesce(n)` 后再写 |
| 定期合并历史小文件 | 单独跑一个合并作业 |

## 七、本项目踩过的坑（清单）

| # | 坑 | 现象 | 根因 / 解法 |
|---|---|---|---|
| 1 | **`metastore.jars` 没配** | 连不上元数据 / `Invalid method name` | Spark 内置 Hive 客户端 2.3.9 ≠ 集群 metastore 3.1.3 → 必须 `jars=path` 指定集群的 Hive lib |
| 2 | **`partitionOverwriteMode` 没设** | 补跑单日时**其他分区被静默清空**（不报错！） | 默认 `STATIC` 会先清空整表 → 必须设 `dynamic` |
| 3 | 用了 **Hive 没有的 `sequence()`** | `Error 10011 Invalid function sequence` | 那是 Spark 的函数；Hive 用 `posexplode(split(repeat(',',364),','))` |
| 4 | Spark 4 的 **ANSI 模式**风险 | SQL"跑得起来但结果不一样" | 避坑方式：**不升 4.x**（JDK 8 也升不了） |
| 5 | 把 **`PMem` 当成 YARN 容量** | 差点按 4860MB 设计 Executor | 那是**物理内存使用量**；真容量看 `Configured Resources`（2048MB） |
| 6 | 日志里的 **`TTransportException`** | 报"连接 metastore 失败"但结果是对的 | **良性噪音**，见 §7.1 |

### 7.1 重点讲一个：怎么判断"日志报错"是不是真故障

Spark 日志里出现过这样的报错：

```
WARN RetryingMetaStoreClient - MetaStoreClient lost connection.
Attempting to reconnect (1 of 1) after 1s.
org.apache.thrift.transport.TTransportException: Cannot write to null outputStream
```

**怎么判断它是不是故障**（★ 一套可复用的方法论）：

| 判据 | 这次的情况 |
|---|---|
| **① 异常出现在哪条路径上** | 出现在 `listPartitionsWithAuthInfo`（**读分区元数据**），不在数据读取路径上 |
| **② 有没有自动恢复** | `RetryingMetaStoreClient` **内置重试，且日志明写 `Connected to metastore`** |
| **③ 结果对不对** | 查询结果 **10,630,245**，与基线**逐位一致** |
| ④ 重跑一次是否复现 | **复现，且结果仍正确** → 是**确定性噪音**，不是偶发故障 |

> ★ **核心判断**：**"控制面报错 ≠ 数据面失败"**。
> 但注意后半句——**不是"忽略它"，而是"证明它不影响结果"**。
>
> 面试里问"日志有异常你怎么办"，正确答案是给出上面这套**证明过程**，而不是"我一般忽略 Warn"。

## 八、怎么用 Spark UI 定位问题（三个页面就够）

`http://lrh-1:4040`（应用运行时才有）

| 页面 | 什么时候看 | 看什么 |
|---|---|---|
| **Jobs** | 想快速知道"慢在哪个作业" | 每个 Job 的耗时和状态 |
| **Stages** | ★ **最常用** | 哪个 Stage 慢；**Shuffle Read/Write 的量**；task 耗时的**分布**（看倾斜） |
| **SQL** | 想看执行计划长什么样 | 每条 SQL 的 DAG 图 —— **能直观看到哪里切了 Stage、哪里是 Exchange（shuffle）** |
| **Executors** | 怀疑内存/GC 问题 | 每个执行器的内存使用、GC 时间、失败次数 |

**排查顺序建议**：

```
① Stages 页面 → 找最慢的 Stage
② 看这个 Stage 的 Shuffle Read/Write 大不大 → 大 → 优化 shuffle
③ 看 task 耗时分布 → 个别特别长 → 数据倾斜
④ 看 Executors 的 GC 时间 → 占比高 → 内存不够
```

## 九、和 Hive 调优的异同（一句话对照）

| | Hive / MapReduce | Spark |
|---|---|---|
| 内存单位 | **容器**（一个容器一个任务） | **Executor**（一个 Executor 跑多个任务） |
| 内存怎么给 | `mapreduce.*.memory.mb` + `-Xmx` | `executor.memory` + `memoryOverhead` |
| 并行度怎么控 | `mapreduce.job.reduces` | `spark.sql.shuffle.partitions` |
| **共同的瓶颈** | **shuffle（跨机器搬数据）** | **shuffle** |
| 共同的病 | 数据倾斜、小文件 | 数据倾斜、小文件 |
| 共同的第一原则 | **先找瓶颈，不要猜** | 同 |

> ★ **最有价值的认知**：**换了引擎，瓶颈还是那些瓶颈。**
> shuffle、倾斜、小文件 —— 这些是"分布式计算的固有难点"，不是某个引擎的缺陷。
> **所以你在 Hive 上学到的调优思路，在 Spark 上基本通用。**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 两个内存参数**
- `executor.memory` = **堆内**内存（Java 对象、数据、缓存），由 JVM 的 `-Xmx` 控制
- `memoryOverhead` = **堆外**开销（JVM 自身结构、网络缓冲、字符串常量），默认 `max(384MB, 10%)`
- 为什么不能超 2048：**YARN 按"两者之和"给你划容器**；
  `1408 + 384 = 1792 ≤ 2048`；写 `2g` 会变成 `2048+384=2432 > 2048` → **YARN 拒绝分配，作业起不来**

**2. 两种"内存不够"**
- `OutOfMemoryError: Java heap space` → **堆内不够** → 调大 `executor.memory`
- `Container killed ... exceeding memory limits` → **容器总额度被超** → 调大 `memoryOverhead`（或减小堆内）
- 关键：一个是程序内部不够，一个是申请的额度被超，**解法不同**

**3. shuffle.partitions**
- 默认 **200**
- 小集群（6 核）上：200 个任务排队等 6 个核 → 大量任务在等；还会产生 200 个小文件
- 本项目配成 **6**（与核数、与 Hive 侧 reduce 数对齐）
- 判断规则：片数 ≈ 总核数 × 1~2，或每片目标 128~256MB

**4. 数据倾斜**
- 定位：看 Spark UI 的 **Stages 页面中 task 耗时分布**（Max 远大于中位数）；
  或先 `GROUP BY key ORDER BY COUNT(1) DESC` 看哪个 key 特别大
- 解法（举两个即可）：① **过滤/单列异常 key**（本项目 `unknown` 占 31.9%）；
  ② **两阶段聚合（给 key 加随机前缀先局部聚合，再去前缀全局聚合）**；
  ③ 大表关联小表时**广播小表**

**5. 怎么判断日志异常是不是真故障**
- ① 异常发生在**哪条路径**（元数据读取 ≠ 数据读取）
- ② 有没有**自动恢复**（是否重试成功）
- ③ **结果对不对**（与基线比对）
- ④ 重跑是否复现（复现且结果正确 → 确定性噪音）
- 核心："**控制面报错 ≠ 数据面失败**"，但要**证明**，不能默认忽略

**6. 为什么调优思路通用**
- 因为瓶颈是**分布式计算的固有难点**，不是某个引擎的缺陷：
  **shuffle（跨机器搬数据）、数据倾斜、小文件** —— 两边都有，解法思路也相通
- 差别只在"参数名字和内存单位不同"（容器 vs Executor）
</details>
