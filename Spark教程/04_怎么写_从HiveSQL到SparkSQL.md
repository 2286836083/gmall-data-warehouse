# 04 · 怎么写：从 Hive SQL 到 Spark SQL

> **这篇解决什么**：Hive SQL 你**已经会写了**（`零基础教程/06`），
> 而 Spark SQL 长得和它**几乎一样** —— 但正因为"太像"，有几个地方会让你**掉进坑里还不报错**。
>
> **"相似"本身就是陷阱。** 本篇把相同点、不同点、以及一份迁移检查清单给你。

---

## 一、三种跑法（先知道怎么把 SQL 送进去）

| 方式                    | 命令                          | 适合什么                               | 注意                                                          |
| ----------------------- | ----------------------------- | -------------------------------------- | ------------------------------------------------------------- |
| **① SQL 命令行** | `spark-sql -e "SELECT ..."` | 单条查询、临时看一眼                   | ⚠️ 每次都要付约 35 秒启动开销                               |
| **② 批量脚本**   | `spark-sql -f 脚本.sql`     | **跑 ETL（本项目用的就是这个）** | ★**多段 SQL 务必放同一个文件**，否则每段都付一次启动费 |
| **③ 提交应用**   | `spark-submit xxx.py/.jar`  | 写代码的作业（Python/Scala）           | 数据开发岗用得较少                                            |

**本项目实际怎么跑的**：

```bash
SP=/opt/spark-3.5.9-bin-hadoop3/bin/spark-sql

# ❌ 反面写法：8 段 SQL 分别执行 → 付 8 次启动开销（280 秒白花）
$SP -f step1.sql
$SP -f step2.sql
...

# ✅ 正确写法：8 段拼进一个文件，一个会话跑完
$SP -f all_steps.sql          # 实测比上面快 5 倍
```

> ⚠️ **名词**：**`spark-sql`** 是 Spark 自带的**SQL 命令行工具**（类似 Hive 的 `beeline`）。
> 启动它 = 建立一个**会话（SparkSession）**，这个动作本身就要 35 秒。
> **会话建立一次、里面跑多少条 SQL 都行** —— 这就是第 01 篇那个"收益来自会话复用"的操作层面含义。

---

## 二、哪些地方**完全一样**（可以放心直接搬）

| 能力               | 说明                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------- |
| **建库建表** | `CREATE DATABASE` / `CREATE TABLE ... PARTITIONED BY` / `STORED AS ORC` 基本一致 |
| **读表**     | 因为连的是**同一份 Hive 元数据**，`SELECT ... FROM gmall.xxx` 直接能用         |
| **写表**     | `INSERT OVERWRITE TABLE ... PARTITION (dt)` 同样可用（但语义有坑，见 §四）          |
| **分区**     | `SHOW PARTITIONS`、`WHERE dt='...'` 都一样                                         |
| **常用函数** | `COUNT/SUM/CASE WHEN/COALESCE/NULLIF/SPLIT/REGEXP_REPLACE` 这些两边都有              |
| **窗口函数** | `ROW_NUMBER / LAG / SUM OVER` 也都有（写法基本一致）                                 |

**本项目实测**：同一份 SQL、同一个文件，两个引擎跑出来的结果**逐位一致**：

| 表                        | Hive 版                 | Spark 版                   |
| ------------------------- | ----------------------- | -------------------------- |
| `dws_user_event_day`    | 1,622,820               | **1,622,820** ✅     |
| `dws_product_event_day` | 1,265,817               | **1,265,817** ✅     |
| `dws_trade_day` GMV     | **57,575,996.50** | **57,575,996.50** ✅ |
| 分区数                    | 31                      | **31** ✅            |

> → **换引擎不改结果**。这句话很重要：它是你敢于在生产上换引擎的底气。

## 三、哪些地方**不一样**（★ 踩了就记住）

### 3.1 有些函数只有一边有

| 函数/写法                       | Hive                     | Spark                       | 怎么处理                                                   |
| ------------------------------- | ------------------------ | --------------------------- | ---------------------------------------------------------- |
| `sequence(0, 364)` 造数字序列 | ❌**没有**         | ✅ 有                       | Hive 里用`posexplode(split(repeat(',', 364), ','))` 代替 |
| `dayofweek()` 的返回值        | ⚠️**1 = 星期日** | ⚠️ 与 Hive 不同（需实测） | **做星期维度必须单独验证**，别假设                   |

> 📌 **本项目真实踩坑**：写"造 365 天日期"的 SQL 时用了 `sequence()` —— 那是 **Spark SQL 的函数，Hive 没有**，
> 报 `Error 10011 Invalid function sequence`。
>
> ★ **教训**：**"Hive 和 Spark SQL 高度相似"这件事本身就是陷阱。**
> 你会因为"看起来一样"而跳过验证。**跨引擎迁移语法假设，必须先验证再写进脚本。**

### 3.2 `INSERT OVERWRITE` 分区表的语义不同（★ 最容易出事的）

|                                                 | Hive                           | Spark（默认）              |
| ----------------------------------------------- | ------------------------------ | -------------------------- |
| `INSERT OVERWRITE TABLE t PARTITION (dt) ...` | 只覆盖**本次涉及的分区** | **先清空整张表**再写 |

**Spark 侧必须加**：

```properties
spark.sql.sources.partitionOverwriteMode = dynamic
```

**不加的后果**：全量跑没事；**补跑某一天时，其他天数的分区会被静默清空** —— 不报错，数据没了。

> 详见第 03 篇 §六。这里放在"写法差异"里再强调一次，因为它属于**写 SQL 时就要知道的事**。

### 3.3 类型和空值的"严格程度"不同

| 场景                       | Hive                         | Spark                                       |
| -------------------------- | ---------------------------- | ------------------------------------------- |
| 字符串和数字比较           | 比较宽松（会隐式转换）       | **更严格**（可能直接报错或返回 null） |
| `NULL` 参与运算          | 结果 null                    | 结果 null（相同）                           |
| `NULL` 参与比较（`=`） | 返回 null（不是 true/false） | 相同                                        |

**实践建议**（两个引擎都安全）：

```sql
-- ❌ 依赖隐式转换
WHERE user_id = '123'                -- user_id 是 bigint，用字符串比

-- ✅ 显式转换，两边行为一致
WHERE user_id = CAST('123' AS BIGINT)
```

### 3.4 `INSERT INTO ... VALUES` 的行为

- Spark 支持得比 Hive 好（Hive 里一条一条 VALUES 会非常慢）
- 但**离线数仓里两边都不该用它** —— 数据应该用 `INSERT ... SELECT` 或 `LOAD DATA`

### 3.5 报错信息的风格不同

|       | 报错特点                                                               |
| ----- | ---------------------------------------------------------------------- |
| Hive  | 报`Error 10xxx` 代码，配合日志                                       |
| Spark | 报 Java 异常栈（很长），但**通常会在开头给出"哪一行、什么问题"** |

> 提示：Spark 报错**先看第一段**（`AnalysisException` / `ParseException` 之类），
> 那是真正的错误；后面的几十行栈是调用链，初学阶段可以先不看。

## 四、迁移检查清单（把 Hive 脚本改成 Spark 版照着走）

| # | 检查项                                                                                | 为什么                             |
| - | ------------------------------------------------------------------------------------- | ---------------------------------- |
| 1 | 有没有用**Hive 独有的函数**？（`sequence` 之类）                              | 会直接报函数不存在                 |
| 2 | `INSERT OVERWRITE` 分区表 → **确认 `partitionOverwriteMode=dynamic` 已设** | 否则会清空整表，**且不报错** |
| 3 | 日期函数（`dayofweek`、`date_add`…）的**返回值**是否一致                   | 星期编号这类约定两边可能不同       |
| 4 | 有没有依赖**隐式类型转换**的比较/聚合                                           | Spark 更严格                       |
| 5 | `UNION ALL` 各段的**列类型**是否完全一致                                      | 一边宽松一边严格                   |
| 6 | 写入目标表**是否已存在**（结构是否兼容）                                        | Spark 不像 Hive 那么宽容           |
| 7 | 跑完**对账**：行数 + 关键指标（如 GMV）与 Hive 版逐项比                         | **这是唯一可靠的验证**       |

> ★ **第 7 条是灵魂**：光"跑通了"不算迁移成功，**"跑出来和原来一样"才算**。
> 本项目就是靠"8 张表行数逐项比对 + GMV 逐位比对"证明迁移无损的。

## 五、怎么看它到底怎么跑的（可观测性的三个入口）

### 5.1 `EXPLAIN` —— 看"打算怎么跑"

```sql
EXPLAIN
SELECT dt, COUNT(DISTINCT user_id) FROM gmall.dwd_event_log_di GROUP BY dt;
```

**重点看**：

- 有没有出现 `Exchange`（**这就是 shuffle**，是性能杀手，也是 Stage 分界）
- 计划是一个 DAG 还是一串

> ⚠️ **名词**：**`Exchange`** 是 Spark 执行计划里对 **shuffle** 的叫法。
> 你在计划里看到的每一个 `Exchange`，都意味着一次"跨机器搬数据"。

### 5.2 Spark UI（网页）—— 看"实际怎么跑的"

Spark 应用跑起来后，Driver 会开一个网页（默认 4040 端口）：
`http://lrh-1:4040`

| 页面                | 看什么                                                       |
| ------------------- | ------------------------------------------------------------ |
| **Jobs**      | 有几个作业、各自多久                                         |
| **Stages**    | ★ 哪些阶段慢、**shuffle 读写量多大**                  |
| **SQL**       | 每条 SQL 对应的 DAG 图（**能直观看到哪里切了 Stage**） |
| **Executors** | 每个执行器的内存/CPU 使用                                    |

### 5.3 Event Log + History Server —— 跑完之后还能回看

配置了 `spark.eventLog.dir` 之后，作业的历史会被记录到 HDFS，
用 History Server（默认 18080 端口）可以**回放已结束作业的 DAG**。

> 📌 **本项目现状**：event log 目录已建好（`hdfs:///spark/eventlogs`），
> 但 **History Server 还没启用**（在待办里）。
> 这是个很好的演示素材：面试时能现场回放 DAG —— 记在"下一步"里。

## 六、DataFrame API：不用写 SQL 的写法（了解即可）

**名词**：**DataFrame（数据框）** = 带列名的二维表（第 02 篇讲过）。
除了写 SQL，Spark 也允许你用"链式调用的代码"操作它：

```python
# Python 版本（PySpark）—— 和上面的 SQL 等价
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("demo").enableHiveSupport().getOrCreate()

dws_user = (spark.table("gmall.dwd_event_log_di")
    .filter(F.col("event_type") == "purchase")        # 过滤
    .groupBy("user_id", "dt")                          # 分组
    .agg(F.count("*").alias("purchase_cnt")))          # 聚合

dws_user.write.mode("overwrite").insertInto("gmall.xxx")
```

**该学吗？** 对数据开发岗位：

| 场景                                   | 建议                                          |
| -------------------------------------- | --------------------------------------------- |
| 日常做数仓 ETL                         | **写 SQL 就够了**（本项目 100% 是 SQL） |
| 需要写循环、动态生成逻辑、调用外部接口 | 用 DataFrame API / PySpark                    |
| 面试                                   | 知道"两种写法等价、SQL 更常用"即可            |

> 💡 **一个重要认知**：**Spark SQL 和 DataFrame 最终会变成同一套执行计划**。
> 你写 SQL，Spark 内部也翻译成 DataFrame 操作再优化。所以**不存在"哪个更快"**，
> 只有"哪个更好写、更好维护"。

## 七、本项目实测：同一份 SQL 在两个引擎上的表现

（这里只放结论，完整分析见第 05 篇）

```
8 段 SQL（DWS 4 张 + ADS 4 张），同一份 SQL 文件：

单会话连跑：    Spark 75 秒   vs  Hive 389 秒   → 5.0 倍
每段各起会话：  Spark 381 秒  vs  Hive 421 秒   → 1.10 倍
轻作业（DWS-trade）：Spark 45 秒，Hive 26 秒  → Hive 更快
```

**结果一致性**：8 张表行数逐项一致、GMV 逐位一致（57,575,996.50）、分区 31 = 31。

## 八、自测

**每题标了对应小节——答不出来就回去看那节。**

1. 跑 8 段 SQL，为什么"拼进一个文件"比"分 8 次执行"快 5 倍？—— 对应 **§一**
2. 为什么"Hive SQL 和 Spark SQL 很像"反而是个陷阱？举一个本项目的真实例子。—— 对应 **§3.1**
3. `INSERT OVERWRITE` 分区表在两个引擎上有什么不同？不处理会怎样？—— 对应 **§3.2**
4. 把 Hive 脚本迁到 Spark，你的检查清单里最重要的是哪一条？—— 对应 **§四**
5. `EXPLAIN` 里出现 `Exchange` 意味着什么？—— 对应 **§5.1**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 为什么要拼进一个文件**

- 每次启动 `spark-sql` = 建立一个会话，要付约 **35 秒**固定开销
- 8 段分别执行 = 8 × 35 ≈ **280 秒**白花（占分段模式下总耗时的 73%）
- 一个会话里跑 8 段 → 只付一次

**2. 为什么"像"是陷阱**

- 因为看起来一样，你会**跳过验证**，把 Hive 的写法直接搬到 Spark（或反过来）
- 本项目真实例子：用了 `sequence(0,364)` 造日期序列 —— 那是 **Spark 的函数，Hive 没有**，
  报 `Error 10011`
- 正确做法：**跨引擎的语法假设必须先验证再写进脚本**

**3. `INSERT OVERWRITE` 分区表**

- Hive：只覆盖**本次涉及的分区**
- Spark 默认（`STATIC`）：**先清空整张表**再写
- 必须设 `spark.sql.sources.partitionOverwriteMode=dynamic`
- 不设的后果：全量跑没事，**补跑单日时其他分区被静默清空**（不报错）

**4. 检查清单里最重要的一条**

- **跑完对账**：行数 + 关键指标（GMV 等）与 Hive 版逐项比对
- 理由："跑通了"不等于"跑对了"；换引擎要证明**结果不变**，而不是只证明能跑

**5. `Exchange` 意味着什么**

- 就是 **shuffle**（跨机器搬数据）—— 最贵的操作，也是 Stage 的分界线
- 看到它就说明这里有一次数据重分布；优化 Spark 作业本质就是**减少/优化 shuffle**

</details>
