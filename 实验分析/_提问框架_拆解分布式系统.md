# 提问框架 · 怎么拆解任何一个「分布式系统」

> **这份文档解决什么问题**：你知道各个组件"负责什么"（NameNode 管目录、DataNode 存数据），但说不清它们"怎么干"、顺序是什么、和硬件是什么关系。更麻烦的是——**你不知道该问什么**。
>
> 这个框架给你 7 个固定的问题 + 1 条万能问法。拿到任何一个陌生组件或陌生故障，照着问一遍，就能把它拆开。
>
> 建立日期：2026-09-28 · 全部例子都取自本项目的真实故障（实验报告 03）
> 适用：Hadoop / HDFS / YARN / Hive / Spark / Kafka / 任何"跑在多台机器上的系统"

## 一、万能问法：先分类，再深挖

遇到任何"慢 / 卡 / 失败"，**先别急着看日志**，先把它归类：

> ### 它是 **算不过来**、**写不过来**、还是 **搬不过来**？

这三类的排查方向完全不同：

| 类型 | 典型症状 | 该看什么 | 本项目的实例 |
|---|---|---|---|
| **算不过来** | CPU 打满、任务跑很久但进度在动 | CPU 使用率、并行度、数据倾斜 | — |
| **写不过来** | 任务"算完了但没输出"、磁盘 IO 忙、超时 | 磁盘 IO、副本数、并发写入流数量 | ✅ **今天就是这个** |
| **搬不过来** | 网络带宽打满、shuffle 阶段卡住 | 网络流量、shuffle 数据量 | — |

**怎么用它做判定**：看 Hive/MR 的收尾统计行，一次就能分辨：

```
Stage-Stage-1: Map: 6  Reduce: 6   Cumulative CPU: 137.54 sec   ← 只用了 137 秒 CPU，一点都不累
    HDFS Read: 1419781250  HDFS Write: 0                        ← 读到了 1.4GB，写出去 0 字节
```

**CPU 只用了 137 秒、却写出去 0 字节 → 立刻排除"算不过来"，锁定"写不过来"。** 这一条判断省掉了几十分钟的盲查。

## 二、7 个问题（配可执行的验证命令）

每个问题都分三段：**问什么** → 为什么值得问 → 在你的集群上怎么验证。

---

### 问题 1：谁和谁说话？走网络还是本地？

**为什么问**：这是理解一切分布式系统的起点。系统图上画的所有箭头，物理上不是"发消息"就是"读写本地文件"。分不清这两者，就看不懂性能瓶颈在哪。

**关键结论（HDFS 的例子）**：写文件时存在**两条通道**——

| 通道 | 参与者 | 传什么 | 大小 |
|---|---|---|---|
| **控制流** | 客户端 ⇄ NameNode | 只传"位置信息"（该写哪几台、写完了） | 几百字节 |
| **数据流** | 客户端 → DataNode → DataNode → DataNode | 真正的数据块，逐级转发复制 | 几百 MB ~ TB |

> ⭐ **NameNode 全程一个字节的数据都没碰过。** 这是 Hadoop 最重要的设计，它直接推出两个结论：
> 1. NameNode 的内存压力**与数据总量无关，只与"文件数/块数"有关** → 所以 HDFS 天生不适合存海量小文件（1KB 和 1GB 文件在它眼里占的目录条目一样大）
> 2. NameNode 挂了不会丢数据（数据不在它那儿），但集群会"不知道数据在哪"

**怎么验证**：

```bash
# 看 NameNode 到底管什么：查一个文件，只得到元数据（位置、大小、副本）
hdfs dfs -stat '%n %o %r' /user/hive/warehouse/gmall.db/dwd_event_log_di/dt=2019-10-01/000002_0
#   %n 文件名   %o 块大小   %r 副本数    ← 全是"描述"，没有数据本身

# 看两条通道的端口是分开的（9000=控制，9866=数据）
ss -lntp | grep -E "9000|9866"
```

### 问题 2：数据此刻在哪台机器的哪块磁盘上？什么时候只在内存？

**为什么问**："数据在哪"决定了"下一步要走网络还是走本地盘"。走本地盘比走网络快一到两个数量级，所以几乎所有分布式系统的优化都是在**把网络搬运变成本地读写**。

**关键结论（一个 MapReduce 作业）**：

| 阶段 | 数据在哪 |
|---|---|
| 读 HDFS 分片 | 从某台 DataNode 的磁盘读到子进程内存（**尽量调度到数据所在机器上跑**，这就是"数据本地性"） |
| map 输出 | **写本机磁盘**，不进 HDFS——因为是一次性中间数据，没必要付 3 副本的代价 |
| shuffle | 跨网络搬到 reduce 所在机器，**先落盘再读盘** |
| reduce 结果 | 写回 HDFS（走问题 1 的流程，付 3 副本代价） |

**怎么验证**：

```bash
# 找 map 输出的临时目录（在本地磁盘上，不在 HDFS 里）
ls -d /opt/hadoop/hadoop-3.3.6/tmp/nm-local-dir/usercache/*/appcache/*/output 2>/dev/null | head

# 看某个作业的本地性统计（有多少 map 是在数据所在机器上跑的）
/opt/hadoop/hadoop-3.3.6/bin/mapred job -status <application_id> | grep -i local
```

### 问题 3：谁负责"知道"，谁负责"存"？

**为什么问**：几乎所有分布式系统都会把"**元数据**"（谁在哪、有多大）和"**数据本身**"拆成两类角色。认清这条分界线，就能预测系统的容量瓶颈和单点故障在哪。

| 系统 | 负责"知道" | 负责"存" |
|---|---|---|
| HDFS | NameNode（只记目录） | DataNode（存数据块） |
| YARN | ResourceManager（记资源账） | NodeManager（干活） |
| Hive | MetaStore（表结构、分区位置） | HDFS |
| Kafka | ZooKeeper / KRaft（记谁是 leader） | Broker（存消息） |

**关键结论**：**"知道"的那个角色，通常就是单点**，也是调优时最该省内存的地方。本项目里我们给 NameNode 堆设 512MB，就是因为它是内存敏感型。

**怎么验证**：

```bash
# 看"知道"的角色内存占用（NameNode 只记目录，内存却最敏感）
jps -l | grep -E "NameNode|DataNode|ResourceManager"

# 看元数据存在哪（Hive 的表结构全在 MySQL 里，不在 HDFS）
mysql -u root -p -e "SELECT COUNT(*) FROM hive.COLUMNS_V2; SELECT COUNT(*) FROM hive.TBLS;"
```

### 问题 4：一个动作从发起到完成分几步？哪一步最贵？

**为什么问**：性能优化 90% 的收益来自优化那 1~2 个最贵的步骤。不先定位"最贵的一步"，优化就是瞎改。

**关键结论（写一个文件 = 6 步）**：

```
① 客户端问 NameNode：该写到哪几台？        ← 很小的控制消息
② NameNode 只回地址（DN1/DN2/DN3）        ← 不碰数据
③ 客户端把数据发给 DN1
④ DN1 写自己磁盘 → 同时转发给 DN2 → DN2 同样转发给 DN3   ← 最贵：3 次磁盘写 + 2 次网络
⑤ 逐级回传"已收到"
⑥ 客户端通知 NameNode 完成，NameNode 记元数据
```

**关键结论（一个 MR 作业 = 8 步，最贵的是第 7 步 shuffle）**：shuffle 贵在三处——① 必须**等所有 map 完成**才能开始（木桶效应）；② 数据**先落盘再被拉走**；③ 纯搬运，没有计算产出。

> **推论：在小集群上，跑批的时间大头往往不是"算"，而是 shuffle + 写回。**

**怎么验证**：

```bash
# 看一个作业的时间花在哪几个阶段
/opt/hadoop/hadoop-3.3.6/bin/mapred job -status <application_id> | grep -E "map|reduce" | head -20

# 看 Hive 把一条 SQL 拆成了几个作业（本项目实测：1 天规模 1 个，全量 1063 万行 11 个）
journalctl -u hive-server2 --since "-2h" --no-pager | grep -E "Total jobs|Launching Job [0-9]+ out of"
```

### 问题 5：出错了谁发现？怎么补救？

**为什么问**：这是分布式系统与单机程序最大的区别。单机出错了直接崩；分布式必须靠**持续探测 + 主动剔除 + 重试**，而这些机制本身就会制造故障。

**关键结论（心跳与剔除）**：DataNode 每隔几秒向 NameNode 报一次心跳。NameNode 收不到就认为它可能有问题。

**但今天踩的是另一层**：错误发生在**写入管线的临时剔除**上——

```
could only be written to 0 of the 1 minReplication nodes.
There are 3 datanode(s) running and 3 node(s) are excluded in this operation.
```

翻译：**三个 DataNode 全部被踢出了这次写入，一个副本都没写成。** 注意原文写的是 `3 datanode(s) running`——**节点是活着的**，只是在这条写入管线上响应不过来，被逐个剔除了。

> **关键区分**：`running` 但 `excluded` —— 这是"忙不过来"，不是"宕机了"。这个区别决定了修复方向完全不同（前者调并发，后者查服务）。

**怎么验证**：

```bash
# 看节点是否活着、是否被标记为死节点
/opt/hadoop/hadoop-3.3.6/bin/hdfs dfsadmin -report | grep -E "Live datanodes|Dead datanodes|Last contact"

# 看是否真的健康（排除"服务活着但写不进去"的情况）
/opt/hadoop/hadoop-3.3.6/bin/hdfs dfs -touchz /tmp/health_check && echo "HDFS 可写" && /opt/hadoop/hadoop-3.3.6/bin/hdfs dfs -rm /tmp/health_check
```

### 问题 6：这个设计换来了什么？代价是什么？

**为什么问**：分布式系统里没有免费的午餐。每条"能力"都对应一个"代价"，能说清代价才叫真懂，也才知道什么场景下**不该**用它。

| 设计 | 换来了 | 代价 |
|---|---|---|
| 3 副本 | 坏一台不丢数据 | 写 1 份要付 3 倍的磁盘写入 + 2 倍网络传输；**且三台全在写入管线上，任一掉线就失败** |
| NameNode 不管数据 | 不被数据量压垮 | 元数据全在内存 → 海量小文件场景会内存爆炸 |
| map 输出落本地盘 | 省下 3 副本开销 | 那台机器一挂，这个 map 得重算 |
| YARN 容器化 | 资源隔离、可多租户 | 容器有固定配额（本项目 512MB），配额给少了会 OOM 被杀 |

**本项目真实的一次取舍**：为了让写入成功，把写入期副本数从 3 降到 **2**。
- 换来了：容忍一台机器掉线（3 副本落在 3 台机上，容错度其实是**零**）
- 代价是：写入窗口内只剩 2 份，此时再坏一台就丢数据
- **能接受的前提**：数据源在本机完整保留可重跑、写入窗口只有 8 分钟、跑完立刻恢复 3

> ⚠️ **换成"数据源已丢失、副本必须 3"的生产场景，这一条就不能这么用**，而应该改成"按日期分批写入"来降峰值。**同一个手法在不同前提下的对错完全不同**——这就是为什么要显式写出代价和前提。

### 问题 7：规模放大 100 倍，先崩的是哪一环？

**为什么问**：这是判断"这个设计能不能上生产"的最快办法。**一个在本项目 1063 万行下能跑通的东西，放到 10 亿行未必还能跑**——而先崩的通常是写盘或 shuffle，不是计算。

**关键结论（今天实测的规模效应）**：

| 数据规模 | Hive 计划的 MR 作业数 | 结果 |
|---|---|---|
| 1 天（34 万行） | **1 个** | 顺利通过 |
| 全量（1063 万行） | **2 个 → 执行中膨胀到 11 个** | 写入被彻底压垮，失败 |

**规模放大时最先崩的三个环节（按概率排序）**：
1. **写盘**——并发写入流 × 副本数，磁盘 IO 排队（今天就是这个）
2. **shuffle**——中间数据量超线性增长，网络和本地盘同时吃紧
3. **"知道"的那个角色**——元数据条目数暴涨，内存先满

**怎么验证**：

```bash
# 跑批期间盯这三个就够（跑完才看余量是没用的，中间数据的峰值才是真实瓶颈）
df -h /            # 磁盘：本项目实测中间数据一度把根分区从 8.9GB 压到 6.7GB，跑完自动回收
free -m            # 内存
iostat -x 1 5      # 磁盘 IO 饱和度（若已安装 sysstat）
```

## 三、完整示范：用这个框架拆解今天的真实故障

**故障**：1063 万行清洗落表，跑 21 分 39 秒后失败。

| 问题 | 当时的答案 | 证据 |
|---|---|---|
| **万能问法：算 / 写 / 搬？** | **写不过来** | `Cumulative CPU: 137.54 sec`（不累）但 `HDFS Write: 0`（写不出） |
| **1. 谁和谁说话？** | reducer → DataNode（数据流）；DataNode → DataNode（副本转发） | 报错里的 `_task_tmp.-ext-10000/dt=2019-10-22/_tmp.000000_3` 是写入管线上的临时文件 |
| **2. 数据在哪？** | 31 个动态分区，每个分区一个文件，写在 DataNode 本机磁盘 | 报错路径含 `dt=2019-10-22`，说明是按日期分区写 |
| **3. 谁"知道"谁"存"？** | NameNode 记目录（正常），DataNode 存数据（**响应不过来**） | `3 datanode(s) running` → 节点是活的，"知道"没坏 |
| **4. 分几步？哪步最贵？** | 8 步里死在第 8 步"写回 HDFS" | `Stage-Stage-1: Map: 6 Reduce: 6 ... FAIL` |
| **5. 谁发现、怎么补救？** | 客户端发现 DataNode 响应超时 → 逐个剔除；**三个都剔完 → 0 副本 → 判定失败** | `0 of the 1 minReplication nodes ... 3 node(s) are excluded` |
| **6. 换来什么、代价是什么？** | 3 副本换来容错，代价是**三台全在管线上，任一掉线即失败** | 本集群只有 3 台，3 副本的容错度实际为 0 |
| **7. 放大 100 倍先崩哪？** | 已经崩了——崩在写盘（并发写入流汇聚到宿主机同一块物理盘） | 6 reducer × 31 分区 × 3 副本 ≈ 186 条并发写入流 |

**按框架得出的结论**：不是算力问题、不是容量问题、不是代码问题，而是**并发写入形态**问题。
**修复方向因此唯一确定**：降低并发（排序后再写）、减少工人（reducer 3）、减少副本（2）、少起作业（关合并）。

**修复后实测**：失败（1299s）→ **成功（481s，快 63%）**，ORC 落盘 620MB / 31 分区，副本实测 2。

## 五、配套速查：同一台机器的四个视角

搞不清"逻辑角色"和"硬件"的关系时，记住它们是**同一台机器的四种看法**：

| 视角 | 内容 | 例子（本项目 lrh-1） |
|---|---|---|
| ④ 逻辑角色 | 文档/架构图上的名字 | NameNode、ResourceManager、HiveServer2、DataNode、NodeManager |
| ③ 真实进程 | 真正在跑的东西 | java 进程 ×6，各有 `-Xmx512m` 上限、各监听端口、各读写本机磁盘 |
| ② 操作系统 | 分配 CPU/内存、管文件、跑网络协议栈 | Ubuntu 24.04 + systemd |
| ① 硬件 | 宿主机的物理资源切出一块 | 2 vCPU / 7168MB 内存 / 30GB 磁盘 / 1 张虚拟网卡 |

**三句翻译**（把文档语言翻成物理语言）：

| 文档说 | 物理上是 |
|---|---|
| "NameNode 和 DataNode 通信" | 两个 JVM 通过 TCP 端口互发消息 |
| "DataNode 把数据写到磁盘" | 那个 JVM 调操作系统的 `write()`，落到本机磁盘 |
| "内存不足 / OOM" | 这个 JVM 要的堆内存超过了操作系统的余量 |

> **最后提醒一句**：三台虚拟机的「30GB 磁盘」其实是宿主机的三个普通文件，**所有写入最终排队到同一块物理盘上**。
> 这是本项目"3 台机器却只有 1 块盘的吞吐"的根本原因——**虚拟化会放大磁盘压力**，这也是很多"配置看起来够、跑起来就是卡"的隐藏原因。
