# 实验报告 02 · 根治 Hive 元数据库中文注释乱码

> **一句话结论**：查清「Hive 表/字段中文注释全变成 `???`」的根因是 **Hive 官方元数据库 schema 把注释列声明成了 `latin1`**，而 Hive 用 `utf8mb4` 连接写库，中文被 MySQL 静默替换成 `?`（0x3F）；改掉 12 个注释列的字符集后，**新建表中文注释直接正常，存量 103 条列注释 + 15 条表注释全部补回，零残留**。
>
> 实验日期：2026-09-27 · 环境：三节点 Hadoop 3.3.6 / Hive 3.1.3 / MySQL 8 / Ubuntu 24.04
> 执行方式：远程 SSH + 脚本（`fix_metastore_charset.sh` + `gen_comment_fix.py`）

## 二、背景：问题是什么

### 2.1 环境是什么样的（零基础版）

先解释三个名词：

| 名词 | 类比 |
|---|---|
| **Hive** | 一个"把 SQL 翻译成大数据作业"的翻译官。你写 `SELECT`，它去 HDFS 里捞数据 |
| **元数据库（Metastore）** | Hive 的**图书卡片目录**。书（数据文件）堆在 HDFS 里，但"哪本书叫什么、有几章、每章讲什么"记在目录里。Hive 用 MySQL 存这个目录 |
| **字符集（Charset）** | 一套"字符 ↔ 字节"的字典。`utf8mb4` 是能表示中文/emoji 的大字典；`latin1` 是只有 256 个格子的西文小字典 |

**关键机制**：当一段中文要写进一个 `latin1` 的格子时，MySQL 的动作是——

> 查小字典 → 找不到"中"这个字 → **不报错**，直接塞一个问号 `?` 进去。

这就是本实验的核心。注意最后半句：**它不报错**。所以你看到的现象是"库建好了、表能查、数据也对，只有注释是问号"。

### 2.2 症状 / 触发原因

**症状**：在 beeline 里执行 `DESC gmall.ads_dau`，注释列显示 `??SKU`、`????`。

**怎么发现的**：本次是装载真实数据集（REES46 电商行为数据）到 ODS 后，做常规校验时顺手看了一眼注释，发现是问号。

**不解决会有什么后果**：

1. 面试/答辩时打开表结构，满屏 `????`，直接暴露"环境没调干净"
2. 更麻烦的是**它是静默的**——如果没发现，后面新写的表会一直带着坏注释，越积越多
3. 项目根目录早有一份 `中文注释乱码排查报告.md`，但问题依然存在，说明**上次没查到真正的层面**

### 2.3 实验前的基线数据

先确认"到底是显示坏了还是存储坏了"。这一步决定后面所有排查方向：

```sql
-- 直接读 MySQL 里的真实字节
SELECT COLUMN_NAME, COMMENT, HEX(COMMENT) FROM COLUMNS_V2 WHERE ... ;
```

实测结果：

```
sku_id    ??SKU    HEX = 3F3F534B55
log_time  ????     HEX = 3F3F3F3F
order_id  ??ID     HEX = 3F3F4944
```

**读法**：`0x3F` 就是问号字符本身。如果是"终端显示不出来"，MySQL 里存的应该是正确的 UTF-8 字节（`E4...` 开头），只是显示时乱码。而这里**存的就已经是问号了**。

更关键的一行证据：

```
3F3F 534B55
└┬┘  └──┬─┘
两个问号  "SKU"（ASCII 原样保留）
```

**中文变问号、英文毫发无伤** —— 这是字符集转换"无法映射就替换"的标准指纹，直接锁定了问题性质。

全库统计（影响面）：

```
含问号的列注释: 103 条
含问号的表注释: 15 条
```

**结论：整个 gmall 数仓的中文注释全军覆没**，不是只有新表。

## 三、实验设计：每个猜测 → 对应行动 → 实测结果

**本章是核心。** 我把"中文为什么变成 `?`"拆成 5 个可能的嫌疑点，逐个用证据排除，最后定位到真正的那一个。

### 3.1 根因排查（5 个嫌疑）

| # | 假设（动手前的判断） | 对应行动 | 实测结果 | 判定 |
|---|---|---|---|---|
| H1 | 只是**终端显示**问题，库里存的其实是对的 | 查 MySQL 真实字节（`HEX()`） | 库里存的就是 `3F3F...`（问号本身），且中文全坏、ASCII 完好 | ❌ **判断错** |
| H2 | 是 **JVM 字符集**问题——systemd 启动的 Hive 进程没继承 `LANG`，JDK 8 会退化成 US-ASCII | 用 `jcmd <pid> VM.system_properties` 直接问运行中的 JVM；查 `/proc/<pid>/environ` | `file.encoding=UTF-8`、`sun.jnu.encoding=UTF-8`、`LANG=en_US.UTF-8` —— **全部正常** | ❌ **嫌疑排除** |
| H3 | 是 **JDBC 连接串**少配了 `characterEncoding` | 读 `hive-site.xml` 的 `javax.jdo.option.ConnectionURL` | 已配 `useUnicode=true&characterEncoding=UTF-8` | ❌ **嫌疑排除** |
| H4 | 是 **MySQL 服务端**字符集不是 utf8mb4 | `SHOW VARIABLES LIKE 'character_set%'` | `character_set_server / client / connection` **全为 utf8mb4** | ❌ **嫌疑排除** |
| H5 | 是**某一列本身**被定义成了 latin1 | 查 `information_schema.COLUMNS` 的 `CHARACTER_SET_NAME` | `COLUMNS_V2.COMMENT` = **latin1**；`TABLE_PARAMS.PARAM_VALUE` = **latin1** | ✅ **命中根因** |

### 3.2 方案设计验证（4 个假设）

| # | 假设 | 对应行动 | 实测结果 | 判定 |
|---|---|---|---|---|
| H6 | 把注释列改成 `utf8mb4` 后，中文就能正常写入 | 对 12 个注释列执行 `ALTER ... CHARACTER SET utf8mb4`；新建一张含中文注释的表验证 | 新建表的注释 HEX = `E4B8BBE994AEE6A087E8AF86`（真 UTF-8），存得进去 | ✅ **成立** |
| H7 | `ALTER TABLE ... ALTER COLUMN c COMMENT 'x'` 是 Hive 3.1.3 支持的语法 | 用它写重刷脚本并执行 | `ParseException: cannot recognize input near 'ALTER' 'COLUMN'` —— **不支持** | ❌ **判断错** |
| H8 | 索引列（`COLUMN_NAME`、`TBL_NAME`）也应一并转 utf8mb4 | 先测算索引字节数再决定 | `COLUMN_NAME varchar(767)` 转 utf8mb4 后单列 **3068 字节**，加 bigint 主键 **3076 > InnoDB 索引上限 3072**，会失败；且这些列实际只存 ASCII | ❌ **方案否决（正确决定）** |
| H9 | 只有新建的 `ods_event_log_di` 受影响 | 全库统计坏注释数量 | **103 列 + 15 表全部损坏**，是历史遗留，远超预期 | ❌ **判断错** |

### 3.3 数据修复验证（3 个假设）

| # | 假设 | 对应行动 | 实测结果 | 判定 |
|---|---|---|---|---|
| H10 | 中文可以直接塞进 `ssh` 命令行传给远端 | 在 ssh 参数里写含中文的 SQL 做验证查询 | **返回空**（参数被破坏，语句没执行成功）→ 改为 scp 传文件 | ❌ **判断错** |
| H11 | DDL 文件里的中文注释原文可直接用于重刷（结构与元数据库一致） | 写生成器，把 DDL 解析出的 103 个 (表,列) 与元数据库实际列做交叉校验 | 表注释 15/15、列注释 **103/103** 全部匹配，**零不匹配** | ✅ **成立** |
| H12 | 只改注释字段不会影响任何数据 | 对比修复前后的分区数与行数 | 31 分区 / 10,630,245 行，**与装载基线完全一致** | ✅ **成立** |

### 3.4 统计

> **12 个假设：4 个成立，8 个被证伪（其中 3 个是"嫌疑排除"，4 个是真实判断错误，1 个是方案否决）。**

**其中最该被记住的是 H1、H7、H9** —— 这三个都是"我以为我知道，其实我不知道"。

## 四、实验过程详录

### 4.1 前置安全核查

**动手前必须回答**：改元数据库的 schema，会不会把集群搞崩、把数据弄丢？

| 核查项 | 方式 | 结论 |
|---|---|---|
| 会不会影响 HDFS 数据？ | 元数据库只存"卡片目录"，数据文件在 HDFS | ✅ **完全不影响**，注释甚至不参与查询 |
| 会不会触发 Hive 的 schema 版本校验？ | Hive 只校验 `VERSION` 表的版本号，不校验列字符集 | ✅ 安全 |
| 改坏了能不能回去？ | 先整库 dump | ✅ 307 KB 备份已落盘 |
| 改的时候能有并发写吗？ | 先停 HiveServer2 / MetaStore | ✅ 无并发 |

### 4.2 步骤一：备份元数据库

改 schema 前**必须**有退路，这一步不能省：

```bash
sudo mysqldump --single-transaction --routines --events \
     --default-character-set=utf8mb4 hive > /opt/backup/$(date +%F)/hive_metastore_$(date +%H%M).sql
```

结果：`/opt/backup/2026-09-27/hive_metastore_1622.sql`，**307 KB**。

> `--single-transaction` 让备份在不锁表的情况下拿到一致性快照，避免影响正在跑的服务。

### 4.3 步骤二：把 12 个注释列迁移到 utf8mb4

**为什么只改注释列、不改索引列**（这是本步骤最关键的设计决策）：

| 列类型 | 改不改 | 原因 |
|---|---|---|
| `COMMENT`、`PARAM_VALUE`、`PKEY_COMMENT`、`DESC` | ✅ **改** | 承载中文，且不参与任何索引 |
| `COLUMN_NAME`、`TBL_NAME`、`DB_NAME` | ❌ **不改** | 参与索引。`varchar(767)` 转 utf8mb4 = 3068 字节，加 bigint 主键 3076 字节，**超过 InnoDB 3072 字节上限**；且这些列实际只存 ASCII |

执行结果：**12/12 全部 OK，失败项数 0**。

```
OK   COLUMNS_V2         COMMENT        varchar(256)
OK   TABLE_PARAMS       PARAM_VALUE    mediumtext
OK   PARTITION_KEYS     PKEY_COMMENT   varchar(4000)
OK   DBS                DESC           varchar(4000)
... 共 12 个
```

校验：

```
COLUMNS_V2.COMMENT        → utf8mb4   ✅
TABLE_PARAMS.PARAM_VALUE  → utf8mb4   ✅
COLUMNS_V2.COLUMN_NAME    → latin1    ✅（刻意保留）
TBLS.TBL_NAME             → latin1    ✅（刻意保留）
```

> **为什么用 `utf8mb4_bin` 而不是默认的 `utf8mb4_0900_ai_ci`**：注释是给人看的、需要精确等值比较，用二进制排序规则避免大小写/重音被"智能合并"，行为最可预测。

### 4.4 步骤三：验证根因是否真的消除（关键分水岭）

**不能只验证存量修好，还要验证"以后新写的也对"**，否则等于没修根因。

建一张测试表（注意：**Hive 表名不能以下划线开头**，这是上次实验失败的坑）：

```sql
CREATE TABLE gmall.zz_enc_probe (
  id   int     COMMENT '主键标识',
  name string  COMMENT '名称字段'
) COMMENT '中文注释验证表';
```

实测存储字节：

```
id         主键标识      HEX = E4B8BBE994AEE6A087E8AF86
name       名称字段      HEX = E5908DE7A7B0E5AD97E6AEB5
表注释     中文注释验证表  HEX = E4B8ADE69687E6B3A8E9878AE9AA8CE8AF81E8A1A8
```

`E4B8BB` 是"主"的 UTF-8 编码 → **根因已消除，新建表直接正常**。测试表随后清理。

### 4.5 步骤四：生成存量注释修复脚本

**为什么不重跑建表 DDL**：`ods_event_log_ddl.sql` 里有 `DROP TABLE`，重跑会连带丢掉已装载的 31 个分区、1063 万行数据。必须用 `ALTER` / `UPDATE` 只改元数据。

**为什么弃用 `CHANGE COLUMN`，改用直接 `UPDATE` 注释字段**：

| 方案 | 致命问题 |
|---|---|
| `ALTER TABLE ... CHANGE COLUMN` | 必须**重述类型**。一旦写的类型与当前元数据不一致，会**静默改掉表结构**（比如把 `string` 改成 `decimal`），风险不可接受 |
| 直接 `UPDATE COLUMNS_V2 SET COMMENT=...` | 只碰注释字段，**结构零风险**；且能一次覆盖库注释/表注释/列注释/分区列注释 |

生成的脚本由 `gen_comment_fix.py` 产出，它的安全设计是**交叉校验**：

- 注释**文本**来自 DDL（权威源头）
- "这张表有没有这一列"**以元数据库为准**
- 任何一边对不上 → **只报告，不硬写**

校验输出：

```
表注释  : 写入 15 条 / 缺失 0 条
列注释  : 写入 103 条 / 缺失 0 条
分区注释: 写入 2 条 / 缺失 0 条
需要注意的 1 处：
  - DDL 里没有表 tmp_order_user_cnt，跳过
```

**103 条零不匹配** —— 这个数字本身就是一份证据：说明 DDL 与线上元数据库结构完全一致。

### 4.6 步骤五：应用并重启

```bash
sudo mysql --default-character-set=utf8mb4 hive < fix_comments.sql
sudo systemctl restart hive-metastore && sudo systemctl restart hive-server2
```

**为什么要重启 Hive**：排除"元数据缓存"这个变量。不重启的话，即使数据对了，也无法排除"看到的是缓存里的旧值"。重启后读到的必然是磁盘上的真值——**这样验证才算闭环**。

> `--default-character-set=utf8mb4` 同样不能省：MySQL 客户端会按系统 locale 猜字符集，写错的话 SQL 文件里的中文在**客户端侧**就被破坏了。

## 六、复盘：被证伪的假设（**必写，最有价值**）

### ❌ H1：「只是终端显示问题」

- **我原本的判断**：注释是问号，大概是 beeline 或终端编码不对，数据本身应该没事。
- **实测结果**：MySQL 里存的就是 `3F3F...`——`0x3F` **就是问号字符本身**。
- **为什么会错**：我把"乱码"当成了一个笼统的现象，没意识到它其实是**两类完全不同的问题**：
  - **显示型乱码**：库里字节是对的，只是终端用错了字典去"翻译"
  - **存储型乱码**：字典在**写入时**就用错了，原始信息**当场丢失**

  **区分方法极其简单**：看十六进制。显示型乱码的十六进制是合法的 UTF-8（`E4B8BB...`）；存储型乱码的十六进制会是 `3F`（真问号）或者一串"看似合法但其实毫无意义"的字节。

  **修正后的认知**：遇到乱码，**第一步不是猜编码，而是取十六进制**。这一步能省掉后面所有无效排查。事实上，正是这一条证据让我立刻把方向从"环境变量"转到了"列定义"。

### ❌ H2：「systemd 没传 `LANG`，导致 JDK 的 `file.encoding` 退化成 US-ASCII」

- **我原本的判断**：这是 Linux 上 JVM 中文乱码的经典成因，而且 systemd 单元里确实**没有** `Environment=LANG=...`，看起来很像。
- **实测结果**：`jcmd <pid> VM.system_properties` 显示 `file.encoding=UTF-8`、`sun.jnu.encoding=UTF-8`，`/proc/<pid>/environ` 里 `LANG=en_US.UTF-8`。
- **为什么会错**：我只看了"systemd 单元里没写 LANG"，就推断"进程没有 LANG"。但 systemd 会从**系统默认 locale**（`/etc/default/locale`、`/etc/locale.conf`）继承，不是只有显式写了才有。

  **修正后的认知**：判断进程环境**必须读进程本身**（`/proc/<pid>/environ`、`jcmd`），不能从配置文件"推断"。配置文件里"没写"，不等于"没有"。

### ❌ H3 / H4：JDBC 连接串、MySQL 服务端字符集

- **我原本的判断**：这两个是字符集问题的常见来源。
- **实测结果**：JDBC 已配 `characterEncoding=UTF-8`；MySQL 服务端 `character_set_server/client/connection` 全是 `utf8mb4`。
- **价值**：这两条虽然被排除，但**排除本身就缩小了范围**。当"连接侧"和"服务端"都干净时，剩下的只能是**列定义**——这是一次典型的排除法推进。

### ❌ H7：`ALTER TABLE ... ALTER COLUMN c COMMENT 'x'` 是 Hive 3.1.3 支持的语法

- **我原本的判断**：记得 Hive 支持用 `ALTER COLUMN` 只改注释、不必重述类型，是最安全的写法，还专门在脚本注释里写了"最安全"。
- **实测结果**：`ParseException: cannot recognize input near 'ALTER' 'COLUMN' 'event_time'`——**Hive 3.1.3 不认这个语法**。
- **为什么会错**：我把**更高版本才加入的语法**当成了 3.1 的既有能力。类似 `ALTER COLUMN ... COMMENT` 这种"顺手就有"的语法糖，很容易在记忆里被"版本模糊"。

  **修正后的认知**：**能不能用某条 DDL，必须在目标版本上真跑一次**，不能凭印象。脚本里的"最安全"三个字，在没验证之前是不成立的自我安慰。

### ❌ H9：「只有新建的 `ods_event_log_di` 受影响」

- **我原本的判断**：注释坏掉是本次建表引入的，范围就是这一张表。
- **实测结果**：全库 **103 条列注释 + 15 条表注释**全是坏的；`ads_dau` 这种早期建的表同样如此。
- **为什么会错**：我默认"问题 = 本次操作引入的"。但字符集转换问题是**环境属性**，不是**操作属性**——只要元数据库是那个 schema，**从建库第一天起写中文就是坏的**。

  **修正后的认知**：遇到问题先问一句"**这是这次引入的，还是本来就有的？**"。判断方法：查一个**与本次操作无关的早期对象**。这次正是查了 `ads_dau` 才确认是历史遗留。

  **附带价值**：项目根目录的 `中文注释乱码排查报告.md` 之所以没解决问题，很可能就是这个原因——**当时只盯着当下那张表，没做全库统计**。

### ❌ H10：中文可以直接塞进 `ssh` 命令行

- **我原本的判断**：`ssh host "mysql -e \"SELECT '中文'\""` 这样传应该没问题。
- **实测结果**：**查询返回空**，语句根本没成功执行。
- **为什么会错**：Git Bash 在 Windows 下，**命令行参数会经过本地代码页编码**再交给 `ssh.exe`，非 ASCII 字符在这一步被破坏。注意：**输出方向不受影响**（远端打印的中文能正常显示），只有**输入方向**有问题——这一点很容易让人误判为"远端环境有毛病"。

  **修正后的认知**：往远端传含非 ASCII 的内容，**一律走文件通道**（heredoc `cat > file`、`scp`），不要走命令行参数。本次所有含中文的 SQL 后来都改成"先写远端文件、再执行"。

### ❌ H8：索引列也应一并转 utf8mb4（方案否决）

- **我原本的倾向**：既然要根治，干脆把所有 latin1 列都转了。
- **测算结果**：`COLUMNS_V2.COLUMN_NAME` 是 `varchar(767)`，转 utf8mb4 后单列占 `767×4 = 3068` 字节，加上主键里的 `bigint`（8 字节）共 **3076 字节**，**超过 InnoDB 的 3072 字节索引上限** → `ALTER` 会直接失败。
- **为什么算"否决正确"**：这是我**先测算、再决定**，而不是先改再踩错。而且这些列实际只存 ASCII（列名、表名都是英文），转过去没有任何收益。

  **修正后的认知**：字符集迁移要考虑**索引键长度上限**。`varchar(n)` 的字节数 = `n × 单字符最大字节数`（latin1 是 1、utf8mb3 是 3、utf8mb4 是 4）。这个换算在改任何索引列之前必须先做。

## 八、面试官可能会追问的问题

**Q1：你怎么确定问题在存储层而不是显示层？**

A：看十六进制。`??SKU` 的 HEX 是 `3F3F534B55`——`3F` 是问号字符本身。如果是显示问题，库里存的应该是合法的 UTF-8 字节（`E4...` 开头），只是终端翻译错了。而且注意 `534B55` 正是 `SKU` 的 ASCII，**中文变问号、英文完好**，这是字符集转换"无法映射就替换"的标准指纹。所以信息在写入时就丢了。

**Q2：为什么 MySQL 不报错，就这么悄悄写坏了？**

A：这是 MySQL 的默认行为——字符集转换遇到无法映射的字符时用替换字符（`?`）代替，而不是抛异常。它是"尽力而为"的设计，代价是**静默数据损失**。如果要让它报错，得开 `STRICT` 模式相关的告警，或者应用层自己校验。这也解释了为什么这个问题能潜伏这么久——没有任何一行错误日志。

**Q3：为什么改的是元数据库的列，而不是改连接串去绕开？**

A：绕开的路子确实存在（把 JDBC 连接字符集改成 `latin1`，让字节原样穿透），但那是让**上下游都假装是 latin1**。后果是：任何一次 Hive 版本升级、任何一次别人用别的工具连这个库，都会重新踩坑，而且数据是以"非预期的编码"存着的，读出来还得再转换。改列字符集是**把数据本身修正到正确的表示**，一次到位。

**Q4：为什么不用 `ALTER TABLE ... CHANGE COLUMN` 重刷注释，而是直接 UPDATE？**

A：两个原因。第一，`CHANGE COLUMN` **必须重述类型**，一旦我写的类型和线上元数据不一致（比如 DDL 写 `string`、实际是 `varchar`），它会**静默把表结构改掉**——这是不可接受的风险。第二，Hive 3.1.3 根本不支持 `ALTER COLUMN ... COMMENT` 这个更安全的语法（我实测被 `ParseException` 拒了），而改分区列注释也没有对应 DDL。直接 UPDATE 注释字段则**只碰注释、零结构风险**，还能一次覆盖库/表/列/分区列四种注释。

**Q5：改元数据库的字段，就不怕 Hive 和它不一致吗？**

A：注释是纯元数据，不参与任何查询逻辑、不参与各种统计信息，没有一致性约束。而且我做了三件事保证闭环：一是改完**重启 Hive**，排除缓存；二是用 **beeline 亲自 `DESC` 读回**，证明 Hive 侧看到的就是中文（不是只看 MySQL）；三是**新建一张表验证未来**。至于表结构本身——我一个字都没动，只改了 `COMMENT` / `PARAM_VALUE` / `PKEY_COMMENT` / `DESC` 这四个注释字段。

**Q6：103 条列注释，你怎么保证补回去的内容是对的，而不是又写错一批？**

A：用**交叉校验**。注释文本来自 DDL 文件（这是权威源头），但"这张表到底有没有这一列"**以元数据库为准**——两边对上才生成 SQL，对不上只报告不硬写。最终 103 条**零不匹配**、15 张表**零缺失**。这个数字本身也是一份证据：说明线上元数据库和 DDL 文件的结构是完全一致的。

**Q7：这个实验里你判断错了多少次？**

A：**12 个假设，8 个被证伪**。其中有 3 个是嫌疑排除（JVM 编码、JDBC 串、MySQL 服务端），属于排查的正常消耗；但有 4 个是真实的判断错误——我误判了"显示问题"、误以为"只有一个表受影响"、凭记忆用了 Hive 3.1 不支持的语法、还假设中文能直接走 ssh 命令行。最有价值的一条是：我一开始把"systemd 单元里没写 LANG"等同于"进程没有 LANG"，但 systemd 会从系统 locale 继承，实际读写进程环境**必须直接读 `/proc/<pid>/environ`**。

**Q8：如果让你重做一遍，你会怎么做更快？**

A：第一步就取十六进制。这一步直接区分了"显示型乱码"和"存储型乱码"，能在 5 分钟内把排查范围从"整个技术栈"缩小到"写入链路"。我就是因为**先猜了编码、后取证**，才在 `file.encoding`、JDBC 串、MySQL 变量上多花了三轮。另外，取完证后应该立刻做**全库统计**——如果早发现是 103 条而不是 1 条，就不会有"只修新表"的误判。

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| **Hive 元数据库（Metastore）** | Hive 的"图书卡片目录"，用 MySQL 存着"有哪些库/表/列、叫什么、什么类型、注释是什么"。数据本身在 HDFS，目录在 MySQL |
| **字符集（Charset）** | 一套"字符 ↔ 字节"的字典。`latin1` 是只有 256 格子的西文小字典，`utf8mb4` 是能装下中文和 emoji 的大字典 |
| **字符集转换** | 把用 A 字典表示的文字，改写成用 B 字典表示。**B 字典装不下的字符会被替换成 `?`，且不报错** |
| **`0x3F`** | `?` 这个字符的十六进制编码。看到它就说明"转换已经发生过、原始信息已丢失" |
| **`HEX()`** | MySQL 函数，把内容转成十六进制。**判断乱码类型的决定性工具**——比肉眼看"乱码长什么样"可靠得多 |
| **`latin1` vs `utf8mb4`** | latin1 每字符固定 1 字节（只能表示 256 个西文字符）；utf8mb4 每字符最多 4 字节（能表示几乎所有文字） |
| **`file.encoding` / `sun.jnu.encoding`** | JVM 启动时确定的"默认字符集"。它错了，程序读写文本就会乱码 |
| **systemd 的 `Environment=`** | 给服务进程设环境变量。**没写不代表没有**——还会从系统默认 locale 继承 |
| **InnoDB 3072 字节索引上限** | MySQL 单列索引键最多 3072 字节。`varchar(n)` 转 utf8mb4 后占 `n×4` 字节，n 大了就超限 |
| **`mysqldump --single-transaction`** | 在不锁表的前提下拿到一致性备份快照 |
| **Hive 保留字** | 如 `rows`、`order` 等，用作别名会让语句解析失败（且可能静默无输出） |
| **幂等脚本** | 重复执行结果相同的脚本。本实验的 `fix_metastore_charset.sh` 和生成的 SQL 都是幂等的 |
