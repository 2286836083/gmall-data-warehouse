# 实验报告 07 · 项目改名与迁移（OneDrive → D 盘）

> **一句话结论**：把项目从 `D:\OneDrive\桌面\大数据开发\` 改名为 `数据开发` 并迁到 `D:\数据开发\`，同时把配套的密钥目录 `D:\大数据开发\` 改名为 `D:\数据开发环境\`——**193 个文件逐字节校验一致、SSH 用新路径实测连通**。但过程中**我的 3 个判断被证伪**：路径引用数量低估了 3 倍（21→72 处）、正则匹配在多层转义下完全失效、以及**复制时项目根本不是静止的**。
>
> 实验日期：2026-09-29 · 环境：Windows 11 + Git Bash / Python 3.13 / gmall 三节点集群（运行中）
> 执行方式：`cp` 复制 + `mv` 改名 + Python 脚本批量替换 + SSH 实测

## 二、背景：为什么要迁移

### 2.1 名词先解释（零基础版）

| 名词 | 类比 | 实际是什么 |
|---|---|---|
| **OneDrive** | 一个自动帮你备份到云端的文件夹 | 放在它里面的东西会被持续同步到微软服务器 |
| **SSH 密钥** | 一把家门钥匙（文件形式） | 一个 399 字节的私钥文件，集群免密登录靠它 |
| **硬编码路径** | 写在便签上的地址 | 写在脚本/文档里的具体文件路径，位置一变就失效 |

### 2.2 症状 / 触发原因

项目一直放在 `D:\OneDrive\桌面\大数据开发\`。两个问题：

1. **OneDrive 会持续同步整个项目**——包括里面可能变大的数据产物，占用带宽、偶尔造成文件锁冲突
2. **项目名与实际不符**——用户把它定位成「数据开发」（含数仓、SQL、调度、可视化的完整链路），而不只是「大数据开发」

**不迁移的后果**：不是"报错"，而是**长期的低效**——每次改文件都可能触发同步，而且名字不贴合定位。

### 2.3 迁移前的基线

| 项 | 值 |
|---|---|
| 项目大小 | **3.2 MB**（193 文件 / 17 目录） |
| 最大子目录 | `项目产出/` 1.5 M |
| 记忆文件 | `.workbuddy/memory/` 4 个（`MEMORY.md` + 3 份日志） |
| 配套目录 | `D:\大数据开发\VMware\`（**54 文件**：SSH 密钥、13 个运维脚本、ISO 目录） |
| 硬编码引用（初次粗扫） | 21 处 |

## 四、实验过程详录

### 4.1 前置安全核查

**动手前必须回答：这个操作会不会误伤？**

| 核查项 | 结论 |
|---|---|
| 会不会误删数据？ | **不会**——用户选择「先复制、原目录暂留」，原位置是天然回滚点 |
| 有没有进程占用旧目录？ | ⚠️ **有**——见 4.2，这个差点被漏掉 |
| 目标路径会不会冲突？ | `D:\数据开发\` 不存在，可直达 ✅ |
| 改密钥目录会不会锁死自己？ | 会——所以**必须最后改名，且改完立刻用新路径验证** |
| 集群要不要停？ | 不用——迁移是纯文件操作，与集群无关（但需要集群在线才能做 SSH 验收） |

### 4.2 执行顺序（四步，顺序有讲究）

```
① 复制项目  →  ② 逐字节校验  →  ③ 改名密钥目录  →  ④ 替换引用  →  ⑤ SSH 验收
    (无风险)      (确认无损)        (此刻旧路径失效)    (修复影响)     (证明可用)
```

**为什么密钥改名必须排在验证之前、引用替换之后**：

密钥目录是**唯一一个"改名即失效"的东西**——15 处以上引用直接指向它（含进度看板脚本）。所以：
- 排在替换引用**之前**：替换时新路径已经真实存在，替换后立刻可用
- 排在 SSH 验收**之前**：验收要用的就是新路径，这本身就是最好的验证

### 4.3 复制与逐字节校验

**做了什么**：`cp -r` 复制整个项目目录。

**观察到什么**：文件数 193 = 193 ✅，但 `du` 显示大小差 20 KB（3178 vs 3158 KB）。

**为什么不放过这 20 KB**：`du` 是**块级**统计（受文件系统簇大小、稀疏文件影响），不等于内容大小。所以改用**逐文件 MD5**：

```
源 193 个文件 / 目标 193 个文件
!! 内容不一致 1 个: 项目产出\进度看板\progress.json
   源=759e9b6a58 (2219 字节)  目标=f9953fff53 (2219 字节)

按文件内容累加的真实字节数: 源 2778724 / 目标 2778724  一致
```

**结论**：没有文件丢失或损坏；唯一的差异是一个**运行时生成的数据文件**，见 H9。

### 4.4 改名密钥目录

**做了什么**：`mv D:\大数据开发 D:\数据开发环境`。

**观察到什么**：54 个文件全部保留，`cluster_ed25519` 私钥与公钥都在，权限位未变。

> 💡 顺带发现：密钥目录里的 13 个运维脚本**没有任何一处硬编码「大数据开发」**——所以改名不会影响脚本内容。**动手前先查这个，比改完再发现安全得多。**

### 4.5 批量替换引用（72 处）

替换规则分五类（**用纯字符串替换，不用正则**——原因见第六章 H7）：

| 规则 | 查找 | 替换为 | 处数 |
|---|---|---|---|
| A 密钥目录 | `D:\大数据开发\` | `D:\数据开发环境\` | 22 |
| B1 项目路径（反斜杠） | `[dD]:\OneDrive\桌面\大数据开发` | `D:\数据开发` | 23 |
| B2 项目路径（正斜杠） | `[dD]:/OneDrive/桌面/大数据开发` | `D:/数据开发` | 4 |
| B3 项目路径（WSL） | `/mnt/d/OneDrive/桌面/大数据开发` | `/mnt/d/数据开发` | 23 |
| **合计** | | | **72** |

**关键技术处理**：用**二进制读写**（`rb` / `wb`）而不是文本模式——因为文本模式会做换行符转换，可能把 CRLF 文件整体改写（导致 diff 全红）。

### 4.6 端到端验证（★ 不能只看"命令没报错"）

| 验证项 | 命令/方法 | 实测 |
|---|---|---|
| **正向**：新路径能用 | `ssh -i "D:\数据开发环境\VMware\sshkeys\cluster_ed25519" lrh@192.168.87.131` | ✅ 返回 `lrh-1` 与时间 |
| **反向**：旧路径确实失效 | 检查旧目录是否存在 | ✅ 已不存在（证明改名真实生效） |
| 关键文件路径已更新 | 6 个文件的字符串检查 | ✅ 6/6 |
| 换行符未被破坏 | 统计 `\r\n` | ✅ 保持 LF |
| 中文未被破坏 | 统计 U+FFFD | ✅ 0 个 |
| 文件总数 | 递归计数 | ✅ 193 |
| 脚本语法 | Python `compile()` | ✅ `serve.py` 正常 |

> **"正向 + 反向"两条一起验，才说明改名真的生效了。** 只证明"新路径能用"是不够的——如果旧路径也还能用，说明你根本没改成功。

## 六、复盘：被证伪的假设（**本章最有价值**）

### ❌ H6：硬编码路径大约 21 处

**我原本的判断**：用 `Grep` 粗扫了一遍，看到 21 处，就以为了解了全部。

**实测结果**：精确扫描（含正斜杠、WSL 路径、小写盘符等变体）得到 **72 处 / 31 个文件**——**低估了 3.4 倍**。

**为什么会错**：

我第一次搜的是**一种写法**：`D:\大数据开发`。但同一个路径在项目里有 **5 种写法**：

```
D:\大数据开发\              ← 大写盘符 + 反斜杠
d:\OneDrive\桌面\大数据开发  ← 小写盘符
D:/OneDrive/桌面/大数据开发  ← 正斜杠
/mnt/d/OneDrive/桌面/大数据开发  ← WSL 挂载路径
D:\...\大数据开发\           ← 省略中间层
```

**类比**：就像统计"有多少人姓张"——你只搜了"张"，漏掉了"張"、"zhang"、"Zhang"，还有写成"弓长"的。

**修正后的认知**：

> **统计"某个东西有多少"时，先枚举它所有可能的写法，再统计。**
> 只搜一种写法得到的数字**不是"下限"，而是"错的"**——因为它会让人以为已经掌握全貌。
>
> 这与此前总结的「只看状态标志会被骗」是同一类：**用一个不完备的口径去测量，得到的不是近似值，是误导。**

### ❌ H7：用 `re.compile` 能可靠匹配路径串

**我原本的判断**：路径里有反斜杠，用正则 `r"D:\\大数据开发\\"` 应该能匹配。

**实测结果**：**命中 0 处**——而那个文件里明明写着 `D:\大数据开发\VMware\...`。

**为什么会错**：这条命令经历了 **JSON → Bash → Python 三层**，每一层都会对反斜杠做一次转义解释：

```
我以为写的是:   r"D:\\大数据开发\\"        （正则里 \\ = 一个反斜杠）
JSON 解析后:    r"D:\大数据开发\"           （\\ → \，且原始字符串不能以奇数反斜杠结尾）
```

实际传给 Python 的和我想的**完全不是一回事**。

**定位过程**（这一步值得记）：

```bash
# 用 od -c 看文件里的真实字节，确认文件内容没问题
grep -o "D:.\{0,4\}大数据开发" serve.py | od -c
# 输出: D  :  \ 345 244 247 ...   ← 单个反斜杠 (0x5C)，文件是对的
```

**排除法**：确认文件对 → 那问题在正则/转义 → 重新设计。

**修正后的认知**：

> **多层嵌套传递时，不要用正则表示路径。用 `chr(92)` 拼字符串 + `str.replace`，彻底绕开转义。**
>
> ```python
> B = chr(92)            # 一个反斜杠，谁都转义不了它
> old = "D:" + B + "大数据开发" + B
> text.replace(old, new)  # 纯字符串替换，零转义风险
> ```
>
> **通用原则：转义层数越多，越要选"不需要转义"的表达方式。**

### ❌ H8：可以用命令行参数调 Python 检查中文路径下的脚本

**我原本的判断**：`python -m py_compile "D:\数据开发\项目产出\进度看板\serve.py"` 应该能检查语法。

**实测结果**：

```
python.exe: can't open file 'D:\数据开发\项目产出\进度看板\serve.py':
[Errno 2] No such file or directory
```

**文件明明存在。**

**为什么会错**：这是 Git Bash → Windows 原生程序的**参数编码问题**。中文路径作为命令行参数传递时，会被本地代码页破坏，Windows 程序收到的是一个**乱码路径**——所以它说"文件不存在"。

**这和项目里既有的一条坑完全同源**：

> 既有记忆：「**中文不要塞进 `ssh` 命令行**（Git Bash 本地代码页会破坏参数 → 静默返回空）。**只有输入方向坏、输出正常**，极易误判为远端故障。」

这次是同一类错误换了个对象：**输入方向（命令行参数）坏掉，而我误以为是文件问题。**

**修正后的认知**：

> **凡是中文路径，不要通过命令行参数传给 Windows 程序。**
> 改成：把逻辑写进脚本内部，用 `os.path.exists()` + `compile()` 检查。
>
> **更一般的判断**：报错说"文件不存在"时，先分清是**文件真不在**，还是**你给它的路径在传递中坏了**。
> 用 `python -c "import os; print(os.path.exists(...))"`（在脚本内部构造路径）就能区分。

### ❌ H9：复制时项目内容是静止的

**我原本的判断**：项目就是一堆文档，复制期间不会变，所以 MD5 应该全一致。

**实测结果**：

```
!! 内容不一致 1 个: 项目产出\进度看板\progress.json
```

**为什么会错**：**有一个进度看板进程还活着**（监听 8765 端口），它每 5 秒 SSH 拉一次集群状态并**改写 `progress.json`**。复制进行到一半时，它刚好写了一次。

**这是个隐蔽的坑**：`pgrep -f serve.py` 查不到它（Git Bash 的 `pgrep` 看不全 Windows 原生进程），只有 `netstat -ano | grep :8765` 才暴露。

**怎么发现的**：正是因为坚持了"逐文件 MD5 校验"——如果只看 `du` 那 20KB 差异，很容易归结为"文件系统统计误差"就放过去了。

**修正后的认知**：

> **任何"复制/快照"类操作，动手前必须先确认没有进程在写目标目录。**
> 判断有没有写：不看进程名（可能查不到），**看端口、看文件修改时间**。
>
> 反过来，这次也证明了一件事：**逐字节校验的价值不在于"确认成功"，而在于"能不能发现异常"**。
> 如果只比文件数和大小，这个"有进程在写"的事实就会被 20KB 的统计误差掩盖过去。

### 📌 三个证伪的共同点

| 错误 | 类型 | 一句话 |
|---|---|---|
| H6 低估 3 倍 | **口径不完备** | 只搜一种写法，得到的不是近似值，是错值 |
| H7 正则失效 | **转义层数过多** | 多层嵌套时，选不需要转义的表达方式 |
| H8 路径传参失败 | **输入方向坏** | 报"文件不存在"时，先分清是文件还是路径坏了 |

## 八、面试官可能会追问的问题

**Q1：迁移一个项目目录，你觉得最难的是什么？**

**A**：不是移动本身，是**找出所有引用了旧路径的地方**。这次精确统计是 **72 处 / 31 个文件**，而我最开始粗扫只找到 21 处。**漏掉的会以"某天突然跑不通"的形式暴露**，而且很难联想到是几天前改的名字。

**Q2：怎么保证复制没丢东西？**

**A**：不看文件数和大小——`du` 是块级统计，本次就差了 20KB。用**逐文件 MD5**：`源 193 个 / 目标 193 个，字节数 2,778,724 完全一致`。而且 MD5 还帮我发现了一个额外事实：有进程在复制期间改写文件。

**Q3：为什么要"先复制、不直接移动"？**

**A**：为了留回滚点。复制后原目录原封不动，万一新位置有问题，改个名字就能回去。这次也确实用上了——H7/H8 两个失败都是靠"旧位置还在"才能安全地反复重试。

**Q4：改名过程中最容易把自己锁死的是什么？**

**A**：**SSH 密钥目录**。它是唯一一个"改名即失效"的东西，而所有集群操作都依赖它。所以顺序必须是：先复制项目 → 校验 → **再改名密钥** → 立刻替换引用 → **最后用新路径实测 SSH**。如果一上来就改密钥目录，我连验收自己都做不了。

**Q5：批量替换路径，怎么防止"改多"？**

**A**：每一处保留都必须能说出理由。本次替换后还剩 4 处「大数据开发」，全部有明确理由：2 处是知识库里**真实存在的文件名**（改了会指向不存在的文件）、1 处是**行业岗位名**、1 处是文件名本身。**批量替换最大的风险不是漏改，是改多。**

**Q6：你这次最大的失误是什么？**

**A**：**H6——我把"搜到 21 处"当成了"一共 21 处"。** 同一个路径在项目里有 5 种写法（大写小写盘符、反斜杠正斜杠、WSL 挂载路径、省略写法），我只搜了一种。只搜一种写法得到的数字**不是下限，是错的**——因为它会让人以为已经掌握全貌，从而跳过进一步检查。

**Q7：为什么不用正则做替换？**

**A**：因为这条命令要经过 JSON → Bash → Python 三层，**每层都会解释一次反斜杠**。我写的 `r"D:\\大数据开发\\"` 到 Python 手里已经不是那个东西了，结果是命中 0 处。定位方法是 `od -c` 看文件里的真实字节，先确认文件没错，再重新设计。最后改成 `chr(92)` 拼字符串 + `str.replace`，零转义风险。

**Q8：迁移后怎么验收？**

**A**：**正向 + 反向两条一起验**。正向：用新密钥路径实测 SSH，能返回主机名和时间。反向：确认旧路径**已经不在了**。只验正向是不够的——如果旧路径也能用，说明根本没改成功。

## 九、风险控制与回滚

| 风险 | 控制手段 |
|---|---|
| 复制不完整 | 逐文件 MD5 校验（不看 `du`） |
| 改密钥目录后锁死自己 | 顺序：先复制 → 再改名 → 立刻替换引用 → 最后 SSH 验收 |
| 批量替换误伤内容 | 纯字符串替换（非正则）；保留项逐一说明理由 |
| 换行符/编码被改写 | 二进制读写（`rb`/`wb`），不用文本模式 |
| 有进程在写目标目录 | 动手前用 `netstat -ano` 查端口占用（`pgrep` 查不到 Windows 原生进程） |

**回滚命令**（可直接复制执行）：

```bash
# ── 场景 A：只想把项目移回旧位置 ──
# 1) 先确认新位置的东西没用了（或先备份）
# 2) 删除新位置
rm -rf "/d/数据开发"                     # ⚠️ 确认无误再执行
# 3) 旧位置一直在，无需恢复 —— 直接继续用 D:\OneDrive\桌面\大数据开发\

# ── 场景 B：把密钥目录也改回去 ──
mv "/d/数据开发环境" "/d/大数据开发"
# 然后把项目内所有 D:\数据开发环境\ 改回 D:\大数据开发\（72 处里的 22 处）

# ── 场景 C：只想撤销"引用替换"，不影响目录结构 ──
# 从旧位置重新复制一份即可（旧位置是替换前的原始版本）：
rm -rf "/d/数据开发"
cp -r "/d/OneDrive/桌面/大数据开发" "/d/数据开发"

# ── 场景 D：确认一切正常后，清掉旧位置释放空间 ──
# ⚠️ 执行前请再次确认新位置可用（SSH 能连、记忆能读、看板能起）
rm -rf "/d/OneDrive/桌面/大数据开发"      # 3.2 MB
```

> ⚠️ **本报告不推荐立即执行场景 D**。用户明确选择了"先保留"，建议至少用几天、确认新位置读写正常后再删。

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| **OneDrive** | 自动同步到云端的文件夹；移出后不再云备份 |
| **硬编码路径** | 写在脚本/文档里的具体地址，位置一变就失效 |
| **MD5** | 文件内容的"指纹"；内容一样指纹就一样，用来验证复制无损 |
| **`du`** | 统计磁盘占用（**块级**，受簇大小影响，不等于内容大小） |
| **CRLF / LF** | Windows / Unix 的两种换行符；文本模式读写会转换，二进制不会 |
| **U+FFFD** | Unicode 的"替换字符"，出现它说明编码被破坏过 |
| **转义（escaping）** | 用反斜杠表示特殊字符；层数越多越容易出错 |
| **Git Bash 参数编码** | 中文作为命令行参数传给 Windows 程序时会被代码页破坏 |
| **回滚点** | 出问题时能退回的那个状态（本次是未删除的旧目录） |
