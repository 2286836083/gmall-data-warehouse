# 实验报告 01 · 三节点大数据集群内存调优

> **一句话结论**：在**不增加任何硬件**的前提下，让集群可用内存从 601MB 提升到 1.0–1.25GB（单节点 1.9GB→6.0GB 总量口径下相当于少用了约 1.9GB），swap 从 419MB **归零**，且所有集群服务**零影响**、全部改动**一条命令即可回滚**。

## 二、背景：这套集群是什么，问题出在哪

### 2.1 三台机器在干什么（零基础版）

想象一个小型数据加工厂，由三台电脑组成：

| 机器 | 角色 | 上面跑的程序（用类比说） |
|---|---|---|
| **lrh-1** | 厂长办公室 | 「图书馆目录柜」（NameNode，记录文件在哪）、「车间主任」（ResourceManager，派活）、「账本」（MySQL，记录表结构）、「前台」（HiveServer2，接收 SQL 查询） |
| **lrh-2** | 生产车间 | 「书架管理员」（DataNode，真正存数据）、「工位工头」（NodeManager，执行具体任务） |
| **lrh-3** | 生产车间 | 同上 |

三台机器互相认识（配了免密登录），数据存三份（副本因子 3），坏一台不丢数据。

### 2.2 症状：最忙的那台，反而分到最少的内存

| 机器 | 内存配额 | 要跑的 Java 程序数 | 实际可用内存 |
|---|---|---|---|
| **lrh-1** | 4096 MB | **9 个** | **只剩 601 MB** ⚠️ |
| lrh-2 | 4392 MB | 4 个 | 2414 MB |
| lrh-3 | 4096 MB | 4 个 | 2086 MB |

**问题一眼就看出来了**：最忙的 lrh-1 和最清闲的 lrh-3 分到了同样多的内存，而它要多跑 5 个程序。

可用内存只剩 601MB 的后果是：系统把暂时用不到的内存**临时挪到硬盘上**（这叫 swap / 换出，好比桌面放不下了，先把东西塞进抽屉，要用时再翻出来）。lrh-1 当时有 **419MB 被塞进了"抽屉"**——每次用到这部分数据都要从硬盘读回来，速度慢几十倍。

### 2.3 实验前的完整基线数据

```
lrh-1：总 3868MB / 已用 3028MB / 可用 601MB / swap 已用 419MB
lrh-2：总 4152MB / 已用 1487MB / 可用 2414MB / swap 已用 0
lrh-3：总 3868MB / 已用 1533MB / 可用 2086MB / swap 已用 0
```

这是本报告的核心部分。**我把动手前的每个判断都写成了可验证的假设**，然后用实测数据判定成立与否——包括两个最后被证伪的。

| # | 假设（动手前的判断） | 对应行动 | 实测结果 | 判定 |

| H4 | 关闭桌面**不会**影响集群服务 | 关闭后检查所有 Java 进程 PID 是否变化 | 三个守护进程 **PID 完全未变**，服务零影响 | ✅ 成立 |
| H5 | 关闭桌面**可以随时恢复** | 执行「关闭 → 验证 → 恢复 → 验证」完整往返 | 恢复后桌面正常、服务正常 | ✅ 成立 |
| H6 | 把 JVM 堆上限从约 1GB 调到 512MB，能释放 400–600MB | 三台统一调整并重启全部服务 | **只释放了约 60MB**，远低于预期 | ❌ **证伪** |

**8 个假设，6 个成立，2 个证伪。** 被证伪的两个恰恰是最有价值的收获（见第六章）。

## 四、实验过程详录

### 4.1 前置安全核查（为什么不能直接动手）

改配置之前，必须回答一个问题：**关掉桌面，会不会把集群服务一起关掉？**

在 Linux 里，开机启动哪些服务是由「**启动目标**」（target）决定的。系统有个规则：切换启动目标时，会停掉"不属于新目标"的服务。

核查结果：

| 服务 | 挂在哪个启动目标下 | 切换后会被停掉吗 |
|---|---|---|
| hadoop（lrh-1） | multi-user（目标本身） | **不会** |
| zookeeper | multi-user | **不会** |
| hive-metastore / hive-server2 | multi-user | **不会** |
| mysql | multi-user | **不会** |
| gdm3（桌面） | graphical（被切走的那个） | 会，这正是我们要关的 |

**额外发现**：lrh-2 / lrh-3 上**根本没有 hadoop 这个服务**。这两台的 DataNode / NodeManager 是由 lrh-1 通过 SSH 远程拉起来的「游离进程」，不受服务管理机制控制——所以更加不会被误停。

结论：**安全，可以动手。**

### 4.2 实验 A：桌面到底能不能随时开关（可逆性验证）

这是用户最关心的问题——因为桌面是老师要求装的，万一关了就回不来，那就不能动。

在 lrh-3 上做了完整的往返测试：

| 阶段 | 已用内存 | 可用内存 | 三个守护进程 | 桌面服务 |
|---|---|---|---|---|
| 关闭前 | 1546 MB | 2073 MB | 在（PID 1678 / 2429 / 863） | 运行中 |
| **关闭后** | **1007 MB** | **2633 MB** | **在，PID 完全没变** | 已停止 |
| **恢复后** | 1288 MB | 2340 MB | 在 | 运行中 |

**这个实验最有说服力的一点**：三个 Java 进程的 PID 从头到尾**一模一样**。

PID 是进程的唯一编号，进程只要重启过，PID 就会变。PID 不变说明——关闭桌面**根本没有触碰这些进程**，不是"关了又恢复"，而是"压根没被影响"。这比任何"看起来正常"的描述都更可靠。

**结论：可以随时开关，完全可逆。**

### 4.3 实验 B：关闭桌面（三台）

| 机器 | 关闭前可用 | 关闭后可用 | 释放 |
|---|---|---|---|
| lrh-1 | 621 MB | **1190 MB** | +569 MB |
| lrh-2 | 2397 MB | **2987 MB** | +590 MB |
| lrh-3 | 2355 MB | **2622 MB** | +267 MB |

同时产出可复用脚本 `desktop_switch.sh`，支持 `off / on / status` 三个动作，在 lrh-1 上一条命令操作三台。

### 4.4 实验 C：JVM 堆与系统参数调优（含被证伪的 H6 / H7）

**改了什么**（三台统一，MySQL 仅 lrh-1）：

| 项目 | 改动前 | 改动后 | 为什么这么改 |
|---|---|---|---|
| Hadoop 各守护进程堆上限 | 未设置（JVM 按内存自动推算约 1GB） | 512 MB | 防止负载上来后每个进程都膨胀到 1GB |
| YARN 容器调度上限 | 未设置（默认 8192MB，而实际只给 2048MB，存在超分隐患） | 2048 MB | 让申请量和实际可用量对齐 |
| MapReduce 容器内存 | 默认 1024 MB | 512 MB | 数据量不大，容器小一点可以并发更多 |
| MapReduce JVM 重用 | 默认 1（每个小任务都启一个新 JVM） | 10 | **这是跑批提速的关键点之一**，省掉反复启动的开销 |
| ZooKeeper 堆 | 1000 MB | 512 MB | 它只负责"谁在线"这类小信息，用不了 1GB |
| 系统换出倾向（swappiness） | 60 | 10 | 减少不必要的"往抽屉塞东西" |
| MySQL | 性能监控默认开启 | 关闭 | 这套库只存表结构信息，不需要性能监控 |

**H6 为什么错了**（详见第六章）、**H7 为什么错了**（详见第六章）。

### 4.5 服务重启与 swap 回收

重启顺序（**顺序很重要**）：

1. **ZooKeeper 逐台重启**（lrh-3 → lrh-2 → lrh-1）。为什么不能三台一起？ZooKeeper 三台互相投票，必须保持多数派（至少 2 台在线）才能正常工作，逐台重启能保证任何时候都有 2 台活着。
2. **Hadoop 整体重启**（在 lrh-1 执行一条命令，会自动滚动重启三台的所有守护进程）。
3. **MySQL → MetaStore → HiveServer2**——必须按依赖顺序，因为后两者要连 MySQL 读表结构。

重启完成后回收 swap：把"抽屉"里的东西搬回"桌面"。**加了安全判断**：只有当可用内存比换出量多出 500MB 时才执行，否则跳过——防止搬不回来反而把系统撑爆。

结果：三台 swap **全部归零**。

### 4.6 端到端验证（不是"看起来没事"，是真的跑了一遍）

| 验证项 | 命令 | 结果 |
|---|---|---|
| 存储是否健康 | `hdfs dfsadmin -report` | **Live datanodes (3)**，无掉线节点 |
| 计算资源是否正常 | `yarn node -list` | **3 个节点全部 RUNNING** |
| **真实计算作业能否跑通** | `SELECT COUNT(*) FROM gmall.dwd_user_behavior_di` | **返回 100000，正确** |
| 报表数据是否可读 | `SELECT dt, dau FROM gmall.ads_dau` | 正常返回 5 天数据 |

第三条最关键——它触发了一次**真实的分布式计算作业**（MapReduce），全程走的就是本次新改的容器内存配置。作业能正确算出 10 万条记录，说明配置改动**真正落地生效了**，而不是"配置文件写对了但没被读取"。

## 六、复盘：两个被证伪的假设（本报告最有价值的部分）

一个实验报告如果只写"一切符合预期"，那是宣传材料，不是实验报告。下面两个判断我**猜错了**，而错误本身带来了更重要的认识。

### 6.1 H6 证伪：调小 JVM 堆，并不会释放等量内存

**我原本的判断**：把上限从约 1GB 压到 512MB，应该能省 400–600MB/台。
**实测结果**：只省了约 60MB。

**为什么错？** 我把"预留的上限"和"实际占用的空间"混为一谈了。

打个比方：

> JVM 就像一个员工，**堆上限**是给他预留的办公桌面积。我原本以为"把预留面积从 10 平米改成 5 平米，就能腾出 5 平米"。
> 但实际上，这位员工**本来就只用了 2 平米**（其余是空着的）。我改的是"最多能用多少"，而不是"已经占了多少"。
> 而且员工真正占的地方，除了办公桌，还有**文件柜、电脑主机、椅子**（这些对应 JVM 的 metaspace、代码缓存、线程栈等非堆部分）——这部分跟堆上限完全无关。

**所以这一步白做了吗？没有**，但价值不在"省内存"，而在：

- 原本 6 个进程各自都能膨胀到约 1GB，合计 **6GB**——对一台 3.8GB 的机器是**定时炸弹**
- 现在封顶 512MB，负载上来时不会失控
- **这正是为下一阶段上 Spark 做的必要准备**（Spark 本身也是 JVM 程序，同样的道理）

**修正后的认知**：评估 JVM 内存优化时，要区分「上限（reserved）」和「实际占用（RSS）」，前者影响最坏情况下的稳定性，后者才是当下能救急的。

### 6.2 H7 证伪：调 Hadoop 参数，结果连带影响了 Hive

**我原本的判断**：改的是 Hadoop 的配置，只影响 Hadoop 相关进程。
**实测结果**：Hive 的堆上限**被顺带从 256MB 提到了 512MB**，两个 Hive 进程的内存各涨了约 125MB。

**为什么？** 因为 Hive 启动时会**读取 Hadoop 的环境配置**（这是它的设计机制，为了方便复用 Hadoop 的连接信息）。我设的这个变量名是"全局"性质的，Hive 读到了，于是它的上限也被改了。

**我最终的处理**：**保留 512MB 不动**。理由是下一阶段要用 100 万条数据跑完整流程，原本 256MB 会偏紧。这是一次"意外但结果可以接受"的副作用——**但我把它记录下来，而不是假装没发生**，因为如果当时 Hive 内存更紧张，这个副作用就可能导致故障。

**教训**：全局环境变量会沿着依赖链扩散。改配置前要查清"谁会读到这个变量"，而不是只看名字像什么。

## 七、意外发现（非计划内，但有价值）

### 7.1 lrh-2 / lrh-3 上根本没有 hadoop 服务

在核查服务依赖时发现：这两台机器上执行 `systemctl is-enabled hadoop` 会报"文件不存在"。

**真实情况**：这两台的 DataNode / NodeManager 是由 lrh-1 通过 SSH **远程拉起来的游离进程**，不属于任何受管理的服务。这意味着：

- 优点：关桌面时它们绝不会被误停（实验也证实了 PID 未变）
- **隐患**：它们的启动依赖 lrh-1 先起来。如果某一台先开机、或者 lrh-1 的服务启动失败，这两台的数据进程可能起不来
- **顺带查出文档错误**：项目里的《虚拟机集群使用指南》写着"DataNode 掉线就到 lrh-2 执行 `systemctl restart hadoop`"——**这条命令在 lrh-2 上不存在，照做只会报错**。这是运维文档必须修正的一处

### 7.2 集群长期跑着完整的图形桌面

三台服务器本来应该是纯命令行的，但实际都跑着 GNOME 桌面环境（40 多个常驻进程，含一个独占 245MB 的"软件更新提示"窗口）。

**这是本项目最大的一处资源浪费**，也是本次实验收益的主要来源。处理方式做成了可开关脚本，需要给老师演示时一条命令恢复。

## 八、面试官可能会追问的问题

**Q1：为什么不直接加内存条，而是做这些调优？**
A：因为排查后发现**根因不是"内存总量不足"，而是"分配和使用错了"**——最忙的节点分到最少的内存，同时 600MB 被一个用不上的图形桌面占着。加内存能掩盖问题，但找根因才是数据工程师该做的事。而且这套调优是**零成本**的。

**Q2：你怎么确定关闭桌面不会影响集群服务？**
A：分两步。**动手前**核查了各服务挂在哪个启动目标下（都挂在 multi-user 下，不受影响），并发现两台机器的数据进程根本不受服务管理；**动手后**对比了三个守护进程的 PID——**PID 完全没变**，说明进程从未中断。这比"看服务状态是 active"更严格，因为状态查询可能有延迟或缓存。

**Q3：你调小 JVM 堆，为什么没能省下内存？**
A：这是本次实验里我判断错误的一点。JVM 的**堆上限**和**实际占用内存**是两回事——原来的 1GB 上限从未被吃满过，实际占用只有 240–370MB，而这些占用主要来自 metaspace、代码缓存、线程栈等非堆部分，跟堆上限无关。调小上限的真实价值是**防止负载升高时失控**，而不是立刻省内存。（能主动说出自己判断错在哪，比只说成功更重要）

**Q4：那这次调优到底解决了什么？**
A：三件事。① 可用内存从 601MB 提升约一倍，swap 从 419MB 归零；② 建立了几条**边界**（容器内存上下限对齐、JVM 堆封顶、关闭推测执行），消除超分和膨胀隐患；③ 顺带产出两个可复用脚本，环境操作从"手工改配置"变成"一条命令"。

**Q5：MapReduce 的 `jvm.numtasks=10` 是什么？为什么能提速？**
A：默认情况下，每个小任务（map/reduce）都要**启动一个新的 JVM**，而 JVM 启动本身要花几秒到十几秒。设成 10 就是让一个 JVM **连续跑 10 个任务再退出**，省掉反复启动的开销。在这个数据量下，这笔启动开销占总时间的比例相当大。这也解释了为什么后面要做 Spark 对比——Spark 的长驻进程模型从原理上就避开了这个问题。

**Q6：为什么 ZooKeeper 要一台一台重启？**
A：ZooKeeper 是三台组成的集群，靠**多数派投票**工作（3 台中至少 2 台在线）。逐台重启能保证任何时刻都有 2 台存活，服务不中断。如果三台同时重启，整个集群会短暂失去多数派，依赖它的调度系统（DolphinScheduler）会报错。

**Q7：你怎么证明改动真的生效了，而不是白改？**
A：三重验证。① 检查进程的实际启动参数，确认拿到了 `-Xmx512m`；② 校验 XML 配置文件语法合法（写错的话服务根本起不来）；③ **跑了一个真实的 MapReduce 计算作业**，正确算出 10 万条记录——作业全程走的是新配置，算对了就说明配置真正落地了。

**Q8：如果改完发现有问题怎么办？**
A：所有被改的配置文件都在动手前自动备份到了 `/opt/backup/2026-09-27/`，一条 `cp` 即可还原；桌面有专门的开关脚本；虚拟机的内存配置改前会复制 `.vmx.bak`。**每一步都有回滚路径**，这是做环境改动的前提。

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| **HDFS** | 分布式文件系统，把数据切成块分散存在多台机器上，每块存多份 |
| **NameNode** | 记录"哪个文件存在哪台机器"，不存真实数据 |
| **DataNode** | 真正存数据块的进程 |
| **YARN** | 决定"这个计算任务分给哪台机器跑"的资源调度框架 |
| **NodeManager** | 每台机器上的执行代理，负责在本地跑任务 |
| **Hive** | 把 SQL 翻译成分布式计算任务的引擎 |
| **MapReduce** | Hadoop 原生的分布式计算模型，启动开销较大 |
| **ZooKeeper** | 分布式协调服务，保存"谁在线、谁是主"这类关键小信息 |
| **DolphinScheduler** | 任务调度平台，把一串任务编排成流程图定时跑 |
| **JVM / 堆** | Java 程序的运行环境 / 给程序预留的内存上限 |
| **RSS** | 进程实际占用的物理内存 |
| **swap（换出）** | 内存不够时把数据临时挪到硬盘，读写慢几十倍 |
| **启动目标 target** | Linux 开机时决定启动到"图形界面"还是"纯命令行"的开关 |
| **副本因子** | 一份数据存几份，本项目为 3 |
