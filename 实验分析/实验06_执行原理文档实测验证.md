## 二、背景：问题是什么

### 2.1 环境是什么样的（零基础版）

**这个集群做的事**：把 1063 万条电商用户行为日志，从原始层（ODS）一层层加工成指标表（ADS），最后画成大屏。

**涉及的角色**（用类比）：

| 角色                | 类比        | 实际是什么                                       |
| ----------------- | --------- | ------------------------------------------- |
| **HDFS**          | 一个巨大的共享网盘 | 把文件切成块、每块存 3 份在多台机器上                        |
| **YARN**          | 公司的派工部    | 决定"这个任务去哪个工位跑、给多少资源"                        |
| **容器（Container）** | 一个工位      | **不是 Docker**，就是 NodeManager 在本机起的一个 JVM 进程 |
| **Hive**          | 翻译官       | 把你写的 SQL 翻译成 MapReduce 作业，交给 YARN           |
| **JVM 堆**         | 这个工位的桌面面积 | 用 `-Xmx` 设上限；桌面太小，活儿就摊不开                    |

### 2.2 症状 / 触发原因

**起因**：这个项目连续撞了 4 个报错，每一个都看不懂：

```
GC overhead limit exceeded
Error 10096: Dynamic partition strict mode requires at least one static partition column
could only be written to 0 of the 1 minReplication nodes
return code 2 from MapRedTask
```

**诊断结论**：知识库里的 27 份教程是**操作型**的（讲"怎么写能跑"），但不讲"为什么这样跑、为什么炸"。实测关键词覆盖率：

| 概念                           | 在 27 份教程里出现                          |
| ---------------------------- | ------------------------------------ |
| `Xmx`                        | **0 次**                              |
| `GC overhead limit exceeded` | **0 次**                              |
| `minReplication`             | **0 次**                              |
| `shuffle`                    | 只出现在配置项名 `mapreduce_shuffle` 里，无任何解释 |

**于是做了一套补充材料**：`知识库/数据开发/执行原理/`，7 份（00 导读 + 6 份正文），每份都带「🔬 可跑验证」小节。

**但新问题来了**：**这些"预期"是我写的，谁能保证它们是对的？**

这就是本次实验要解决的——**把预期变成实测**。

### 4.2 启动集群（含一个顺序决策）

**做了什么**：用 `vmrun` 冷启动三台虚拟机。

**为什么是"先 worker 后 master"**：项目里有过一次真实故障——三台**同时**冷启动时，lrh-1 的服务通过 SSH 去拉 worker，但那一刻 worker 还没就绪，**静默失败不报错**，结果只有 1 个 DataNode 在跑。

所以这次刻意**先起 lrh-2、lrh-3，间隔 4 秒，最后起 lrh-1**。

**观察到什么**：一次成功。

```
Live datanodes (3)       ← 三个全注册
Total Nodes:3            ← YARN 三个全在
lrh-2 hadoop-worker=active
lrh-3 hadoop-worker=active
```

**额外等待**：NameNode 启动时 `Safe mode is ON`（安全模式），5 秒后自动 `OFF`。**这是正常行为**——它在等 DataNode 汇报块信息。

### 4.3 第一版脚本：跑通了，但结论是错的

**做了什么**：上传 `verify.sh` 并后台执行。

**观察到什么**：218 秒跑完，8 段全过，**看起来一切正常**。

**但逐条核对时发现问题**——Part 1 输出的是：

```
✔ 符合预期：秒级失败且无作业 → 这是【编译期】错误

报错内容:
Error: Could not open client transport with JDBC Uri: jdbc:hive2://lrh-1:10000:
java.net.ConnectException: Connection refused
```

**它给自己打了绿勾，但报错是"连不上 HiveServer2"，压根不是编译期错误。**

### 4.4 修正脚本（三处）

| 问题           | 修正                                            |
| ------------ | --------------------------------------------- |
| 判据只判形态不判类型   | 先匹配 `ConnectException`，命中则直接判"本项无效"           |

另外把验证查询从 `COUNT(1)` 改为 `COUNT(DISTINCT user_id)`——因为 H11 证伪了。

## 六、复盘：被证伪的假设（**本章最有价值**）

### ❌ H8：「秒级失败 + 无作业」足以判定编译期错误

**我原本的判断**：编译期错误"秒级返回 + 无 MR 作业"——这两个特征都命中，就是编译期错误。

**实测结果**：**假阳性**。第一版脚本输出了绿勾，但真实报错是：

```
java.net.ConnectException: Connection refused        ← 根本没连上服务
```

**为什么会错**：

我犯的&#x662F;**"用形态代替本质"**&#x7684;错误。`Connection refused` 也满足"秒级返回"（连不上就立刻失败）和"无作业"（都没连上，当然没作业）——**两个判据全部误命中**。

**类比**：这就像**发烧就判定是感冒**——发烧确实是感冒的症状，但也是肺炎、流感的症状。**只看症状不看检查，就会开错药。**

**修正后的认知**：

> **判据必须包含"是什么错"，而不只是"错得多快、错成什么样"。**
>
> 更一般地说：**任何"只看形态"的判据，都可能被另一种原因伪装。**  
> 这和我之前总结的另一条是同一类错误：**"参数写了"不等于"参数生效了"**、  
> **"命令执行了"不等于"状态达标了"**。

**我原本的判断**：看 DataNode 负载用 `dfsadmin -report` 里的 `XceiverCount` 字段。

> 已修正 `04_写入路径.md` 三处，并加显式提醒。

### ❌ H10：`systemctl` 显示 active 就说明服务可用了

**我原本的判断**：冷启动后，五服务全部 `active`，可以开始验证。

**实测结果**：

| 时刻        | 事件                                       |
| --------- | ---------------------------------------- |
| 19:24:10  | `systemctl` 报告 hive-server2 = **active** |
| ~19:25:00 | 连 10000 端口 → **Connection refused**      |
| 19:29:11  | 手工复测 → 正常返回 `row_cnt = 10623154`         |

**系统标记 active 之后，至少 50 秒内服务仍不可用。**

**为什么会错**：

`systemd` 的 `active` 只保证**进程已经起来了**。但 HiveServer2 是一个 Java 服务，它启动后还要：

1. 连 MySQL（读元数据 schema）
2. 初始化 session manager
3. **绑定并监听 10000 端口**

**这些都在 `active` 之后**。systemd 不负责等这些——它只管"进程没退出"。

**类比**：就像**餐厅门开了（active），但厨房还没准备好**——门开着不代表能点菜。

**修正后的认知**：

> **判断服务可用性，必须用"外部可观测"的判据：端口在监听 + 真实请求成功，不能只看服务状态标志。**
>
> **这条最值得反省的地方是**：**我自己在「组件详解」和「执行原理 04」里反复强调过"服务 active ≠ 服务可用"**，  
> 结果**写脚本时照样踩了**——因为我写的是"服务起来了吗"这个检查，而不是"能接受请求吗"。
>
> **知道一个原则 ≠ 在具体实现里执行了这个原则。**

### ❌ H11：`COUNT(1)` 一定会起 MR 作业

**我原本的判断**：用 `SELECT COUNT(1) FROM dwd_event_log_di` 提交查询，能抓到容器进程。

**实测结果**：第一版脚本等了 150 秒**没抓到容器**，查询结果也拿不到。

**为什么会错**：当 `hive.compute.query.using.stats` 生效时，Hive 可以**直接读表统计信息返回行数**，根本不提交作业——**没有作业，自然没有容器。**

**修正后的认知**：

> **选验证用的查询时，要选"必然触发目标行为"的构造。**  
> 想抓容器，就得用**一定会起 MR** 的查询——`COUNT(DISTINCT user_id)` 因为要 shuffle，**必然起作业**。
>
> 修正后：第二版一次就抓到了。

> 它们比"明显的错误"危险得多——因为**它们都长着一张"成功"的脸**。

## 八、面试官可能会追问的问题

**Q1：你为什么要写验证脚本？文档里不是已经写了"预期"吗？**

**A**：因为"我写的预期"和"实测值"是两件事。这次验证的结果恰好证明了这一点——**20 条验证里有 3 条存在问题，全部是我写文档时的想当然**。如果不跑一遍，这 3 处会一直躺在文档里，读者照着做会失败，而且**不会怀疑是文档的问题**。

**Q2：这次的证伪率高不高？**

**A**：11 个假设证伪 4 个，**36%**。而且分布很有意思——**4 条里有 3 条是关于"我自己的判据"，只有 1 条是关于集群行为**。这说明**风险主要不在被观察的对象，而在观察者的判断方式**。

**Q3：`systemctl active` 之后服务还不能用，那怎么判断服务真的好了？**

**A**：用**外部可观测的判据**，而不是服务状态标志。具体两条：① `ss -lntp` 确认端口在监听 ② 发一次**真实请求**并确认返回。本次实测 HiveServer2 的 `active` 和"可接受连接"之间**至少差 50 秒**。

**Q4：为什么 `-Xmx` 从 1GB 调到 512MB，进程内存只降了几十 MB？**

**A**：因为 `VmRSS`（真实占用物理内存）里，**堆只是一部分**。本次实测一个 `-Xmx410m` 的容器：`VmSize` 是 2.0 GB、`VmRSS` 只有 132 MB。堆是**按需增长**的，`-Xmx` 只是天花板。另外 Metaspace、线程栈（16 个线程）、JIT 代码缓存**完全不随 `-Xmx` 变化**。所以调小 `-Xmx` 的真正作用是**压低峰值**，不是**回收内存**。

**Q5：报错里 `0 of the 1 minReplication nodes` 的那个 1 是什么？**

**A**：是 `dfs.namenode.replication.min`，**默认值 1**，本次实测确认。它和副本目标数（`dfs.replication = 3`）**不是一回事**：3 是"写完之后应该有几分"，1 是"写入时至少要有几个节点成功才算这次写成了"。所以那句报错的准确含义是：**"底线只要 1 份，实际一份都没成功。"**

**Q6：怎么证明"写入放大"？**

**A**：`hdfs dfs -du -h <表目录>` 输出两列：第一列是**实际数据大小**，第二列是**含副本的总占用**。本次实测某分区是 `18.2 M / 54.6 M`——**正好 3 倍，和副本数 3 吻合**。这比讲道理直观得多。

**Q7：你这次最大的失误是什么？**

**A**：**H10——我明明在文档里反复强调"服务 active ≠ 服务可用"，结果自己写脚本时照样踩了。** 原因是我实现的检查是"服务起来了吗"，而不是"能接受请求吗"。**知道一个原则，和在具体实现里真的执行了这个原则，中间隔着一道坎。** 这条我写进脚本的 `Part 0.5`，变成机械可执行的检查了。

**Q8：下次再做类似验证，你会怎么改进？**

**A**：三条：① **判据要包含"错的是什么"，不能只判"错得多快"** ② **脚本里凡是要读的字段名/端口号，从真实输出复制**，不凭记忆写 ③ **验证手段本身要先被验证**——比如"用哪个查询来抓容器"这件事，本身就值得先试一次。

## 附录：本次涉及的概念速查（零基础）

| 名词                   | 一句话解释                                        |
| -------------------- | -------------------------------------------- |
| **容器（Container）**    | YARN 在某台机器上起的一个 JVM 进程 + 内存配额。**不是 Docker**  |
| **`-Xmx`**           | JVM 堆的**上限**（天花板），不是"预留这么多"                  |
| **堆（Heap）**          | JVM 里放对象的地方；`-Xmx410m` = 最多 410MB            |
| **Metaspace**        | 存放类元数据的区域，**不随 `-Xmx` 变化**                   |
| **`VmRSS`**          | 进程真实占用的物理内存（给系统造成的压力）                        |
| **`VmSize`**         | 进程的虚拟地址空间（JVM 会预留很多）                         |
| **YarnChild**        | MapReduce 任务进程的主类名，就是"容器里的干活进程"              |
| **ShuffleHandler**   | NodeManager 上的服务（端口 13562），reduce 从这拉 map 输出 |
| **Stage**            | 一段执行计划；每遇到一个 shuffle 边界切一刀，通常对应一个 MR 作业      |
| **副本（Replication）**  | 同一份数据存几份；3 副本 = 磁盘写入放大 3 倍                   |
| **`minReplication`** | 写入的**底线**：至少几个节点写成功才算成功（默认 1）                |
| **`Xceivers`**       | DataNode 上正在进行的并发数据流数量（负载信号）                 |
| **安全模式（Safe mode）**  | NameNode 启动时等 DataNode 汇报块信息的阶段，此期间不能写       |
| **会话级参数**            | Hive 的 `SET` 只对当前连接有效，下次连接回到默认值              |
