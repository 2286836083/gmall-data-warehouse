# 实验报告 03 · 千万行 ETL 写入失败排查与调优

> **一句话结论**：1063 万行「ODS → DWD」清洗落表**首次运行 21 分 39 秒后失败**（三个 DataNode 被**全部**踢出写入通道，`HDFS Write = 0`，一个字节都没写出去）。根因不是磁盘满、不是环境坏、不是 SQL 写错，而是**写入并发过高**——一条 `INSERT` 被 Hive 拆成 **11 个 MapReduce 作业**、6 个 reducer 同时往 31 个动态分区写文件且每个写 3 副本，2 核虚拟磁盘的吞吐撑不住。加 4 条会话参数（降并发、排序后再写、写入期副本降到 2）后**重跑成功，耗时 481 秒**，ORC 落盘 620MB、31 个分区齐全。

> 实验日期：2026-09-28 · 环境：VMware 三节点 Hadoop 集群（lrh-1 / lrh-2 / lrh-3，Hadoop 3.3.6 + Hive 3.1.3 + MapReduce 引擎）
> 执行方式：全程 SSH 远程操作；长任务用 `setsid nohup` 放后台，配套进度看板实时观测
>
> ✅ **本报告状态**：**已完整闭环**。五个步骤全部成功（15:14:46 → 15:35:39，总耗时 **20 分 53 秒**，日志零错误），端到端行数一致性已逐项验证（见 4.6 节），写入期降配的副本已恢复为 3。

## 二、背景：问题是什么

### 2.1 这套系统在干什么（零基础版）

数据要从「原始事件日志」变成「能直接画图的指标表」，中间要经过几道加工工序，这套工序叫**数仓分层**（好比小麦要经过脱壳、磨粉、筛分才能做面包）。

| 层 | 干什么 | 本次的角色 |
|---|---|---|
| **ODS** | 原始数据原样存进来，不加工 | 1063 万行事件已装载好（前序工作） |
| **DWD** | 清洗：去重、解析时间、拆类目、空值归一 | **本次要跑的这一步** |

要理解的几个关键概念：

| 名词 | 一句话解释 |
|---|---|
| **HDFS** | 分布式文件系统。一份数据不是存在一台机器上，而是切成块散在多台机器上，像一个"分散在三个仓库的图书馆" |
| **DataNode** | 真正存数据的进程，每台机器一个。写数据时必须**同时写进去**才算成功 |
| **副本（replication）** | 同一份数据存几份。设成 3 就是三台各存一份，坏一台不丢数据 |
| **minReplication** | 一次写入**最少**要成功的份数。如果连这个数都达不到，写入直接判失败 |
| **MapReduce 作业** | 一批数据的加工过程。分「Map（分头处理）」和「Reduce（汇总）」两个阶段 |
| **reducer** | 负责汇总的那一组工人。**数量越多，同时干的活越多，但同时对磁盘的压力也越大** |
| **动态分区** | 按某个字段的值自动切成多个小目录存（本次按日期切成 31 个）。好处是查询快，代价是**写入时要同时开很多文件** |

### 2.2 症状：跑得好好的，21 分钟后失败了

**怎么发现的**：为长任务做了个实时进度看板（每 5 秒从集群拉状态）。15:09 时看板显示 **"已停止（未完成）"**。

**失败时的报错**（真正的信息藏在 `Caused by` 链里，第一行的 `FAILED: Execution Error` 本身没有信息量）：

```
Caused by: ... File /user/hive/warehouse/gmall.db/dwd_event_log_di/
    .hive-staging_.../_task_tmp.-ext-10000/dt=2019-10-22/_tmp.000000_3
    could only be written to 0 of the 1 minReplication nodes.
    There are 3 datanode(s) running and 3 node(s) are excluded in this operation.

Stage-Stage-1: Map: 6  Reduce: 6   Cumulative CPU: 137.54 sec
    HDFS Read: 1419781250  HDFS Write: 0   FAIL
```

**翻译成人话**：
- `could only be written to 0 of the 1 minReplication nodes` —— 要求至少写成功 1 份，实际写成功 **0 份**
- `3 node(s) are excluded` —— **三个 DataNode 全被踢出了这次写入**
- `HDFS Write: 0` —— 算完了，**一个字节都没写出去**

**不解决的后果**：DWD 层空着，下游 DWS / ADS / 大屏全部没数据，整个项目卡在数据链路的第二层。

## 三、实验设计：9 条假设 → 行动 → 实测结果

**本章是核心。** 我把排查过程中出现的每一个判断都写成了可验证的假设——**包括最后被证伪的，以及我自己犯的那一次判断失误**。

| # | 假设（当时的判断） | 对应行动 | 实测结果 | 判定 |
|---|---|---|---|---|
| H1 | 看板显示"已停止"可能是**显示 bug**，任务其实还在跑 | 直接 SSH 读集群上的状态文件 `status.tsv` | 状态文件记录 `FAIL 退出码 2`——**看板是准的，不是 bug** | ❌ **证伪** |
| H2 | YARN 里查不到作业，说明**作业根本没提交** | 扩展排查：`yarn application -list -appStates ALL`、`mapred job -list all`、直接读 HiveServer2 日志 | 作业**一直在跑**（日志显示 reduce 已爬到 72%）。原因是非交互 SSH 下裸写 `yarn` 命令不存在，而我用 `2>/dev/null` 把报错吞了 → 输出为空被误读成"没有作业" | ❌ **证伪**（我的失误） |
| H3 | HDFS **磁盘写满**导致无法写入 | `hdfs dfsadmin -report` 查各节点剩余空间 | 三节点分别剩 30.15% / 34.46% / 35.25%，**完全够用** | ❌ **证伪** |
| H4 | **inode 耗尽**（文件数量上限用光，空间还有但建不了新文件） | `df -i /` | 使用率 **14%** | ❌ **证伪** |
| H5 | HDFS 本身**坏了/不可写** | 造一个 50MB 文件实测写入 | **写入成功**（测完已删除） | ❌ **证伪** |
| H6 | **SQL 算子写错了**（去重 / 时间解析 / 拆类目任一环节） | 取 1 天数据（34 万行）跑**同型 SQL** 冒烟 | **跑通**：`smoke_row_cnt = 311,743`，ORC 落盘 17.7MB | ❌ **证伪** |
| H7 | 真正原因是**写入并发过高**，把 DataNode 逐个踢出写入通道 | 对比"1 天规模"与"全量规模"的作业数；查看失败的 6 个 reducer 与 31 个分区的写入组合 | 1 天规模 `Total jobs = 1`；全量规模 `Total jobs = 2 → 执行中膨胀到 11`。6 reducer × 31 分区 × 3 副本 = 大量并发写 → **根因成立** | ✅ **成立** |
| H8 | 一条 `INSERT` 语句会被 Hive 拆成**远多于 1 个** MR 作业 | 抓 HiveServer2 日志里全部 `Launching Job N out of M` | 全量 **11 个**，1 天规模只有 **1 个** → 与数据规模正相关 | ✅ **成立** |
| H9 | 4 条 SET 调优能生效，且能让重跑**稳定成功** | 加调优参数 → 重跑 → 验证 reducer 数、耗时、副本数、分区数 | reducer 日志确认 `Defaulting to jobconf value of: 3`（原为自动估 6）；**481 秒成功**；副本实测 = 2；31 分区齐全 | ✅ **成立** |

**9 个假设，3 个成立，6 个证伪。**

> 说明：H3 ~ H6 属于**排除性假设**——证伪它们本身就是收获，每排除一个嫌疑，搜索范围就缩小一圈。这不是"猜错了 6 次"，而是"用 4 次廉价实验避免了 4 次错误的昂贵改动"。

## 四、实验过程详录

### 4.1 前置安全核查

动手前必须回答：**重跑会不会破坏已有数据？**

| 核查项 | 方式 | 结论 |
|---|---|---|
| 新表是否与旧表冲突 | 检查表名 | DWD 三张表是新表（`dwd_event_log_di` / `dwd_purchase_fact_di` / `dim_product`），**不碰模拟数据时代的旧表** |
| 大屏数据源会不会被影响 | 检查依赖 | 大屏读的是旧 ADS 表，与本次完全无关 → **失败也不影响现有演示** |
| 重跑是否幂等 | 检查 DDL | DDL 用 `DROP TABLE IF EXISTS` + `CREATE`，`INSERT` 用 `INSERT OVERWRITE` → **可重复执行** |
| 磁盘够不够 | `df -h` + HDFS 报告 | 根分区剩 8.9GB、HDFS 每节点剩 30%+ → 够 |

**结论：可以安全重跑。**

### 4.2 取证顺序：从"静默失败"到定位

远程跑长任务的难点是**失败时往往看不到任何输出**。这次形成的取证顺序（已固化为技能）：

1. **先读状态文件**，拿退出码与最后一行报错 —— 不要相信"感觉还在跑"
2. **从 HiveServer2 日志抓 `Caused by`** —— 真正的错误原因在这一串里；`cut` 不要截太短，关键信息常在 200~400 字符处
3. **看 `Stage-Stage-N: Map: x Reduce: y HDFS Read/WRITE` 这一行** —— 本次 `HDFS Write: 0` 是决定性信号：**算完了但一个字节没写出去**，问题在"写"而不在"算"
4. **验证环境是否仍然可用**（缩小范围）
5. **做小规模冒烟**（见 4.4）

### 4.3 排除法缩小范围（对应 H3~H6）

依次做了 4 个廉价实验，把"空间不足 / inode 耗尽 / 环境损坏 / SQL 写错"全部排除：

```
HDFS 剩余空间   → 30~35%，充足        → 排除"磁盘满"
inode 使用率    → 14%                 → 排除"文件数耗尽"
50MB 实测写入   → 成功                → 排除"环境损坏"
1 天规模冒烟    → 通过（31 万行）      → 排除"SQL 写错"
```

到这一步，"写不进去"只可能来自**写入行为本身**，而不是容量或代码。

### 4.4 关键手法：小规模冒烟验证

**这一步是全实验最有价值的动作。** 与其等 21 分钟再赌一次全量，不如先用 1 天数据（34 万行，约 1/31 的量）把同一套算子跑一遍：

```sql
-- 只处理 dt='2019-10-01'，其余 SQL 与全量完全一致
CREATE TABLE gmall.tmp_smoke_event STORED AS ORC AS
SELECT MD5(CONCAT_WS('|', ...)) AS event_id, ...
FROM (SELECT DISTINCT ... FROM gmall.ods_event_log_di
      WHERE dt = '2019-10-01') o;
```

**实测结果**：通过，`311,743` 行，落盘 17.7MB。

**更重要的产出是"规模对比"**：

| 规模 | Hive 计划的 MR 作业数 |
|---|---|
| 1 天（34 万行） | **1 个** |
| 全量（1063 万行） | **2 个 → 执行中膨胀到 11 个** |

**这一步把问题性质彻底定性了：不是"能不能跑"，而是"规模一大就跑不动"。**

### 4.5 调优与重跑（对应 H7~H9）

针对"写入并发过高"，加了 4 条会话参数（写进运行器的公共参数块，每次 beeline 调用都会带上）：

| SET 参数 | 作用 | 类比 |
|---|---|---|
| `hive.optimize.sort.dynamic.partition = true` | **最关键**：reducer 先把数据按分区排好序，再依次写文件，不再同时打开上百个分区文件 | 快递员先把包裹按小区分好堆，再一车一车送，而不是同时拎着 31 个袋子跑 |
| `mapreduce.job.reduces = 3` | 原本按数据量自动估出 6 个 reducer，人为压到 3 | 减少同时开工的工人数，降低对仓库出入口的拥堵 |
| `dfs.replication = 2` | 写入期副本数从 3 降到 2（**跑完恢复 3**） | 三份数据要落在三台机器上，掉一台就整体失败；只要两份，容忍度更高 |
| `hive.merge.mapfiles / mapredfiles = false` | 关掉小文件合并作业，减少额外 MR 作业 | 11 个作业里有一部分是"收尾合并"，先关掉 |

**15:14:46 带调优重跑。**

**先验证参数确实生效**（不能只看"我写了配置"）：

```
Hive 日志：Number of reduce tasks not specified. Defaulting to jobconf value of: 3
```

—— 关键点：显示的是 `jobconf value of: 3` 而**不是** `Estimated from input data size`。**默认会自动估算，只有被显式指定才会显示 jobconf 值**，所以这一行证明调优真的下发了。

**执行结果**：

| 步骤 | 耗时 | 结果 |
|---|---|---|
| 1 建表 DWD/DIM 三张 | 11 秒 | OK |
| **2 清洗事件明细 1063 万行** | **481 秒** | **OK**（失败那次是 1299 秒） |
| 3 派生购买事实 | 84 秒 | OK |
| 4 派生商品维度 | 501 秒 | OK（计划 4 个 MR 作业，是五个步骤里最重的一步，但**没有触发预案**） |
| 5 校验三张表行数 | 176 秒 | OK，输出见 4.6 节 |

**全链路合计 20 分 53 秒，`ALL_DONE 2026-09-28 15:35:39`，日志中错误关键字匹配 0 行。**

### 4.6 端到端验证

**要求：不能只看"服务状态是 active"，要跑真实业务动作。**

| # | 验证项 | 命令 | 预期 | 实际 | 判定 |
|---|---|---|---|---|---|
| 1 | 真实 MR 作业能跑通 | 1 天规模同型 SQL 全流程 | 通过 | **通过**，311,743 行 | ✅ |

## 六、复盘：被证伪的假设（**本章最有价值**）

### 6.1 H1 —— 我以为"看板是坏的"

**原本判断**：看板显示"已停止"，而任务按预期该跑 20 分钟以上，怀疑是看板的显示逻辑有问题。
**实测**：直接读集群上的 `status.tsv`，里面明确写着 `FAIL 退出码 2`。
**为什么错**：我下意识地把"我不希望看到的结果"归因为"工具出错"。**教训：怀疑工具之前，先去读最原始的记录。** 状态文件是运行器自己写的、最接近事实的一手证据，看板只是它的渲染。

### 6.2 H2 —— 我误判"作业根本没提交"（**最该记住的一次失误**）

**原本判断**：`yarn application -list` 输出为空 → 结论是"作业没提交上去，所以卡住了"。
**实测**：作业其实一直在跑，Hive 日志里 reduce 已经爬到 72%。
**为什么会错**：两个错误叠加——

1. **非交互 SSH 环境下，`PATH` 不含 Hadoop 的 bin 目录**，裸写 `yarn` 实际是"command not found"；
2. 我为了屏蔽 SLF4J 警告加了 `2>/dev/null`，**把"命令不存在"这个报错也一起吞了** → 得到一个空输出。

**"命令不存在"和"命令执行成功但结果为空"在这里表现完全一样**，于是我得出完全相反的结论。

**修正后的认知**：
- 远程调 Hadoop 命令**一律用全路径** `/opt/hadoop/hadoop-3.3.6/bin/yarn`
- **`2>/dev/null` 是有代价的**——它会抹平"失败"与"空结果"的区别，只应该在确认命令本身没问题后使用
- 这条已固化进技能与探针脚本

> 这个失误的隐蔽性在于：**它不会报错，只会给出一个看起来合理的空答案。** 面试时主动讲这个，比讲任何一个成功案例都更能体现排查能力。

### 6.3 H3 ~ H6 —— 四个"看起来很合理"的嫌疑全被排除

**原本判断**：`HDFS Write: 0` 最像"磁盘满"或"环境坏了"，这是最省事的解释。
**实测**：空间剩 30%+、inode 只用 14%、50MB 写入成功、1 天规模 SQL 通过 —— **全部排除**。
**为什么重要**：如果当初直接采信"磁盘满"这个假设，就会去做**清理磁盘**这种完全无效的改动，21 分钟后原样再失败一次。**这四个廉价实验的价值是"避免了一次方向错误的昂贵改动"。**

**修正后的认知**：`HDFS Write: 0` 这个信号**只说明"写失败了"，不说明"为什么写失败"**。剩余空间、inode、DataNode 排除列表、并发规模，是四个独立的可能原因，必须逐个用实验排除，不能凭"哪个最常见"直接下结论。

### 6.4 事后回看：哪一条最接近踩坑边缘

**`dfs.replication = 2` 这一条。** 它确实换来了成功率，**但这是用可靠性换的**——写入期只有 2 份副本，此时如果恰好有一台机器坏了，数据就丢了。这次是可以接受的，因为：

1. 数据源（REAMES46 原始 zip + 采样产物）在本机完整保留，随时可重跑
2. 写入窗口只有 8 分钟
3. 跑完立即把副本恢复到 3

**但这必须显式记录、必须恢复、必须在报告里写清楚**。如果换成一个"数据源已丢失、且副本必须为 3"的生产场景，这一条就**不能这么用**，而应该改用"按日期分批写入"来降低峰值，而不是降副本。

### 6.5 本次没有备份动手前的脚本（自我批评）

按本项目 Phase 1 定下的规矩是"**配置改前统一备份到 `/opt/backup/<日期>/`**"。本次修改 `dwd_run.sh` **没有先备份**，导致回滚只能手工删掉那 5 行 SET。

## 八、面试官可能会追问的问题

**Q1：`HDFS Write: 0` 和"磁盘满"报错怎么区分？为什么先怀疑磁盘？**
A：`HDFS Write: 0` 只说"最终没写成功"，**不说原因**。"磁盘满"的典型报错是 `No space left on device` 或 DataNode 的 `DiskOutOfSpaceException`，而本次报的是 `could only be written to 0 of the 1 minReplication nodes ... 3 node(s) are excluded` —— 这是**副本写入通道全部失效**，属于写入路径问题，不是容量问题。我先怀疑磁盘是因为它最常见、检查成本最低，但**用 4 个廉价实验排除掉了**，而不是直接采信。

**Q2：为什么调优优先选 `hive.optimize.sort.dynamic.partition`，而不是加内存或加节点？**
A：因为问题性质是**并发写导致 DataNode 被踢出**，不是算力或内存不足——6 个 reducer 的 CPU 累计只有 137 秒，根本不累。加内存/加节点解决不了"同时开 31 个分区文件"这个结构问题。
`sort.dynamic.partition` 让 reducer 把数据按分区排好序再写，**同一时刻只写一个分区文件**，把"并发写"改成"串行写"，直接命中根因。事实也证明有效：耗时从 1299 秒（失败）降到 481 秒（成功）。

**Q3：把副本降到 2 是不是在用可靠性换成功率？**
A：**是，而且这是有意的取舍。** 三节点集群配 3 副本意味着"三份数据必须落在三台机器上，任何一台掉线写入就失败"——容错度是零。降到 2 之后容忍一台掉线。
**但这必须有前提**：① 数据源在本机完整保留可重跑；② 写入窗口很短（8 分钟）；③ **跑完立即恢复 3**。
如果换成"数据源已丢失的生产场景"，正确做法是**按日期分批写入**降峰值，而不是降副本。

**Q4：为什么一条 `INSERT` 会变成 11 个 MR 作业？**
A：编译期 Hive 只报告 `Total jobs = 2`，但执行中膨胀到 11。原因是这条 SQL 里有 `SELECT DISTINCT`（需要一轮去重）、`MD5` 计算、`SPLIT` 拆类目、以及**动态分区写入**（要按 31 个日期分目录），加上小文件合并作业，被 Hive 拆成了多个连续 MR 作业。
**关键对比**：1 天数据只有 **1 个**作业，全量 1063 万行是 **11 个** —— 作业数与数据规模正相关，这也是它跑 21 分钟的原因（每个作业都要重扫 1.4GB）。

**Q5：你怎么确认这不是偶发抖动？**
A：做了三件事：① **1 天规模冒烟**先证明算子和环境是好的；② 调优后**验证参数真的下发**（Hive 日志显示 `jobconf value of: 3`，而不是"按数据量估算"，说明确实被显式指定）；③ **重跑成功且副本数实测为 2**，说明写入路径按预期工作。
**但要坦白**：目前只成功了一次。判断它稳定，还需要第 4、5 步也跑完、并且行数校验通过，才算闭环。

**Q6：你排查过程中有判断失误吗？**
A：有一次，而且很典型。我用 `yarn application -list` 查不到作业，就判断"作业没提交"。实际是**非交互 SSH 的 PATH 不含 Hadoop bin，裸写 `yarn` 是 command not found**，而我加了 `2>/dev/null` 把报错一起吞了——于是"命令不存在"和"命令成功但结果为空"表现完全一样，我得出完全相反的结论。
**修正**：远程调 Hadoop 命令一律用全路径；`2>/dev/null` 只在确认命令本身可用后才加。

**Q7：为什么不干脆把 SQL 改成按天分批写入？**
A：按天分批能从根本上降低峰值（每次只写 1 个分区），是**更彻底的方案**。但它意味着 31 次 Hive 调用，每次都有一轮 JVM 冷启动和作业调度开销，总耗时会显著变长。
所以顺序是**先用调优参数解决**（成本 4 行配置、效果已验证），把分批作为**调优失效时的下一张牌**。工程上先选改动最小、可验证最快的方案，这个顺序是刻意的。

**Q8：这次调优对后面的第 4 步（窗口函数）有用吗？**
A：**部分有用，但不能指望。** 有用的是 `mapreduce.job.reduces` 和副本控制——它们降低的是**写入压力**。
但第 4 步 `dim_product` 的风险性质不同：它要用**嵌套窗口函数按 `product_id` 对 1063 万行做全排序**，瓶颈在**排序阶段的磁盘落盘和 reducer 内存**，不是写入并集。
所以对第 4 步已经准备好备选方案：**改成两段 `GROUP BY`**（先求属性组合计数，再取出现最多的那组），绕开窗口函数的全排序。

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| **HDFS** | 分布式文件系统，数据切成块散在多台机器上，像分散在三个仓库的图书馆 |
| **DataNode** | 真正存数据的进程。写数据必须同时写进去才算成功 |
| **副本（replication）** | 同一份数据存几份。设 3 就是三台各一份，坏一台不丢数据 |
| **minReplication** | 一次写入最少要成功的份数，达不到就整笔失败 |
| **MapReduce** | 批量数据处理框架，分 Map（分头处理）和 Reduce（汇总）两阶段 |
| **reducer** | 负责汇总的那组工人。数量越多同时干的活越多，但对磁盘压力也越大 |
| **动态分区** | 按字段值自动切成多个小目录存。查询快，但写入时要同时开很多文件 |
| **ORC** | 一种列式存储格式。查询时只需读用到的列，体积约为纯文本的 1/5~1/10 |
| **inode** | 文件系统里"文件的编号"。编号用光了，即使还有空间也建不了新文件 |
| **MR 作业数（Total jobs）** | 这条 SQL 被拆成几个 MapReduce 作业。作业越多，重复扫描越多，越慢 |
| **副本因子 / `dfs.replication`** | 可以按会话临时调整，影响本次写入生成的文件副本数 |
| **`hive-staging` 目录** | Hive 写入时的临时目录，写入成功后会改名成正式文件 |
| **冒烟验证** | 用极小规模数据先跑通全流程，确认算子没坏、快速定位问题性质 |
