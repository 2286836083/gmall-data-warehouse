## 二、背景：问题是什么

### 2.1 环境是什么样的（零基础版）

先补两个必须的名词，不然后面看不懂：

> **名词：调度系统（DolphinScheduler）** —— 类比"**闹钟 + 流水线工长**"。
> 你有一串任务要按顺序做（先洗菜、再切菜、最后炒菜），调度系统负责**到了时间自动开始**、**按顺序分发**、**某一步失败就停在那并通知你**、**记录每次执行的结果**。
> 物理上：**一组常驻进程 + 一个网页界面 + 存任务定义和运行记录的数据库**。

> **名词：工作流（Workflow / Process Definition）** —— 类比"**一张菜谱**"。
> 它定义"有哪些步骤、谁依赖谁"，但不等于"某一次真的做了一遍"。
> 与之相对的是**实例（Instance）**——类比"**照着菜谱做的那一顿饭**"。同一张菜谱可以每天做一次，每次就是一个实例。

> **名词：SHELL 节点** —— 调度系统里"**这一站执行一条 shell 命令**"的节点类型。
> 类比：流水线上的某一站，工人手里拿着的就是这一段指令。本项目的所有计算任务都用这种节点，因为最灵活。

实验前的状态：

```
【正式链路】DS 工作流 gmall_evt_pipeline（16 节点，全 Hive）
    ODS ──▶ DWD ──▶ DWS ──▶ ADS ──▶ 校验       ← 写进正式库 gmall

【旁路实验】只在命令行跑过（实验10），调度系统里没有
    DWD(只读) ──▶ DWS ──▶ ADS                  ← 写进隔离库 gmall_bench
```

### 2.2 症状 / 触发原因

**问题**：实验10 做完了双引擎对比（Spark 单会话 75 秒 vs Hive 389 秒），结论是"Spark 值得用"。但那个结论有个致命缺口——

**它只在命令行验证过，没有证明"放进每天自动跑的调度里也能用"。**

这中间的差距不是小事：调度系统里任务的执行环境（谁在跑、环境变量是什么、标准输入输出通向哪里）和你在终端里手打命令**完全不同**。项目里就有过这样的坑——`spark-sql` 是交互式 shell，没有控制终端时会被 SIGTTOU 冻住，表现为"永远运行中、日志无报错、不提交作业"。

**不解决的后果**：每次说到"我们支持双引擎"都只能说"我手动跑通了"，讲不出调度、幂等、失败重试、账单 这些生产环节。

## 四、实验过程详录

### 4.1 前置安全核查

**动手前必须回答的问题：这个操作会不会误伤到正式数据？**

| 风险点 | 核查结论 |
|---|---|
| Spark 工作流会不会写坏正式库 `gmall`？ | **不会**。所有 `INSERT OVERWRITE TABLE gmall.*` 被 sed 改写成 `gmall_bench.*`；实测各段写入目标 8/8 全是 `gmall_bench` |
| 输入会不会和 Hive 侧不同，导致对比失真？ | **不会**。分段 SQL 里 `FROM gmall.*` 保持不变（源表仍读正式库），保证**输入一致** |
| 会不会抢走正在跑的作业的资源？ | 下手前确认 `YARN running apps = 0`，且同时在跑的实例只有一个 |
| 改了 Hive 版的任何东西吗？ | **没有**。新工作流是独立的 process definition，Hive 版一行未动 |

### 4.2 步骤一：环境恢复（发现了 H6 的错误判断）

**做了什么**：检查三个 vmx 目录有没有 `.vmss` 文件。

**观察到**：三台都有 `.vmss` —— 这意味着它们是**挂起（suspend）**状态，不是关机。

**为什么这一步重要**：

> **名词：挂起 vs 关机** —— 类比"**待机 vs 拔电源**"。
> 挂起是把内存里的东西完整写到磁盘上一份快照（`.vmss`），下次恢复是"把照片原样铺回内存"，速度快、而且你之前打开的窗口还在。
> 物理后果：**此时绝对不能改 vmx 配置文件**，否则挂起状态会失效，快照作废。

**行动**：按 **worker 先、master 后** 的顺序恢复（不能反过来——master 起来后就会去连 worker，worker 没起来会导致注册失败）。

### 4.3 步骤二：服务验收（顺手踩了一个判据错误）

核心服务恢复得很快（50 秒内 DN=3 / NM=3 / HS2 / HMS 全就绪）。但中途出现一次误判：

```
执行：beeline --silent=true -e "SELECT COUNT(1) FROM ..." | grep -E "^[0-9]+"
结果：无输出   → 我一度以为 Hive 服务没起来
```

**真实原因**：`--silent` 模式下输出是**表格格式** `| 31 |`，我的 grep 规则 `^[0-9]+` 匹配不上。

**教训**：这正是项目里那条老坑的重演——

> ★ **判据写错了，比对象坏了更难发现。** 因为你会去修一个根本没坏的东西。

修正方式：保留 stderr（`2>&1`）重查，就能看到真实输出。

### 4.4 步骤三：设计 Spark 工作流（三个关键决策）

**决策一：用 SHELL 节点跑 `spark-sql`，而不是 DS 原生的 SPARK 节点类型**

| 方案 | 为什么选/不选 |
|---|---|
| DS 原生 SPARK 节点 | 本质是封装了 `spark-submit`，要求指定主类（`--class`）。对"跑一段纯 SQL"这种场景很别扭 |
| **SHELL 节点跑 `spark-sql -f`** ✅ | 与现有 Hive 节点**结构完全相同**——对比时**只有"引擎"这一个变量**，其余都不变（这叫控制变量） |

**决策二：节点内部的两个必备细节**（直接继承自 Hive 版的踩坑经验）

```bash
ssh -o StrictHostKeyChecking=no -n lrh-1 '... spark-sql <参数> -f xxx.sql </dev/null 2>&1'
```

| 细节 | 少了会怎样 |
|---|---|
| `</dev/null` | `spark-sql` 是交互式 shell（jline），没有控制终端又不重定向 stdin 时会被 **SIGTTOU 冻住**，状态 `Tl+`，表现为"**永远运行中、日志无报错、不提交作业**" |
| `2>&1` | Spark 的报错只进 stdout 之外的通道，不合并的话**日志里看不到异常**，排错时一片漆黑 |

**决策三：11 个节点的构成**

```
spark_preflight     ← 残留 Spark 应用检查（有残留就拒绝开工，避免脏数据入库）
spark_bench_ddl     ← 建 gmall_bench 的 8 张表
spark_dws_user      ┐
spark_dws_product   │
spark_dws_category  ├─ DWS 四段（写 gmall_bench，读 gmall）
spark_dws_trade     ┘
spark_ads_active    ┐
spark_ads_funnel    │
spark_ads_repurchase├─ ADS 四段
spark_ads_topn      ┘
spark_reconcile     ← 对账：与 gmall 逐表比行数
```

**为什么不含 DWD**：与实验10 保持同一范围（DWS/ADS 八段），两次结果可以互相印证。DWD 段的双引擎对比仍是待办。

### 4.5 步骤四：生成分段 SQL（保证源正式、目标隔离）

```bash
# 把写库指向隔离库，源表不变
sed 's/INSERT OVERWRITE TABLE gmall\./INSERT OVERWRITE TABLE gmall_bench./g' \
    evt_etl.sql > evt_etl_bench.sql

# 按注释标记切段：每遇到一个 "===== STEP " 就换一个新文件
awk -v d="$RUN" '/^-- ===== STEP /{n++; print > (d"/step_" n ".sql"); next}
                 n>0{print >> (d"/step_" n ".sql")}' evt_etl_bench.sql
```

校验结果：
```
分段生成数：8
各段写入目标：全部 gmall_bench.*        ✅
源表引用：全部 gmall.*                  ✅
```

## 五、结果数据汇总

### 5.1 性能对比 · A 组（跨窗口，**仅供参考**）

> ⚠️ Hive 数据来自 **2026-10-03** 的实例 13，Spark 来自 **2026-10-15** 的实例 14。
> 两者不在同一时间窗口，集群负载状态不可比。按本项目"基线不可复现，对比就毫无意义"的纪律，**这组数据只能说明量级，不能作为结论**。

| 段 | Hive（10-03） | Spark（10-15） | Spark 相对 |
|---|---|---|---|
| `dws_user` | 155s | 116s | 快 25% |
| `dws_product` | 152s | 97s | 快 36% |
| `dws_category` | 106s | 80s | 快 25% |
| **`dws_trade`** | **64s** | **88s** | **慢 38%** ⚠️ |
| `ads_active_user` | 209s | 83s | 快 60% |
| `ads_funnel` | 96s | 71s | 快 26% |
| `ads_repurchase` | 154s | 73s | 快 53% |
| `ads_topn` | 106s | 69s | 快 35% |
| **八段合计** | **1042s** | **677s** | **快 1.54×** |

**八段里有七段 Spark 更快，但 `dws_trade` 这一段 Hive 反而快了 38%。** 这个"逆反者"很重要，第六章会讲。

### 5.2 性能对比 · B 组（同期基线）—— **以这组为准**

> Hive 实例 15 与 Spark 实例 14 **相隔 30 分钟**（14 于 19:31:54 结束，15 于 20:02:06 开始），
> 中间没有任何其他作业，同一集群、同一份输入、同一天。
> 这是满足 A/B 条件的数据。**下面每个数字都来自 DS 自己的数据库，不是回忆。**

**数据来源（可复现，一条命令）**：

```bash
# 在 lrh-1 上执行：直接从 DS 的元数据库取每个任务的真实起止时刻
sudo -n mysql -N -B dolphinscheduler -e "
SELECT process_instance_id, name, state,
       TIME_FORMAT(start_time,'%H:%i:%s'), TIME_FORMAT(end_time,'%H:%i:%s'),
       TIMESTAMPDIFF(SECOND,start_time,end_time)
FROM t_ds_task_instance WHERE process_instance_id IN (14,15)
ORDER BY process_instance_id, start_time;"
```

#### 5.2.1 怎么读这张表（先看这条，否则会读错）

两个实例**节点数不一样**：Spark 实例 14 是 **11 个节点**（只跑 DWS + ADS），Hive 实例 15 是 **16 个节点**（跑完整全链路，含 ODS→DWD）。

所以：

| 能比的 | 不能比的 |
|---|---|
| **八段同名任务**（`dws_user` / `dws_product` / `dws_category` / `dws_trade` / `ads_active_user` / `ads_funnel` / `ads_repurchase` / `ads_topn`）——两边跑的是**同一批 SQL 文件**，唯一变量就是引擎 | **总时长**（886s vs 3387s）——15 多跑了 ODS/DWD 五个节点和 948s 的 `verify`，14 多跑了 100s 的 `spark_bench_ddl`。**拿总时长比等于拿"一顿饭"和"一顿饭+买菜+洗碗"比** |

## 六、复盘：被证伪的假设（**必写，最有价值**）

### 6.1 ❌ H3：以为数据会"逐位一致"，结果是 double 的浮点尾巴

**原本的判断**：既然是同一份 SQL、同一份输入，那 `sum(gmv)` 应该两边算出同一个字符串。

**实测结果**：

```
GMV.gmall   5.757599649999998E7
GMV.spark   5.757599650000003E7
                    ↑↑↑↑↑↑↑↑↑↑↑↑↑↑
              第 15 位有效数字之后开始不一样
```

**差多少**：两者相差约 `5e-8`，对 **5757 万**这笔钱来说，是**五十亿分之一**。业务上完全等价。

**为什么会错**——机制如下：

> **名词：double（双精度浮点）** —— 类比"**只能记 15 位有效数字的便签纸**"。
> 无论多大的数，它只能保证前 15 位左右是准的，后面的位是"凑合的"。
> 而且**多个数相加时，加的顺序不同，累积的误差就不同**——就像先算 `(1+0.1)` 再加 `0.2`，和先算 `(0.1+0.2)` 再加 `1`，结果用有限位数的纸记下来可能差最后一位。

所以：

```
Hive：按自己划分的 MR 作业顺序聚合      → 误差累积路径 A
Spark：按 6 个 shuffle 分区并行再汇总   → 误差累积路径 B
两者路径不同 → 尾数不同（但都"对"）
```

**证据**：把 fields 类型查出来之后确认了根因——

```
describe gmall.dws_trade_day;
  gmv                      double        成交金额合计
  avg_order_amount         double        客单价 = gmv / order_cnt
```

**结论与修正后的认知**：

1. **这不是引擎的错，是建模的错。** 金额字段用 `double` 本来就不合适——财务口径的金额应该用 **`DECIMAL(m,2)`**（定点数，加法精确）。这是一个真实存在的建模缺陷，已记录但尚未修复（见 §七）。
2. **修正后的判断方法**：涉及浮点的跨引擎对比，必须用 `round(x, 2)`（或业务允许的精度）之后再比。实测 round 之后两边是**同一个字符串** `5.75759965E7`。
3. ★ **面试可以这样说**："我用 round 到业务精度做对账，而不是比原始值——因为 double 累加顺序不同必然有尾数差，比原始值是在制造假 bug。"

### 6.2 ⚠️ H4 的部分证伪：`dws_trade` 段 Hive 反而更快

**原本的判断**：既然八段里 Spark 大部分都快，那它应该全面占优。

**实测结果**：`dws_trade` 段 **Hive 66 秒 vs Spark 88 秒**（同期 B 组，Spark 慢 33%；跨窗口 A 组是 64s vs 88s，慢 38% —— 两组独立数据都指向同一个方向）。

**为什么会错**——这恰好印证了实验10 里已经发现的现象：

> **Spark 每次建会话有约 35 秒的固定开销**（启动 Driver + 连 metastore + 向 YARN 申请 Executor 并等它就绪）。

对于**数据量小、本身只跑几十秒**的作业，这 35 秒的固定成本**吃掉了 Spark 并行计算的收益**，甚至让它反而更慢。

`dws_trade_day` 只有 **31 行**（每天一行），是八段里最小的一张表——所以它最能体现"固定开销主导"的情形。

**修正后的认知**：

> ★ **更准确的表述不是"Spark 更快"，而是：
> 「数据量足够大时 Spark 更快；数据量小到接近会话开销的量级时，Hive 可能更快。」**

这条也直接推翻了一个常见误解——很多人以为"新引擎一定全面优于旧引擎"。实测告诉你：**要看作业规模**。

### 6.3 ❌ H6：以为三台 VM 是关机

**原本的判断**：集群离线 = 关机，走冷启动流程。

**实际**：三台都有 `.vmss`，是**挂起**状态。

**差别为什么重要**：

| 状态 | 恢复方式 | 如果处理错了会怎样 |
|---|---|---|
| 关机 | 直接 `start`，走完整开机 | —— |
| **挂起** ✅ | 也是 `start`，但**不能改 vmx** | 改了 vmx → 挂起快照失效 → 之前所有内存状态丢失 |

幸好这一步先侦察再动手。**教训：动手前的侦察步骤不能省，尤其是"你以为的状态"和"实际的状态"可能不一样。**

### 6.4 顺便说 H1：这个假设成立，但它本来可以不成立

H1 之所以一次通过，**不是运气好**——是因为复用了 Hive 版踩过的两个坑：

- `</dev/null` —— 防交互式 shell 被 SIGTTOU 冻住
- `2>&1` —— 让异常进 DS 日志

★ **修正后的认知（这条比具体技术点更值钱）**：

> **踩过的坑必须"工程化解决"，而不是"记住"。**
> 项目里就有过反例：`nonstrict` 那条坑**明知存在还是踩了**，因为凭记忆手写 SQL、绕开了执行器。
> 这次把它做进脚本模板里（`_spark()` / `_shell()` 函数），**新节点只要调用这个函数就自动带上防护**——这才是防坑。

### 7.1 GMV 那 31.50 的差额是怎么结案的

**原来的疑问**：报告里写"本次实测 `57,575,965.00`"，但项目记忆里到处是 `57,575,996.50`，差 31.50。当时不敢下结论，标了"待核实——可能是口径不同（另一张表 / 另一个字段）"。

**复核方法**：回集群，把**所有能算出全月 GMV 的路径**都查一遍，看有没有哪条真能算出 57,575,965.00。

**实测结果（2026-10-18，Hive 3.1.3）**：

| # | 路径 | SQL | 结果 |
|---|---|---|---|
| 1 | 交易维度 | `sum(gmv)` on `gmall.dws_trade_day` | `5.75759965E7` |
| 2 | 商品维度 | `sum(gmv)` on `gmall.dws_product_event_day` | `5.75759965E7` |
| 3 | 类目维度 | `sum(gmv)` on `gmall.dws_category_event_day` | `5.75759965E7` |
| 4 | ADS 层 | `sum(gmv)` on `gmall.ads_trade_day` | `5.75759965E7` |
| 5 | DWD 事实表 | `sum(amount)` on `gmall.dwd_purchase_fact_di` | `5.75759965E7` |
| 6 | Spark 结果（隔离库） | `sum(gmv)` on `gmall_bench.dws_trade_day` | `5.75759965E7` |
| 7 | Spark 结果 | `sum(gmv)` on `gmall_bench.dws_product_event_day` | `5.75759965E7` |
| 8 | Spark 结果 | `sum(gmv)` on `gmall_bench.dws_category_event_day` | `5.75759965E7` |

**8 条路径、两个引擎、两个库，全部是 `5.75759965E7` = `57,575,996.50`。**

**两条独立证据否定了"口径不同"这个猜测**：

1. **算术上不成立**：`dws_trade_day` 一行就是一天。若真是"另一张表/另一个字段"，差异会**以整天 GMV 为单位（百万级）**，不可能正好差 31.50。
   反过来说，`31.50` 这个量级只可能是**抄写/四舍五入以外的录入错误**。
2. **时间线上有嫌疑但机制上不成立**：§七 这条是 20:09 写的，而实例 15 当时正在跑（20:02:06~20:58:33），
   确实存在"跑到一半就去查数"的可能。但**半途的表只会缺整天数据，差额同样是百万级**，不会是 31.50。

**结论**：`57,575,996.50` 是对的；`57,575,965.00` 是**写报告时手抄出错**（`…996.50` 抄成了 `…965.00`），
项目里其余 20 多处文档记的都是 `57,575,996.50`，**以它们为准**。

> ★ **这条最该记的不是"哪个数对"，而是当时的处理方式**：
> 发现两个数打架时，写"待核实"而不是"肯定是另一个错了"——**这个克制是对的**。
> 但克制之后必须有一道"回集群复核"的动作把它闭环。**没有闭环的"待核实"，过三天就变成项目里的一个悬案。**

## 八、面试官可能会追问的问题

**Q1：为什么不直接用 DS 原生的 SPARK 节点类型？**
A：原生 SPARK 节点封装的是 `spark-submit`，要求指定主类，适合跑打好的 jar 包；本项目是"跑一段 SQL"的场景，用 `spark-sql -f` 最直接。更重要的是——**用同一个 SHELL 节点结构，Hive 版和 Spark 版的差异就只有"引擎"这一个变量**，对比才有意义。原生节点会引入一堆它自己注入的参数，反而不好判断。

**Q2：11 个节点，一份 SQL 7 为什么用隔离库？**
A：三个理由。① **正式数据零风险**——写错了随时 `DROP DATABASE gmall_bench`，`gmall` 一个字节不受影响；② **输入还是同一份**——源表仍读 `gmall.*`，所以输入一致，差异才能归因到引擎；③ **可重复做**——实验想怎么折腾都行。

**Q3：数据一致性你怎么证明的？**
A：三层。第一行数（8/8 一致）；第二 key business 值 round 到业务精度后对比（GMV / 成交笔数 186,059 / 买家数 133,258 / 商品数 69,072 全部逐位一致）；第三补充维度（分区数 31=31、一级类目基数 14=14）。**行数一致是最弱的证据**——两张表行数一样但内容完全不同是可能的，所以我加了第二层和第三层。

**Q4：那 float 尾数不一致你怎么解释？是 bug 吗？**
A：不是 bug，是 `double` 类型的固有性质。差距在第 15 位有效数字之后（5.757599649999998E7 vs 5.757599650000003E7），对 5757 万来说是五十亿分之一。**根因是金额字段用 `double` 建模不合适**——金额应该用 `DECIMAL`。这也算这次实验的一个额外产出：**发现了一个已存在的建模缺陷**。

**Q5：Spark 到底快多少倍？**
A：**不要脱口而出一个数字**，要看口径。
- 实验10（命令行、单会话连跑 8 段）：Spark 75 秒 vs Hive 389 秒，**5.0×**
- 实验10（命令行、8 段各起会话）：381 秒 vs 421 秒，**只快 10%**
- 本次（DS 调度、8 段各一个节点）：**同期 1099 秒 vs 677 秒，1.62×**（B 组，以此为准）；跨窗口 A 组是 1042 vs 677，1.54×
机制是：**Spark 把成本从"每次作业"挪到了"每次会话"（约 35 秒）**。所以会话复用得越多越划算。

**Q6：有哪一段 Spark 反而更慢？为什么？**
A：`dws_trade`，Hive 66 秒 vs Spark 88 秒（同期 B 组）。因为这张表只有 **31 行**（每天一行），作业本身几十秒就跑完了，而**每次会话的 35 秒固定开销**占比过高，把并行计算的收益全吃掉了。这条正好证明了"不能笼统说 Spark 更快"。**而且这个结论是两组独立数据交叉验证过的**（A 组 Hive 64s、B 组 Hive 66s，只差 2 秒）。

**Q7：如果让你优化，下一步做什么？**
A：两件事。第一，**把 8 段合并进一个会话跑**——调度里可以按"层"组织节点（一个节点跑完整个 DWS），省掉 7 次会话开销，代价是失去逐段可观测性（得用别的方式补，比如状态文件）。第二，**也可能是更该先做的**——把 `gmv` 从 `double` 改成 `DECIMAL(18,2)`，因为金额精度问题是实打实的缺陷。

**Q8：这个改动有什么风险？怎么回滚？**
A：最大的风险其实被设计规避了——**正式库一个字节没动**，所有写入都在 `gmall_bench`。所以回滚只需要把新工作流下线/删除（见第九章），`gmall` 完全不受影响。**这也是"先做隔离库"这个决策的价值：它把风险从"回滚可能丢数据"降到了"删掉一个实验工作流"。**

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| 调度系统（DolphinScheduler） | 闹钟 + 流水线工长：到点开跑、按顺序分发、失败停下并记录 |
| 工作流（Workflow） | 一张菜谱：定义步骤与依赖，不等于某一次执行 |
| 实例（Instance） | 照着菜谱做的那一顿饭：同定义可以每天跑一次，每次一个实例 |
| SHELL 节点 | 调度里"这一站执行一条 shell 命令"的节点类型 |
| 挂起（suspend） | 待机：内存状态完整写盘（`.vmss`），恢复快；**此时不能改 vmx** |
| SIGTTOU | 一个信号，会让后台进程在读/写终端时被暂停；`spark-sql` 在没终端时会撞上它 |
| double（双精度浮点） | 只能保证约 15 位有效数字；**加法顺序不同，结果尾数就不同** |
| DECIMAL | 定点数，十进制精确；**金额应该用这个，不该用 double** |
| 隔离库 | 专门用来做实验的独立数据库，折腾坏了也不影响正式数据 |
| 控制变量 | 对比实验里只让一个因素变化，其余全部相同，差异才能归因 |
