## 二、背景：为什么要对外部项目做对标

### 2.1 对标对象是什么

**Olist 电商数仓**（GitHub: `fengeer97-debug/DataWarehouse`）：
基于 Olist 巴西电商公开数据集，遵循 **Kimball 维度建模**与 **ODS→DWD→DWS→ADS 四层架构**，
共 **48 张表**（ODS 9 / DWD 10 / DWS 15 / ADS 14），最终回答 **14 个业务问题**。

### 2.2 对标发现的三个短板

| # | 短板 | 对方怎么做的 | 我们的现状 |
|---|---|---|---|
| 1 | **粒度声明不规范** | **每张表都显式声明粒度**（如 `dwd_trade_order_detail_di` = 一单一行一商品） | 粒度信息**散落在自由文字里**（"一行一个商品"混在说明中间），旧链路 15 张表**完全没有** |
| 2 | **维度体系单薄** | 5 张维表（date / customer / seller / product / geo）+ 一致性维度 | 只有 1 张 `dim_product`，"维度建模"在项目里体现不出来 |
| 3 | **业务问题不显式** | ADS **一表一问题**、DWS 表标注"服务的业务问题编号" | ADS 是指标主题，**没有"这表回答什么问题"的声明**；且大屏有跨层消费 |

### 2.3 我们的真实优势（不妄自菲薄）

对标不是为了否定自己。客观事实：

| 维度 | 我们 | 他们 |
|---|---|---|
| 数据量 | **1063 万行**（真实行为日志） | 约 155 万行（9 张 CSV） |
| 调度编排 | **DolphinScheduler 16 节点工作流，已上线实跑** | 无（仅 Shell） |
| 计算引擎 | **Hive/MR + Spark 3.5.9 双引擎实测对比** | 仅 Hive |
| 可视化 | **ECharts 离线大屏** | 无 |
| 性能调优 | 有实测（GC 排查、内存分层、分区调优） | 未提及 |
| 建模规范 | 偏弱 ← **本次优化的对象** | **强** |
| 业务问题驱动 | 偏弱 ← **本次优化的对象** | **强（14 个问题）** |

**结论**：不是"谁替代谁"，而是**取长补短** —— 我们的工程深度已经够，缺的是把建模规范显性化。

### 4.1 前置安全核查

| 问题 | 核查方式 | 结论 |
|---|---|---|

| 改大屏取数会不会让图表变样？ | 改前先备份 `dashboard_data_real.js`，改后逐字节比对 | 完全一致 |

### 4.2 步骤一：给 30 张表补粒度声明

统一格式：`【链路】新·真实 | 【粒度】用户 × 天 | DWS 用户主题：行为与消费汇总`

关键点：**用 `【链路】` 标记把"新旧两条链路"在元数据层面就区分开** ——
以前只能靠表名猜，现在 `desc` 一眼就知道这表属于哪条链路。

执行 27 条 `ALTER TABLE`（另 3 张是新表，建表时已带注释）。

**验证**：查询"不含'粒度'二字的表" → 结果 **0**。

### 4.3 步骤二：新建 `dim_date` 时间维

| 字段 | 说明 |
|---|---|
| `date_key` | 日期键 yyyyMMdd |
| `date_str` | 与各事实表 `dt` 对齐的 yyyy-MM-dd |
| `year / quarter / month / day` | 年 / 季 / 月 / 日 |
| `week_of_year` | 年内第几周 |
| `day_of_week` | **1=周一 … 7=周日**（已从 Hive 原生的 1=周日 换算） |
| `day_of_week_name` | 星期中文名 |
| `is_weekend` | 是否周末 |

**关键细节**：Hive 的 `dayofweek()` 原生返回 **1=周日、2=周一**，与常识相反，
所以做了换算，并在字段注释里写明 —— 否则下一个人一定会踩。

### 4.4 步骤三：补 2 张 ADS 表，修正跨层消费

**问题**：大屏的类目图与交易图直接查 `dws_category_event_day` / `dws_trade_day`，
**跳过了 ADS 层**，违反"应用层只消费 ADS"的原则。

**修正**：新建 `ads_category_day`（一级类目 × 天）与 `ads_trade_day`（天），
并把导出脚本的取数改到这两张表。

**⚠️ 关键设计**：`ads_category_day` 的 `buyer_cnt`（去重买家数）**必须回 `dwd_purchase_fact_di` 重算**，
**不能**从 DWS 的二级类目 `SUM` 加总 —— 因为 `COUNT(DISTINCT)` **不可加**
（同一个用户买了 A、B 两个二级类目，在二级层各算 1 次，加总就变成 2）。
这是本项目早已记录的"聚合不可逆"原则，本次严格遵守。

### 4.5 端到端验证

| 验证项 | 方法 | 结果 |
|---|---|---|
| 粒度声明覆盖 | 查"不含'粒度'的表数" | **0** ✅ |
| `dim_date` 行数与范围 | `count(*) / min / max` | **365 行 / 2019-01-01 / 2019-12-31** ✅ |

## 六、复盘：被证伪的假设（**必读**）

### ❌ H3：以为 Hive 有 `sequence()` 函数

- **原判断**：我在 Spark 里常用 `explode(sequence(0, 364))` 生成日期序列，想当然认为 Hive 也有
- **实测**：`Error while compiling statement: FAILED: SemanticException [Error 10011]: Invalid function sequence`
- **为什么会错**：`sequence` 是 **Spark SQL 的函数**，Hive 3.1.3 里没有。
  我把 Spark 的知识**无意识地迁移**到了 Hive —— 两个引擎 SQL 高度相似，**相似性本身就是陷阱**
- **修正后的做法**：用 Hive 的经典技巧生成序列：
  ```sql
  SELECT posexplode(split(repeat(',', 364), ',')) AS (i, v)
  ```
  （`repeat` 造 364 个逗号 → `split` 拆成 365 个空串 → `posexplode` 给出 0..364 的序号）
- **教训**：**跨引擎迁移语法假设，必须先验证再写进脚本**。
  "看起来一样"的 SQL 恰恰是最容易翻车的地方

### ❌ H4：以为"记住陷阱 14"就不会再踩（更值得记的一条）

- **原判断**：项目 `CONTEXT.md` 陷阱 14 白纸黑字写着"公共 SET 必须拼进每个分段 SQL 才生效（曾因此报 `Error 10096`）"，
  我**完全知道**这条
- **实测**：写新 ADS 表的 INSERT 时**直接写了 SQL，没带 `SET hive.exec.dynamic.partition.mode=nonstrict`**
  → **立刻报 `Error 10096: Dynamic partition strict mode requires at least one static partition column`**
- **为什么会错**：**"知道"和"手上有这个动作"是两回事**。
  知识存在脑子里 ≠ 每次写 SQL 时都会自动带上参数。这不是理解问题，是**流程问题**
- **修正后的认知**：**靠记忆防坑是不可靠的**。正确做法是把参数**固化到模板/脚本**里 ——
  项目的 `evt_run.sh` 早就是这么做的（`setup.sql` 拼进每个分段 SQL），
  而我这次是**绕开了既有机制自己手写 SQL**，于是把已经被工程化解决的坑又踩了一遍
- **给项目的改进**：所有涉及**动态分区写入**的 SQL 都应通过既有执行器（`evt_run.sh`）跑，
  而不是手工 `beeline -e`；若必须手写，应在文件头**固定带上 4 行 SET**

### 事后回看：哪一条最接近踩坑边缘

**H1（改表注释会不会乱码）** —— 如果 metastore 字符集没提前修好，
30 张表的注释会全部变成 `?` 且**不会有任何报错**，直到有人打开 `desc` 才发现。
本次因为**先试了 1 张表**才发现风险为零，这个"先小范围验证"的动作值得保留。

## 八、面试官可能会追问的问题

**Q1：你说"粒度声明"很重要，它到底解决什么问题？**
A：解决**"这张表能不能这么用"的判断**。举个真实的例子：`dws_category_event_day` 是"一级×二级类目×天"粒度，
它的 `buyer_cnt` 是去重买家数。如果不声明粒度，很容易有人把二级类目加总当成一级类目的买家数 ——
但 `COUNT(DISTINCT)` **不可加**，同一用户买两个类目会被算两次，**结果是错的却不报错**。
声明粒度就是让这种错误在使用前就被拦住，而不是等报表对不上才发现。

**Q2：你为什么用 `ALTER TABLE ... SET TBLPROPERTIES` 而不是改 DDL 重建表？**
A：重建表意味着**数据要重跑或迁移**（这套链路全量跑一次要 54 分钟），风险远大于收益。
表注释存在 metastore 的 `TABLE_PARAMS` 里，`SET TBLPROPERTIES('comment')` 只改元数据、不动数据 ——
实测 30 张表全部改完，行数一行没变。

**Q3：`dim_date` 看起来只是把日期拆成字段，有什么实际价值？**
A：三个用处。① **统一口径**：不同主题表要按周/季汇总时，不用各自写 `weekofyear()` 逻辑；
② **补全缺失日期**：事实表里某天没数据，直接 GROUP BY 会缺行，JOIN 维表能补齐（这是做趋势图的常见坑）；
③ **业务属性注入**：`is_weekend` 这类字段让"周末 GMV 是否更高"这类问题一条 SQL 就能答。
⚠️ 还有一个坑我在注释里写明了：Hive 的 `dayofweek()` 原生是 **1=周日**，与常识相反，我做了换算。

**Q4：你说大屏"跨层消费"，这算错误吗？为什么一定要改？**
A：严格说它**不报错、结果也对**（DWS 也是面向分析的表），所以很多人不会改。
但它是**规范性问题**：分层架构的意义就是"每层职责单一、上层只依赖下一层"。
如果应用层可以随便读 DWS，那 ADS 层的存在意义就被架空了，口径也没法在 ADS 统一收口。
我的修正是：补 ADS 表 + 改取数 + **用逐字节比对证明数值没变** —— 修改要可验证，不能"凭感觉改完就好"。

**Q5：`ads_category_day` 的 buyer_cnt 为什么要回 DWD 重算，直接从 DWS 加总不行吗？**
A：不行，这是**聚合不可逆**问题。`COUNT(DISTINCT user_id)` 在二级类目层算一次，
到一级类目层直接 `SUM` 会**重复计数**（一个用户买两个二级类目 → 被算 2 次）。
只有 `SUM` 类指标可加，`COUNT(DISTINCT)` 不可加 —— 这个原则我在项目早期就记录过，本次严格遵守。

**Q6：这次优化里你自己有没有犯错？**
A：有，而且有一次**明知故犯**。
① 我以为 Hive 有 `sequence()` 生成日期序列（那是 Spark SQL 的函数）→ 报 `Invalid function sequence`，
改用 `posexplode(split(repeat(',', 364), ','))` 解决。
② 更值得说的是第二条：项目文档里**早就记录过**"动态分区必须设 `nonstrict`，否则报 `Error 10096`"，
我完全知道，但写 SQL 时还是忘了带 SET → **立刻踩中**。
这说明**靠记忆防坑是不可靠的**，坑要被工程化解决（固化进执行器模板），而不是靠"记住"。

**Q7：对标开源项目，你觉得自己项目最大的差距是什么？**
A：**建模方法论的正统性**。对方用 Kimball 星型模型，事实表声明粒度、维度有一致性设计、
有 SCD 策略说明、ADS 一表一问题 —— 这套是数仓岗面试的核心考点。
我的项目工程深度更强（1063 万行真实数据、DS 编排、双引擎对比、性能调优），
但"能不能讲清建模"这块确实弱。本次优化就是针对性地把粒度、维表、业务问题映射补上。
差距还有：**事实表拆分**（对方 4 张：订单/明细/支付/评价；我 2 张）、**SCD 策略**（我未涉及）。

**Q8：改完这些，你怎么证明没改坏东西？**
A：三层证据。

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| **粒度** | "这张表的**一行代表什么**"。比如"用户 × 天"= 一行代表一个用户在某一天的情况。粒度没定清楚，表就没法正确使用 |
| **维度表 / 事实表** | 维表 = "描述性信息"（商品是什么、用户是谁、日期是哪天）；事实表 = "发生了什么"（谁在什么时候买了多少） |
| **`COUNT(DISTINCT)` 不可加** | 去重计数**不能跨维度直接相加**。用户买了 A、B 两类商品，在两个类目里各算 1 个买家，加起来是 2 —— 但实际只有 1 个人 |
| **跨层消费** | 应用层绕过 ADS 直接读 DWS/DWD。不报错，但破坏了分层职责，口径无法统一收口 |
| **动态分区** | `INSERT ... PARTITION (dt)` 里 `dt` 的值由数据决定（而不是写死），适合一次写入多天数据 |
| **`SET TBLPROPERTIES('comment')`** | 修改表的注释，属于**元数据操作**，不碰数据文件 |
| **`posexplode(split(repeat(',', n), ','))`** | Hive 里生成 0..n 数字序列的经典技巧（因为 Hive 没有 `sequence()`） |
