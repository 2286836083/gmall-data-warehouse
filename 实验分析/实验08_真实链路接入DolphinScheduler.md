## 二、背景：问题是什么

### 2.1 环境是什么样的（零基础版）

这套项目是"**一个电商数仓**"，跑在三台虚拟机（VMware 里的三台"假电脑"）上。类比一条**自来水厂流水线**：

| 组件 | 类比 | 在本项目里干什么 |
|---|---|---|
| **HDFS** | 仓库货架 | 存 1063 万行原始行为日志和各级结果表 |
| **YARN** | 车间调度员 | 把一个大计算切成很多小任务，分配给三台机器干 |
| **MapReduce** | 工人班组 | 真正干活的（Hive 把 SQL 翻译成它） |
| **Hive** | 会 SQL 的翻译官 | 让人写 SQL 就能操作 HDFS 上的海量数据 |
| **DolphinScheduler（DS）** | **工厂的自动排班系统** | 决定"几点跑哪个任务、先跑谁后跑谁、失败了怎么办" |
| **ZooKeeper** | 值班室的对讲机 | 记录"谁在线、谁是领导"（DS 靠它发现 master/worker） |
| **MySQL** | 档案柜 | 存 DS 的工作流定义、执行历史，以及 Hive 的元数据 |

**关键区分**：Hive/YARN 负责"**算得对**"，DolphinScheduler 负责"**按时、按依赖自动地算**"。一个数仓项目如果只有前者，那叫"手工跑批脚本集合"，不叫"调度平台跑通全流程"。

**两条链路并存**（这是本项目特有的复杂性）：

```
【旧链路】模拟数据 15 张表  → 大屏当前用的就是它（数值是直线，演示效果差）
【新链路】真实数据 12 张表（REES46，1063 万行）
          ODS → DWD/DIM → DWS(4 张) → ADS(4 张)  ← 本次要接进 DS 的就是这条
```

### 2.2 症状 / 触发原因

用户的原话是"**这个项目的 DolphinScheduler 应该还没搞好，你检查一下这个项目，看看全流程是否通畅**"。

这句话里有两个隐含判断需要验证：

1. "**应该还没搞好**" —— 是"差一点点（比如少一个节点）"，还是"差得远"？
2. "**全流程是否通畅**" —— 通畅的判据是什么？只看服务 `active`？还是看端到端跑出结果？

**不解决的后果**：项目汇报材料里写着"自建调度：DolphinScheduler 工作流 `gmall_dw_pipeline`（9 节点），按天定时跑数"、"到什么点自动干活"。如果实际跑的不是这条链路、也没有定时，那么**演示时点"运行"是跑不出真实数据的**，而且面试官只要问一句"这个工作流里有没有类目主题节点"就会暴露。

### 4.2 审计 DS 元数据：把"以为"换成"事实"

一条 SQL 就能问清"DS 到底有什么"，比翻文档可靠：

```sql
select code, name, version, release_state, update_time from t_ds_process_definition;
select count(*) from t_ds_schedules;                        -- → 0
select id,name,state,start_time,end_time from t_ds_process_instance order by id;
select count(*) from t_ds_command;                          -- → 0（没有排队/执行中的命令）
```

再把这 14 个节点的 `rawScript` 全部拉出来看它们 `-f` 的是哪个 SQL —— 这一步定案：**全是旧链路脚本**。

### 4.3 抓到"活体故障"：DS 说杀掉了，其实还在跑

这是本次最有价值的发现，证据链完整：

```
① task_instance 19 (dws_order)   state=9 (KILL)   start=09-30 10:41:49  end=10:42:20
② worker 日志（lrh-3）           exitStatusCode:143 , processExitValue:143   ← SIGTERM
   但同一份日志在 10:42:26 之后**还在继续输出**（Stage-3 正在提交 application_..._0023）
③ lrh-1 上有一个活着的 beeline   父进程链：sshd(不分配 tty) → bash -c → beeline
④ YARN: application_..._0023      Start=09-30 10:42:25   Finish=10-03 09:44:39
   application_..._0024.._0031     全部在 10-03 09:44~10:51 之间跑完，dt 从 08-21 一路到 08-24
⑤ 结果表 dws_order_day            5 天分区全齐（这轮"被停掉"的任务其实跑完了）
```

**机制**（用类比）：DS 停任务时，只杀得掉 worker 机器（lrh-2/3）上的进程树。而任务脚本本体是 `ssh lrh-1 'beeline ...'` —— 命令跑在 lrh-1 上，由 lrh-1 的 sshd 拉起。因为是非交互会话（**没有分配终端**），ssh 连接断开时 sshd **不会**给这个子进程发 SIGHUP，于是它变成孤儿继续跑。

> 这条正好是本项目《DolphinScheduler 全流程排障汇总》里的**第 4 坑**——也就是说它不是新问题，而是**又发生了一次**，而且这次跨了 3 天才被发现。
> **可复现判据**：`ps -ef | grep jdbc:hive2` 在 `t_ds_process_instance` 已终态后仍能看到 beeline。

### 4.4 脚本漂移对账：项目文件夹 ≠ 集群

用 `md5sum` 双侧对账，发现静默漂移（这是最危险的一类问题：**现象对不上时你会去怀疑集群，其实是文件不是同一份**）：

| 文件 | 漂移内容 | 危害 |
|---|---|---|
| `evt_verify.sql` | 集群是**修正前旧版**：把"浏览≥加购 AND 加购≥购买"写成一条判断，31 天里误报 15 天违例 | **高**：重跑第 10 步会得到错误结论 |
| `ods_event_log_ddl.sql` | 仅注释文案不同（本地版记录了 31.9% 类目缺失等画像结论） | 低（无结构差异） |
| `batch_load.sql` / `etl_dws_*.sql` / `etl_ads_opt.sql` / `verify_ads.sql` | 集群版比项目版**多 9 行 `-- ds-tuned (small cluster)` 调优头**（`mapreduce.*.memory.mb=1024`、`-Xmx768m`） | **高**：照项目版重跑会重演 `GC overhead limit exceeded` |

> 这印证了 `CONTEXT.md` §四.12 的教训："**统一配置看起来整洁，实际是丢信息**"。集群上那份带分层调优的才是"真身"。

### 4.6 设计并建成 16 节点工作流

**为什么按"一个节点一个 SQL"拆？** 因为 DS 的价值就在**节点级可见性**——演示时能指着界面说"这是类目主题节点，它扫了 1063 万行"。这也是项目原计划里"新链路有 4 个 DWS 节点"的意图。

| # | 节点 | 执行内容 | 为什么这么排 |
|---|---|---|---|
| 1 | `preflight` | 5 服务 active / 3 DataNode / 3 NM / HS2 端口+真实查询 / **无残留 beeline** / 生成分段 SQL | 挡住 H5 那个坑；`is-active=active ≠ 能连`（本项目老坑） |
| 2 | `ods_ready` | 源 CSV 在就重装载；不在就用**外部判据**核验 31 分区 / 10,630,245 行 | ODS 是一次性接入口；源文件已按约定移出集群，不能假装重载 |
| 3 | `dwd_ddl` | `dwd_ddl.sql`（建 DWD/DIM 三表，ORC+SNAPPY） | 先有表结构 |
| 4 | `dwd_event_clean` | `ds_steps/dwd_step2.sql` | 1063 万行清洗去重（最重的一步） |
| 5 | `dwd_purchase_fact` | `ds_steps/dwd_step3.sql` | 由事件流派生购买事实 |
| 6 | `dwd_dim_product` | `ds_steps/dwd_step4.sql` | 派生商品维度 |
| 7 | `evt_ddl` | `evt_ddl.sql`（4 DWS + 4 ADS） | DWS 必须先建 |
| 8-11 | `dws_user` / `dws_product` / `dws_category` / `dws_trade` | `ds_steps/evt_step1..4.sql` | **4 个 DWS 主题各自一个节点**（原计划要补的"类目主题"就在这里） |
| 12-15 | `ads_active_user` / `ads_funnel` / `ads_repurchase` / `ads_topn` | `ds_steps/evt_step5..8.sql` | 4 张指标表，各自可见 |
| 16 | `verify` | `evt_verify.sql`（**不加** `--silent`，让三层校验表格完整进日志） | 人可读的验收证据 |

**两个关键工程决定：**

1. **公共 Hive 调优参数从既有 runner 里"抽取"，而不是重抄。**
   分段 SQL 由 `ds_prepare_steps.sh` 生成：直接切 `etl_ods_to_dwd.sql` / `evt_etl.sql`（正文唯一真源），而公共 `SET` 参数用 `sed` 从 `dwd_run.sh` / `evt_run.sh` 的 heredoc 里**抠出来**。这样以后调优只改 runner，不会再出现"参数文件生成了 ≠ 参数生效了"（本项目 Error 10096 的老坑）。生成后还做**启动前自检**：`grep` 每个分段文件里有没有 `hive.exec.dynamic.partition.mode` 和 `mapreduce.job.reduces`，查不到就非 0 退出。

2. **重活节点不自动重试（`failRetryTimes=0`）。**
   既有定义用的是重试 1 次。但 `INSERT OVERWRITE` 尽管幂等，一旦上一轮留下了孤儿 beeline，重试就会变成**两个 beeline 抢 HiveServer2**（排障文档第 4 坑）。宁可失败停在原地让人看日志。

**节点脚本模板**（沿用项目里已实测跑通的写法，`</dev/null` 不能省——否则 beeline 会被 SIGTTOU 冻住，表现为"一直运行中、日志无报错、永不提交作业"）：

```bash
ssh -o StrictHostKeyChecking=no -n lrh-1 'export JAVA_HOME=/opt/jdk/jdk1.8.0_202; \
  export PATH=$JAVA_HOME/bin:$PATH; \
  /opt/hive/apache-hive-3.1.3-bin/bin/beeline -u jdbc:hive2://localhost:10000 \
  --silent=true -f /home/lrh/workspace/ds_steps/evt_step1.sql </dev/null 2>&1'
```

**为什么脚本里要 `ssh` 回 lrh-1**：DS 的 worker 跑在 lrh-2/lrh-3，那两台**没装 Hive 客户端**，所以任务必须跳回 lrh-1 执行 beeline。这是项目既有设计，保留。

### 4.7 建/上线/触发：踩了 3 个 DS 接口的坑

走官方 REST 接口（不手改数据库——DS 的 master 会把定义缓存在内存里，直接写库它看不到）：

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| **A. `query-by-name` 是坏的** | 对**确实存在**的定义也回 `50003 does not exist` | 该接口在本 build 下不可用 | 改用分页列表接口 `GET /process-definition?pageNo=1&pageSize=200` 自己按名字找 |
| **B. `releaseState` 不能传 0/1** | 回笼统的 `10108 release process definition error` | 参数类型是枚举 `ReleaseState`，Spring 要**枚举名** | 传 `ONLINE` / `OFFLINE` |
| **C. `timeout` 不能传 0** | 回 `10002 task timeout parameter is not valid` | 反编译 `ExecutorServiceImpl` 字节码可见校验是 `timeout > 0 && timeout <= 86400` | 传 `86400`（24 小时，远大于本链路约 1 小时） |

> 坑 B、C 的教训：**接口只回一句笼统的错误码时，别猜，去读它的字节码/源码。** 我用 `javap -c ExecutorServiceImpl.class | grep -B12 TASK_TIMEOUT` 直接把判断条件读了出来（`ifle` → `>0`、`ldc 86400` → `<=86400`），比试错快得多。
>
> 另外：**新建请求里指定的 `code` 会被 DS 忽略**，必须回读真实 code（排障文档第 14 坑，实测再次确认）。

## 六、复盘：被证伪的假设（**必写，最有价值**）

### ❌ H1：以为 DS 里已经有真实链路，只差一个节点

- **原判断**：`项目状态.md` 写的是"DS 工作流补节点 —— `gmall_dw_pipeline` 现有 3 个 DWS 节点，新链路有 4 个"，读起来像是**小修**。
- **实测**：DS 里 2 个定义的 14 个节点**全部**指向旧模拟链路脚本，新链路**零节点**。不是"少一个节点"，而是"整条链路没进来"。
- **为什么错**：我把"**新链路有 4 张 DWS 表**"和"**DS 工作流里有 3 个 DWS 节点**"这两个事实，误当成同一套东西的差集。实际上前者是新链路（`evt_*` 脚本），后者是旧链路（`etl_*` 脚本）——**两张表、两套命名、两条链路**，节点数碰巧都是 DWS 而已。
- **修正后的认知**：**读"进度文档"时，凡是涉及数量的描述，都要回到权威数据源核对"这些数字指的是同一批对象吗"。** 文档里一个含糊的"现有 N 个"，会让人把"重建整条链路"误估成"加一个节点"。

### ❌ H2：以为"9 节点全流程跑通过"有库里证据

- **原判断**：`项目介绍与环境架构.md` 里程碑表写着"✅ DS 工作流 `gmall_dw_pipeline`（9 节点）"。
- **实测**：`t_ds_process_instance` 里 **9 节点全流程一次成功实例都没有**。09-22 排障时为了止住 master 的 NPE 死循环，用 `DELETE FROM t_ds_process_instance WHERE id IN (1,2,3)` 把早期实例清掉了，连带把证据一起删了。只有 5 节点**尾段**有 1 次成功（09-22 22:01:47）。
- **为什么错**：我没意识到"清库排障"这一步**顺手删掉了唯一的成功证据**。
- **修正后的认知**：**排障时清理脏数据前，先把"这是唯一证据"这件事检查一遍**，或者至少把关键结论先写进报告/截图留档。否则"跑通过"就只剩口头记忆——而口头记忆在下次换工具/换人时等于不存在。

### ❌ H3：以为"按天定时跑数"已经实现

- **原判断**：多处文档写"按天定时跑数""到什么点自动干活"。
- **实测**：`t_ds_schedules` **0 条**。
- **为什么错**：文档把"**具备定时能力**"（DS 这个平台能干这事）写成了"**已经定时了**"（我们配了 crontab）。这类"能力描述"和"状态描述"混写，是说明书最容易犯的错。
- **修正后的认知**：**能力 ≠ 状态。** 描述调度必须区分"平台支持"和"已配置"，判据就是 `t_ds_schedules` 有没有行。

### ❌ H4：以为 09-30 那次失败是 SQL 问题

- **原判断**：日志尾部有 Hive/MR 输出，看起来像 SQL 跑挂了。
- **实测**：`exitStatusCode:143` = 收到 SIGTERM，task state=9 (KILL)、实例 state=5 (STOP) —— 是**被主动停掉**的。
- **为什么错**：日志尾部同时有"⚠ process has exited ... exitStatusCode:143"和"Stage-3 正在提交 job"这两类互相矛盾的行。我只看了"有报错样子的那部分"，没注意 **143 这个数字本身就是结论**（128+15 = SIGTERM）。
- **修正后的认知**：**退出码先于日志文本。** 判"失败"还是"被杀"，先看退出码（143=TERM、137=KILL、`0`=正常），再看日志。这条能省掉大量误判。

### ❌ H5：以为被停掉的进程早就结束了

- **原判断**：实例已是终态（STOP），进程自然没了。
- **实测**：孤儿 beeline **从 09-30 10:42 一直跑到 10-03 09:44**，YARN 应用 `_0023` 的 Start/Finish 时间戳（`1790736145393` / `1790991879114`）是铁证；后续 `_0024.._0031` 把 `dt=08-21..08-24` 全跑完。
- **为什么错**：把"**DS 认为任务结束了**"等同于"**任务真的结束了**"。DS 的状态机管的是它自己派发的进程树，管不到远端 sshd 拉起的孤儿。
- **修正后的认知**：**"控制面"和"数据面"要分开验证。** 停任务之后必须用 `ps -ef | grep jdbc:hive2` + `yarn application -list` 从**数据面**确认，而不是只看 DS 界面变绿/变灰。这也直接催生了工作流第 1 个节点 `preflight` 里的残留检查。
- **附带的好运气**：这轮"被停掉"的任务其实把 5 天数据跑完了，`dws_order_day` 是齐的。**如果它在写到一半时被杀，表就是半截数据**——而当时没人知道。

### ❌ H6：以为项目文件夹里的脚本就是集群上跑的那份

- **原判断**：脚本都在版本管理里，应该一致。
- **实测**：8 个文件不一致。最危险的是 `evt_verify.sql`：集群是修正前旧版，而修正内容恰恰是"**原来那条方向性校验会误报 15 天违例**"。
- **为什么错**：本地改了、忘了 `scp`；或者反过来，集群上现场调优了（`-- ds-tuned` 那 9 行）、没同步回本地。两边都在"各自进化"。
- **修正后的认知**：**"同名文件"必须用哈希证明是同一份**，不能靠"我记得传过"。`md5sum` 双侧对账是 10 秒的事，能挡掉几小时的错误排查方向。（顺手也说明：`说明.md` 那句"集群上的同名脚本才是实际执行的版本"是对的，而且**必须当成硬约束执行**。）

### ⚠️ H7：以为按 OpenAPI 文档调接口就行（部分成立）

- **原判断**：Swagger 文档写了参数，照着调即可。
- **实测**：文档只写"参数名 + 是否必填"，**没写枚举取值范围**，也没写业务校验。于是 `releaseState=1`（文档里 `type: None`，看不出要枚举名）、`timeout=0`（文档没写必须 >0）全部踩坑，而返回的只有笼统错误码。
- **修正后的认知**：**枚举参数一律先确认取值集合**；遇到笼统错误码时，**反编译看校验逻辑**（`javap -c`）比试错快。另外，**官方 Swagger 里存在的接口不一定可用**（`query-by-name` 就是坏的），要有备用路径。

## 八、面试官可能会追问的问题

**Q1：你怎么证明"全流程通畅"？只跑一次就能说明问题吗？**
A：分两层证明。**编排层**看 DS 的 16 个 task_instance 是否全部 state=7，这是一次运行的**过程**证据；**数据层**看 12 张表的行数是否回到基线（`ods_event_log_di` 10,630,245、`dws_user_event_day` 1,622,820 等），这是**结果**证据。只跑一次确实不能证明"每次都行"，所以我把可复现性做进了设计：ETL 全是幂等覆盖写、`preflight` 会拒绝在集群不干净时开工、`failRetryTimes=0` 避免残留进程导致重试打架。要证明稳定性，正确做法是再跑 2 次并对比耗时/行数（已列入 §10）。

**Q2：为什么用 REST 接口建工作流，而不是直接 INSERT 数据库？**
A：因为 DS 的 **master 会把工作流定义缓存在内存里**。直接写库，master 看不到新定义（这正是排障文档第 1 坑"master 内存态与库不一致"的同类问题）。另外 `code`、`version`、依赖边的自洽性由服务端保证——我手写 16 条边，出错概率远高于让它自己算。**代价**是要忍受它含糊的错误码，所以我去反编译了 `ExecutorServiceImpl` 确认 `timeout` 的取值范围。

**Q3：16 个节点是不是太多了？为什么不把 DWS 四张表放进一个节点？**
A：这是**可观测性与开销的取舍**。放一个节点里，界面只能看到一个绿点，失败时也不知道是四张表里哪张挂了；拆开后每个主题的耗时、行数都能单独看（演示价值高）。代价是每个节点要重新起一次 beeline 会话（约 5~10 秒），16 个节点多花 1~2 分钟——相对整链约 50 分钟可以忽略。**反过来说，如果链路有 50 个节点，我就会按"层"合并**，因为会话启动开销会变成主要成本。

**Q4：你说参数"从 runner 里抽取而不重抄"，为什么不干脆把参数直接写在生成的 SQL 里？**
A：因为本项目**已经因为这个踩过坑**：`CONTEXT.md` §四.12 记录了"socket 调优被统一压到 512MB，抹掉了分层设计"，§四.14 记录了"参数文件生成了但没拼进分段 SQL，导致 Error 10096"。**同一份配置存在于两处，就一定会漂移。** 抽取的代价是 `sed` 依赖 heredoc 的格式（较脆），所以我加了生成后自检：`grep` 不到关键参数就非 0 退出——**让漂移变成"立即失败"，而不是"静默跑错"**。

**Q5：`preflight` 节点里为什么要检查"没有 beeline 在跑"？这不是过度设计吗？**
A：不是。这是本次审计**抓到活体故障**后加的。09-30 被停掉的任务，其 beeline 实际跑到了 10-03 且把 5 天数据全写完了。如果那时我们直接启动新一轮，就是两个 beeline 同抢 HiveServer2、同时 `INSERT OVERWRITE` 同一张表——**结果不可预测**。这个检查 24 秒就能跑完，却能挡掉一类很难复现的故障。

**Q6：H1 那个误判，如果让你重来一次，你会怎么做？**
A：我会**先查权威数据源，再读进度文档**。具体就是先跑那 4 条 SQL（`t_ds_process_definition` / `t_ds_schedules` / `t_ds_process_instance` / `t_ds_command`），5 分钟就能得到"DS 里到底有什么"。我先读了 `项目状态.md`，被"现有 3 个 DWS 节点"这句带进了"只差一个节点"的框架，后面所有估算都建立在这个错误前提上。**教训是：进度文档适合回答"想去哪"，不适合回答"现在在哪"——"现在在哪"必须问系统本身。**

**Q7：如果让你给这套链路加"按天定时跑"，你会怎么做？有哪些坑？**
A：DS 侧就是给定义配 `t_ds_schedules`（crontab + 时区），或用 `release-workflow` 接口一起放出来。但**坑比配置本身多**：（1）这份数据的 `dt` 是 2019-10-01~31 的历史快照，不是"昨天"，定时跑要先解决**增量口径**（现在 ETL 是全量覆盖 31 天，每天重跑约 50 分钟）；（2）要加**互斥**——上一轮没跑完时下一轮不能启动（`runMode=RUN_MODE_SERIAL` 或前置检查）；（3）要有**失败告警**，现在 `warningType=NONE`，失败了没人知道；（4）内存只有 7GB/台，定时任务和人工调试撞车会 OOM。所以我这次**故意没加定时**，把它列进 §10 而不是偷偷配上。

**Q8：你提到"退出码先于日志文本"，能再举个例子吗？**
A：本次就是例子。task 19 的日志尾部看起来像 Hive 报错（有大段 MR 输出 + "process has exited"），很容易判成"SQL 跑挂"。但 `exitStatusCode:143` 说明是 SIGTERM——**有人主动停的**。同理 137 = SIGKILL（多半是 OOM 被内核杀）。如果当时按"SQL 问题"去查，会去翻 SQL 语法和调优参数，方向完全错；而正确方向是去查"**谁发的停止命令**"，从而发现孤儿进程这条线。这正是 `CONTEXT.md` 那句"**错误的'原因'比错误的'现象'更危险**"的具体案例。

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| **DolphinScheduler (DS)** | 工厂的自动排班系统：决定几点跑、先跑谁后跑谁、失败了怎么办。它管"什么时候算"，不管"算得对不对" |
| **工作流定义 / 实例** | 定义 = 排班表（图纸）；实例 = 今天这一次实际执行（一张填过的表）。同一个定义可以有很多实例 |
| **上线（release）/ 下线** | 图纸归档（下线）后运行按钮是灰的。要跑必须先上线 |
| **SHELL 节点** | 工作流里的一个格子，内容就是一段 shell 命令。本项目 16 个格子各跑一个 SQL |
| **依赖边（relation）** | 格子之间的箭头。本项目是 16 个格子串成一条直线，"上一个不成功，下一个不动" |
| **task state 码** | 1=运行中、6=失败、7=成功、9=被杀死(KILL)。**9 和 6 完全不同：9 是"有人叫停"，6 是"自己跑挂"** |
| **退出码 143 / 137** | 143 = 128+15 = 收到 SIGTERM（被叫停）；137 = 128+9 = 被强杀（常见于内存不足被系统杀）。**看退出码能快速区分"被杀"和"跑错"** |
| **幂等（INSERT OVERWRITE）** | 同一段写入跑一次和跑十次，结果一样。所以 ETL 失败可以直接重跑，不用先清数据 |
| **孤儿进程** | 父进程没了但自己还活着的进程。本项目里 `ssh` 断开后，lrh-1 上的 beeline 就成了孤儿，DS 也管不到它 |
| **外部判据** | 判断"服务好了没"不看它自己报的状态（`is-active`），而是从**外面**试一下（端口是否监听 + 发一次真实查询是否返回） |
| **md5sum 对账** | 用哈希值比对两份文件是不是同一份。同名 ≠ 同内容，这是最容易踩的静默坑 |

### C.1 用户的观察是对的，但原因不是"没保存"

先排除"是不是漏保存了"：

| 检查项 | 结果 |
|---|---|
| `taskDefinitionList` | **16 个** ✓ |
| `processTaskRelationList` | **16 条串行边** ✓ |
| `view-tree` | **17 个节点**（1 个 DAG 根 + 16 个任务）✓ |
| `locations`（画布坐标） | **16 个** ✓（880 字节，已存库） |
| 该实例的 `task_instance` | **16 条，全部 SUCCESS** ✓ |

**什么都没丢。** 我把原因**先猜错过一次**（见 C.2），真正的原因是**整数精度**：

> **DS 的接口把 task code 当 JSON *数字* 返回，而浏览器用 JavaScript 的 `Number`（IEEE754 双精度浮点）解析。
> 双精度只能精确表示 ≤ 2^53 = 9007199254740992（约 9.0e15）的整数。**
>
> 我程序化建时把 task code 定成了 19 位：`3300000000000000001` ≈ **3.3e18**。
> 在这个量级，双精度的最小间隔（ULP）约 **512** —— 最后两三位根本存不下。
> 于是 **16 个 code 在浏览器里全部塌缩成同一个数** `3300000000000000000`：
> DAG 按 code 建 map → **只剩 1 个节点**；`locations` 里的 `taskCode` 同样塌缩 → 只剩 1 个坐标。

**实测判据**（一条 SQL 定案）：

```bash
sudo -n mysql dolphinscheduler -N -B -e "
select concat('最大 task code = ', max(code),
              '   2^53 = ', 9007199254740992,
              '   安全？ ', if(max(code) <= 9007199254740992, '✅', '❌ 画布会塌缩成 1 个'))
from t_ds_task_definition;"
```

| code 来源 | 量级 | 浏览器能分清吗 | 画布 |
|---|---|---|---|
| **网页拖节点，DS 自动生成**（`gen-task-codes` 实测） | `23242403233824`（2.3e13） | ✅ | ✅ 16 个正常 |
| 我程序化手写的 19 位 | `3300000000000000001`（3.3e18） | ❌ | ❌ 只剩 1 个 |
| **旧工作流 `gmall_dw_pipeline`** | `1100000000000000001`（1.1e18） | ❌ | ❌ 一直只剩 1 个 |
| **旧工作流 `gmall_dw_pipeline_tail`** | `2200000000000000001`（2.2e18） | ❌ | ❌ 一直只剩 1 个 |

> ⚠️ **最后两行是本次最意外的发现**：本项目那两个旧工作流的 code 也是 19 位手写值
> （估计是之前某次为了"好记"编的），**所以它们从一开始就只显示 1 个节点** ——
> 只是从来没人打开画布看。**这是历史遗留缺陷，不是本次新引入的。**

**副产物（不是根因，但确实也错了）**：我第一版还把节点坐标间距设成了 45px
（DS 节点图形宽约 180~200px），**即使 code 修好，45px 也会挤成一团**。
两个条件都要满足：**code ≤ 2^53 且 间距 ≥ 220px**。

> ★ **这坑为什么难发现 —— 本次最值钱的一条认知**：
> **"跑得对"和"显示得对"是两条独立的技术栈。**
> 执行链路是 **Java（64 位整数）**，显示链路是 **浏览器 JavaScript（双精度浮点）**，
> 同一个 ID 在两边能表示的**范围不一样**。
> 所以所有自动化测试（行数、GMV 四路对账、16/16 SUCCESS）**全部通过**，
> 只有**人眼看画布**才会发现 —— 这是"AI 自测全绿、用户一眼看出问题"的典型案例：
> **能自动验证的维度之外，还有"看起来对不对"这一维。**

### C.2 更正一：真正的元凶是 `startNodeList`，不是"改定义"

### C.3 更正二：排障文档 §3.1 的旧根因结论是错的

`手把手教程/DolphinScheduler全流程排障汇总.md` §3.1 原文写：

> "NPE 来自 **master 进程内存态**……**重启即可清除**，不需要改定义"

**本次实验证明它不成立**：

- **重启 master 修不好**（重启后 master 重新捡起那条实例继续循环，实测复现 2 次）
- 触发条件与"定义是否被更新过"**无关** —— 我用**从没被更新过**的新定义 + `startNodeList`，一样必挂
- 当时之所以"重启看起来有效"，是因为**同时把脏实例从库里删掉了**：**起作用的是"删实例"，不是"重启"**

> **教训**：**"做完 A 和 B 之后问题消失了"不等于"A 和 B 都是解药"。**
> 当时同时做了两件事（清库 + 重启），却把功劳记在了重启上，于是错误结论被写进文档并流传了下来。
> **要确定因果，必须做受控对照** —— 本次就是靠"只改启动方式"这一个变量，才把真凶揪出来。

### C.4 更正三：`PUT` 更新定义确实有个副作用（但不是 NPE 的原因）

排查中发现的**独立**问题：`PUT /process-definition/{code}` 更新定义时，会往
**`t_ds_task_definition_log` / `t_ds_process_definition_log`**（版本历史表）里再写一份，
导致同一 task code 出现两个版本 → API 返回的 `taskDefinitionsList` **节点数翻倍（16 → 32）**。

实测残留量：

```
t_ds_task_definition      = 16      ← 当前版本
t_ds_task_definition_log  = 66      ← 历史残留
```

**清库时必须连 `*_log` 一起清**，否则重建出来的工作流节点数会翻倍。

> **顺带解开一个旧谜题**：`gmall_dw_pipeline` 被 PUT 更新过一次（version=2）、
> **一直跑不起来、库里没有成功实例** —— 它的 `*_log` 里同样有重复行。
> 说明**在本 build 下，改工作流的可靠做法是"删掉重建"，而不是"更新"**
> （注：网页 DAG 编辑器点"保存"，走的也是这个 PUT 路径）。

### C.5 ★★ 更正四（最重要的一条）：画布只剩 1 个节点，真根因是 **code 超过 2^53**

> **这一条是用户在 C.1~C.4 之后再次反馈"依然只有 1 个"才查出来的。**
> 我当时的"45px 间距"诊断**是错的** —— 改成 220px 后画布**依然**只有 1 个节点。
> 这验证了本项目那句纪律：**错误的"原因"比错误的"现象"更危险**。

| 检查 | 结果 |
|---|---|
| 接口返回 `taskDefinitionList` | 16 个 ✓ |
| 接口返回 `code` 的类型 | **JSON 数字**（不是字符串） |
| 16 个 code 在 Python/Java 里 | 16 个**互不相同** ✓ |
| **16 个 code 在浏览器 JS 里** | **塌缩成 1 个**（全等于 `3300000000000000000`）❌ |

**根因**：JS 的 `Number` 是 IEEE754 双精度浮点，**只能精确表示 ≤ 2^53 = 9007199254740992 的整数**。
我把 task code 定成 19 位（3.3e18），该量级的 ULP ≈ 512，**最后两三位存不下** →
16 个 code 在浏览器里全部变成同一个数 → DAG 只剩 1 个节点（`locations.taskCode` 同理）。

| code 来源 | 量级 | 浏览器能分清吗 |
|---|---|---|
| **网页拖节点，DS 自己生成**（`gen-task-codes` 实测） | `23242403233824`（2.3e13） | ✅ 能 |
| 我程序化手写的 19 位 | `3300000000000000001`（3.3e18） | ❌ 塌缩成 1 个 |
| **旧工作流 `gmall_dw_pipeline`** | `1100000000000000001`（1.1e18） | ❌ **一直就是 1 个** |
| **旧工作流 `gmall_dw_pipeline_tail`** | `2200000000000000001`（2.2e18） | ❌ **一直就是 1 个** |

> ⚠️ **最后两行是本次最意外的发现**：项目里那两个旧工作流也是 19 位手写 code，
> **所以它们从一开始画布上就只有 1 个节点** —— 只是从没人打开看。**历史遗留缺陷，非本次引入。**

**修正后的正确判据**：

```bash
sudo -n mysql dolphinscheduler -N -B -e "
select concat('最大 task code = ', max(code), '   2^53 = ', 9007199254740992,
              '   安全？ ', if(max(code) <= 9007199254740992, '✅', '❌ 画布会塌缩成 1 个'))
from t_ds_task_definition;"
```

**解法**：**在网页上拖节点建，让 DS 自己生成 code**（最省事也最安全）；
程序化建时自己指定的 code 必须 ≤ 2^53。`ds_evt_pipeline.py` 已加 `assert` 与 `info` 自检。
