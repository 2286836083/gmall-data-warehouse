## 二、背景：问题是什么

### 2.1 环境是什么样的（零基础版）

这套环境是跑在 Windows 上的 **3 台虚拟机**（相当于 3 台独立电脑），共同组成一个"迷你数据中心"：

- **HDFS**（分布式文件系统）= 把 3 台机器的硬盘拼成一个"大网盘"。其中 lrh-1 是"目录管理员"（NameNode），三台各有一个"库管"（DataNode）真正存数据。
- **YARN** = 集群的"调度台"，负责把计算任务分配到各台机器上跑。
- **Hive** = 让不懂 Java 的人也能用 SQL 查大数据的翻译官。
- **ZooKeeper** = 一套"值班登记簿"，各服务启动后要在上面登记，别人才找得到它。
- **DolphinScheduler（DS）** = 任务编排器，按顺序自动跑一整套 ETL 作业（本项目 16 个节点串行）。
- **关键特性**：HDFS/YARN/Hive/ZooKeeper **是开机自启的**；而 **DolphinScheduler 不会自启**，每次重启后必须手工拉起。

### 2.2 症状 / 触发原因

起因是「检查项目状态」时实测发现：**集群核心服务都在跑，唯独 DolphinScheduler 没运行**。
文档里写的"DS 运行中"与实际不符（该不一致本次一并订正）。

用户明确授权："可以重启项目，现在项目没有任务，不影响工作"——即在**无在跑作业**的安全窗口内，
把三台虚拟机**完整重启一遍**，顺便验证"这套集群能否从零恢复"，并把 DS 一起拉起来。

### 2.3 实验前的基线数据

```

lrh-1: hadoop/zookeeper/mysql/hive-metastore/hive-server2  = 全 active

YARN      : Total Nodes 3（全 RUNNING）；运行中应用 0
DS        : 未运行（无进程 / 5678·12345·50052 未监听 / 日志止于 10-03 22:26）
```

## 四、实验过程详录

### 4.1 前置安全核查

| 问题 | 核查方式 | 结论 |
|---|---|---|
| 有没有在跑的 ETL 作业？ | `yarn application -list` | 运行中应用 = **0**，可安全重启 |
| 有没有残留的客户端进程？ | `ps` 数 `beeline` / `jdbc:hive2` | 0 |
| 有没有本机侧轮询脚本？ | 检查进度看板服务 | 已停止（**必须停，否则 RM 停后会堆积僵尸进程**） |
| VM 是"挂起"还是"真关机"？ | 看 `.vmss` / `.vmem`；`vmrun list` | 3 台均在**运行**，属正常在线 |
| 关机顺序为什么不能颠倒？ | 关 HDFS 前必须先停 NameNode | 保证 HDFS 元数据落盘，避免损坏 |

### 4.2 优雅关机（顺序不可颠倒）

```
① lrh-1            : stop hadoop                    → rc=0, inactive（NameNode 安全落盘）
② lrh-2 / lrh-3    : stop hadoop-worker             → 各 rc=0, inactive
③ lrh-1            : stop hive-server2 hive-metastore mysql
④ 三台（lrh-3→2→1）: stop zookeeper                  → 均 inactive
⑤ 三台             : poweroff
```

**为什么是这个顺序**：先停"上层依赖"再停"底层服务"。Hive 依赖 MySQL（存元数据），
ZooKeeper 被 HDFS/DS 依赖，所以 ZK 最后停；HDFS 的 NameNode 必须优雅退出，
否则它会写一半的元数据（相当于"账本记到一半关机"）。

> 注：MySQL 是 `inactive`（干净退出），而 `hive-server2` / `hive-metastore` 显示 `failed`
> —— 这是 systemd 对"用 SIGTERM 杀掉的进程"的记账方式，**不是故障**（见 H8）。

### 4.3 开机：先 worker 后 master

```
vs.
① vmrun start "D:\虚拟机2\...vmx"  (lrh-2)
② vmrun start "D:\虚拟机3\...vmx"  (lrh-3)
③ 轮询等到两台 SSH 可达 + hadoop-worker=active（实测 20 秒）
④ vmrun start "D:\虚拟机\...vmx"   (lrh-1)
```

**为什么不能三台同时起**：lrh-1 启动时会通过 SSH 去"点"另外两台的 DataNode。
如果那两台还没准备好接受 SSH 连接，这一步会**静默失败、不报错**，
表现就是开机后 `Live datanodes (1)`——看起来集群"起来了"，实际只有 1 个存储节点在线。

### 4.4 冷启动耗时实测（外部判据）

| 时刻 | 观测 | 说明 |
|---|---|---|
| +15s | 不可达 | lrh-1 还在引导 |
| +30s | `DN=3 NM=1 HS2=0 HMS=0` | **NodeManager 先只注册 1 个**——正常爬升，不是故障 |
| +45s | `DN=3 NM=3 HS2=0 HMS=1` | NM 补齐到 3 |
| +75s | `DN=3 NM=3 HS2=1 HMS=1` | **核心全就绪** |

对比 09-30 的冷启动记录（SSH 24s → YARN 30s → HS2 60s → DS Web 50s），本次同量级。

### 4.5 拉起 DolphinScheduler（不自启，必须手工）

DS 的角色分布是**用日志时间戳查出来的**，不是猜的：

| 节点 | 角色 | 证据（末次日志时间） |

| lrh-1 | master / api / alert | 10-03 22:26 / 19:25 / 18:25 |

## 六、复盘：被证伪的假设（**最有价值**）

### ❌ H2：欠副本块"应该在数仓目录"

1. **原判断**：文档只提过 DWD 表"副本已恢复 3"，推测欠副本块在数仓里。
2. **实测**：全库 13 个欠副本块中，`gmall.db` **0 个**，`/tmp` **13 个**（`/user/lrh` 也是 0）。
3. **为什么错**：**"欠副本"是文件系统层面的现象，和"它属于哪个业务库"无关**。
    类比：小区里 13 户人家的快递丢了一份，这跟"是不是本小区的业主"没关系——
    `/tmp` 是 Hadoop 的**临时目录**，被中断的作业会在这里留半成品，副本自然可能不全。
    **修正后的认知**：查欠副本要先 `fsck /` 看总量，再**逐目录缩小**，不要先入为主地猜位置。

### ❌ H3：`stop hadoop`（lrh-1）会连带停掉 lrh-2/3 的 DataNode

1. **原判断**：记忆里写"lrh-2/3 的 DataNode 是 lrh-1 经 SSH 拉起的孤儿进程"，据此以为 lrh-1 停会带走它们。
2. **实测**：停完 lrh-1 的 `hadoop` 后，lrh-2/3 **仍各有 1 个 DataNode 和 1 个 NodeManager**；直到 `stop hadoop-worker` 才真正退出。
3. **为什么错**：**"孤儿进程"只说明它们当初可能由 lrh-1 拉起，不代表它们由 lrh-1 管理**。
    类比：同事帮你代收了快递（他经手），但快递放在你家、由你保管——他走了你的快递不会消失。
    **修正后的认知**：远端 DataNode/NodeManager 实际由**各节点自己的 `hadoop-worker` 单元**管理；
    **关机时 lrh-1 的 `hadoop` 和 lrh-2/3 的 `hadoop-worker` 都要停，缺一不可。**

### ❌ H5：`jps` 返回空 = 进程不存在

1. **原判断**：`jps -l | grep MasterServer` 无输出 → DS 没跑。
2. **实测**：同一时刻 `ps -ef` 能看到大量 root 启动的 JVM。`jps` 之所以"瞎"，
    是因为它只读**当前用户**的进程快照目录（`hsperfdata`），而 systemd 是以 **root** 启动这些 JVM 的。
3. **为什么危险**：**这是一个"假阴性"**——它会让你把"我没权限看到"误报成"东西不存在"。
    最坏的情况是：一个正在跑的重要服务，被你的检查判成"没跑"，于是你又去启动一遍（端口冲突/双实例）。
    **修正后的认知**：判进程存在性用 `ps -ef | grep "[d]olphinscheduler"`；
    `jps` 只能用于**确认自己启动的、同用户的** Java 进程。

### ❌ H6：ZK 里只注册了 1 个 worker（注册不全）

1. **原判断**：`ls /dolphinscheduler/nodes/worker | grep -c "server-"` 返回 1 → 只注册了 1 个 worker。
2. **实测**：ZK 里实际是 `[192.168.87.130:1234, 192.168.87.132:1234]`，**2 个都在**，且两台的 worker 日志都在持续写心跳。
3. **为什么错（两层）**：
    - **命名格式**：DS 3.1.8 的注册节点名是 **`ip:port`**，不是 `server-xxxxx`——我的模式串**根本不匹配**。
    - **输出格式**：`zkCli.sh` 的 `ls` 把整个列表**打在一行**里，`grep -c` 数的是**行数**，
      所以无论几个节点都只会得到 `1`。
    **修正后的认知**：先看**原始输出**再写解析；数 ZK 子节点要用
    `echo "ls /path" | zkCli.sh ... | grep "^\[" | tr ',' '\n' | grep -c ':'`。
    **更根本的对策**：能用 **API 心跳**（`/monitor/workers`）就别去数 ZK——API 返回的是结构化的 `host` 字段。

### ❌ H8：`stop` 之后显示 `failed` = 服务出问题了

1. **原判断**：关服务时看到 `hive-server2  failed`，疑心停得不干净。
2. **实测**：进程已退出、10000 端口已释放，重启后一切正常。
3. **为什么错**：systemd 把"进程因 **SIGTERM** 退出"记为 `failed`（在它看来是非正常退出），
    但对我们而言这就是**计划内的关机**。`is-active` 只是**记账标签**，不是**健康结论**。
    **修正后的认知**：**同一个 `is-active` 值，在"启动后"和"停止后"含义完全不同**——
    启动后 `active` 不代表可用（HS2 要再等 50 秒才监听），停止后 `failed` 也不代表故障。

## 八、面试官可能会追问的问题

**Q1：你怎么证明"集群真的起来了"，而不是"看起来起来了"？**
A：每个服务都换**外部判据**验收，而不是看状态标签——HDFS 看 `dfsadmin -report` 的 `Live datanodes` 数（=3）；
YARN 看 `yarn node -list` 的 `Total Nodes`（=3）；Hive 不只是看 `active`，而是**真发一条 SQL 拿到结果**（返回 31 行）；
DS 看 ZK 注册节点 + `/monitor/workers` 心跳（2 个）。
状态标签只能证明"进程在"，外部判据才能证明"能干活"。

**Q2：为什么 HiveServer2 要特别等？**
A：`systemctl is-active` 变 `active` 时，JVM 才刚启动，还要连 metastore、初始化 session、绑 10000 端口。
实测 **active 之后至少还要 50 秒**才真正监听。所以判据用 `ss -lnt | grep 10000` + 发一次真实查询。

**Q3：为什么开机顺序是"先 worker 后 master"？**
A：lrh-1 启动时会通过 SSH 去拉起另外两台的 DataNode。若那两台还没就绪，这一步**静默失败不报错**，
结果就是 `Live datanodes (1)`——表面"起来了"，实际只剩 1 个存储节点。
> ⚠️ 诚实补充：本次**没有做反面对照**（先起 lrh-1 再起 worker），所以"顺序决定成败"目前是**依据既有记录的经验结论，不是本次实验证明的因果**。

**Q4：这套集群重启后哪些会自己起、哪些不会？**
A：HDFS/YARN/ZooKeeper/MySQL/Hive **都开机自启**；**只有 DolphinScheduler 不自启**，必须手工拉起
（api→master→alert 在 lrh-1，worker 在 lrh-2/3）。这是 DS 的默认行为，不是故障。

**Q5：你这次踩到的最大坑是什么？**
A：不是技术问题，是**判据问题**。我用 `jps` 查 DS 进程返回空，差点得出"DS 没跑"的结论——
实际是 systemd 以 root 启动 JVM，`jps` 只读当前用户的快照，**看不到**。
同理我用 `grep -c "server-"` 数 ZK 节点得到 1，误判"worker 注册不全"，
实际是**命名格式不匹配 + 列表打在一行**。
这两次的共同教训：**"查不到"不等于"不存在"，先怀疑判据，再下结论。**

**Q6：为什么关机顺序不能颠倒？**
A：先停上层再停下层：Hive 依赖 MySQL（元数据），ZK 被多个服务依赖所以最后停，HDFS 的 NameNode 必须优雅退出。
如果不先停 NameNode 就关 VM，相当于"账本记到一半拔电源"，有元数据损坏风险。

**Q7：`hive-server2` 关闭后显示 `failed`，你怎么判断它不是故障？**
A：看两个外部事实：进程已退出、10000 端口已释放；重启后功能正常。
`failed` 只是 systemd 对"SIGTERM 退出"的记账方式。

**Q8：DS 有 3 个工作流，为什么 `t_ds_schedules` 是 0？**
A：因为它们从来没有配过**定时调度**，一直是手工/API 触发。
"工作流存在" ≠ "会按天自动跑"——这也是本次重启后仍未做的一件事（见第十章）。

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| 冷启动 | 机器从"完全断电"开始，把整套服务按依赖顺序重新拉起来 |
| 外部判据 | 不依赖服务自己的"状态标签"，而是从**外部**观察它是否真的能提供服务（端口、注册、真实请求） |
| 假阴性 | 把"我没查到"误当成"它不存在"，比假阳性更隐蔽、更危险 |
| 欠副本块 | 一个数据块应有 3 份副本，实际少于 3 份就叫"欠副本" |
| PendingReplication | 正在排队等待复制的副本数；=0 说明复制**没有在推进** |
| 孤儿进程 | 被启动过，但不由任何服务单元管理的进程 |
| 优雅关机 | 先让服务把内存里的状态写盘、正常退出，再断电 |
| SIGTERM | 操作系统发给进程的"请你退出"信号；systemd 会把它记成 `failed` |
| 心跳（heartbeat） | 服务每隔几秒向"登记簿"报一次平安，别人据此判断它是否活着 |

### 11.1 「13 个欠副本块」结案 —— **是假警报，不是数据损坏**

**真根因（本次查明）**：这些文件的**副本因子是 10**，而集群只有 **3 台 DataNode**。

```
/tmp/hadoop-yarn/staging/anonymous/.staging/job_*/job.jar  41873153 bytes, replication=10
  → Target Replicas is 10 but found 3 live replica(s), 0 decommissioned ...
```

配置来源：**`mapreduce.client.submit.file.replication` 默认值就是 10**（YARN 用它决定作业暂存文件的副本数）。
3 节点的集群**永远凑不齐 10 份** → 这些块会**永久处于"欠副本"状态**，但它既不是损坏、也不影响任何业务数据。

**清理**：删除 HDFS `/tmp` 下 **35 个陈旧目录**（4 个 `.staging/job_*` + 5 个 `/tmp/hive/anonymous/*` + 26 个 `/tmp/hive/lrh/*`），
**保留 4 个当日（10-04）会话目录** —— 判据是"目录自身的 mtime 是否为今天"。
用 `-skipTrash`：若走 trash，文件仍保留 repl=10，告警**不会消失**。

| 指标 | 清理前 | 清理后 |
|---|---|---|
| `/tmp` Under-replicated | 13 | **0** |
| 全库 Under-replicated / Missing | 13 / 0 | **0 / 0** |
| 全库 Status | HEALTHY | **HEALTHY** |
| `/tmp` 占用 | 486.5 MB | **342.5 MB** |
| Hive 真实查询 | 31 | **31**（未受影响） |

> ⚠️ **用户决定不修改配置** → 以后每次跑批仍会新生成 repl=10 的暂存文件，**该告警会再次出现，属预期现象**。
> 已写入 `CONTEXT.md` 陷阱 33，避免未来把它当故障排查。

### 11.2 旧项目位置删除 + 本机清理踩到的坑

旧位置 `D:\OneDrive\桌面\大数据开发\` 已**永久删除**（删除前备份为 `D:\数据开发环境\backup\旧项目位置_20261004.zip`，
**898KB / 194 条目，已校验**；删除同步进 OneDrive 云端回收站）。

过程暴露了 5 个本机环境的坑，均已写入 `CONTEXT.md` 陷阱 34：

1. **`Remove-Item` 被 `safe-delete` 保护钩子接管**（强制走回收站）。中文路径 + 目录内有被占用文件 → 报
   `trash operation ... Some operations were aborted` 并 **fail-closed 拒删**；报错里的乱码（`桌面` → `妗岄潰`）
   **是显示问题，不一定是真因**（同一个中文目录在"内容已搬空"后删成功了）。
2. **钩子会把成功误报为失败**：ASCII 目录删除后 detail 写着 `OK`，却被打成 `trash-failed`。
   → **判成功与否看 `Test-Path`，不要看它的报错。**
3. **OneDrive 下的目录搬迁会被句柄打断**：`Move-Item` 只搬一半（顶层文件走了、子目录留下）；
   `项目产出` 报 `Permission denied`（**可读、不可写、不可删** = 被进程独占）。
   绕法：**先把内容逐项搬到纯 ASCII 中转目录，再删中转目录**。
4. 本环境**同时禁用 `Add-Type` 与 COM 实例化** → 拿不到 `Microsoft.VisualBasic` 的回收站 API，也不能用 Shell 的 `delete` 动词。
5. **遗留 1 个 399B 私钥**（`db_ed25519`）因被进程独占而删不掉（重试 4 次、改名亦失败）；它已含在备份 zip 中，
   等句柄释放或重启后连同中转目录一起删即可。
