## 二、背景：这一步在做什么

### 2.1 数仓分层里 DWS / ADS 是什么（零基础版）

数据加工像做菜，一层层来：

| 层 | 类比 | 本次的角色 |
|---|---|---|
| ODS | 菜市场买回来的**原料**，不洗不切 | 已完成（1063 万行原始事件） |
| DWD | **洗好切好**的净菜 | 已完成（去重、解析时间、拆类目） |
| DIM | **调料与配菜表**（商品属性） | 已完成（14 万商品） |
| **DWS** | **按菜品分装**：用户套餐、商品套餐…… | **本次做** |
| **ADS** | **按顾客需求出餐**：今日招牌、热销榜 | **本次做** |

**为什么要有 DWS 这一层？** 因为直接从明细算指标太慢，而且口径容易不一致。DWS 把明细"轻量汇总"一次，ADS 再从 DWS 出指标——**同一份口径被复用，不会各算各的**。

### 2.2 真实数据的三处关键差异（这决定了不能照抄旧脚本）

| 差异 | 旧链路（模拟） | 新链路（REES46） | 影响 |
|---|---|---|---|
| 事件类型 | view / cart / order / pay | **只有 view / cart / purchase** | 两个字段合并为一个 |
| 订单状态 | 已支付 / 已取消 / 已退款 | **不存在这个概念** | 交易表要重新设计 |
| 类目维度 | 只有 category_id | **category_l1/l2/l3 + brand**，且是点分层级路径 | **可以新建类目主题表** |
| 用户首次出现 | 每天都同一批人 | **有真实首次出现日** | **新增用户终于能算出来** |

> 💡 旧链路 `ads_dau` 的 `new_dau` / `wakeup_dau` **恒为 0**，根因就在这里——模拟数据每天都是同一批用户，本来就不存在"新增"。**换真实数据后这个指标才活过来。**

### 2.3 改造前的基线

```

DWS / ADS：仍全部是旧模拟数据链路的 5 天数据
```

## 四、实验过程详录

### 4.1 前置安全核查（为什么不会弄坏大屏）

| 核查项 | 结论 |
|---|---|
| 会不会覆盖大屏在用的表？ | ❌ 不会。新表用**全新语义名**（`dws_user_event_day` 而非 `dws_user_day`），与旧表并存 |
| DWD 三张表会被改动吗？ | ❌ 不会。本次只**读** DWD，只**写**新表 |
| 建表语句有破坏性吗？ | ⚠️ 有——`evt_ddl.sql` 每张表都是 `DROP + CREATE`。所以修 `dws_trade_day` 时**特意另写了单表修复脚本**，没有重跑整个 DDL（否则会连带 DROP 掉已跑出数据的其他三张表，白扔 6 分钟） |
| 写入期副本降到 2 有风险吗？ | 有但可控。数据源在本机可重跑、写入窗口短、**跑完立即 `setrep -w 3` 恢复** |

### 4.2 相对旧链路的四个实质性改进

**改进 1｜动态分区替代硬编码（H6 验证）**

```sql
-- 旧脚本：5 天 = 5 条 INSERT，每天一行 PARTITION (dt='2026-08-20')
-- 新脚本：31 天 = 1 条 INSERT
INSERT OVERWRITE TABLE gmall.dws_user_event_day PARTITION (dt)
SELECT ..., dt FROM gmall.dwd_event_log_di GROUP BY user_id, dt;
```
旧写法扩到 31 天要复制 31 遍——**完全不可维护**。

**改进 2｜窗口函数一次算完，替代逐日 JOIN 历史（H7 验证）**

```
旧 ads_dau：每一天都要 LEFT JOIN「历史所有天」+「昨天」→ 复杂度 O(n²)
新做法：MIN(dt) OVER (PARTITION BY user_id) 求首次活跃日
        LAG(dt) OVER (PARTITION BY user_id ORDER BY dt) 求上一次活跃日
        → 一次扫描产出全部口径
```
`new_dau` / `wakeup_dau` 因此**从恒为 0 变成真实值**。

**改进 3｜先聚合再关联维表**

```sql
-- ❌ 错误：10.6M 行先 JOIN 14 万行维表，再 GROUP BY（多一次大表 shuffle）
-- ✅ 正确：先 GROUP BY 到「商品 × 天」小表（126 万行），再 JOIN 维表
```

**改进 4｜★ 拒绝不可逆的聚合**

类目层的「去重买家数」**不能**从商品层 `SUM` 加总——同一个用户买了 A、B 两个商品，在商品层各算 1 次，加总就变成 2。所以类目层**回 DWD 明细重新 `COUNT(DISTINCT user_id)`**。

> **规律**：`SUM` 可加，**`COUNT(DISTINCT)` 不可加**。这是数仓里最容易犯的错之一。

### 4.3 五个坑的逐个定位与修复

#### 坑 1：`Error 10096` —— 参数写了却没生效（H2）

```
FAILED: SemanticException [Error 10096]:
Dynamic partition strict mode requires at least one static partition column
```

**根因**：运行器里**生成了** `setup.sql`（含 `hive.exec.dynamic.partition.mode=nonstrict`），但**忘了把它拼进每个分段的执行文件**。第 1 步建表不需要动态分区所以能过，第 2 步一写动态分区**2 秒**就暴露。

**修复**：分段后立即拼接，并**加了一道启动前自检**：
```bash
if ! grep -q "hive.exec.dynamic.partition.mode" "$RUN/step_1_run.sql"; then
  echo "!! 参数未拼接进分段文件，终止执行"; exit 1
fi
```

> ⭐ **教训：`参数文件生成了` ≠ `参数生效了`。** 必须验证参数真的到达了执行上下文。
> 呼应实验 03 里的同一条经验——那次是验证 "reducer 数是否真被指定"，这次是验证"参数是否真被拼进去"。

#### 坑 2：`GC overhead limit exceeded` —— 内存配置不通用（H3 → H9）

**失败特征（关键）**：`Map: 3  Reduce: 3  Cumulative CPU: 10.55 sec  HDFS Read: 21899877  HDFS Write: 0  FAIL`
**只读了 21.9MB 就死了**（3 个 map，每个 7MB），而**第 2 步读了 209MB 反而成功**。

诊断消息：
```
Task with the most failures(4):  task_..._m_000000
Diagnostic Messages for this Task:
Error: GC overhead limit exceeded
```

**根因**：步骤 3 按 `product_id, dt` 分组 → 分组组合可达 **14 万 × 31 ≈ 430 万**。map 端聚合要维护一个哈希表，若单个 map 跨读了多个日期分区，条目数上百万 → 撞上 9/27 调优压到的 `-Xmx410m` 堆。

**为什么第 2 步没事**：它按 `user_id, dt` 分组，每个用户每天只有几行，哈希条目数少得多。

**修复（四件事一起做）**：
```sql
SET mapreduce.map.memory.mb = 1024;      -- 512 → 1024
SET mapreduce.reduce.memory.mb = 1024;
SET mapreduce.map.java.opts = -Xmx820m;  -- 410m → 820m
SET mapreduce.reduce.java.opts = -Xmx820m;
SET hive.map.aggr.hash.percentmemory = 0.3;   -- map 端哈希最多占堆的 30%，超了退化落盘
SET mapreduce.input.fileinputformat.split.maxsize = 134217728;  -- 128MB 一个分片，摊薄单 map 哈希
```
**效果**：**637 秒失败 → 63 秒成功**（快 10 倍，因为不再 GC 空转）。

> ⭐ **最大的认知收获**：9/27 的内存调优**不是"调错了"，而是"不通用"**。
> 当时那套参数是为 **写入路径**（动态分区并发写）调的，压小容器换来了更多并发；而**聚合路径**的瓶颈是**单容器内存不够**，压小反而致命。
> **结论：调优参数必须按"作业类型"分别配，不能一套走天下。** 旧 DWS 脚本头部原本写着 `-Xmx768m`，我们统一压到 512/410 时把这条经验丢了。

#### 坑 3：`Error 10004` —— 字段不存在（H4）

```
SemanticException [Error 10004]: Invalid table alias or column reference 'user_session'
```
**根因**：`dwd_purchase_fact_di` 的字段是 `order_id / user_id / product_id / category_id / category_l1~l3 / brand / amount / pay_time / is_paid / dt` —— **没有 `user_session`**。它是"成交视角"的事实表，刻意不保留会话信息。
**修复**：去掉该字段（并**单独写了一个单表修复脚本**，没有重跑整个 DDL，避免连带 DROP 掉已跑出数据的三张表）。
**教训**：**写跨表 SQL 前先对着表结构核字段**，别凭印象写。

#### 坑 4（最值得记录）：漏斗不是漏斗（H5）

**原本的校验断言**：`view_uv >= cart_uv AND cart_uv >= purchase_uv`
**实测**：31 天里 **15 天违例**。

**逐段拆开验证后真相**：

| 检查项 | 结果 |
|---|---|
| 浏览 < 加购 的天数 | **0** |
| 浏览 < 购买 的天数 | **0** |
| **购买 > 加购 的天数** | **15 / 31** |
| 全月加购用户日 | 119,832 |
| 全月购买用户日 | **133,258**（比加购多 **11%**） |

**根因**：**"加购"和"购买"在用户层面不是包含关系**——用户可以**不进购物车直接购买**（从收藏直接下单、从商品页一键购买等）。
所以真正的漏斗是「**浏览 → 购买**」两环节；**加购是并行的另一条路径，不是购买的必经中间态**。

详细复盘见 6.5 节。

#### 坑 5（基础设施层面）：断点续跑

失败会把已经跑好的步骤白扔。本次给运行器加了 `START_FROM` 参数：

```bash
bash evt_run.sh 3     # 从第 3 步接着跑，保留已有 status.tsv
```
加上"跳过已完成步骤"的逻辑，本次**三次续跑**共省下约 5 分钟。

## 六、复盘：被证伪的假设（**本章最有价值**）

### 6.1 H2 —— "生成了配置" 不等于 "配置生效了"

**原本判断**：把调优参数写进 `setup.sql`，运行时就该带上。
**实测**：第 2 步 **2 秒**就报 `10096`——`setup.sql` 压根没被读取。
**为什么错**：我把"文件被创建"当成了"文件被使用"。运行器里 `setup.sql` 与分段 SQL 是**两个独立文件**，中间的拼接步骤我漏写了。
**修正后的认知**：

> **任何"配置类"动作，都必须验证它真的到达了作用点。**
> 具体做法：配置里放一个**可检索的标记**（如 `hive.exec.dynamic.partition.mode`），启动前 `grep` 一次，查不到就终止。
> 这和实验 03 里"用 `jobconf value of: 3` 验证 reducer 数真被指定"是**同一条方法论**。

### 6.2 H3 —— 调优参数是有适用范围的，不是"越省越好"

**原本判断**：9/27 把容器压到 512MB / `-Xmx410m` 是全局最优——小集群就该省着用。
**实测**：DWS 聚合步骤 637 秒后 `GC overhead limit exceeded`；**只读了 21.9MB 就死了**。
**为什么会错**：我用**一套参数**去应付**两类完全不同的作业**：

| 作业类型 | 真实瓶颈 | 容器该多大 |
|---|---|---|
| 写入（动态分区） | **并发写把 DataNode 压垮** | 压小换并发 ✅ 9/27 的做法对 |
| 聚合（大基数 GROUP BY） | **单容器内存不够** | 必须放大 ✅ 本次的做法对 |

**修正后的认知**：

> **"调优参数"必须绑定"作业类型"，不能绑定"集群规模"。**
> 而且**最该记的一条**：**别丢掉老配置里的经验**——旧 DWS 脚本头部本来就写着 `-Xmx768m`（作者标了 `-- ds-tuned`），是我们统一压到 512/410 时把这条经验抹掉了。**统一配置看起来整洁，实际是丢信息。**

### 6.3 H4 —— 我凭印象写 SQL

**原本判断**：交易主题要算"会话数"，于是写了 `COUNT(DISTINCT user_session)`。
**实测**：`Error 10004`，`dwd_purchase_fact_di` 没这个字段。
**为什么错**：我**没有对着表结构核字段**。而且这个错误本来是可以零成本避免的——`DESC table` 一秒钟就能看到。
**修正后的认知**：

> **跨表写 SQL 前，先 `DESC` 一遍所有涉及的表。** 尤其是**自己几天前设计的表**——最容易记错，因为"我以为我记得"。

### 6.4 H5 的前半段 —— 我把"校验"写成了"我以为的业务"

这一条见下节，因为它是本次**技术上最有价值**的发现。

### 6.5 ★ 漏斗不是漏斗：我的建模假设被真实数据推翻

**原本判断**（继承自所有数仓教程和旧链路的四环节漏斗）：
```
浏览 → 加购 → 下单 → 支付     每一步用户数都应递减
```

**实测（31 天真实数据）**：

| 检查项 | 结果 |
|---|---|
| 浏览 < 加购 的天数 | **0 / 31** |
| 浏览 < 购买 的天数 | **0 / 31** |
| **购买 > 加购 的天数** | **15 / 31** |
| 全月加购用户日 vs 购买用户日 | 119,832 vs **133,258**（购买**多 11%**） |

**为什么会错**：我把"加购"当成了"购买"的**必经中间态**。但在真实电商里，**用户可以完全不进购物车直接购买**（从收藏夹下单、商品页一键购买、活动页直接结算）。

所以加购**不是漏斗的一环，而是与购买并行的一条路径**：

```
        ┌──→ 加购 ──→ （可能最终购买，也可能放弃）
浏览 ───┤
        └──→ 直接购买          ← 这一条路径旧链路里根本不存在
```

**修正后的认知**：

> 1. **真正的用户级漏斗只有「浏览 → 购买」两环节**，这两个是严格的包含关系（0 违例）。
> 2. **加购率与购买转化率是两个独立指标，不能相乘当漏斗**。
> 3. **模拟数据永远暴露不了这个问题**——因为生成脚本是按"先加购后下单"的假设造的假数据，它只会**验证我的假设，不会挑战它**。
>
> ⭐ **这是"换真实数据集"这个决策最大的回报**：真实数据不仅能算出新指标，更能**推翻你自以为对的业务假设**。而这恰恰是面试里最容易被追问的地方——"你的漏斗为什么是四环节？"如果答不出业务依据，就说明只是照搬教程。

**顺带一个反直觉结论**（值得单独讲）：`cart_uv < purchase_uv` 并不意味着数据错，反而**说明数据是真实的**。如果一份"真实数据"算出来的漏斗完美单调，那更该怀疑它是不是被加工过。

### 6.6 事后回看：哪一条最接近踩坑边缘

**H3（内存配置不通用）。**

危险在于它**失败得很贵**：637 秒才失败，而且**失败信息藏在 task 的 Diagnostic Message 里**（`Error: GC overhead limit exceeded`），不在 `Caused by` 链里。如果只按实验 03 的经验去 grep `Caused by`，会**什么都搜不到**，很容易误判成"环境问题"。

**这次的定位靠的是一个反常识的信号**：`CPU 只用了 10.55 秒、HDFS 只读了 21.9MB`——**一个本该读 620MB 的作业只读了 21.9MB 就失败了**。这个数量级的不匹配直接把方向从"数据/IO 问题"扭转到"JVM 内存问题"。

> 📌 **可复用的判断法**：作业失败时，先看 `HDFS Read` 和 `Cumulative CPU` 的**量级是否符合预期**。
> - Read 远小于输入量级 → 死得很早，多半是**初始化/内存**问题
> - Read 正常但 Write = 0 → 算完了写不出去，是**写入**问题（实验 03）
> - Read 正常、Write 正常但耗时长 → 是**搬运/倾斜**问题

### 6.7 本次的自我批评

1. **两个失误本可避免**：`setup.sql` 没拼接、字段没核对——都属于"动手前少花 1 分钟检查，事后花 20 分钟排查"。
2. **旧配置里的经验被我抹掉了**：旧 DWS 脚本原本写着 `-Xmx768m`，我们统一压到 512/410 时没意识到这是**按作业类型分层**的设计。
3. **校验断言写成了业务假设**：`view ≥ cart ≥ purchase` 这条断言我**没有先向数据求证**就写成了硬校验，导致 15 天"违例"需要二次排查。

## 八、面试官可能会追问的问题

**Q1：你为什么不像旧脚本那样每天写一条 INSERT，而要用动态分区？**
A：因为**规模不可维护**。旧脚本 5 天写了 5 遍完全相同的 SQL（只是 `PARTITION (dt='...')` 不同），扩展到 31 天就要复制 31 遍。
改成 `PARTITION (dt)` + `GROUP BY dt` 后，**31 天只要 1 条语句**。
代价是动态分区写入是并发写多目录，对 DataNode 压力大——这正是实验 03 里踩过的坑，所以配套加了 `hive.optimize.sort.dynamic.partition=true`（排序后串行写）。

**Q2：DAU 里的"新增用户"和"回流用户"怎么算的？**
A：用窗口函数**一次扫描**算出两个辅助列：
- `MIN(dt) OVER (PARTITION BY user_id)` = 该用户**首次活跃日** → 等于当天就是"新增"
- `LAG(dt) OVER (PARTITION BY user_id ORDER BY dt)` = 该用户**上一次活跃日** → 正好是昨天就是"连续活跃"，不是昨天就是"回流"

旧做法是每一天 LEFT JOIN「历史所有天」+「昨天」，复杂度 O(n²)。新做法 O(n)。
而且只有真实数据才能算出真实的新增/回流——**旧链路是模拟数据，每天都是同一批用户，这两个指标恒为 0**，等于白算。

**Q3：这个 `GC overhead limit exceeded` 报错，你怎么定位的？**
A：靠**量级不匹配**。失败的作业 `Cumulative CPU` 只有 10.55 秒、`HDFS Read` 只有 21.9MB——**一个本该读 620MB 的作业只读了 21.9MB 就失败了**，说明它死得极早，问题在初始化/内存，不在数据。
然后去 task 的 Diagnostic Message 里找到 `Error: GC overhead limit exceeded`。
**注意这一点**：这个错误**不在 `Caused by` 链里**，只在 task 诊断消息里。如果只按经验 grep `Caused by`，会什么都搜不到。
根因是分组基数太大（`product_id × dt` 最多 430 万组合），map 端聚合哈希撞上了 `-Xmx410m` 的堆。

**Q4：为什么之前把容器调成 512MB，这次又要调回 1024MB？是不是之前的调优白做了？**
A：**不是白做，是"不通用"。** 之前的调优解决的是**写入路径**的问题——6 个 reducer 并发写 31 个动态分区把 DataNode 压垮，压小容器是为了换更多并发。
这次的瓶颈在**聚合路径**——单个容器的堆不够，压小反而致命。
**所以正确的做法是按"作业类型"分层配置，而不是一套参数全局统一。** 而且我要反省一点：旧 DWS 脚本头部原本就写着 `-Xmx768m`，是我们统一压到 512/410 的时候，**把这条按类型分层的经验丢掉了**。

**Q5：你怎么证明这批数据是算对的，而不是"跑通了就行"？**
A：做了三层校验，其中**第二层是硬证据**：

| 层 | 方法 | 结果 |
|---|---|---|
| 一 | 行数与分区数 | 8 张表全部 31 个分区；TopN 表 1,550 行 = 31×50 ✅ |
| **二** | **交叉对账** | **商品 / 类目 / 交易 / DWD事实表 四条完全独立的计算路径，GMV 全部 = `5.75759965E7`** ✅ |
| 三 | 方向性 | 浏览<加购 0 天、浏览<购买 0 天、复购>总买家 0 天 ✅ |

第二层是重点：**四条路径的维度不同、算法不同、表不同，但算的是同一批 purchase 事件**。任何一条路径写错，GMV 就不会收敛到同一个数上。

**Q6：你说的"聚合不可逆"是什么意思？**
A：**`SUM` 可以再 `SUM`，但 `COUNT(DISTINCT)` 不能。**
具体到本次：类目层的"去重买家数"**不能**从商品层 `SUM(buyer_cnt)` 得到——同一个用户买了 A、B 两个商品，在商品层各算 1 次，加总就变成 2，**去重语义被破坏**。
所以类目层的买家数必须**回 DWD 明细重新 `COUNT(DISTINCT user_id)`**。这是数仓开发里最常见的错误之一。

**Q7：你的转化漏斗是几个环节？**
A：**两个：浏览 → 购买。**
我原本按教程写成三环节（浏览→加购→购买）并写了单调性校验，结果 **31 天里 15 天"违例"**。拆开逐段验证后发现：
- 浏览 ≥ 加购：**0 违例**
- 浏览 ≥ 购买：**0 违例**
- **购买 > 加购：15 天**（全月购买用户日 133,258 比加购用户日 119,832 多 11%）

根因是**用户可以完全不进购物车直接购买**，所以**加购不是购买的必经中间态，而是与购买并行的一条路径**。
**这个错误恰恰说明了换真实数据集的价值**——模拟数据是按"先加购后下单"的假设造的，它只会验证我的假设、不会挑战它。

**Q8：这次改造会破坏现有的演示大屏吗？**
A：**不会**，这是刻意的设计。新表用**全新语义名**（`dws_user_event_day`、`ads_active_user_day` 等）与旧表**并存**，大屏读的还是旧表。
而且全程**只读 DWD、只写新表**，旧链路零改动。
等新链路全绿、大屏切过去并验证通过后，再统一决定旧表去留——**先并行、后切换，任何时候都能回退**。

## 附录：本次涉及的概念速查（零基础）

| 名词 | 一句话解释 |
|---|---|
| **DWS** | 按主题（用户/商品/类目）轻度汇总的宽表层 |
| **ADS** | 直接给报表和大屏用的指标层 |
| **动态分区** | 写入时根据数据内容自动创建分区目录（本项目一次写 31 天） |
| **静态分区** | 分区值写死在 SQL 里（旧脚本的 `PARTITION (dt='2026-08-20')`） |
| **窗口函数** | 在不折叠行的前提下做跨行计算（如 `MIN(...) OVER (PARTITION BY ...)`） |
| **`LAG` / `ROW_NUMBER` / `MIN OVER`** | 取上一行 / 编号 / 分组内最小值 |
| **聚合不可逆** | `SUM` 可再 `SUM`，但 `COUNT(DISTINCT)` 不能——去重语义会被破坏 |
| **`GC overhead limit exceeded`** | JVM 把 98% 时间花在垃圾回收却收不回 2% 堆，等于"堆被撑爆了" |
| **容器（Container）** | YARN 分配给一个任务的 CPU + 内存配额，超了会被杀 |
| **`-Xmx`** | JVM 堆内存上限 |
| **map 端聚合哈希** | map 阶段先本地汇总以减少传输量，它要占内存维护一个哈希表 |
| **交叉对账** | 用不同的计算路径算同一个指标，看结果是否收敛 |
| **断点续跑** | 失败后从失败步骤继续，不重做已成功的步骤 |
