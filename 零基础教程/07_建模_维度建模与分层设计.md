# 07 · 维度建模与分层设计 ★

> **这章是全课最重要的一章。**
>
> 会写 SQL 的人很多。真正区分水平的是这两件事：
> **① 你能不能说清"这张表的一行代表什么"；② 你定的口径能不能经得起别人追问。**
>
> 这两件事都叫**建模**。它决定了你这个项目是"一堆 SQL"还是"一个数仓"。

---

## 一、先讲粒度（Grain）—— 建模的第一件事，也是最容易做错的事

### 1.1 什么是粒度

**粒度 = 这张表的一行代表什么。**

用一句完整的话说出来，比如：

| 表 | 粒度（一句话） |
|---|---|
| `ods_event_log_di` | 一行 = 一条原始用户行为事件 |
| `dwd_event_log_di` | 一行 = 一条清洗后的用户行为事件 |
| `dwd_purchase_fact_di` | 一行 = 一笔成交 |
| `dim_product` | 一行 = 一个商品 |
| `dws_user_event_day` | 一行 = **一个用户一天** |
| `dws_product_event_day` | 一行 = **一个商品一天** |
| `dws_trade_day` | 一行 = **一天** |
| `ads_top_product_day` | 一行 = **一天的一个排名位次** |

> 📌 **本项目对照**：案例项目给全部 **30 张表**都补了统一格式的粒度声明，写在表注释里，
> 格式是 `【链路】新·真实 ｜ 【粒度】用户 × 天 ｜ 说明…`。
> 效果是 **`DESC 表名` 一打就能看到它一行代表什么**，不用去翻设计文档（文档会过期，注释跟着表走）。

### 1.2 为什么说不清粒度就一定会出事

**真实事故**：某个"类目买家数"指标，开发同学是从商品层 SUM 上来的。

```
商品层：  商品A 买家数 = 1（用户 u1 买了）
         商品B 买家数 = 1（还是用户 u1 买的）
加总后：  这个类目买家数 = 2
实际：    这个类目只有 u1 一个人买 → 应该是 1
```

**根因**：同一个用户在类目下买了两个商品，被算了两次。

**这类错误的共同特征**：
- **不报错**。数字是错的，但看起来很合理
- 只有交叉对账（换个算法重算一遍）才会发现
- 发现时，报表已经给老板看了三个月

### 1.3 一条铁律：聚合不可逆

| 聚合方式 | 能不能跨层加总 | 例子 |
|---|---|---|
| `SUM` / `COUNT` | ✅ 可加 | 金额、次数 |
| `COUNT(DISTINCT)` | ❌ **不可加** | 去重用户数、去重买家数 |
| `AVG` | ❌ 不可加（要带权重重算） | 平均客单价 |
| `MAX` / `MIN` | ✅ 可加（取 max） | 最早/最晚时间 |
| 比率 | ❌ 绝对不能加 | 转化率、复购率 |

> **规则：只要上层需要 `COUNT(DISTINCT)`，就必须回到能拿到明细的那一层重算，不能从中间层加总。**

> 📌 **本项目对照**：`dws_category_event_day` 的 `buyer_cnt` 是**回 `dwd_event_log_di` 明细重算**的，
> 不是从商品层加的。案例项目的表设计文档里把这一条单独列为"口径易错点 #1"。

## 二、分层：四层各自的职责与判定标准

### 2.1 四层一览

```
ODS  贴源层      原样落地，一个字不改              ← "外面给我什么，我就存什么"
  ↓
DWD  明细层      清洗、解析、归一，产出干净的明细     ← "全公司唯一的口径来源"
  ↓            + DIM 维度层（商品维、时间维…）
DWS  汇总层      按主题做中度汇总，供多方复用        ← "半成品，谁都能拿去接着做"
  ↓
ADS  应用层      一个需求一张表，直接给报表/大屏      ← "成品，装盘上桌"
```

### 2.2 每一层的判定标准（**用这个自查，别凭感觉**）

| 层 | ✅ 应该 | ❌ 不应该 |
|---|---|---|
| **ODS** | 字段与源系统一致；保留原始脏数据；只做加分区 | 不做清洗、不改名、不删行、不做类型转换 |
| **DWD** | 去重、解析时间、拆字段、空值归一；**保留最细粒度** | 不做业务聚合、不丢明细 |
| **DIM** | 一行一个实体；属性稳定 | 不放事实（金额/次数） |
| **DWS** | 按主题（用户/商品/类目/交易）聚合到"主题 × 时间" | 不做非常专用的指标（那是 ADS 的活） |
| **ADS** | 一个业务问题一张表；字段就是报表要显示的字段 | 不给别的 ADS 当输入（避免 ADS 依赖 ADS） |

### 2.3 一条重要的纪律：不许跨层消费

```
❌ 大屏直接读 DWS     （把应用和中间层绑死，中间层一改大屏就崩）
❌ ADS 直接读 ODS     （绕过了全部清洗，口径必然打架）
✅ 大屏 → ADS → DWS/DIM → DWD → ODS
```

> 📌 **本项目对照**：这是案例项目**真实违反过又被修正**的一条。
> 大屏的类目图与交易图原本直接读 DWS，违反"应用层只消费 ADS"。
> 补了两张 ADS 表（`ads_category_day` / `ads_trade_day`）才改正。
> **验证方式值得学**：改完之后把新旧导出文件**逐字节比对**，确认只差时间戳——
> 证明新 ADS 确实是从 DWS 正确派生的，没有改数。**改动要有可验证的判据。**

## 三、维度建模：事实表与维度表

### 3.1 两类表

| | **事实表（Fact）** | **维度表（Dimension）** |
|---|---|---|
| 装什么 | **发生了什么**（业务动作的记录） | **谁/什么/在哪**（描述性属性） |
| 典型字段 | 数值型：金额、次数、时长 | 字符串：名称、类目、品牌、日期 |
| 行数 | 千万 ~ 百亿 | 几百 ~ 几十万 |
| 变化 | 不断增加（每天新数据） | 相对稳定 |
| 例子 | `dwd_purchase_fact_di`（一笔成交一行） | `dim_product`（一个商品一行） |

**一句话**：**事实表记"动作"，维度表记"动作的参与者是谁"。**

### 3.2 星型模型

```
                  dim_date
                      │
                      │
dim_product ────► fact_purchase ◄──── dim_user
                      │
                      │
                  dim_brand
```

中间是事实表，四周是维度表，像一颗星。

**为什么这样设计**：
- 事实表只存 **ID**（product_id、user_id、dt），不存商品名、品牌名
- 名字/属性放在维度表里，靠 ID 关联
- **好处**：商品改名了，只改维度表一行，历史事实不用动；事实表体积小（只存 ID）

> ⚠️ **实践中常做的妥协**：DWS 层会适度**冗余**几个常用维度字段（比如把 `category_l1` 直接写进汇总表），
> 避免每次查询都要 JOIN。**这叫"宽表"，是用空间换时间的正常做法**，
> 但要清楚：冗余的字段来自维度表，且**维度变更时它不会自动跟着变**。

### 3.3 维度建模四步（照着做就能设计出表）

> 这是 Kimball 的经典方法论，四步有**严格顺序**：

| 步骤 | 做什么 | 案例（电商行为分析） |
|---|---|---|
| **① 选业务过程** | 你要分析什么动作？ | 用户的浏览/加购/购买行为 |
| **② 定粒度** | ★ 一行代表什么？（**最重要，也最容易被跳过**） | 一行 = 一条事件 |
| **③ 定维度** | 从哪些角度看它？ | 时间、用户、商品、类目、品牌 |
| **④ 定事实** | 要度量什么？ | 事件次数、金额、**去重用户数** |

**为什么②先于③④**：不知道"一行是什么"，就无法判断哪些维度能加、哪些度量能算。
粒度定粗了，后面想要的明细永远要不回来；粒度定细了，还能往上聚合。**宁细勿粗。**

## 四、指标设计：三类指标与三种可加性

### 4.1 指标的三层

| 类型 | 定义 | 例子 |
|---|---|---|
| **原子指标** | 不可再拆的最基本度量 | 成交金额、购买次数 |
| **派生指标** | 原子指标 + 时间/维度限定 | "**2024年10月**手机类目的成交金额" |
| **衍生指标** | 由多个指标算出 | 转化率 = 购买人数 / 浏览人数；客单价 = GMV / 订单数 |

**设计原则**：**原子指标要少而稳，派生指标随便加。**
原子指标一旦改定义，所有上层报表都要改。

### 4.2 口径必须写成"可执行的句子"

❌ 坏写法：`活跃用户数`
✅ 好写法：`当天产生过任意事件（view/cart/purchase）的去重用户数，按 dt 统计`

> 📌 **本项目对照**：案例项目把 DAU 拆成四个口径，一次扫描全算出来：
> `dau`（当天有任意事件）、`new_dau`（首次出现日 = 当天）、
> `active_dau`（上次活跃日 = 昨天）、`wakeup_dau`（非首次且上次活跃不是昨天）。
> 这四个加起来等于 `dau`，是对得上账的。**能拆成互斥且完备的子集，才说明口径定义清楚了。**

## 五、维度表设计：两个真实难题

### 5.1 难题一：同一个商品，属性不一致怎么办

**现象**：源数据里 `product_id=123` 的商品，有的事件里 brand 是 `apple`，有的是空，类目也不同。
（真实数据里确实存在：同一商品在不同时间的属性记录不一致。）

❌ 错误做法：`SELECT DISTINCT product_id, brand, category...` —— 会得到多行，粒度被破坏（"一行一个商品"失效）。

✅ 正确做法（案例项目的解法）：

```sql
-- 1) 先数出每个"属性组合"出现了多少次
-- 2) 取出现次数最多的那组；并列时取日期更近的
ROW_NUMBER() OVER (
  PARTITION BY product_id
  ORDER BY attr_cnt DESC, dt DESC      -- attr_cnt = 该属性组合的出现次数
) AS rn
-- 3) 取 rn = 1
```

**思路可以复用到很多地方**：当源数据对一个实体的描述有冲突时，
**不要随便挑一个，要定义一条明确的"选哪个"的规则，并把它写进注释。**

### 5.2 难题二：时间维表怎么造

时间维（`dim_date`）是数仓里最标准的维度表：一行一天，预先生成好，永远不用来回算。

```sql
-- Hive 没有 sequence()，用 posexplode + repeat 造序列
INSERT OVERWRITE TABLE gmall.dim_date
SELECT
  DATE_ADD('2019-01-01', i)                          AS dt,
  YEAR(DATE_ADD('2019-01-01', i))                    AS year,
  MONTH(DATE_ADD('2019-01-01', i))                   AS month,
  DAY(DATE_ADD('2019-01-01', i))                     AS day,
  CASE WHEN DAYOFWEEK(DATE_ADD('2019-01-01', i)) IN (1, 7)
       THEN 1 ELSE 0 END                             AS is_weekend
FROM (SELECT posexplode(split(repeat(',', 364), ',')) AS (i, v)) t;
```

**两个必须记住的点**：
1. Hive 没有 `sequence()`（那是 Spark SQL 的函数）
2. **Hive 的 `dayofweek()` 是 1=星期日**，不是周一！做星期维度必须换算

> 📌 **本项目对照**：`dim_date` 365 行，覆盖数据范围 31/31 天（**覆盖率要验**，别造完不管）。

## 六、缓慢变化维（SCD）：知道有这回事

**问题**：商品的类目从"手机"调到"智能设备"了，历史订单要不要跟着改成新类目？

| 类型 | 做法 | 适用 |
|---|---|---|
| **SCD Type 1** | 直接覆盖，历史也变 | 纠错（原来填错了） |
| **SCD Type 2** | **加一行新版本**，带 `生效日期/失效日期/是否当前` | 要保留历史视角（最常用） |
| SCD Type 3 | 加一列存"旧值" | 只看一次变化 |

> ⚠️ **诚实标注**：案例项目**没有实现 SCD**——它的 `dim_product` 取的是"出现最多的属性组合"，
> 是一个**快照式维度**。这是本项目与成熟数仓的差距之一。
> 面试被问到"维度变化了怎么办"，你应该**知道概念并诚实说当前做法**，
> 而不是吹牛说做了拉链表。

## 七、命名规范（看起来琐碎，其实很影响协作）

案例项目用的规范，可直接抄：

```
<层前缀>_<主题>_<粒度后缀>

层前缀：  ods_ / dwd_ / dim_ / dws_ / ads_ / tmp_
粒度后缀： _di（日增量 day increment） / _day（按天汇总） / _df（日全量）

例：
  ods_event_log_di        原始层 · 事件日志 · 日增量
  dwd_purchase_fact_di    明细层 · 购买事实 · 日增量
  dim_product             维度 · 商品
  dws_user_event_day      汇总层 · 用户事件 · 按天
  ads_active_user_day     应用层 · 活跃用户 · 按天
```

**原则**：**看表名就知道它在哪一层、讲什么主题、一行代表什么范围。**
做到这一点，协作时你就不用每次都去问"这张表是啥"。

> 📌 还有一个实战教训：**新链路不要直接复用旧表名**。
> 案例项目另起 `dws_user_event_day` 而不是覆盖 `dws_user_day`，
> 因为旧表**正在被大屏使用**，同名覆盖会让大屏当场断掉。
> **并存 → 验证通过 → 再决定旧表去留**，这个顺序不能反。

## 八、建模自检清单（设计完对着打勾）

| # | 检查项 | 不过会怎样 |
|---|---|---|
| 1 | 每张表都能一句话说清粒度 | 没人敢用你的表 |
| 2 | 粒度声明写进了**表注释** | 三个月后你自己也忘了 |
| 3 | 上层需要的 `COUNT(DISTINCT)` 都回到了明细层重算 | 数字虚高且不报错 |
| 4 | DWD 保留了最细粒度 | 想要明细时要不回来 |
| 5 | 维度表里没有事实（金额/次数） | 粒度和语义混乱 |
| 6 | 应用层只消费 ADS | 应用和中间层绑死 |
| 7 | 时间维覆盖了数据范围（**要验**） | JOIN 出来一堆 NULL |
| 8 | 空值有统一兜底（`'unknown'` 而不是 NULL） | `GROUP BY` 结果多出一行 NULL，且不同人处理不一样 |
| 9 | 每张表都能重跑（幂等） | 重跑一次数据翻倍 |
| 10 | 指标口径写成了可执行的句子 | 两张报表对不上，谁也说服不了谁 |

## 十、常见坑

| 现象 | 根因 | 解法 |
|---|---|---|
| 两个报表数字对不上 | 口径定义不一致（空值/去重/时间边界） | 口径写成可执行句子；**统一在 DWD 层处理** |
| 去重数加总后虚高 | `COUNT(DISTINCT)` 不可加 | 回明细重算 |
| JOIN 之后行数变多 | 维度表不是"一行一实体"（有重复） | 维度表必须先保证粒度唯一 |
| 维度字段全是 NULL | 关联键类型不一致（string vs bigint）或不匹配 | `DESC` 两边类型；查匹配率 |
| 重跑一次数据翻倍 | 用了 `INSERT INTO` 而不是 `INSERT OVERWRITE` | 离线数仓**一律 OVERWRITE**（幂等） |
| 表越来越多，没人敢删 | 没有粒度声明，不敢判断有没有人用 | 补粒度 + 注释；下线前先改名观察 |

  - `dim_product` → 一行 = **一个商品**
- 加分项：案例把粒度写进**表注释**（`desc` 一打就能看到），因为文档会过期、注释跟着表走

**2. 为什么不能跨层加总**
- 例子：用户 u1 买了商品 A 和商品 B → 商品层各算 1 个买家 → 加总 = 2，**实际只有 1 个买家**
- 规则：`SUM/COUNT` 可加；**`COUNT(DISTINCT)`、`AVG`、比率不可加**
- 做法：只要上层需要去重数，就**回能拿到明细的那一层重算**
  （案例 `ads_category_day.buyer_cnt` 回 `dwd_event_log_di` 重算）

**3. 四步 + 为什么粒度在前**
- ① 选业务过程 → ② **定粒度** → ③ 定维度 → ④ 定事实
- 粒度先于维度：**不知道"一行是什么"，就判断不了哪些维度能加、哪些度量能算**
- 附原则：**宁细勿粗**——细的能往上聚合，粗的永远回不去

**4. 事实表 vs 维度表**
- 事实表：记**动作**（金额、次数），行数大、只存 ID
- 维度表：记**参与者属性**（名称、类目），行数小、相对稳定
- 错误例子：把"商品累计销量"放进 `dim_product` —— 事实进了维度表，粒度和语义双重混乱

**5. 应用层只消费 ADS**
- 规范：**大屏/BI → ADS → DWS/DIM → DWD → ODS**，应用层不直接读 DWS/DWD/ODS
- 违反的后果：**应用和中间层绑死**，中间层一改应用就崩
- 案例真实违反过（大屏类目图/交易图直接读 DWS），补了 `ads_category_day` / `ads_trade_day`；
  **验证方式是新旧导出文件逐字节比对**

**6. 维度属性冲突**
- **不能"随便取一个"**，要定义一条明确的"选哪个"规则，并写进注释
- 案例规则：按属性组合计数 → 取**出现次数最多**的那组 → 并列时取**日期更近**的
  （`ROW_NUMBER() OVER (PARTITION BY product_id ORDER BY attr_cnt DESC, dt DESC)`）

**7. SCD Type 2**
- 做法：加**一行新版本**，带 `生效日期 / 失效日期 / 是否当前`，保留历史视角
- 案例**没有实现**（`dim_product` 是快照式维度，取"出现最多的属性组合"）
- 诚实回答：**"当前是快照式；如果要按'当时的口径'做分析，我会用 Type 2 拉链表"**
  ——被问到不会的东西，说清概念 + 说清现状，比硬吹做了要好
</details>
