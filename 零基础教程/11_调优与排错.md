# 11 · 调优与排错

> **这章解决什么**：任务跑挂了、跑得慢、或者"看起来挂了其实没挂"时，你往哪个方向想。
>
> **这是区分"会跑"和"能扛事"的一章。** 前面所有章节教你把事情做对，这章教你**做错时怎么办**。
> 面试里，"你遇到过什么故障、怎么定位的"是拉开差距的问题。

---

## 一、调优的第一原则：先找瓶颈，不要猜

**错误做法**：任务慢 → 加内存 → 还是慢 → 加并行度 → 还是慢 → 重启。

**正确做法**：先回答三个问题。

### 1.1 三个必问

| 问题 | 怎么回答 |
|---|---|
| **① 它死在哪个阶段？** | 看 YARN 的 Counter：`HDFS Read` / `HDFS Write` / `CPU` / `GC time` |
| **② 它慢在哪个阶段？** | 看 8088 页面：map 阶段多久、reduce 阶段多久 |
| **③ 是"慢"还是"卡"？** | 慢 = 一直在推进；卡 = 进度不动（在等资源 / 等 IO / 死锁） |

### 1.2 ★ 判断法则：这个作业"囤不囤数据"

> **这是案例项目最值钱的一条经验，来自一次 637 秒失败 → 63 秒成功的调优。**

**判断依据不是"作业叫什么类型"，而是「这个作业有没有要同时装住大量数据的结构」。**

| 作业特征 | 容器内存 | 为什么 |
|---|---|---|
| **不囤数据**（写入型 / 清洗型，边读边写） | **可以压小** | 瓶颈在磁盘 IO，压小不会直接失败 |
| **囤数据**（大基数 `GROUP BY` / `DISTINCT` / 非 MapJoin / 全表 `ORDER BY`） | **必须放大** | 容器小**必然**失败 |

**实测数据**：

```
作业：GROUP BY product_id, dt  （组合数达 430 万）
配置 A：容器 512MB / -Xmx410m  → GC overhead limit exceeded，跑了 637 秒后失败
配置 B：容器 1024MB / -Xmx820m → 63 秒成功
```

**物理原因**：`GROUP BY` 要在内存里维护一张哈希表（430 万个键）。
内存不够 → JVM 不停 GC → 98% 时间都在 GC → JVM 抛 `GC overhead limit exceeded`。

> ⚠️ **一个反面的教训**：案例项目旧脚本里本来写着 `-Xmx768m`（还标了 `-- ds-tuned`），
> 后来被"统一压到 512/410"时**抹掉了按类型分层的设计**。
> **统一配置看起来整洁，实际是丢信息。**

### 1.3 参数清单（知道每个在管什么）

```sql
-- 容器能申请多少内存（不能超过节点容量！）
SET mapreduce.map.memory.mb = 1024;
SET mapreduce.reduce.memory.mb = 1024;

-- JVM 堆上限（一般设为容器的 0.8 左右，留 20% 给堆外）
SET mapreduce.map.java.opts = -Xmx820m;
SET mapreduce.reduce.java.opts = -Xmx820m;

-- reduce 个数（输出文件大小 ≈ 每个 reduce 1~2 个块）
SET mapreduce.job.reduces = 6;

-- 小表自动 map-join（避免大表 JOIN 的 shuffle）
SET hive.auto.convert.join = true;
SET hive.mapjoin.smalltable.filesize = 25000000;   -- 25MB 以下算小表

-- 无依赖阶段并行跑
SET hive.exec.parallel = true;
```

> ⚠️ **硬约束**：案例集群 `yarn.nodemanager.resource.memory-mb=2048`
> → **单个容器最多 2048MB**。你调不出比节点容量更大的容器。
> 调之前先确认：`yarn node -list` 里的容量是多少。

## 二、数据倾斜：90% 的"卡在 99%"都是它

### 2.1 现象

- 大部分任务几秒完成，**个别 reduce 跑几十分钟**
- 进度条卡在 99% 不动
- 或者：**大多数 reduce 输出几 KB，某一个输出几 GB**

### 2.2 定位

```sql
-- 先猜：哪个 key 特别大？
SELECT category_l1, COUNT(1) AS cnt
FROM gmall.dwd_event_log_di
GROUP BY category_l1
ORDER BY cnt DESC
LIMIT 20;
```

如果某几个 key 占了绝大部分（比如 `unknown` 占 31.9%），就是倾斜。

### 2.3 解法（按优先级）

| 解法 | 做法 | 适用 |
|---|---|---|
| **① 过滤掉异常 key** | `WHERE category_l1 <> 'unknown'` | 脏数据造成的倾斜 |
| **② 两阶段聚合** | 先给 key 加随机前缀局部聚合，再去前缀全局聚合 | 大基数聚合型倾斜 |
| **③ map-join** | 小表广播，不走 shuffle | JOIN 型倾斜 |
| **④ 单独处理热点 key** | 热点 key 走一条路径，其余走另一条，最后 UNION | 极少数超级热点 |

**两阶段聚合示例**：

```sql
-- 原写法（倾斜）
SELECT key, COUNT(1) FROM t GROUP BY key;

-- 加盐两阶段
SELECT key, SUM(cnt) FROM (
  SELECT CONCAT(key, '_', CAST(FLOOR(RAND()*10) AS STRING)) AS salted_key,
         SUBSTR(salted_key, 1, INSTR(salted_key,'_')-1)      AS key,
         COUNT(1) AS cnt
  FROM t
  GROUP BY CONCAT(key, '_', CAST(FLOOR(RAND()*10) AS STRING))
) x
GROUP BY key;
```

## 三、排错方法论：四条纪律

### 3.1 纪律一：用外部判据，不用状态字段

| ❌ 不算证据 | ✅ 算证据 |
|---|---|
| `systemctl is-active xxx` = active | 端口真的在监听：`ss -lntp \| grep 10000` |
| 进程存在 | **发一次真实查询并拿到结果** |
| 调度界面显示"已停止" | 数据面确认：`ps` + `yarn application -list` |
| HDFS 报 `3 datanodes running` | `dfsadmin -report` 看 `Live datanodes` 且**真的读写一次** |

> 📌 **真实案例**：HS2 被标记 `active` 后**还要 50 秒**才真正监听端口。
> 只看 `is-active` 的人会在前 50 秒里反复重启服务，把问题搞得更复杂。

### 3.2 纪律二：控制面与数据面分开验证

调度系统（控制面）说成功/停止，**不等于**数据真的产出了/停了。
（第 09 章那个"停了但 beeline 跑了 3 天"的事故。）

```bash
# 控制面：调度 UI 说 SUCCESS
# 数据面（必须自己查）：
SELECT COUNT(1) FROM 目标表;                 # 行数对不对
SELECT COUNT(DISTINCT dt) FROM 目标表;        # 分区对不对
ps -ef | grep "[j]dbc:hive2"                 # 有没有残留进程
```

### 3.3 纪律三：退出码先于日志文本

| 退出码 | 含义 | 第一反应 |
|---|---|---|
| **0** | 成功 | — |
| **1** | 一般错误 | 看日志 |
| **2** | 用法/语法错误 | 看 SQL |
| **143** | **SIGTERM（被主动停止）** | **别找 bug，先查谁停的** |
| **137** | **SIGKILL（常被 OOM killer 杀）** | **查内存** |

> 📌 **真实教训**：案例项目有一次日志尾部看起来像 SQL 报错（有 `Error` 字样），
> 实际退出码是 143 —— **是被人主动停的**。
> 如果先看日志，会往完全错误的方向排查。

### 3.4 纪律四：错误的"原因"比错误的"现象"更危险

> 现象错了 → 你照做会失败 → 立刻能发现 → 改掉就行。
> 原因错了 → 你带着错误的世界观去排查所有其他问题 → **永远发现不了**。

**写原因时必须能回答：「我怎么证明这个因果？」**

举例：

| 说法 | 能不能证明 | 判断 |
|---|---|---|
| "任务失败是因为网络抖动" | 你有丢包的证据吗？ | ❌ 猜的 |
| "失败是因为容器内存超限"（附 YARN Diagnostics 里 `beyond memory limits` + 容器配置值） | ✅ | 可信 |
| "DS 显示只注册了 1 个 worker" | 你用什么数的？`grep -c "server-"` 是错的（见下） | ⚠️ 方法本身可能是坏的 |

## 四、★ 会让你得出"看起来很正式的错误结论"的诊断手法

这一节列出案例项目**真的被骗过**的四种手法。它们共同的特点是：
**输出看起来很规整、很有说服力，但答案是错的。**

### 4.1 `jps` 返回空 ≠ 进程不存在

lrh-1 上由 **root**（systemd）启动的 JVM（含 DS 全部服务）**不在 `lrh` 用户的 `hsperfdata` 目录里**，
`jps -l` 会返回空。

```bash
# ❌ 坏判据
jps -l | grep MasterServer        # 返回空 → 你以为 DS 没跑

# ✅ 真判据
ps -ef | grep "[d]olphinscheduler"
ss -lnt | grep -E "5678|12345"
```

### 4.2 用 `grep` 数 `ps` 的输出会虚高

**你这条命令自身的命令行也会被 `ps` 算进去。**

```bash
# ❌ 数出 MasterServer=3，实际是 0
ps -ef | grep MasterServer | wc -l

# ✅ 用方括号打断字面量
ps -ef | grep "[M]asterServer" | wc -l
```

### 4.3 ZK 里数注册节点，别用 `grep -c`

DS 3.1.8 的注册节点名是 `ip:port`（**不是** `server-xxxxx`），
而 `zkCli.sh` 的 `ls` **把整个列表打在一行** → `grep -c` 数的是**行数**，无论几个节点都返回 1。

```bash
# ✅ 正确数法
... | grep "^\[" | tr ',' '\n' | grep -c ':'
# ✅ 更优：走 API，拿结构化数据
curl -s http://lrh-1:12345/dolphinscheduler/monitor/workers
```

### 4.4 别用 `uptime` / `ps lstart` 推因果

虚拟机"开机 → 挂起 → 多日后恢复"时，**墙钟会跳几天**，
但 `/proc/uptime` 不含挂起时间 → `uptime` 说"up 33 min"、`ps` 把所有进程启动时间往后推了 3 天。

```bash
# ✅ 判"挂起 vs 真重启"要看 boot 区间
journalctl --list-boots
```

## 五、报错对照表（按你看到的字面量查）

### 5.1 Hive / SQL

| 报错 | 根因 | 解法 |
|---|---|---|
| `Error 10096` | 动态分区没开 `nonstrict` | 补 4 行 SET（第 06 章 §4.1） |
| `Error 10004` | 引用了不存在的表/列 | **跨表写 SQL 前先 `DESC` 所有涉及的表** |
| `Error 10011 Invalid function sequence` | 用了 Spark 专有函数 | 换 Hive 写法 |
| `SemanticException ... rows` | `rows` 是保留字 | 改别名（用 `row_cnt`） |
| 中文注释变 `?` | 元数据库字符集 latin1 | 元库改 utf8mb4；客户端加 `--default-character-set=utf8mb4` |
| 语句静默返回空 | stderr 被丢掉了 + 用了保留字 | **别丢 stderr** |

### 5.2 执行 / 资源

| 报错 | 根因 | 定位方法 |
|---|---|---|
| `GC overhead limit exceeded` | 内存不够，98% 时间在 GC | ⚠️ **它不在 `Caused by` 链里**，只在 task 的 Diagnostic Messages。靠量级不匹配判断 |
| `Container killed ... exceeding memory limits` | 容器用量超申请值 | 调大 `memory.mb` 和 `-Xmx` |
| `beyond virtual memory limits` | 虚拟内存超限 | 虚拟机环境设 `vmem-check-enabled=false` |
| `Exit code 137` | OOM 被杀 | 查内存 |
| `Exit code 143` | 被人停止 | 查谁停的，不是 bug |
| 一直 ACCEPTED | 资源被占满 | 看 8088 的集群资源 |
| `0 of the 1 minReplication nodes` | 可用 DataNode < `dfs.namenode.replication.min`（默认 1） | 那是**写入底线**不是副本目标（3）。查 Live datanodes |

### 5.3 HDFS

| 报错 / 告警 | 根因 | 解法 |
|---|---|---|
| `Under-replicated blocks` | ⚠️ **先看副本因子** | `fsck` 看是不是 `Target Replicas is 10 but found 3` → **配置造成的假警报**，非数据损坏 |
| `Missing blocks` | 真丢块了 | 紧急处理，查 DataNode 状态 |
| 只能读不能写 | safemode | 等副本上报；紧急 `safemode leave` |
| `Live datanodes: 0` | 重复 format 导致集群 ID 不一致 | 删三台 tmp 目录重新格式化 |

## 六、看日志的正确姿势

```bash
# systemd 服务
journalctl -u hive-server2 -n 100 --no-pager
journalctl -u hadoop -f                      # 实时跟踪

# YARN 作业（★ 报错必用）
yarn application -list
yarn logs -applicationId application_xxx_0001 | less
yarn application -kill application_xxx_0001

# Hive 本地日志
tail -f /tmp/lrh/hive.log

# 抓容器进程（★ 注意抓 java 那一层）
jps -l | grep YarnChild          # ❌ ps 会先抓到外层 bash（VmRSS 只有几 MB）
```

> 💡 **容器进程树是 `bash -c → java`**。
> 用 `ps -ef | grep YarnChild` 会先抓到外层 bash，看到的内存只有几 MB，
> 你会误判"这个任务根本没用内存"。**要抓 `java` 那一层。**

## 七、动手实验室

### 实验 11-1：复现一次 `GC overhead limit exceeded`（**强烈建议亲手做一次**）

```sql
-- 用很小的容器跑一个大基数 GROUP BY
SET mapreduce.reduce.memory.mb = 512;
SET mapreduce.reduce.java.opts = -Xmx410m;

SELECT product_id, dt, COUNT(1)
FROM gmall.dwd_event_log_di
GROUP BY product_id, dt;          -- 430 万个组合
```

观察：
1. 多久才失败？（案例实测 637 秒）
2. 报错出现在哪？（**在 task 的 Diagnostic Messages 里，不在 `Caused by` 里**）
3. Counters 里的 `HDFS Read` 是多少？（远小于输入 → 死得很早 → 内存问题）

然后调大：

```sql
SET mapreduce.reduce.memory.mb = 1024;
SET mapreduce.reduce.java.opts = -Xmx820m;
```

再跑一次 —— **63 秒成功**。**690 秒的差距，只因为一行参数。**

> 做完这个实验，你就真正理解"调优不是玄学，是找那个瓶颈"。

### 实验 11-2：练习用 Counter 定位

随便跑一个慢 SQL，打开 8088，记录：
`HDFS Read` / `HDFS Write` / `Cumulative CPU` / `GC time elapsed`

然后回答：这个作业**是算得慢，还是搬得慢，还是在 GC**？

### 实验 11-3：识破一个假诊断

```bash
# 故意用错误的数法
ps -ef | grep MasterServer | wc -l
# 再用正确的数法
ps -ef | grep "[M]asterServer" | wc -l
```

两个数字差多少？**这个差就是"看起来很正式的结论"和"真相"之间的距离。**

## 八、自测

**每题标了对应的正文小节——答不出来就回去看那节，不要硬想。**

1. 判断一个作业该给多少内存，你看什么特征？（不是看"它是什么类型"）—— 对应 **§1.2**
2. `GC overhead limit exceeded` 应该去哪里找？为什么搜 `Caused by` 找不到？—— 对应 **§5.2**
3. 退出码 143 和 137 分别意味着什么？第一反应分别是什么？—— 对应 **§3.3**
4. 什么叫"控制面 vs 数据面"？举一个例子。—— 对应 **§3.2**
5. 举两个"诊断手法本身是坏的、会给出错误结论"的例子。—— 对应 **§四**
6. 为什么"错误的原因"比"错误的现象"更危险？—— 对应 **§3.4**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 给多少内存看什么特征**
- 不看"它是什么类型的作业"，看**它囤不囤数据**：
  - **不囤数据**（写入型 / 清洗型，边读边写）→ 可以压小（瓶颈在磁盘 IO，压小不会直接失败）
  - **囤数据**（大基数 `GROUP BY` / `DISTINCT` / 非 MapJoin / 全表 `ORDER BY`）→ **必须放大**
- 量化案例：`GROUP BY product_id, dt`（430 万组合）
  - 512MB / `-Xmx410m` → `GC overhead limit exceeded`，**637 秒后失败**
  - 1024MB / `-Xmx820m` → **63 秒成功**
- 硬约束：容器不能超过节点容量（案例 2048MB）

**2. GC overhead 去哪找**
- 在 **task 的 `Diagnostic Messages`** 里，**不在 `Caused by` 异常链里** → 所以搜 `Caused by` 找不到
- 定位靠**量级不匹配**（看 Counter）：
  - `HDFS Read` 远小于输入量 → 死得很早 → **内存/初始化问题**
  - Read 正常但 `Write = 0` → 算完了写不出去 → 写入并发
  - Read/Write 都正常但耗时长 → 搬运/倾斜
- 第一反应是**加内存**，不是加 CPU

**3. 退出码**
- **143** = SIGTERM（**被主动停止**）→ 第一反应："谁停的？"（不是找 bug）
- **137** = SIGKILL（常见 OOM killer）→ 第一反应："查内存"
- 纪律：**退出码先于日志文本**

**4. 控制面 vs 数据面**
- 控制面 = 系统/UI/调度显示的状态；数据面 = 数据与进程的**真实**状态
- 例：DS 显示任务已 KILL（`state=9`、`143`），但 lrh-1 上的 `beeline` 还在跑，**跨 3 天把 5 天数据跑完了**
- 所以"调度说停了"之后，必须自己确认：
  `ps -ef | grep "[j]dbc:hive2"` + `yarn application -list`

**5. 两个坏掉的诊断手法**
- ① **`jps` 返回空 ≠ 进程不存在**：root（systemd）启动的 JVM 不在你的 `hsperfdata` 里
  → 真判据 `ps -ef | grep "[d]olphinscheduler"` + `ss -lnt`
- ② **`ps | grep xxx | wc -l` 会把自己数进去** → 计数虚高（曾数出 3 个 MasterServer，实际 0 个）
- ③（加分）**ZK 里数 DS 节点**：注册名是 `ip:port` 且 `ls` 把列表打在一行 → `grep -c` 恒为 1
- ④（加分）**`uptime` / `ps lstart` 推不了因果**：挂起恢复时墙钟跳变，`/proc/uptime` 不含挂起时间

**6. 为什么"错误的原因"更危险**
- **现象错了** → 你照做会失败 → **立刻能发现** → 改掉就行
- **原因错了** → 你带着错误的世界观去排查**所有**其他问题 → **永远发现不了**
- 所以写原因时必须能回答：**「我怎么证明这个因果？」**
  - "失败是因为网络抖动" ❌ 猜的
  - "失败是因为容器内存超限"（附 Diagnostics 原文 + 容器配置值）✅ 可信
