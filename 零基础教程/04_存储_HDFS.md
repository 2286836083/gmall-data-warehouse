# 04 · HDFS：数据到底存在哪、怎么存的

> **这章解决什么**：你往"HDFS"里放了一个 1GB 的文件，它物理上变成了什么？放在哪台机器的哪个目录？
> 为什么坏一台机器数据不丢？为什么不能往里面塞一亿个小文件？
>
> 搞懂这个，你才知道"我的表数据在哪"、"为什么这个文件读这么慢"、"空间怎么突然不够了"。

---

## 一、先记住 HDFS 的三个设计前提

HDFS 不是"更快的硬盘"，它是**为特定场景牺牲了特定东西**换来的：

| 前提 | 含义 |
|---|---|
| **硬件会坏** | 机器故障是常态而非例外 → 必须有副本 |
| **数据量大、一次写入不再改** | 所以不支持随机修改文件（只能追加）→ 换来高吞吐 |
| **批量读比低延迟更重要** | 不在乎一次读要 100ms，在乎 1TB 多久读完 |

**由此推出的两个核心设计：切块 + 多副本。**

---

## 二、机制：文件是怎么被切块和复制的

### 2.1 块（Block）

一个 1GB 的文件，默认按 **128MB** 切成 8 块：

```
events.csv  (1 GB)
  ├── blk_001  (128MB)
  ├── blk_002  (128MB)
  ├── ...
  └── blk_008  ( 96MB)   ← 最后一块可以不满
```

**为什么是 128MB 这么大？（对比：普通文件系统块是 4KB）**

两个物理原因：

1. **减少寻址开销**：磁盘的顺序读远快于随机读。块越大，一次连续读的时间越长，磁头移动占比越低。
2. **减少元数据量**：NameNode 要在**内存**里记住每个块的位置。
   块越大 → 块数越少 → 元数据越少 → NameNode 内存压力越小。

> **算一下**：1TB 数据，128MB 一块 = 8192 个块；4KB 一块 = 2.6 亿个块。
> 每个块元数据约 150 字节 → 前者 1.2MB，后者 **39GB 内存**。NameNode 直接死。

### 2.2 副本（Replication）

每个块默认存 **3 份**，放在不同机器上：

```
blk_001 → lrh-1, lrh-2, lrh-3
blk_002 → lrh-2, lrh-3, lrh-1     ← 打散，不固定
blk_003 → lrh-3, lrh-1, lrh-2
```

**物理代价**：写 1GB 数据，集群实际写入 **3GB**，网络传输 3GB。
**这就是"空间只剩三分之一"的原因**（第 03 章让你算的那个账）。

> 📌 **本项目对照**：`hdfs-site.xml` 里 `dfs.replication=3`。
> 但有一个反直觉的现象——作业提交时上传的 `job.jar` 之类暂存文件，副本因子被设成了 **10**
> （`mapreduce.client.submit.file.replication` 的默认值），而集群只有 3 台 DataNode，**永远凑不齐 10 份**。
> 于是 `fsck` 一直报 "Under-replicated blocks"。
> **这不是数据损坏，是配置造成的假警报。** 案例项目查清后决定不改配置，每次跑批后它会再出现，属预期现象。
> ——**这说明"告警"和"故障"是两件事，会看告警背后的数字才是本事。**

## 三、顺序：写一个文件的完整流程（★ 面试高频）

**场景**：你在 lrh-1 上执行 `hdfs dfs -put events.csv /data/`，文件 1GB。

```
① 【客户端 → NameNode】"我要写 /data/events.csv，多大"
     走网络（一次 RPC 调用），NameNode 检查权限、目录是否已存在

② 【NameNode → 客户端】"可以写，第一个块放这三台：B, C, D"
     ★ NameNode 只给地址，它自己不碰数据

③ 【客户端 → DataNode B】建立 TCP 管道，开始发数据
     B 收一点点就立刻转发给 C，C 再转发给 D —— 这叫 pipeline（流水线），
     不是"客户端分别发给三台"（那样客户端出口带宽要 ×3）

④ 【D → C → B → 客户端】逐级回报"我写完了"，最后回到客户端
     客户端再告诉 NameNode："blk_001 完事了，给我下一个块的地址"

⑤ 重复 ③④ 直到 8 个块写完

⑥ 【客户端 → NameNode】"文件写完了，关掉"
     NameNode 在内存里记录：/data/events.csv → [blk_001..blk_008]，每块在哪三台
```

**三个关键结论**：

| 结论 | 为什么重要 |
|---|---|
| **NameNode 全程不碰数据** | 它只管"目录和块在哪"。数据从客户端直接流到 DataNode。这是 HDFS 能横向扩展的根本原因 |
| **写是流水线** | 客户端只发给一台，由 DataNode 之间接力复制，省客户端带宽 |
| **元数据在内存** | NameNode 重启后要靠磁盘上的镜像 + 编辑日志恢复，这就是为什么它启动要几十秒 |

### 3.1 物理代价一览

**下表的编号 = 上面 §三 流程图的步骤编号**（①②③④⑤⑥ 就是那六步，别当暗号看）：

| 对应哪一步 | 这一步干了什么 | 消耗的物理资源 | 量级 |
|---|---|---|---|
| ① ② | 问地址、拿地址 | 网络往返（两次 RPC） | 很小 |
| **③** | **客户端发数据、DataNode 接力复制** | **网络：客户端出口带宽**<br>**磁盘：三台各写一份** | **★ 唯一的大头** |
| ④ | 逐级回报"我这一份写完了" | 网络回报 | 很小 |
| ⑤ | 重复 ③④，处理下一个块 | —— 不额外消耗，就是把 ③④ 再来一遍 | — |
| ⑥ | 告诉 NameNode 收尾 | NameNode 内存里多几条记录 | 很小 |

**为什么只有 ③ 是大头？拆开看三个原因：**

1. **走的是"客户端出口"带宽**——数据从**你操作的那台机器**的网卡发出去。
   家用/办公网的上行常常只有 10~50Mbps（≈1.2~6MB/s），所以 1.3GB 传起来要**几分钟**。
   > 这也解释了一个日常现象：**在服务器上直接 `hdfs dfs -put` 本机文件，比"从自己的笔记本上传"快得多**——
   > 后者是被你的出口带宽卡的，不是被集群卡的。
2. **要乘 3**——副本因子是 3，1.3GB 的数据最终写进**三台机器的磁盘**（网络传输也是 3 份）。
3. **DataNode 之间走的是内网**——接力复制发生在集群内部（案例集群千兆，≈125MB/s），
   比你的出口带宽快，所以那一段通常不是瓶颈。

> 📌 **本项目对照**：上面说的 1.3GB，是 REES46 数据集的 **31 个按天 CSV**（就是本章开头那张表里的数据）。
> 案例项目的装载脚本专门注释了"拷贝 1.3GB 数据进 HDFS，需几分钟"，
> 并且**把 62 条语句（31 组 ALTER + LOAD）合并进一个文件一次执行**——
> 因为每调一次 `beeline` 都要冷启一个 JVM（约 5 秒），31 天 ×3 次调用 ≈ 93 次启动，白等七八分钟。

## 四、顺序：读一个文件的流程

```
① 【客户端 → NameNode】"我要读 /data/events.csv"
② 【NameNode → 客户端】"8 个块，每个块在三台的这些位置"（返回的是列表）
③ 【客户端 → 最近的 DataNode】直接读块
     就近原则：同机器 > 同机架 > 跨机架
④ 读完一个块，接着读下一个；某个副本读失败就换一台重试
```

**关键点**：NameNode 只在开头出现一次。**后面 1GB 的数据流完全不经过它**。
所以它不会成为吞吐瓶颈——它只是"问路的地方"。

---

## 五、元数据：NameNode 脑子里装的是什么

NameNode 的内存里维护两张表（**纯内存，这是它最贵的地方**）：

```
① 文件树： /data/events.csv → 属性（权限、大小、时间）
② 块映射： 文件 → [blk_001, blk_002, ...] → 每个块在哪些 DataNode 上
```

**它不存**：块里的内容是什么。

### 5.1 崩溃恢复：fsimage + edits

内存一断电就没了，所以磁盘上还有两个东西：

| 文件 | 是什么 | 类比 |
|---|---|---|
| `fsimage` | 某一时刻的完整快照 | 存档 |
| `edits` | 从那之后的每一次改动（追加写） | 流水账 |

重启时：加载 fsimage（大，慢）+ 回放 edits（可能很长，也慢）→ 恢复出内存里的两张表。
**这就是 NameNode 启动要几十秒的原因。**

`edits` 会越来越大，所以需要有人定期把它合并进 fsimage——这个活是 **SecondaryNameNode** 干的（checkpoint）。

> ⚠️ **常见误解**：SecondaryNameNode **不是** NameNode 的热备份，它挂了不影响集群运行。
> 它只是个"定期帮你整理账本的人"。（真正的高可用方案是 HDFS HA + JournalNode + ZooKeeper，本教程不展开。）

## 六、命令：每天要用的那些

```bash
# ── 查看 ──
hdfs dfs -ls /user/hive/warehouse/gmall.db/        # 列目录
hdfs dfs -ls -h /data                              # -h 人类可读大小
hdfs dfs -cat /data/part-0000 | head               # 看内容（小文件）
hdfs dfs -du -s -h /user/hive/warehouse/gmall.db/ods_event_log_di   # 这个目录多大

# ── 上传下载 ──
hdfs dfs -put ./local.csv /data/                   # 上传
hdfs dfs -put -f ./local.csv /data/                # -f 覆盖
hdfs dfs -get /data/part-0000 ./                   # 下载
hdfs dfs -cp /data/a /data/b                       # 集群内复制
hdfs dfs -mv /data/a /data/b                       # 集群内移动

# ── 删除 ──
hdfs dfs -rm /data/x.csv
hdfs dfs -rm -r /data/old_dir                      # 递归删目录
hdfs dfs -rm -skipTrash /data/x.csv                # 跳过回收站（默认会进 .Trash）

# ── 运维 ──
hdfs dfsadmin -report                              # ★ 集群健康总览
hdfs fsck / -files -blocks                         # 检查块健康/副本情况
hdfs dfsadmin -safemode get                        # 安全模式状态
hdfs dfsadmin -safemode leave                      # 强制退出安全模式（只读不能写时）
```

### 6.1 怎么看表数据在 HDFS 上长什么样

**Hive 的表 = HDFS 上的一个目录；分区 = 子目录**（这是最重要的一条对应关系）：

```bash
hdfs dfs -ls /user/hive/warehouse/gmall.db/ods_event_log_di/
# dt=2019-10-01/
# dt=2019-10-02/
# ...

hdfs dfs -ls /user/hive/warehouse/gmall.db/ods_event_log_di/dt=2019-10-01/
# part-m-00000     ← 真正的数据文件
```

> 记住这个结构，你就会明白：
> **"删分区" = 删掉一个子目录；"查一天的数据" = 只读一个子目录（不用扫全表）。**

### 6.2 `du` 的两列是什么意思

```bash
hdfs dfs -du -s -h /user/hive/warehouse/gmall.db/ods_event_log_di
# 1.3 G   3.9 G   /user/hive/warehouse/...
#  ↑        ↑
#  实际大小  含副本的总占用（= 前者 × 副本数）
```

**看第二列你就知道"写入放大"了多少。**

## 七、动手实验室

### 实验 4-1：亲眼看到一个文件被切成块

```bash
# 造一个 300MB 的文件（会被切成 3 块）
dd if=/dev/zero of=/tmp/big.bin bs=1M count=300
hdfs dfs -put /tmp/big.bin /test/big.bin

# 看块信息（★ 这条命令能把你前面学的一切具象化）
hdfs fsck /test/big.bin -files -blocks -locations
```

输出里你会看到类似：

```
/test/big.bin 314572800 bytes, 3 block(s):
 blk_1073741825_1001 len=134217728 repl=3 [lrh-2, lrh-3, lrh-1]
 blk_1073741826_1002 len=134217728 repl=3 [lrh-3, lrh-1, lrh-2]
 blk_1073741827_1003 len=41943040  repl=3 [lrh-1, lrh-2, lrh-3]
```

数三件事：**块数（3）**、**每块大小（134217728 = 128MB）**、**副本分布（repl=3，打散在三台）**。

### 实验 4-2：停一台机器，数据还在吗

```bash
hdfs dfs -cat /test/big.bin | wc -c          # 先确认能读，记下字节数
ssh lrh-3 "hdfs --daemon stop datanode"      # 停一台
hdfs dfsadmin -report | grep -E "Live|Dead"
hdfs dfs -cat /test/big.bin | wc -c          # 还能读吗？（能 —— 这就是副本的意义）
ssh lrh-3 "hdfs --daemon start datanode"
```

> 想明白一个问题：**如果停掉两台呢？**（大概率还能读，但你会看到 Under-replicated 告警刷屏）

### 实验 4-3：小文件有多可怕

```bash
# 建 1000 个 1KB 的小文件
for i in $(seq 1 1000); do echo "x" > /tmp/s_$i.txt; done
hdfs dfs -put /tmp/s_*.txt /test/small/
hdfs dfs -du -s -h /test/small/              # 实际大小 vs 占用大小，对比一下
```

1000 个 1KB 文件，逻辑上只有 1MB，但：
- 每个块在 NameNode 内存里都有一条记录 → **1000 条元数据**
- MapReduce 处理时，默认**一个块一个 map 任务** → 1000 个任务，启动开销远大于计算

> **这就是"小文件问题"**。后果是 NameNode 内存吃紧 + 作业变慢。
> 解法：合并小文件、用 HAR 归档、或者在写入侧就控制文件大小（第 11 章）。

## 八、常见坑

| 现象 | 根因 | 解法 |
|---|---|---|
| `Live datanodes: 0` | 重复格式化导致集群 ID 不一致 | 删三台 tmp 目录重新格式化（第 03 章） |
| 一直报 Under-replicated | 副本因子 > DataNode 数量（如暂存文件 repl=10） | 先 `fsck` 看消息是不是 `Target Replicas is 10 but found 3`——是则为**假警报** |
| 只能读不能写 | 处于安全模式（safemode） | 等副本上报完；紧急情况 `safemode leave` |
| 空间够却写不进 | 某台 DataNode 磁盘满了 | `dfsadmin -report` 看每台剩余 |
| `Permission denied` | HDFS 权限 | 学习环境设 `dfs.permissions.enabled=false` |
| 表数据莫名没了 | 误删了 HDFS 目录 / 用了 `DROP TABLE`（内部表会连数据一起删） | 重要数据用**外部表**（第 06 章） |
| 删了文件空间没释放 | 进了回收站 `.Trash` | 默认保留一段时间；用 `-skipTrash` 直接删 |

## 九、自测

**每题标了对应的正文小节——答不出来就回去看那节，不要硬想。**

1. 1GB 文件、128MB 块、副本 3，物理上写入了多少 GB？分布在几台机器上？—— 对应 **§2.1、§2.2**
2. 写文件时 NameNode 参与数据传输吗？如果不参与，它干嘛了？—— 对应 **§三**
3. 为什么块要 128MB 这么大？给两个物理理由。—— 对应 **§2.1**
4. NameNode 重启为什么要几十秒？—— 对应 **§5.1**
5. Hive 的表和分区在 HDFS 上对应什么？—— 对应 **§6.1**
6. 为什么"一亿个小文件"会拖垮集群？—— 对应 **§七（实验 4-3）**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 算账**
- 块数 = 1GB ÷ 128MB = **8 块**（最后一块可能不满）
- 每块 3 副本 → 物理写入 **3GB**（网络也传 3GB）
- 分布在 **3 台**（每块在三台各一份，位置打散，不是固定某台）
- 推论：**可用容量约等于一台机器的容量**（30GB × 3 台 ÷ 3 副本 = 30GB）

**2. NameNode 参与吗**
- **不参与数据传输**。它只在开头回一次"这个块放哪三台"（一次 RPC），之后客户端**直接**和 DataNode 传数据
- 加分项：写是**流水线**（客户端→B→C→D 逐级转发），不是客户端发三份，这样省客户端出口带宽
- 为什么这是关键设计：NameNode 不碰数据 → 数据流不会挤过它 → 能横向扩展

**3. 块为什么 128MB**
- ① **减少寻址开销**：磁盘顺序读远快于随机读，块越大，一次连续读越长，磁头移动占比越低
- ② **减少元数据量**：块越大 → 块数越少 → NameNode 内存压力越小
- 量化（加分）：1TB 用 128MB 分 = 8192 块；用 4KB 分 = 2.6 亿块 × ~150B ≈ **39GB 内存**，NameNode 直接死

**4. 重启为什么慢**
- 元数据在内存，断电就没了 → 重启要：加载 `fsimage`（快照，大而慢）+ **回放 `edits`**（流水账，可能很长）
- 加分项：`edits` 由 **SecondaryNameNode** 定期合并进 `fsimage`（checkpoint）；它**不是热备份**

**5. Hive 表 ↔ HDFS**
- 表 = HDFS 上一个目录：`/user/hive/warehouse/gmall.db/<表名>/`
- 分区 = 子目录：`dt=2019-10-01/`，里面是 `part-m-00000` 这样的数据文件
- 推论：删分区 = 删子目录；查一天 = 只读一个子目录（不扫全表）

**6. 一亿个小文件为什么可怕**
- **NameNode 侧**：每个文件/块在内存里至少一条记录 → 一亿个文件 = 一亿条元数据，内存爆
- **计算侧**：MapReduce 默认**一个块一个 map 任务** → 一亿个任务，启动开销远大于计算本身
- 解法：写入侧合并、HAR 归档（第 11 章）
</details>
