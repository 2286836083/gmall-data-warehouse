## 一、数据集：我们手上有什么

**数据集**：REES46 eCommerce behavior data（Kaggle 公开数据集，CC BY 4.0）
**范围**：2019 年 10 月单月，按用户 1/4 采样 → **31 天、10,630,245 行**

**一行长这样（CSV，9 个字段）**：

```
2019-10-01 00:00:11 UTC,view,44600062,2103807459595387724,,shiseido,35.79,541312140,f7f8b3c8-...
│                     │  │      │            │           │    │       │      │        └ user_session 会话ID
│                     │  │      │            │           │    │       │      └ user_id 用户ID
│                     │  │      │            │           │    │       └ price 价格
│                     │  │      │            │           │    └ brand 品牌（约14.4%为空）
│                     │  │      │            │           └ category_code 类目路径（约31.9%为空）
│                     │  │      │            └ category_id
│                     │  │      └ product_id 商品ID
│                     │  └ event_type 事件类型：view / cart / purchase
│                     └ 注意这个 " UTC" 后缀
└ event_time 事件时间
```

**真实数据的三个特征（这也是它比模拟数据有价值的原因）**：

| 特征 | 具体表现 | 影响 |
|---|---|---|
| **有脏数据** | 类目 31.9% 为空、品牌 14.4% 为空 | 必须归一成 `'unknown'`，否则 `GROUP BY` 多出 NULL 组 |
| **有重复行** | 实测 **7,091 行**九个字段完全重复 | 必须去重，否则 GMV 虚高 |
| **有价格 0** | `price=0` 只出现在 view/cart，purchase 无 0 值 | **不要删**（是真实特征），且不影响 GMV |

> 📌 **反面教材**：案例项目最早用的是**模拟数据**（5 天、31.7 万行）。
> 结果 `ads_dau` 每天恒为 1000、复购率恒在 0.99 以上——**画出来的折线是一条直线**。
> 模拟数据会**掩盖所有真实的分布问题和脏数据问题**。
> 这也是后来换成真实数据的原因。**做项目尽量用真实数据，哪怕小一点。**

## 二、需求：要回答六个业务问题

| # | 业务问题 | 产出表 | 粒度 |
|---|---|---|---|
| **Q1** | 每天有多少活跃用户？新增和回流各占多少？ | `ads_active_user_day` | 天 |
| **Q2** | 浏览 → 加购 → 购买，转化如何？ | `ads_funnel_day` | 天 |
| **Q3** | 复购情况如何？ | `ads_repurchase_day` | 天 |

## 三、Step 0：把数据装进 ODS

### 3.1 建表（原样落地，不改任何东西）

**先明确"不加工"到底是什么意思**——这是最容易自作聪明的地方：

| ✅ ODS 该做的 | ❌ ODS 不该做的 |
|---|---|
| 原样存字段（含空值、含重复、含 `" UTC"` 后缀） | 去重 |
| 加分区、建目录 | 解析时间格式 |
| 记录来源与装载时间 | 把空串转成 `'unknown'` |
| —— | 重命名字段、删掉"看起来没用"的行 |

**为什么这么严？看两个反例：**

1. 假设你在 ODS "顺手"把 `2019-10-01 00:00:11 UTC` 解析成了 `timestamp`、把空品牌换成了 `'unknown'`。
   三个月后业务方说"我想看**原始字符串**长什么样，怀疑采集端有问题"——**你永远拿不回来了**，原始形态已被你改写。
2. 假设你在 ODS 就去了重。后来发现去重规则定错了（把两条真实不同的记录当成重复），
   你需要**重新去重**——但重复行已经没了，只能回源头重新拉数据。

**一句话原则**：**ODS 是"证据保全"，DWD 才是"加工车间"。**
每一层都要能回答"上游给我的原始样子是什么"，否则出错时你无法回溯。

```sql
CREATE DATABASE IF NOT EXISTS gmall COMMENT '电商用户行为分析离线数仓';

CREATE TABLE gmall.ods_event_log_di (
  event_time    string  COMMENT '事件时间（原始文本，含 UTC 后缀，解析在 DWD 做）',
  event_type    string  COMMENT 'view/cart/purchase',
  product_id    bigint  COMMENT '商品ID',
  category_id   bigint  COMMENT '类目ID',
  category_code string  COMMENT '类目路径 electronics.smartphone',
  brand         string  COMMENT '品牌（约14.4%为空）',
  price         double  COMMENT '价格（USDT）',
  user_id       bigint  COMMENT '用户ID',
  user_session  string  COMMENT '会话ID'
)
COMMENT 'ODS 原始层：电商用户行为事件日志（原样接入不做加工）'
PARTITIONED BY (dt string COMMENT '日期分区，取自 event_time 前10位')
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
STORED AS TEXTFILE;
```

### 3.2 逐天装载（31 天）

```sql
ALTER TABLE gmall.ods_event_log_di ADD IF NOT EXISTS PARTITION (dt='2019-10-01');
LOAD DATA LOCAL INPATH '/home/lrh/workspace/new_chain/real_data/2019-10-01.csv'
  OVERWRITE INTO TABLE gmall.ods_event_log_di PARTITION (dt='2019-10-01');
-- ... 重复 31 天
```

**★ 工程化要点（真实踩过的效率坑）**：
不要每天调一次 `beeline`。**每调一次都要冷启一个 JVM（约 5 秒）**，
31 天 × 3 次调用 ≈ 93 次启动，白等七八分钟。

正确做法是**把 62 条语句（31 组 ALTER + LOAD）拼进一个文件，一次执行**：

```bash
SQL="/tmp/load_ods.sql"; : > "$SQL"
for f in "$DATADIR"/*.csv; do
  d=$(basename "$f" .csv)
  echo "ALTER TABLE $TABLE ADD IF NOT EXISTS PARTITION (dt='$d');" >> "$SQL"
  echo "LOAD DATA LOCAL INPATH '$f' OVERWRITE INTO TABLE $TABLE PARTITION (dt='$d');" >> "$SQL"
done
beeline -u jdbc:hive2://lrh-1:10000 -f "$SQL"
```

### 3.3 立刻校验（**装载完必须做，别等到最后**）


## 四、Step 1：ODS → DWD（清洗）

### 4.1 清洗规则（**每一条都有实测依据**）

| # | 规则 | 为什么 |
|---|---|---|
| 1 | 时间解析：剥掉 `" UTC"` 后转 `timestamp` | 原始是字符串，不能直接算时间 |
| 2 | **整行去重**（按原始 9 字段） | 实测存在 **7,091 行**完全重复 |
| 3 | 类目拆三级，`SPLIT(category_code,'[.]')`，缺层补 `'unknown'` | 便于按类目聚合 |
| 4 | 空值归一：`brand`/`category_code` 空 → `'unknown'` | **避免 NULL 干扰 GROUP BY**（NULL 会自成一组，且不同人处理不同） |
| 5 | **`price=0` 保留不删** | 只出现在 view/cart，是真实特征；purchase 无 0 值，不影响 GMV |

### 4.2 完整 SQL

```sql
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;
SET hive.exec.max.dynamic.partitions = 200;
SET hive.exec.max.dynamic.partitions.pernode = 100;

INSERT OVERWRITE TABLE gmall.dwd_event_log_di PARTITION (dt)
SELECT
  -- event_id 用「原始 9 字段」参与 md5：与去重的键完全一致，保证去重后一定唯一
  MD5(CONCAT_WS('|', o.event_time, o.event_type,
        CAST(o.product_id AS STRING), CAST(o.category_id AS STRING),
        o.category_code, o.brand, CAST(o.price AS STRING),
        CAST(o.user_id AS STRING), o.user_session))        AS event_id,
  o.user_id,
  o.event_type,
  CAST(REGEXP_REPLACE(o.event_time, ' UTC$', '') AS TIMESTAMP) AS event_time,
  o.product_id,
  o.category_id,
  o.category_code,
  COALESCE(NULLIF(SPLIT(o.category_code, '[.]')[0], ''), 'unknown') AS category_l1,
  COALESCE(NULLIF(SPLIT(o.category_code, '[.]')[1], ''), 'unknown') AS category_l2,
  COALESCE(NULLIF(SPLIT(o.category_code, '[.]')[2], ''), 'unknown') AS category_l3,
  COALESCE(NULLIF(o.brand, ''), 'unknown')                  AS brand,
  o.price,
  o.user_session,
  SUBSTR(o.event_time, 1, 10)                              AS dt
FROM (
  SELECT DISTINCT
         event_time, event_type, product_id, category_id, category_code,
         brand, price, user_id, user_session
  FROM gmall.ods_event_log_di
) o;
```

**基数校验**：`10,630,245 → 10,623,154`，**少了 7,091 行** —— 正好等于去重掉的完全重复行。
**对得上，才说明你的清洗规则真的生效了。**

### 4.3 派生购买事实表

```sql
INSERT OVERWRITE TABLE gmall.dwd_purchase_fact_di PARTITION (dt)
```

## 五、Step 2：DWD → DIM（商品维）

难点：同一商品在不同事件里属性不一致 → 不能简单 `SELECT DISTINCT`。

```sql
INSERT OVERWRITE TABLE gmall.dim_product
SELECT product_id, category_id, category_code,
       category_l1, category_l2, category_l3, brand,
       first_seen_dt, last_seen_dt, event_cnt
FROM (
  SELECT product_id, category_id, category_code,
         category_l1, category_l2, category_l3, brand,
         MIN(dt)  OVER (PARTITION BY product_id) AS first_seen_dt,
         MAX(dt)  OVER (PARTITION BY product_id) AS last_seen_dt,
         COUNT(1) OVER (PARTITION BY product_id) AS event_cnt,
         ROW_NUMBER() OVER (
           PARTITION BY product_id
           ORDER BY attr_cnt DESC, dt DESC     -- ★ 取出现最多的属性组合；并列取更近的
         ) AS rn
  FROM (
    SELECT product_id, category_id, category_code,
           category_l1, category_l2, category_l3, brand, dt,
           COUNT(1) OVER (PARTITION BY product_id, category_id, category_code,
                                       category_l1, category_l2, category_l3, brand) AS attr_cnt
    FROM gmall.dwd_event_log_di
  ) a
) b
WHERE rn = 1;
```

**行数**：**140,665**（一行一个商品，粒度唯一）

## 六、Step 3：DWD → DWS（四张汇总表）

### 6.1 用户主题（用户 × 天）

```sql
INSERT OVERWRITE TABLE gmall.dws_user_event_day PARTITION (dt)
SELECT
  user_id,
  COUNT(CASE WHEN event_type = 'view'     THEN 1 END) AS pv_cnt,
  COUNT(CASE WHEN event_type = 'cart'     THEN 1 END) AS cart_cnt,
  COUNT(CASE WHEN event_type = 'purchase' THEN 1 END) AS purchase_cnt,
  SUM(CASE WHEN event_type = 'purchase' THEN price ELSE 0 END) AS pay_amount,
  COUNT(DISTINCT user_session) AS session_cnt,
  MIN(event_time) AS first_event_time,
  MAX(event_time) AS last_event_time,
  dt
FROM gmall.dwd_event_log_di
GROUP BY user_id, dt;
```

**行数**：**1,622,820**

> 💡 `COUNT(CASE WHEN ... THEN 1 END)` 是数仓里最高频的写法：
> 一次扫描同时算出多个口径（行转列式的条件统计），**比为每个指标各跑一次快得多**。

### 6.2 商品主题（商品 × 天）—— ★ 先聚合再关联

```sql
INSERT OVERWRITE TABLE gmall.dws_product_event_day PARTITION (dt)
SELECT a.product_id, p.category_l1, p.category_l2, p.category_l3, p.brand,
       a.pv_cnt, a.cart_cnt, a.purchase_cnt, a.gmv, a.buyer_cnt, a.dt
FROM (
  SELECT product_id, dt,
         COUNT(CASE WHEN event_type = 'view'     THEN 1 END) AS pv_cnt,
         COUNT(CASE WHEN event_type = 'cart'     THEN 1 END) AS cart_cnt,
         COUNT(CASE WHEN event_type = 'purchase' THEN 1 END) AS purchase_cnt,
         SUM(CASE WHEN event_type = 'purchase' THEN price ELSE 0 END) AS gmv,
         COUNT(DISTINCT CASE WHEN event_type='purchase' THEN user_id END) AS buyer_cnt
  FROM gmall.dwd_event_log_di
  GROUP BY product_id, dt            -- ★ 先聚合到小表
) a
LEFT JOIN gmall.dim_product p ON a.product_id = p.product_id;   -- 再关联 14 万行维表
```

**★ 为什么"先聚合再关联"**：
错误写法是 1063 万行 `LEFT JOIN` 之后才 `GROUP BY` —— 多一次**大表 shuffle**（那个 shuffle 要跨网络搬上千万行）。
正确写法先把 1063 万行压到 126 万行，再去 JOIN 14 万行的维表，**网络传输量少一个数量级**。

**行数**：**1,265,817**

### 6.3 类目主题（类目 × 天）—— ★ 不可加的指标回明细重算

```sql
INSERT OVERWRITE TABLE gmall.dws_category_event_day PARTITION (dt)
SELECT
  category_l1, category_l2,
  COUNT(CASE WHEN event_type = 'view'     THEN 1 END) AS pv_cnt,
  COUNT(CASE WHEN event_type = 'cart'     THEN 1 END) AS cart_cnt,
  COUNT(CASE WHEN event_type = 'purchase' THEN 1 END) AS purchase_cnt,
  SUM(CASE WHEN event_type = 'purchase' THEN price ELSE 0 END) AS gmv,
  COUNT(DISTINCT CASE WHEN event_type='purchase' THEN user_id END) AS buyer_cnt,  -- ★ 回明细重算
  dt
FROM gmall.dwd_event_log_di
GROUP BY category_l1, category_l2, dt;
```

**行数**：**1,853**

> ⚠️ 这里的 `buyer_cnt` **必须回 DWD 明细重算**，不能从商品层 SUM（第 07 章第 1.3 节）。
> 表注释里也写了这条。

### 6.4 交易主题（天）

```sql
INSERT OVERWRITE TABLE gmall.dws_trade_day PARTITION (dt)
SELECT COUNT(1) AS order_cnt,
       COUNT(DISTINCT user_id) AS buyer_cnt,
       SUM(amount) AS gmv,
       ROUND(SUM(amount) / COUNT(1), 2) AS avg_order_amount,
       COUNT(DISTINCT product_id) AS product_cnt,
       dt
FROM gmall.dwd_purchase_fact_di
GROUP BY dt;
```

**行数**：**31**（一天一行）

## 七、Step 4：DWS → ADS（回答六个问题）

### 7.1 Q1 活跃用户（★ 窗口函数一次算出四个口径）

```sql
INSERT OVERWRITE TABLE gmall.ads_active_user_day
SELECT
  t.dt,
  COUNT(1)                                              AS dau,
  COUNT(CASE WHEN t.first_dt = t.dt THEN 1 END)         AS new_dau,
  COUNT(CASE WHEN t.prev_dt = CAST(DATE_SUB(t.dt,1) AS STRING) THEN 1 END) AS active_dau,
  COUNT(CASE WHEN t.first_dt < t.dt
              AND (t.prev_dt IS NULL
                   OR t.prev_dt <> CAST(DATE_SUB(t.dt,1) AS STRING))
             THEN 1 END)                                AS wakeup_dau
FROM (
  SELECT user_id, dt,
         MIN(dt) OVER (PARTITION BY user_id)              AS first_dt,  -- 首次活跃日
         LAG(dt) OVER (PARTITION BY user_id ORDER BY dt)  AS prev_dt   -- 上一次活跃日
  FROM gmall.dws_user_event_day
) t
GROUP BY t.dt;
```

**四个口径互斥且完备**：`new_dau + active_dau + wakeup_dau = dau` —— **这是对账的依据**。

> 💡 **对比旧做法**：旧链路是"每一天 LEFT JOIN 历史所有天 + 昨天"，复杂度 O(n²)。
> 窗口函数**一次扫描**就全算出来了，而且让 `new_dau`/`wakeup_dau` **从恒为 0 变成真实值**
> （旧链路是模拟数据，每天都是同一批用户，算出来必然是 0）。

**实测结论**：首日 DAU **47,854**，此后 46,392 → 42,621，**有真实波动**（模拟数据是一条直线）。

### 7.2 Q2 转化漏斗

```sql
INSERT OVERWRITE TABLE gmall.ads_funnel_day
SELECT dt,
  COUNT(CASE WHEN pv_cnt > 0       THEN 1 END) AS view_uv,
  COUNT(CASE WHEN cart_cnt > 0     THEN 1 END) AS cart_uv,
  COUNT(CASE WHEN purchase_cnt > 0 THEN 1 END) AS purchase_uv,
  ROUND(COUNT(CASE WHEN cart_cnt>0 THEN 1 END) * 1.0
        / NULLIF(COUNT(CASE WHEN pv_cnt>0 THEN 1 END),0), 4)     AS cart_rate,
  ROUND(COUNT(CASE WHEN purchase_cnt>0 THEN 1 END) * 1.0
        / NULLIF(COUNT(CASE WHEN cart_cnt>0 THEN 1 END),0), 4)   AS cart_to_purchase_rate,
  ROUND(COUNT(CASE WHEN purchase_cnt>0 THEN 1 END) * 1.0
        / NULLIF(COUNT(CASE WHEN pv_cnt>0 THEN 1 END),0), 4)     AS overall_rate
FROM gmall.dws_user_event_day
GROUP BY dt;
```

> ⚠️ **真实数据推翻了"三层漏斗"的直觉**：
> 实测 31 天里有 **15 天"购买用户数 > 加购用户数"**。
> 原因：**用户可以完全不进购物车直接购买** → 加购和购买是**并行**路径，不是必经的中间态。
> 所以 `cart_rate` 和 `cart_to_purchase_rate` 是**两个独立指标，不能相乘当漏斗**。
> ——**这是"先假设后验证"的价值：直觉设计的漏斗，被真实数据证伪了。**

### 7.3 Q3 累计复购率

```sql
INSERT OVERWRITE TABLE gmall.ads_repurchase_day
SELECT dt,
  COUNT(1) AS total_buyers,
  COUNT(CASE WHEN cum_orders >= 2 THEN 1 END) AS repurchase_buyers,
  ROUND(COUNT(CASE WHEN cum_orders >= 2 THEN 1 END) * 1.0
        / NULLIF(COUNT(1),0), 4) AS repurchase_rate
FROM (
  SELECT user_id, dt,
         SUM(purchase_cnt) OVER (
           PARTITION BY user_id ORDER BY dt
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW     -- 累计到下订单当天
         ) AS cum_orders
  FROM gmall.dws_user_event_day
  WHERE purchase_cnt > 0
) t
GROUP BY dt;
```

### 7.4 Q4 TopN 商品

```sql
INSERT OVERWRITE TABLE gmall.ads_top_product_day
SELECT dt, rank_num, product_id, brand, category_l1, category_l2,
       gmv, purchase_cnt, buyer_cnt
FROM (
  SELECT dt, product_id, brand, category_l1, category_l2, gmv, purchase_cnt, buyer_cnt,
         ROW_NUMBER() OVER (PARTITION BY dt ORDER BY gmv DESC, purchase_cnt DESC) AS rank_num
  FROM gmall.dws_product_event_day
  WHERE gmv > 0
) t
WHERE rank_num <= 50;          -- 每天只留前 50（31 × 50 = 1550 行）
```

**行数**：**1,550**

> 💡 **为什么要在这里截断 Top50，而不是导出时再截**：
> 每天 500 行全导出来再丢掉 450 行，属于"白导"。**能在 SQL 里做的过滤别留给下游。**

## 八、Step 5：校验（**这一步决定了你敢不敢对外报数**）

### 8.1 三层校验清单

### 8.2 行数基线（案例项目实测）

| `dws_category_event_day` | 1,853 | 类目 × 天 |
| `dws_trade_day` | 31 | 天 |
| `ads_*`（4 张） | 31 / 31 / 31 / 1,550 | 天 / 天×排名 |

### 8.3 交叉对账：GMV 四路收敛（★ 最有力的一致性证明）

```
路径①：SUM(price) FROM dwd_event_log_di  WHERE event_type='purchase'
路径②：SUM(amount) FROM dwd_purchase_fact_di
路径③：SUM(gmv) FROM dws_trade_day
路径④：SUM(gmv) FROM dws_category_event_day
                        ↓
              四个数必须完全相等
```

**实测：四路全部收敛到 `57,575,996.50`。**

> 为什么这比"看一眼没报错"强得多：
> 四条路径走了不同的表、不同的聚合顺序。它们能收敛，说明**链路每一层都没有算错**。
> 任何一层有重复、漏行、口径偏移，这个数就会对不上。

### 8.4 方向性违例检查（把"业务常识"写成断言）

```sql
-- 这些都应该返回 0 行
SELECT dt FROM ads_active_user_day WHERE dau < new_dau;              -- 新增不能超过活跃
SELECT dt FROM ads_funnel_day WHERE view_uv < purchase_uv;           -- 买的人不能比看的人多
SELECT dt FROM dws_trade_day WHERE gmv < 0;                          -- 金额不能为负
SELECT dt FROM ads_repurchase_day WHERE repurchase_rate > 1;         -- 比率不能超过 1
```

**实测 0/0/0/0 违例。**
> 💡 第 02 条（view ≥ purchase）通过了，但前面提到的"购买 vs 加购"**没有**这种必然关系。
> **写断言前先想清楚这个不等式是不是真的成立。**

## 九、工程化：让这条链路能重复跑、能看到进度

### 9.1 必须满足的四条

| 要求 | 做法 |
|---|---|
| **幂等**（重跑不出错、不翻倍） | 一律 `INSERT OVERWRITE`，不用 `INSERT INTO` |
| **可断点续跑** | 脚本支持 `bash evt_run.sh <起始步骤号>` |
| **进度可见** | 每步写状态文件（`status.tsv`），能查到"现在在第几步" |
| **长任务后台** | `setsid nohup ... &`（第 02 章） |

### 9.2 一个分步执行器的骨架

```bash
#!/usr/bin/env bash
set -eu
START="${1:-1}"                       # 支持从任意步开始（断点续跑）
RUN_DIR=/home/lrh/workspace/evt_run
STATUS="$RUN_DIR/status.tsv"
: > "$STATUS"

run_step () {
  local n=$1 name=$2 file=$3
  [ "$n" -lt "$START" ] && { echo -e "$n\t$name\tSKIP" >> "$STATUS"; return; }
  echo -e "$n\t$name\tRUNNING" >> "$STATUS"
  if beeline -u jdbc:hive2://lrh-1:10000 -f "$file"; then
    echo -e "$n\t$name\tOK" >> "$STATUS"
  else
    echo -e "$n\t$name\tFAILED" >> "$STATUS"; exit 1
  fi
}

run_step 1 dwd_event_clean   step1_dwd.sql
run_step 2 dwd_purchase_fact step2_fact.sql
run_step 3 dim_product       step3_dim.sql
run_step 4 dws_user          step4_dws_user.sql
# ...
```

**进度怎么读**：`cat status.tsv`。
**为什么不用 sleep 等**：用状态文件的变化做触发，比"睡 5 分钟再来看"精确得多。

### 9.3 耗时基线（案例项目实测，供你对比自己的环境）

| 环节 | 耗时 |
|---|---|
| DWD 全量跑批（5 步，含 1 次失败重试） | **20 分 53 秒** |
| DWS + ADS 全量（10 步，含 2 次失败重试） | **28 分 01 秒** |
| 走调度整链（16 节点，无失败） | **54 分 10 秒** |

> ⚠️ **性能对比前先问一句：基线稳不稳？**
> 案例项目发现过两次旧基线自相矛盾（同一作业 241s vs 155s、63s vs 152s，差一倍），
> 结论是**旧基线不可用于对比**。
> **必须在同一时间窗口、同一集群状态下重跑做严格 A/B。基线不可复现，对比就毫无意义。**

## 十、这一路上踩过的坑（回放）

| 坑 | 现象 | 教训 |

## 十二、自测

**每题标了对应的正文小节——答不出来就回去看那节，不要硬想。**

1. 为什么 ODS 层"不加工"是原则？举一个"在 ODS 做了清洗"导致的麻烦。—— 对应 **§3.1**
2. `COUNT(DISTINCT)` 回明细重算的原因，说得出具体例子吗？—— 对应 **§6.3**
3. "先聚合再关联"省掉了什么物理开销？—— 对应 **§6.2**
4. GMV 四路对账为什么要走四条不同路径？只走一条行不行？—— 对应 **§8.3**
5. 你的链路支持重跑吗？重跑一次数据会翻倍吗？—— 对应 **§九（9.1）**
6. 校验除了行数，还应该校验什么？—— 对应 **§8.4**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 为什么 ODS 不加工**
- 原则：**ODS 是"证据保全"，DWD 才是"加工车间"**；ODS 要能回答"上游给我的原始样子是什么"
- 反例 A：在 ODS 解析了时间格式 / 把空串转成 `'unknown'`
  → 三个月后有人想看**原始字符串**，**永远拿不回来**了
- 反例 B：在 ODS 就去了重 → 后来发现去重规则错了，要重新去重时，**重复行已经没了**
- 结论：清洗统一放 DWD，才有唯一口径、可重算

**2. COUNT(DISTINCT) 回明细重算**
- 例子：同一用户在类目下买了 2 个商品 → 商品层各算 1 个买家 → 加总变 2，**实际 1**
- 所以 `dws_category_event_day.buyer_cnt` **回 `dwd_event_log_di` 明细重算**，不从商品层 SUM
- 一句话：**聚合不可逆**——`SUM` 可加，`COUNT(DISTINCT)` 不可加

**3. "先聚合再关联"省掉什么**
- 错误写法：1063 万行 **先 JOIN** 14 万行维表 → 再 GROUP BY → **多一次大表 shuffle**（跨网络搬上千万行）
- 正确写法：先 `GROUP BY product_id, dt` 压到 **126 万行** → 再 JOIN 维表
- 省掉的物理开销：**网络传输 + 磁盘溢写**（shuffle 那两个最慢的通道）

**4. 为什么要四条路径**
- 四条路径走**不同的表、不同的聚合顺序**（明细 / 事实表 / 交易汇总 / 类目汇总）
- 它们能收敛，说明**中间每一层都没有算错**（重复、漏行、口径偏移都会导致对不上）
- 只走一条 = 只验证了一条路，链条里其他层错了照样"自洽"
- 案例实测：四路全部收敛到 **57,575,996.50**

**5. 你的链路能重跑吗**
- 能，因为是**幂等**的：全部 `INSERT OVERWRITE`、`CREATE` 前先 `DROP IF EXISTS`
- 重跑**不会翻倍**（`INSERT INTO` 才会）
- 验证办法：**连跑两次**，比行数与 GMV 是否一致 —— 这就是实验 9-3 干的事

**6. 除了行数还校验什么**
- **方向性违例（业务常识断言）**，应返回 0 行：
  `dau >= new_dau`、`view_uv >= purchase_uv`、`gmv >= 0`、比率 ≤ 1
- 加分项：写断言前先想清楚这个不等式是否**必然成立** ——
  案例里"购买 ≤ 加购"这条就**不成立**（15/31 天购买用户多于加购用户），写错了会误报
</details>
