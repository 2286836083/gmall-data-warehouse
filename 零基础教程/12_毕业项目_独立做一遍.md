# 12 · 毕业项目：独立做一遍

> **这章解决什么**：把前 11 章变成你自己的东西。
> 读别人的案例是"看懂"，自己从零做一遍才是"会做"。
>
> 这一章给你：**任务书 → 分阶段验收 → 自检表 → 面试问答**。

---

## 一、任务书

> 假设你刚入职一家公司，老板给了你一份原始数据和一句话需求。
> **从零开始，交付一个能每天自动更新、有可视化报表的离线数仓。**

### 1.1 给你的一份数据（任选其一，或者用你自己的）

| 数据集 | 说明 | 推荐度 |
|---|---|---|
| **你自己的数据** | 学校/实习/爬下来的任何结构化日志 | ⭐⭐⭐ **最好，面试时能讲出细节** |
| REES46 电商行为 | 本教程案例用的，Kaggle 公开 | ⭐⭐ 有基线可对照 |
| 某站点的访问日志 | 自己造：时间、用户ID、页面、停留时长 | ⭐ 数据量小，适合先练流程 |
| 公开数据集 | 纽约出租车、MovieLens 等 | ⭐⭐ 量大、字段丰富 |

**数据要求**（不满足就自己造）：至少 **100 万行、覆盖 ≥ 14 天、至少有一个数值字段和一个 ID 字段**。
太少了体会不到分布式的价值。

### 1.2 交付清单（**这就是验收标准**）

| # | 交付物 | 判据（怎么算做完了） |
|---|---|---|
| 1 | 一套能跑的集群 | `hdfs dfsadmin -report` 显示 ≥2 个 Live datanodes，且能真实读写 |
| 2 | **建模设计文档** | 每张表写了粒度、分层、字段含义；至少覆盖 ODS/DWD/DWS/ADS 四层 |
| 3 | 一套可重跑的 ETL 脚本 | 全部 `INSERT OVERWRITE`；连跑两次行数不变 |
| 4 | 落表数据 | 每层都有数据，行数记录成基线表 |
| 5 | **交叉对账结果** | 至少一条核心指标，用两条不同路径算，结果一致 |
| 6 | 一条调度工作流 | 有依赖关系、能一键运行、有成功实例 |
| 7 | 一个可视化页面 | 双击即开、离线可用、至少 3 张图 |
| 8 | **一份排错笔记** | 至少记录 3 个真实故障：现象 → 定位命令 → 根因 → 解法 |
| 9 | 一份项目 README | 别人照着它能把你的项目跑起来 |

> **第 5 条和第 8 条是大部分人交不出来的。交出来，你的项目就超过 80% 的求职项目。**

## 二、分阶段验收（每阶段一个明确的"做完"标志）

### 阶段一：环境（第 02、03 章）

- [ ] 三台（或一台伪分布式）虚拟机，主机名/IP/免密都配好
- [ ] `hdfs dfsadmin -report` → Live datanodes ≥ 2，**0 个 Missing blocks**
- [ ] `yarn node -list` → 节点数正确
- [ ] **真实读写测试通过**（不是只看进程在）
- [ ] 9870 / 8088 两个网页能打开

⚠️ **没做完别往下走。** 后面所有的错都会叠在这个错上面。

### 阶段二：数据接入（第 04、06 章）

- [ ] 原始数据传到集群
- [ ] ODS 表建好（**建议用外部表**），分区正确
- [ ] 装载完成，分区数 = 天数
- [ ] `SELECT COUNT(1)` 与源文件行数**对得上**

### 阶段三：建模设计（第 07 章）★

- [ ] **每张表能一句话说清粒度**
- [ ] 粒度声明写进了**表注释**（`DESC` 能看到）
- [ ] 标出了哪些字段是事实、哪些是维度
- [ ] 明确了哪些指标是 `COUNT(DISTINCT)`（不可加），并注明从哪里重算
- [ ] 定义了至少 3 个业务问题，每个对应一张 ADS 表

### 阶段四：ETL 实现（第 08 章）

- [ ] ODS → DWD：清洗规则**每条都有依据**（不是"我觉得该去重"）
- [ ] DWD → DWS：至少 2 个主题
- [ ] DWS → ADS：至少 3 张应用表
- [ ] **全部 `INSERT OVERWRITE`**，连跑两次行数不变
- [ ] 每行关键 SQL 有注释说明为什么这么写

### 阶段五：校验（第 08 章 §8）

- [ ] 层数/分区数/行数基线表
- [ ] **交叉对账至少一条**（核心指标走两条不同路径）
- [ ] 方向性违例检查（如 `dau >= new_dau`）返回 0 行

### 阶段六：调度（第 09 章）

- [ ] SQL 切分成节点（不是一个大文件塞一个节点）
- [ ] 工作流有依赖关系、已上线
- [ ] 至少 1 个 SUCCESS 实例
- [ ] 做过"连跑两次验证幂等"

### 阶段七：可视化（第 10 章）

- [ ] 定义了数据契约（字段/类型/粒度）
- [ ] 页面双击即开、离线可用
- [ ] 页面数字与 Hive 数字**对过账**

### 阶段八：调优与排错（第 11 章）

- [ ] 至少做过一次真实的调优，并记录前后耗时
- [ ] **排错笔记 ≥ 3 条**，每条有定位命令

## 四、面试问答（**照着准备，每个都要能讲 2 分钟**）

> **每题都给了答案要点，但你必须能讲出"自己项目里的版本"**（带上你自己的表名、你自己的数字）。
> 想深入某一题，按下表回看对应章节：

| 分组 | 回看章节 |
|---|---|
| 4.1 建模类（Q1–Q5） | **第 07 章**（粒度 / 分层 / 聚合不可逆 / SCD） |
| 4.2 执行原理类（Q6–Q10） | **第 04、05 章**（HDFS 读写流程 / YARN、MR、shuffle） |
| 4.3 调优排错类（Q11–Q16） | **第 11 章**（判断法则 / 退出码 / 控制面数据面）+ 第 09 章 |
| 4.4 项目决策类（Q17–Q20） | 第 07、08、10 章（真实数据 / 对账 / 口径一致） |

### 4.1 建模类（问得最多）

**Q1：为什么数仓要分层？**
> 三层原因：① 清洗逻辑只做一次（复用），② 口径统一（避免两张报表打架），③ 隔离变化（改源数据只改 DWD）。
> 举一个反面例子：不分层时，三个人写三条 SQL 各自清洗，空值处理不一样，数字对不上且谁也说不清谁对。

**Q2：什么是粒度？你项目里每张表的粒度是什么？**
> 一行代表什么。**必须能具体说出你项目里的表**，比如"用户×天"、"一笔成交一行"。
> 加分项：说"我把粒度写进了表注释，`DESC` 就能看到"。

**Q3：`COUNT(DISTINCT)` 能不能跨层加总？**
> 不能。举例：同一个用户在类目下买了两个商品，商品层各算 1 次，加总变 2，实际 1。
> 正确做法：回明细层重算。**补充：比率、平均值也都不可加。**

**Q4：事实表和维度表的区别？**
> 事实表记"发生了什么动作"（金额、次数），维度表记"动作的参与者是谁"（名称、类目）。
> 事实表存 ID，维度表存属性，靠 ID 关联 → 星型模型。

**Q5：维度属性变了怎么办？**
> SCD。Type 1 直接覆盖、Type 2 加新版本行（带生效/失效日期）。
> **诚实回答你项目里的做法**（如果没做，就说"当前是快照式维度，如果要保留历史视角我会用 Type 2"）。

### 4.2 执行原理类

**Q6：我提交一条 Hive SQL，物理上发生了什么？**
> beeline → HS2 → 编译成 MR 作业 → 向 YARN 申请资源 → RM 分配容器 → NM 起 JVM →
> 读 HDFS → map → shuffle（**落盘 + 跨网络**）→ reduce → 写回 HDFS。
> **加分**：说出"shuffle 是最贵的一步，因为它要落盘 + 跨网络搬"。

**Q7：NameNode 是干什么的？它碰数据吗？**
> 管目录和块位置（元数据在内存），**全程不碰数据**。客户端直接和 DataNode 传数据。
> 加分：所以块要 128MB 这么大——减少元数据条目数。

**Q8：为什么 MapReduce 慢？**
> 主要不是算得慢，是**中间结果要落盘 + 跨网络传输**（shuffle）。
> Spark 快在尽量放内存，但内存装不下时一样要落盘。

**Q9：HDFS 写文件的流程？**
> 问 NameNode 要地址 → 客户端发给第一个 DataNode → **流水线**接力复制到第二、三个 → 逐级回报 → 告诉 NameNode 写完。
> 加分：NameNode 不参与数据传输。

**Q10：副本为什么是 3？代价是什么？**
> 3 份能容忍坏 2 台（实际通常容忍 1 台 + 1 块盘）。代价：**写 1GB 实际写 3GB，可用容量只有 1/3**。

### 4.3 调优排错类（**拉开差距的地方**）

**Q11：你遇到过最难排查的故障是什么？怎么定位的？**
> **这里要讲你排错笔记里的真实案例。** 结构：现象 → 我最初的判断（**可以承认是错的**）→ 用什么命令推翻了它 → 真根因 → 解法。
> **主动说出"我一开始判断错了"是加分项**，说明你懂方法论而不是背答案。

**Q12：任务报 `GC overhead limit exceeded`，你怎么处理？**
> 第一反应是**加内存**，不是加 CPU。
> 判断法则：看这个作业"囤不囤数据"——大基数 GROUP BY / DISTINCT 这类必须放大容器。
> **加分**：说出"它不在 `Caused by` 链里，只在 Diagnostic Messages，我靠量级不匹配定位"。

**Q13：任务卡在 99% 不动？**
> 数据倾斜。先查 key 分布，再决定：过滤异常 key / 两阶段聚合（加盐）/ map-join。

**Q14：怎么判断一个服务真的可用？**
> 不用 `systemctl is-active`，用**外部判据**：端口在监听 + **发一次真实查询**。
> 加分：举例"HS2 标记 active 后还要 50 秒才真的监听端口"。

**Q15：调度显示任务已停止，就一定停了吗？**
> **不一定。** 控制面 ≠ 数据面。要 `ps` + `yarn application -list` 到数据面确认。
> 加分：讲 beeline 孤儿进程跑了 3 天的真实案例。

**Q16：退出码 143 和 137 分别说明什么？**
> 143 = SIGTERM（被叫停），137 = SIGKILL（常是 OOM）。
> **先看退出码再看日志**，否则会往完全错误的方向排查。

### 4.4 项目决策类

**Q17：为什么用真实数据而不是模拟数据？**
> 模拟数据会掩盖问题：案例里 `ads_dau` 每天恒为 1000、复购率恒 >0.99，**画出来是一条直线**，
> 所有分布问题和脏数据问题都发现不了。

**Q18：你怎么保证报表上的数字是对的？**
> 三层校验：① 行数与分区数基线；② **交叉对账**（GMV 走四条不同路径必须收敛）；
> ③ 方向性违例断言（如 新增 ≤ 活跃）。

**Q19：Spark 比 Hive 快多少？**
> **不要脱口而出"快很多"。** 案例实测：同 SQL 同资源，单会话连跑 8 段 **75s vs 389s（5 倍）**；
> 但每段各起一个会话时 **381s vs 421s（只快 10%）**，且轻作业上 Spark 反而更慢。
> **结论：收益主要来自会话复用，不是单条 SQL 快**（启动开销约 35 秒/次）。
> **加分**：补一句"我一开始的假设是 Spark 全面更快，被实测证伪了"。

**Q20：如果要重跑，你的链路安全吗？**
> 安全，因为幂等：全部 `INSERT OVERWRITE`，`CREATE` 前先 `DROP IF EXISTS`。
> 加分："我还实际连跑两次验证过行数不变"。

## 五、最后一件事：写一份 README

别人（包括三个月后的你）能不能照着它把项目跑起来，是检验你"真的做完了"的最后一道关。

README 至少包含：

```markdown
# 项目名

## 一句话说明
（这个项目做什么，解决什么问题）

## 环境
（几台机器、什么版本、端口）

## 数据
（来源、量级、字段说明）

## 表设计
（贴出表清单：表名 / 层 / 粒度 / 行数 / 说明）★ 粒度必须有

## 怎么跑起来
1. 启动服务：...
2. 建表：beeline -f ddl.sql
3. 跑数：bash run.sh
4. 预期结果：（贴出应有的行数基线）

## 怎么验证
（交叉对账 SQL + 期望值）

## 已知问题与坑
（排错笔记链接）
```
