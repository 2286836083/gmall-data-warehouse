## 一、先从一个具体得不能再具体的问题开始

假设你在一个电商公司，手上有一份用户行为日志，长这样：

```
2019-10-01 00:00:11 UTC,view,44600062,2103807459595387724,,shiseido,35.79,541312140,f7f8b3c8-...
2019-10-01 00:00:15 UTC,cart,44600062,2103807459595387724,,shiseido,35.79,541312140,f7f8b3c8-...
2019-10-01 00:01:02 UTC,purchase,1468464,2103807459595387724,electronics.smartphone,samsung,290.44,512066475,8a3f...
```

> 📌 **本项目对照**：这就是案例项目用的真实数据（REES46 电商行为数据集，2019 年 10 月单月）。
> 按用户 1/4 采样后是 **10,630,245 行**（`ods_event_log_di`，31 天分区）。

老板问了一句很朴素的话：**"我们每天有多少活跃用户？"**

你要做的逻辑只有一行 SQL：

```sql
SELECT dt, COUNT(DISTINCT user_id) FROM event_log GROUP BY dt;
```

**问题来了：这份数据有 10 亿行、1TB 大小。你的笔记本电脑 16GB 内存、500GB 硬盘。**

## 二、为什么一台机器搞不定——把"搞不定"算出来

不许用"数据太大了"这种含糊的说法。我们算一下物理账：

### 2.1 瓶颈一：读一遍就要很久

| 环节 | 速度 | 读 1TB 需要 |
|---|---|---|
| 机械硬盘 | ~150 MB/s | **约 1.9 小时** |
| SATA 固态 | ~500 MB/s | 约 33 分钟 |
| NVMe 固态 | ~3000 MB/s | 约 6 分钟 |
| 内存 | ~20 GB/s | 约 1 分钟 |

**物理事实**：只要数据必须落盘，单台机器光"把数据读一遍"就要以小时计。
而上面那条 SQL 至少要把全量数据读一遍。

> 有人会说"那把数据放内存里不就好了"。
> 那就要回答瓶颈二：**1TB 数据放不进 16GB 内存**。

### 2.2 瓶颈二：装不下

`COUNT(DISTINCT user_id)` 要同时记住"见过哪些用户"。用户数百万级，每人 8 字节 ID，加上哈希表的开销，
实测下来几百万用户就要几百 MB 到几个 GB 的常驻内存——**单机内存不够，操作系统会把内存换到硬盘（swap），速度掉几十倍**。

> 📌 **本项目对照**：这不是理论。案例集群最初三台各 4GB，
> 主节点上跑了 9 个 Java 进程，可用内存只剩 **601MB**，开始用 swap，整个集群慢到不可用。
> 按负载重新分配（7GB / 3.4GB / 4GB）后可用内存回到 4123MB（`实验分析/实验01_集群内存调优.md`）。

### 2.3 瓶颈三：一台机器坏了，活就停了

单机方案还有个致命问题：硬盘坏了数据全没了。
生产环境不允许"一块盘决定生死"。

### 2.4 那你可能会问：用 MySQL 不行吗？

不行——**因为 MySQL 解决不了上面任何一个瓶颈。**

先搞清楚 MySQL 是什么：它是一个**跑在一台机器上的数据库**。
你平时用的选课系统、教务系统，背后大概率就是它。

拿它对照 §2.1~§2.3 的三个瓶颈，逐个看：

| 瓶颈 | MySQL 能解决吗 | 为什么 |
|---|---|---|
| 读一遍要很久 | ❌ | 数据就存在**那一台机器的磁盘**上，读速照样被 150MB/s 卡死 |
| 内存装不下 | ❌ | 它还是**那一台机器**，内存照样 16GB |
| 硬盘就 500GB | ❌ | **1TB 数据物理上就放不进去** |
| 单机故障 | ❌ | 主库挂了切从库要数分钟，期间写入全停 |

而且它还有两个额外的麻烦：

1. **行式存储**：MySQL 按"整行"存数据。你只想统计 `user_id` 一列，
   它也得把每行 9 个字段全读出来 → **读的数据量是实际需要的 9 倍**
   （列式存储能解决这个，第 06 章讲 ORC 时会细说）。
2. **索引帮不上忙**：`COUNT(DISTINCT)` 是全表扫描型查询，索引救不了它；
   反过来，**每秒几万行的日志写入**会让 MySQL 的 B+ 树索引不断分裂重组，**写入先崩**。

**结论**：MySQL 是"一台更强壮的机器"，但我们的问题是"**一台机器**"本身。
给它换再大的硬盘、再多的内存，读 1TB 还是要以小时计——这是物理，不是配置问题。

> 💡 记住这个结论，第 06 章你会遇到一个看似矛盾的事：
> **Hive 里也有"表"和 SQL，但它不是数据库**——它恰恰是为了绕开这些限制设计的。

## 三、解法：分而治之（这是整个大数据领域的第一原理）

**核心思想只有一句话：既然一台机器读不完，就让 10 台机器各读 1/10。**

```
             1TB 数据
                │
    ┌───────────┼───────────┬───────────┐
    ▼           ▼           ▼           ▼
  机器A       机器B       机器C    …   机器J
  100GB      100GB      100GB        100GB
    │           │           │           │
  统计本机的用户  统计本机的用户  …
  （map：各算各的，不需要通信）
    │           │           │           │
    └───────────┴─────┬─────┴───────────┘
                      ▼
              汇总（reduce：把中间结果合起来）
                      ▼
                 最终答案
```

**这就是 MapReduce 这个名字的由来**：先 map（各干各的），再 reduce（合并）。

请注意这里的关键：**能这么拆，是因为计算是可分解的。**
`COUNT(DISTINCT)` 其实不能简单拆（A 机器和 B 机器可能有同一个用户）——
所以真正的做法是"先按用户分组，让同一个用户的数据一定落到同一台机器上，再各自去重、再相加"。

**这个"把同类数据搬到一起"的过程就叫 shuffle。它同时踩中最慢的两个环节：磁盘和网络。**

看一下硬件速度阶梯（每往下一档慢一个量级）：

| 环节 | 速度 |
|---|---|
| 内存 | ~20 GB/s |
| NVMe 固态 | ~3 GB/s |
| SATA 固态 | ~500 MB/s |
| 机械硬盘 | ~150 MB/s |
| **千兆网络（机器之间）** | **~125 MB/s** |

- map 在自己的机器上干活：读的是**本地磁盘**（150MB/s）
- shuffle 要把数据**跨网络**搬到另一台机器（125MB/s），到了那边**还要再写一次磁盘**

**量级有多大**：中间结果常常和输入数据**相当**——
1TB 输入，可能就有接近 1TB 要过一遍 125MB/s 的网络。

这就是"shuffle 是分布式计算里最贵的一步"的完整物理理由：
**它不是算法慢，是它必须走两个最慢的通道。**
第 05 章会拆开讲它的三个阶段（map 端排序落盘 → 网络拉取 → reduce 端归并）。

## 四、一旦变成多台机器，立刻冒出五个新问题

单机程序不需要考虑这些，所以初学者的直觉在这里全部失效：

| # | 新问题 | 物理上是什么 | 解决方案（组件） |
|---|---|---|---|
| 1 | 数据放哪、坏一块怎么办 | 同一份数据复制成 3 份，放不同机器 | **HDFS**（分布式文件系统） |
| 2 | 这个任务派给谁跑 | 需要有人知道"哪台机器还有空闲内存" | **YARN**（资源调度） |
| 3 | 任务跑到一半机器挂了 | 需要有人发现并重跑那一部分 | YARN + 计算框架的容错 |
| 4 | 我不想写 Java，我想写 SQL | 需要一个翻译官：SQL → 分布式计算任务 | **Hive** |
| 5 | 这一整套每天凌晨 2 点要跑一遍 | 需要一个闹钟 + 流程编排 + 失败告警 | **DolphinScheduler** |

**记住这张表，后面十几个组件都是它的展开。**
组件不是"别人都在用所以我也装"，每一个都对应一个具体麻烦。

## 五、离线数仓是什么（为什么要分层）

现在回答第二个问题：为什么数据要分 ODS / DWD / DWS / ADS 四层，而不是一次算完。

### 5.1 先看不分层会发生什么

如果每个需求都直接从原始数据算：

```
需求1（日活）    → 写一条 SQL 直接读原始日志
需求2（转化率）  → 再写一条 SQL 直接读原始日志
需求3（复购率）  → 又写一条 SQL 直接读原始日志
```

三个问题立刻出现：

1. **重复劳动**：三条 SQL 都要做同样的清洗（去重、解析时间、处理空值）
2. **口径打架**：A 同学习惯把空类目当 NULL，B 同学当成 `'unknown'` → 两张报表数字对不上，谁也说不清谁对
3. **改一次全崩**：源数据字段变了，三条 SQL 全要改，而且你不知道还有多少条没发现

### 5.2 分层的本质：把"清洗"和"算指标"拆开

```
ODS  原始数据层     把外面来的东西原样落地，一个字不改
  ↓
DWD  明细清洗层     去重、解析时间、拆字段、归一空值 —— 全公司只有这一份口径
  ↓
DWS  汇总层         按主题（用户/商品/类目/交易）做中度汇总，供多方复用
  ↓
ADS  应用层         一个需求一张表，直接给报表/大屏用
```

> **类比**：像做菜。ODS 是采购回来的原料，DWD 是洗好切好的净菜，DWS 是炒好的半成品，ADS 是装盘上桌的成品。
> **物理上是什么**：每一层都是 HDFS 上的一批文件 + MySQL 里的一条表结构记录。
> 层与层之间就是"读上一层的分区，算完写进下一层的分区"，一次 ETL 就是一批 MapReduce 作业。

**分层的收益**：清洗只做一次（在 DWD），口径只有一个来源；上层出问题只影响它自己；改源数据只改 DWD 一处。

> ⚠️ **一个真实教训**：分层不是摆设。案例项目的大屏最初**直接读 DWS 层**画图，跳过了 ADS。
> 表面能跑，但违反"应用层只消费 ADS"的约定，等于把应用和中间层绑死了。
> 后来补了两张 ADS 表修正，验证方式是**新旧导出文件逐字节比对**（`实验分析/实验11`）。
> ——**规则被绕过时往往不会报错，只会埋雷。**

### 5.3 什么叫"离线"

- **离线 / 批处理**：数据攒够一批再算，通常是 **T+1**（今天算昨天的数据）。凌晨跑批，早上看报表。
- **实时 / 流处理**：一条数据来了立刻算，秒级延迟（Kafka + Flink，本教程不讲）

本教程做的是**离线数仓**——这也是数据开发岗最基础、要求最多的部分。

## 六、全景图：一条数据从产生到上墙的完整旅程

把上面所有东西串起来。这张图后面每一章都会回到它，请记住自己在哪一步：

```
① 数据采集      用户在 App 上点击 → 埋点日志落到服务器磁盘
                                    ↓
② 数据接入      日志文件传到 HDFS（分布式文件系统）
                                    ↓  （自动切块、每块存 3 份）
③ ODS 建表      在 Hive 里建一张表指向这些文件
                                    ↓
④ DWD 清洗      写 SQL 做去重/解析/拆字段 → 生成新表（跑 MapReduce 作业）
                                    ↓
⑤ DWS 汇总      按主题聚合 → 生成新表
                                    ↓
⑥ ADS 指标      算出最终业务指标 → 生成小表（几十行到几千行）
                                    ↓
⑦ 导出          把 ADS 表导出成 CSV/JS
                                    ↓
⑧ 展示          ECharts 画成图，浏览器打开
                                    ↓
⑨ 调度          上面 ③~⑦ 由 DolphinScheduler 每天自动按顺序跑一遍
```

**每一步的物理代价**（这是面试官最爱追问的地方）——
编号对应上面全景图的 9 个步骤，**全列出来，不跳号**：

| 对应哪一步 | 消耗什么 | 量级 |
|---|---|---|
| ① 数据采集 | 在**业务方的服务器**上产生日志，不占我们集群的资源 | — |
| **② 上传到 HDFS** | **客户端出口带宽**（从你操作的那台机器发出去）+ 集群磁盘（写 3 份） | ★ 大头 |
| ③ ODS 建表 | 几乎为 0（只是在元数据里登记"有个表指向这个目录"，**不搬数据**） | — |
| **④ DWD 清洗** | 读 HDFS（网络+磁盘）→ 内存里算（**含 shuffle**）→ 写回 HDFS（又 3 份） | ★★ 最重 |
| **⑤ DWS 汇总** | 同 ④（也是一批 MR 作业，同样有 shuffle） | ★★ 最重 |
| ⑥ ADS 指标 | 数据量已经很小（几千行），很快 | 小 |
| ⑦ 导出 | 网络（把结果拉回本地）+ 本地磁盘 | 小 |
| ⑧ 展示 | 浏览器渲染，几乎为 0 | — |
| ⑨ 调度 | 几乎不消耗计算资源，只是定时触发 + 记录状态 | — |

> 💡 **"shuffle 不是一个独立步骤"**，它发生在 ④⑤ 这些 MapReduce 作业**内部**
> （map 之后、reduce 之前）。标注出来是为了提醒你：
> **真正的时间大头藏在作业内部，而不是藏在流程图上那些看得见的步骤里。**

**哪一步最可能成为瓶颈？**

先排除一个直觉答案：**不是 CPU**。离线批处理的大部分时间花在
**磁盘 IO**（读 HDFS、每份结果写 3 份）和**网络**（shuffle 搬运）上。
这也是"任务慢了就加 CPU"常常没用的原因——它没碰在瓶颈上。

经验排序：**shuffle（网络）> 写回 HDFS（磁盘 ×3）> 读 HDFS（磁盘）> 内存计算 ≫ CPU 计算**。

## 八、动手实验室（这一章没有集群也能做）

### 实验 1-1：亲手感受"单机 vs 分批"

不需要集群，用你自己的电脑做：

```bash
# 生成一个约 100MB 的测试文件（Linux/Mac/Git Bash）
yes "2019-10-01 00:00:11 UTC,view,44600062,2103807459595387724,,shiseido,35.79,541312140,abc" \
  | head -n 1200000 > events.csv

ls -lh events.csv          # 看大小
wc -l events.csv           # 看行数

# 统计不同用户 ID 的数量（模拟 COUNT(DISTINCT)）
time cut -d, -f8 events.csv | sort -u | wc -l
```

观察三件事：

1. `sort` 为什么要花这么久？——它在**把内存放不下的数据写到临时文件再归并**。
   **这就是 shuffle 的雏形**：数据量超过内存时，必须落盘 + 多路归并，磁盘 IO 和网络就是这么被吃掉的。
2. 再跑一次，是不是快很多？——操作系统缓存（page cache）。
   **分布式系统里也有类似的事**，所以"第一次跑慢、第二次快"不能作为性能结论（第 11 章会讲基线不可复现的坑）。
3. 把 `head -n 1200000` 改成 `12000000`（约 1GB），再感受一次耗时的变化——**这是数据量带来的非线性增长**。

> 这个实验里 `sort` 干的事（分块 → 排序 → 归并），就是 MapReduce 的 shuffle 干的事，只是后者要跨网络。

### 实验 1-2：算一下你自己的账

拿你的电脑回答：

| 问题 | 你的答案 |
|---|---|
| 内存多大？ | `free -g`（Linux） / 任务管理器（Windows） |
| 硬盘多大、剩多少？ | `df -h` |
| 按 150MB/s 算，读满你整个硬盘要多久？ | 自己算 |
| 如果数据是这个盘的 10 倍，你能怎么办？ | （答案应该是"分批 + 多台机器"） |

## 九、常见误解（这些说法都是错的）

| ❌ 错误说法 | ✅ 真相 |
|---|---|
| "大数据就是数据量大" | 数据量只是前提。**真正的难点是"一台机器装不下也读不完"带来的一系列工程问题**（副本、调度、容错、方言） |
| "Hadoop 是一个软件" | Hadoop 是一个**生态**：HDFS（存）+ YARN（调度）+ MapReduce（算）三件套，外面还有 Hive/Spark/HBase 等一堆 |
| "Spark 比 Hive 快，所以都该用 Spark" | 实测过：**同样 8 段 SQL，单会话连跑 Spark 75 秒 vs Hive 389 秒；但每段各起一次会话时 381 vs 421 秒，只快 10%**。<br>收益主要来自**会话复用**而非单条 SQL 快，启动开销约 35 秒/次（`实验分析/实验10`）。轻作业上 Spark 反而更慢 |
| "数据分层是为了好看" | 为了**复用清洗逻辑**和**统一口径**。不分层的项目，三个月后没人知道哪个数字是对的 |
| "我学会写 SQL 就能做数仓" | SQL 是工具。真正决定成败的是**粒度设计**和**口径定义**（第 07 章） |
| "跑批失败了重启一下就好" | 重启会掩盖证据。你要先分清"配置问题 / 资源问题 / 数据问题 / 被人杀掉"（第 11 章） |

3. 有了多台机器之后，多了哪五个单机不存在的问题？—— 对应 **§四**
4. 数仓分四层，解决了不分层时的哪三个具体问题？—— 对应 **§5.1**
5. 一次 ETL 物理上消耗的是什么资源？哪一步最可能成为瓶颈？—— 对应 **§六**

**这五个问题在面试里出现的概率很高。**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对——直接看答案等于没测）</summary>

**1. MySQL 为什么不行**
- MySQL 是跑在**一台机器**上的数据库，§2.1~§2.3 的三个瓶颈它一个都解决不了
- 量化：机械盘 150MB/s，读 1TB 约 **1.9 小时**；16GB 内存装不下；500GB 硬盘物理上放不下 1TB
- 加分项：行式存储要读整行（实际只需 1 列，多读 9 倍）；COUNT(DISTINCT) 是全表扫描，索引帮不上忙；高频写入会先压垮 B+ 树索引

**2. 哪一步跨机器搬数据**
- **shuffle**：把"同一个 key"的数据搬到同一台机器
- 为什么贵：同时走两个最慢的通道——**网络**（千兆 ~125MB/s）+ **磁盘**（两端各读写一次），且中间结果量级常与输入相当
- 对照：内存 20GB/s，是千兆网络的约 160 倍 → 所以原则是"能不搬就不搬"，map 端能算完就在 map 端算完

**3. 五个单机不存在的问题**
- ① 数据放哪、坏一块怎么办 → HDFS 副本
- ② 任务派给谁跑 → YARN
- ③ 跑到一半机器挂了 → 容错重试
- ④ 想用 SQL 不想写 Java → Hive
- ⑤ 每天定时自动跑 → 调度

**4. 分层解决的三个问题**
- ① **重复劳动**：每个需求重复做同样的清洗
- ② **口径打架**：不同人处理空值/去重不一样，数字对不上
- ③ **改一次全崩**：源数据一变，所有 SQL 都要改，还找不全

**5. ETL 的物理消耗与瓶颈**
- 消耗三类资源：**磁盘 IO**（读 HDFS + 结果写 3 份）、**网络**（shuffle）、**内存**（分组/去重的哈希表）
- 最可能的瓶颈：**shuffle（网络）**，其次是写回 HDFS 的三份磁盘写入
- 关键认知：**CPU 很少是瓶颈**——所以"任务慢了加 CPU"常常没用
</details>
