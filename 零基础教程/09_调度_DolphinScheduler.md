# 09 · DolphinScheduler：让它每天自己跑

> **这章解决什么**：把第 08 章那条"手动一步步敲"的链路，变成**每天凌晨自动跑、失败自动告警、可以一键重跑**的产品。
>
> 这一步做完，你的项目才从"一堆 SQL 脚本"变成"一个系统"。

---

## 一、为什么需要调度（不手动跑不行吗）

假设你的链路有 16 个步骤，每天跑一次。手动跑会遇到：

| 问题 | 手动跑的后果 |
|---|---|
| 步骤有依赖 | 你得盯着上一步跑完才能敲下一步，20 分钟干等 |
| 半夜要跑 | T+1 的数据要早上 8 点前 ready → **你得凌晨 3 点起床** |
| 中间失败了 | 你不知道，等老板问"今天报表呢"才发现 |
| 失败了要重跑 | 从头再来一遍？从失败那步接着跑？ |
| 要补历史数据 | 补 30 天 = 手动跑 30 遍 |
| 谁跑过、跑多久 | 没有记录，无法追溯和优化 |

**调度系统就是解决这六个问题的。** 它不是一个可选组件，是**生产环境的必需品**。

## 二、DolphinScheduler（DS）的核心概念

> 国产开源调度系统，中文界面、Web 上拖节点建工作流，对新手非常友好。案例集群用 3.1.8。

### 2.1 五个概念（从大到小）

| 概念 | 是什么 | 类比 |
|---|---|---|
| **项目（Project）** | 顶层分组 | 一个文件夹 |
| **工作流（Workflow / Process）** | 一张 DAG 图，定义"哪些任务、什么顺序" | 一份流程图 |
| **任务（Task）** | 图里的一个节点，比如"执行一个 SQL 文件" | 一道工序 |
| **实例（Instance）** | 工作流**跑起来的那一次** | 这一批活 |
| **定时（Schedule）** | "每天 2:00 跑一次" | 闹钟 |

**工作流 vs 实例**：工作流是**模板**（画一次），实例是**每次运行**（每次生成一条记录）。
改模板不影响历史实例。

### 2.2 架构：四个角色

```
        ┌──────────────────────────────────────┐
        │            Web UI（浏览器）            │
        └───────────────────┬──────────────────┘
                            │ HTTP
        ┌───────────────────▼──────────────────┐
        │              API Server               │  收发请求
        └───────────────────┬──────────────────┘
                            │
        ┌───────────────────▼──────────────────┐
        │          Master Server（主）           │  解析 DAG、拆任务、派活、容错
        └───────────────────┬──────────────────┘
                            │  经 ZooKeeper 发现存活的 worker
        ┌───────────────────▼──────────────────┐
        │        Worker Server（从，可多个）      │  ★ 真正执行任务的那台机器
        └──────────────────────────────────────┘
```

| 角色 | 案例集群 |
|---|---|
| master | lrh-1（端口 5678） |
| worker | lrh-2、lrh-3（端口 1234） |
| api | lrh-1（端口 12345，Web UI 走这个） |
| alert | lrh-1（告警） |

**ZooKeeper 在这干什么**：master 和 worker 都向 ZK 注册自己的地址，
master 通过 ZK 知道"现在有几个 worker 活着"，才能派活。

**Web UI**：`http://<主节点>:12345/dolphinscheduler`（默认 `admin` / `dolphinscheduler123`）

> ⚠️ **DS 不会开机自启**（案例集群是这样）。重启后要手动拉起 master → worker → api。

## 三、实操：把第 08 章的链路接进 DS

### 3.1 先把 SQL 切成"一个节点一段"

**为什么必须切**：调度的最小单位是"任务节点"。
一个跑 28 分钟的 SQL 文件放到一个节点里，你看不到它跑到哪一步、失败也不知道是哪一步。

案例项目的做法：把主 SQL 切成 16 段，每段一个节点：

```
preflight（开工前检查残留）
  → ods_ready（确认 ODS 就绪）
  → dwd_ddl（建表）
  → dwd_event_clean        ← 最慢的之一（8m37s）
  → dwd_purchase_fact
  → dwd_dim_product        ← 7m36s
  → dws_user
  → dws_product
  → dws_category
  → dws_trade
  → ads_active_user
  → ads_funnel
  → ads_repurchase
  → ads_top_product
  → ads_category
  → ads_trade
  → verify（三层校验）     ← ★ 实测最慢的节点：15m23s（占整链 28%）
```

> 💡 **为什么校验节点最慢**：`evt_verify.sql` 里的 `UNION ALL` 被 Hive 编译成 **6 个串行 MR 作业**。
> 想优化就把校验拆成多个并行节点，或者改写 SQL 减少作业数。

### 3.2 建工作流的步骤（Web UI）

1. **建租户**：安全中心 → 租户管理 → 创建（租户名要对应 Linux 上的真实用户，任务是以它身份执行的）
2. **新建工作流**：项目管理 → 工作流 → 创建工作流
3. **拖节点**：从左侧拖 `SHELL` 或 `SQL` 节点到画布
4. **连线**：从上游节点右侧拖到下游节点（**这就是依赖关系**）
5. **配置每个节点**：
   - 节点名称（见上）
   - 任务类型：`SHELL`
   - 脚本内容：`beeline -u jdbc:hive2://lrh-1:10000 -f /home/lrh/workspace/new_chain/ds_steps/step_04.sql`
   - 超时时间：**必须设**（且必须落在 (0, 86400] 秒之间）
6. **保存 → 上线**（**不上线不会出现在调度里**）
7. **运行**：点"运行"，生成一个实例
8. **看实例**：工作流实例 → 点进去看每个节点的状态和日志

> ⚠️ **一个真实踩过的坑**：程序化建工作流时自己指定的 task code **不能超过 2^53**（9007199254740992）。
> 超过之后，浏览器用 JS 双精度浮点解析，**多个不同 code 会塌缩成同一个数**，
> 结果画布上 16 个节点只剩 1 个。而**数据库里是 64 位整数，执行完全正常**——
> 属于"跑得对、显示全错"，自动化测试发现不了，**只能人眼看到**。
> **解法：在网页上拖节点建，让 DS 自己生成 code。**

### 3.3 幂等：调度能用的前提（★ 最重要的设计约束）

**调度的世界里，重跑是常态**（失败了要重跑、要补数、要回溯）。
所以**每个任务都必须能安全地重复执行**。

| ❌ 不幂等 | ✅ 幂等 |
|---|---|
| `INSERT INTO TABLE t ...` | `INSERT OVERWRITE TABLE t PARTITION(dt) ...` |
| `CREATE TABLE t` | `DROP TABLE IF EXISTS t; CREATE TABLE t` |
| `LOAD DATA INPATH`（未加 OVERWRITE） | `LOAD DATA ... OVERWRITE INTO TABLE ...` |
| 追加写文件 | 覆盖写文件 |

**一句话**：**离线数仓里，`INSERT INTO` 基本等于 bug。**

### 3.4 定时与补数

- **定时**：工作流上线后 → "定时"按钮 → 设 crontab（如 `0 0 2 * * ?` 每天凌晨 2 点）→ 设置生效时间范围
- **补数**：指定日期区间，批量生成历史实例（比如补最近 30 天）

> 📌 **本项目对照**：案例集群的 `t_ds_schedules` **仍然是空的**——
> 也就是说"定时调度"这个功能**从未真正配置过**，一直是手动触发。
> 这是有意的选择：全量覆盖 31 天每次要 54 分钟，配了定时就会真的每天占资源。
> **配定时之前要想清楚三件事**：增量口径、互斥（上次没跑完别起下一次）、失败告警。

## 四、告警与监控

| 该配的 | 说明 |
|---|---|
| **失败告警** | 工作流实例失败时发邮件/钉钉。默认 `warningType=NONE` 是**不发**的，要改 |
| **超时告警** | 节点超过预期时间没结束 |
| **worker 心跳** | 通过 `/monitor/workers` 或 ZK 看有几个 worker 活着 |

> 📌 **真实故障**：案例项目有一次跑批，lrh-3 的 worker **掉注册**了。
> DS 的容错机制自动把那个任务换到 lrh-2 重跑（**容错生效，数据无损**），
> 但旧作业没被杀掉，两个作业抢资源 → 那次整链跑了 96 分 58 秒（比基线慢 43 分钟）。
> **这说明：容错能保住正确性，但可能牺牲性能。监控要看的不只是"成功没成功"，还有"花了多久"。**

## 五、★ 控制面 vs 数据面（最重要的一条排错原则）

这是案例项目用一次真实事故换来的认知：

**事故**：在 DS 上点了"停止"，DS 里显示 `state=9 (KILL)`、`exitStatusCode:143`，看起来停了。
**实际**：lrh-1 上的 `beeline` 进程**还活着**，跨了 3 天把 5 天的数据全跑完了。

**根因（物理层面）**：
DS 的任务脚本是 `ssh lrh-1 'beeline ...'`。
**非交互 SSH 会话没有终端**，ssh 断开时 sshd 不发 SIGHUP → 远端进程变成孤儿。
DS 只杀得掉 worker 机器上的进程树，**杀不到另一台机器上的 beeline**。

**由此得出的原则**：

> **调度系统说"已停止"，只是控制面的状态。你必须到数据面去确认它真的停了。**

```bash
# 数据面确认（这两个命令必须都跑）
ps -ef | grep "[j]dbc:hive2"        # 还有没有 Hive 客户端在跑
yarn application -list              # 还有没有 YARN 作业在跑
```

**预防措施**：工作流的**第 1 个节点做 preflight 检查**——
发现有残留进程就拒绝开工，避免两个作业抢资源、互相污染数据。

## 六、常见坑

| 现象 | 根因 | 解法 |
|---|---|---|
| 点"停止"后任务还在跑 | 控制面 ≠ 数据面（见上） | 到数据面 `pkill -f 'jdbc:hive2'`；加 preflight 检查 |
| 退出码 143 | SIGTERM，**被主动停止** | 别当成程序错误去查日志 |
| 退出码 137 | SIGKILL，通常是 OOM | 查内存（第 11 章） |
| 画布上只剩 1 个节点 | task code > 2^53 | 网页上重建，让 DS 自己生成 code |
| 节点数莫名翻倍（16 变 32） | `PUT` 更新会往 `*_log` 历史表再写一份 | 清库要连 `*_log` 表一起清；**改工作流用"删掉重建"而不是"更新"** |
| 实例永远 RUNNING 且不下发任务 | 用了"从指定节点重跑"，触发 master NPE 死循环 | **要重跑就整条重跑**（反正幂等）。别用那个功能 |
| 任务一直等待 | worker 都没注册上 | 看 ZK 注册 / `/monitor/workers` |
| 定时没生效 | 没点"上线"，或定时状态是 OFFLINE | 上线 + 设 `ONLINE` |

> ⚠️ **"从指定节点重跑"这条特别提醒**：案例项目实测 **3/3 必挂**——
> master 进入 NPE 死循环，CPU 打满、日志每秒涨几千行（2 分钟 179MB），
> **重启 master 修不好**，必须停 master + 从库里删掉那条实例。

## 七、动手实验室

### 实验 9-1：建一条三节点的最小工作流

```
节点 A：SELECT 1（SHELL 任务，echo 一句话）
节点 B：依赖 A，跑一条 Hive 查询
节点 C：依赖 B，跑一条校验查询
```

要求：
- 三个节点串行连线
- 给每个节点设超时（比如 300 秒）
- 上线 → 运行 → 在实例页面看到 3 个 SUCCESS

### 实验 9-2：故意让中间节点失败

把 B 的 SQL 写错（引用一个不存在的表），运行后观察：

1. B 的状态是什么？（FAILED）
2. C 的状态是什么？（**应该是"未运行"，而不是失败** —— 依赖没满足）
3. 修好 B 之后，你怎么让它继续？（**整条重跑**，不用"从指定节点重跑"）

### 实验 9-3：验证你的任务是幂等的

**把工作流连跑两次**，然后：

```sql
SELECT COUNT(1) FROM gmall.dws_trade_day;    -- 还是 31 吗？
SELECT SUM(gmv) FROM gmall.dws_trade_day;    -- 还是 57,575,996.50 吗？
```

**如果行数翻倍了，说明你用了 `INSERT INTO`** —— 现在改还来得及。

<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 六个问题**
① 步骤有依赖（要等上一步）
② 半夜要跑（T+1 数据早上要 ready）
③ 中间失败不知道（没有告警）
④ 失败了不知道从哪重跑
⑤ 要补历史数据（补 30 天不能手动跑 30 遍）
⑥ 谁跑过、跑多久（没有审计记录）

**2. 工作流 vs 实例**
- **工作流** = 模板（DAG 图，画一次）
- **实例** = 每次运行生成的一条记录（跑一次一个实例）
- 关键：改模板**不影响**历史实例

**3. 为什么必须幂等**
- 因为调度的世界里**重跑是常态**：失败重跑、补数、回溯
- 不幂等例子：
  - `INSERT INTO TABLE t ...` → 重跑一次**数据翻倍**
  - `CREATE TABLE t` → 重跑直接报"表已存在"
  - `LOAD DATA` 不带 `OVERWRITE` → 数据重复加载
- 幂等写法：`INSERT OVERWRITE` / `DROP IF EXISTS` 再 `CREATE`
- 一句话记住：**离线数仓里，`INSERT INTO` 基本等于 bug**

**4. 控制面 vs 数据面**
- **控制面** = 调度系统显示的状态（SUCCESS / KILL / 143）
- **数据面** = 数据真的产出了吗 / 进程真的停了吗
- 案例：DS 显示 `state=9 (KILL)`、`exitStatusCode:143`，但 lrh-1 上的 `beeline` **还活着，跨 3 天跑完了 5 天数据**
- 根因：非交互 SSH 没有终端 → ssh 断开发不出 SIGHUP → 远端进程变孤儿
- 纪律：**必须到数据面确认**
```bash
ps -ef | grep "[j]dbc:hive2"
yarn application -list
```

**5. 退出码**
- **143** = SIGTERM（**被主动停止**）→ 第一反应是"谁停的"，不是"找 bug"
- **137** = SIGKILL（常见 OOM）→ 查内存
- 纪律：**退出码先于日志文本**（143 那次日志尾部看起来像 SQL 报错，实际是被人停的）

**6. 配定时前要确定的三件事**
① **增量口径**（全量覆盖还是按天增量；案例现在是全量 31 天，约 54 分钟/次）
② **互斥**（上一次没跑完，别起下一次）
③ **失败告警**（`warningType` 默认是 `NONE`，也就是**不发告警**，必须改）
- 加分项：案例集群的 `t_ds_schedules` **至今是空的** —— "定时调度从未真正配置过"，
  是**有意不配**（手动触发演示更可控）。**知道自己的项目哪里没做，比假装都做了重要。**
