一、三节点集群物理架构 Physical topology

集群跑在 VMware Workstation 的三台 Ubuntu Server 虚拟机上，同处一个 NAT 网段并用静态 IP 互认主机名。所有管理类组件集中在 lrh-1，存储与计算分散在 lrh-2 / lrh-3，HDFS 副本因子为 3，真正落在三台机器上。

两个容易踩的点：Hadoop / Hive / ZooKeeper / MySQL 都是 systemd 开机自启，而 DolphinScheduler 不自启——虚拟机每次重启后要手动拉起 api / master / alert 和两台 worker；另外 lrh-1 实测可用内存只有 3868MB，DS 堆内存必须锁死 512MB，不能同时开 alert-server。

二、数仓分层与数据流向 Data lineage

同一份数据在数仓里被加工四次，每层只干一件事：ODS 原样存、DWD 洗干净、DWS 做汇总、ADS 出指标。层与层之间靠 Hive SQL 衔接，全流程由 DolphinScheduler 编排成工作流定时驱动。

表 1 · 分层设计
分层全称它做什么数据粒度存储格式
ODS Operational Data Store 原始数据原样接入，不做任何加工，保留问题数据以便回溯 每条原始记录 按天分区 · TextFile
DWD Data Warehouse Detail 去重、空值处理、格式标准化、脏数据过滤，沉淀干净明细 每条清洗后记录 按天分区 · Parquet
DIM Dimension 用户、商品等维度信息，为事实表提供关联属性 每个维度实体一条 全量快照
DWS Data Warehouse Summary 按用户 / 商品 / 订单三个主题做日粒度宽表汇总 每主体每天一条 按天分区 · Parquet
ADS Application Data Store 直接面向业务的指标结果，供看板与报表直读 每指标每天一条 非分区 · Parquet

三、DolphinScheduler 调度 DAG Workflow

工作流 gmall_dw_pipeline 共 9 个节点，前 4 步严格串行，DWS 三个主题互不依赖可并列执行，最后由 ADS 指标计算收口并做结果校验。等待所有节点成功需要约 1 小时 10 分钟。

六、关键运行参数 Constraints

  • 数据规模：商品 500 条、行为日志 10 万条、订单 5 万条，按 5 天分区落库（可扩展至 30 天 / 百万级）。
  • 副本因子 3：真实分布在三台 DataNode 上，单节点宕机不影响数据完整性。
  • 内存红线：lrh-1 实测 3868MB，全栈起完后 available 约 300MB，swap 用到 1.7GB。DS 堆锁定 -Xms512m -Xmx512m，不随意调大。
  • 任务必须后台跑：长任务用 setsid nohup ... &，避免 ssh 断线导致任务中断。
  • 关机前先停 Hadoop：sudo systemctl stop hadoop，防止 HDFS 元数据损坏。
  • Hive 仓库真实路径：/user/hive/warehouse/gmall.db，由 hive.metastore.warehouse.dir 决定。
