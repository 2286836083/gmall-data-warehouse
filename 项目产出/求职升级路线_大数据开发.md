# 求职升级路线：从「跑通的数仓」到「讲得清的大数据开发项目」

> 制定日期：2026-10-20
> 目标岗位：**大数据开发**（校招）
> 关键外部时间点：**2027 年 3–5 月暑期实习投递**（不由我们决定）
> 状态：**P0 未开始**
> 前置结论：项目底子够，缺的是「可验证的形态」+「自己能讲透的深水区」

---

## 〇、一句话诊断

**组件不缺，形态缺；坑不缺，讲法缺。**

现在这套东西在技术上已经够到"可以投简历"的门槛了（1063 万行真实数据、16 节点调度、有前后对照的调优、反直觉的双引擎结论）。它不够，是因为：

1. 所有证据只存在于 `D:\数据开发` 和集群里，**外部无法验证**；
2. 每一处结论都是"AI 实现 + 我验收"，**面试追问到第三层会断**；
3. 岗位要求里的**编程语言（Java/Scala）**这一栏是空的。

三条都能补，而且补的顺序很重要。

---

## 一、岗位决定了优先级（全篇最重要的一节）

大数据开发和"数据仓库工程师"是两种岗位：

- **数仓工程师**：考建模、指标口径、业务理解
- **大数据开发**：考**引擎原理 + 代码能力 + 场景设计**

按校招实际权重重排：

| 能力 | 权重 | 现状 | 说明 |
|---|---|---|---|
| **Java / Scala** | ★★★★ 门槛 | ❌ **空** | JD 普遍写"熟悉 Java/Scala"；Spark 源码是 Scala |
| Spark / Hive 原理 | ★★★★ | 🟡 半 | 会调参，**不会看执行计划解释为什么** |
| SQL | ★★★ | ✅ 强 | 窗口函数、多表关联都没问题 |
| 数仓建模 | ★★★ | 🟡 够用 | 分层 + 粒度声明已做，缺 SCD/拉链表 |
| 实时 Flink | ★★★ | ❌ 空 | 一线大厂近乎必问 |
| 调度运维 | ★★ | ✅ 强 | DS 那套坑是加分项，不是减分项 |
| 数据湖 | ★★ 加分 | ❌ 空 | Iceberg / Hudi / Paimon |

### 为什么 Java/Scala 排第一，而不是 Flink

1. **它是筛选条件，不是加分项**。语言不过关，简历会被直接筛掉，后面再强也看不到。
2. **它决定你能不能把"现象"讲成"机制"**。现在所有调优结论都是"改参数前后对比"：512MB 失败 637 秒，1024MB 63 秒成功。面试官问"为什么"，答"因为内存不够"——这是现象。能答"因为 `GROUP BY product_id, dt` 有 430 万组合，聚合要驻留内存做 hash，容器 -Xmx410m 装不住触发 GC overhead；而且这是 Map 端聚合失效、退化成单 reducer 之后的必然结果"——这才是机制。
3. **面试必问"你自己写过 UDF / 算子吗"**。现在答不出来。

> 一句话：**Flink 让你多一个技能点，Scala 让你这个项目的所有结论都变得可信。**

## 四、主线路线

```
P0 形态化 ──► P1 Scala+引擎原理 ──► P2 实时链路(Docker) ──► P3 数据湖增量
  ↑ 2-3周         ↑ 4-6周 门槛级          ↑ 4-6周 高频考点         ↑ 3-4周 加分，可砍
  ↑ 所有事情的前提   ↑ 决定一面过不过        ↑ 与 P1 无依赖，可并行
```

### P0 · 形态化（2–3 周）

**目标**：让一个陌生人 5 分钟内能判断"这个项目是真的"，并且你能不看文档讲 15 分钟。

| 动作 | 验收标准（外部判据） |
|---|---|
| P0-1 清理敏感信息 | `VMware/sshkeys/db_ed25519`（真 OpenSSH 私钥）不入库；口令统一为占位符；`git ls-files \| grep -c sshkeys` 返回 0 |
| P0-2 建仓库 | GitHub 可访问；README 正常渲染；`git log` 首条提交不含私钥（历史里也没有） |
| P0-3 写 README | 结构＝**难点 → 方案 → 量化结果**；含架构图、30 张表链路、6 个业务问题导航 |
| P0-4 录演示视频 | **3 分钟**：DS 画布 → 跑起来 → 表行数对账 → 大屏。录屏能播放，不靠嘴说 |
| P0-5 三个故事讲到第三层 | 内存调优 / 双引擎反直觉 / 2^53 bug，每个都能扛住"为什么→为什么→为什么" |
| P0-6 自己跑一遍 | **不看文档**，从 ODS 装载跑到 ADS 校验，全程自己敲命令，结果与基线一致 |

**为什么先做 P0**：成本最低（2-3 周）、收益最直接（简历能不能投出去）、风险最高（私钥一旦推上去，历史里永久保留）。

### P1 · Scala + 引擎原理（4–6 周）★ 门槛级

**目标**：从"改参数试出来的"变成"读执行计划看出来的"。

#### 选型（已定，不再讨论）
- **Scala 2.12**（Spark 3.5.x 官方编译版本就是 2.12，别用 2.13 或 3.x）
- 构建工具 **Maven**（比 sbt 简单，IDEA 开箱即用）
- 运行方式 `spark-submit --master yarn --deploy-mode client`

#### 作业选型（关键，不是 Hello World）
选**商品主题那张 DWS**（就是 `GROUP BY product_id, dt` 出现过 430 万组合、把 512MB 容器压爆的那张）。
表名以 `项目产出/数仓表清单与业务问题映射.md` 为准。

理由：它是已知的 OOM 现场，重写后能直接对照，不需要另造场景。

#### 分四步，每步都要有判据

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| 1.1 | 环境 | `spark-submit --version` 显示 3.5.9 / Scala 2.12；一个 `WordCount` 能在 YARN 上跑通并 `SUCCESS` |
| 1.2 | DataFrame API 重写 | 用 Scala `Dataset` API 重写该段聚合（`groupBy` + `agg`），**至少含一个自定义聚合或 UDF** |
| 1.3 | **对账** | 结果写入隔离库（如 `gmall_bench2`），**行数与 `gmall` 逐项一致**；GMV 等指标 round 后逐位一致 |
| 1.4 | **执行计划对比** | `explain(true)` 打印 Scala 版和 SQL 版 physical plan，指出：shuffle 次数、是否走 Map 端聚合（`partial_` 聚合）、join 策略（broadcast vs sort-merge） |

#### 交付物
- `实验分析/实验13_Scala重写DWS与执行计划对比.md`
- 一段能背下来的话："同一逻辑我写了 SQL 和 Scala 两版，行数逐项一致；A 方案 X 秒、B 方案 Y 秒，差在 physical plan 里 shuffle 是 2 次还是 3 次 / Map 端有没有做预聚合。"

#### ⚠️ 常见坑（提前写在这，避免重复踩）
- Spark 3.5.9 默认读 Hive 需要 `spark.sql.catalogImplementation=hive` + metastore 3.1.3 配置，**已在集群配好，别覆盖**（见 `Spark教程/03`）
- 写分区表必须 `partitionOverwriteMode=dynamic`，否则**先清空整表**（这条已经踩过一次）
- Scala 的 `null` 与 `Option` 在 join 后要显式处理，否则对账会少行

### P2 · 实时链路（4–6 周）· Docker 独立

**目标**：不是跑通一个 Flink demo，而是**让实时结果和离线结果对得上账**。

#### 架构（全部在 Docker，不碰 VMware）
```
CSV 回放脚本 ──► Kafka ──► Flink SQL(事件时间窗口) ──► MySQL / 文件
                              ↑
                    与 ADS 离线结果同日对账
```

#### 步骤

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| 2.1 | `docker-compose` 起 Kafka + Flink | `localhost:8081` 能打开 Flink UI，JobManager/TaskManager 均 RUNNING |
| 2.2 | 回放器 | 从 `D:\数据集\sampled_oct2019\2019-10-XX.csv` 按**事件时间戳节流**发送（不是一次性灌），速率可调 |
| 2.3 | Flink SQL 作业 | 1 分钟滚动窗口算 GMV / UV，输出到 MySQL |
| 2.4 | **对账** | 同一天：实时算出的 GMV vs ADS 离线结果，**差异 < 0.1% 或能解释每一笔差异** |
| 2.5 | 主动制造乱序 | 让回放器打乱顺序 / 注入迟到数据，观察 watermark 行为，记录"丢了哪些、为什么" |

#### 这一步真正的价值
面试问 Flink 不会问"怎么装"，会问：**事件时间 vs 处理时间、watermark 怎么定、迟到数据怎么办、exactly-once 怎么保证**。
2.5 那一步就是专门为了能回答这些。

#### 资源分配建议
Docker Desktop 限 8 GB / 8 核；Kafka 1 GB、JobManager 1.5 GB、TaskManager 3 GB，余量留给 Windows。

### P3 · 数据湖增量 + 数据量放大（3–4 周）· 加分项，**可砍**

**目标**：把"每天全量重写 54 分钟"这个硬伤变成亮点。

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| 3.1 | Spark 加 `iceberg-spark-runtime` | `CREATE TABLE ... USING iceberg` 成功；不新增常驻服务、内存增量≈0 |
| 3.2 | ODS 全量 → 增量 append | 按天追加，`select count(*)` 与 Hive 分区表一致 |
| 3.3 | DWD 用 `MERGE INTO` 合并 | 重跑同一天数据**幂等**（跑两次行数不变）——这是增量表的真正考点 |
| 3.4 | 数据量放大 **4 倍** | 采样 25% → 100%（4,244 万行）；对比**全量重写耗时 vs 增量合并耗时** |

#### 能讲的知识点（都是面试高频）
表格式与 ACID、快照与时间旅行、隐藏分区、小文件合并（compaction）、`MERGE INTO` 的幂等性。

## 五、并行轨道（不占主线，但必须同时做）

### 5.1 场景题答案库（性价比最高，几乎零新增知识）

你已经踩过的坑，恰好覆盖了面试场景题的大部分。**按题目形式重排，不是按时间顺序。**

| 面试题 | 你项目里的真实素材 |
|---|---|
| 数据倾斜怎么处理？ | `GROUP BY product_id, dt` 430 万组合 → 容器的实测反应 |
| 小文件怎么合并？ | 每天一个分区、31 个 HDFS 文件的实际形态 |
| 怎么保证幂等 / 重跑安全？ | 16 节点流水线整条重跑约 54 分钟，为什么不支持"从中间节点重跑" |
| 全量 vs 增量怎么选？ | P3 的前后对比 |
| 容器内存怎么定？ | 512MB 失败 / 1024MB 成功，**判断依据是"有没有要同时装住大量数据的结构"** |
| 调度失败怎么排查？ | worker 掉注册 → DS 容错自动换节点重跑（实测多花 43 分钟但数据无损） |
| 元数据/口径不一致怎么办？ | 中文注释乱码根治、空值是空串不是 NULL |
| 内存不足怎么定位？ | `GC overhead limit exceeded` 不在 `Caused by` 里，在 task 的 Diagnostic Messages |

产出：`项目产出/面试场景题_项目实证版.md`

### 5.2 算法（硬性，不属于项目）

大数据开发校招同样手撕代码。高频 100–150 题，从现在起每周固定投入，**不要等项目做完再开始**。

## 六、被证伪的假设（记录在此，避免重犯）

| 我曾以为 | 实情 | 教训 |

| "三节点硬件上不了 Flink+Kafka" | 错在**默认要塞进 VMware**。本机 31.7 GB + Docker 完全跑得动 | 设计前先问"资源池是哪一个"，别把两个环境混成一个 |

## 八、最小可行版 vs 完整版（时间不够时砍哪个）

| 版本 | 内容 | 效果 |

| **最小可行（约 6 周）** | P0 + P1 的 1.1/1.2/1.3 | 简历能投，一面能过，项目讲得清 |
