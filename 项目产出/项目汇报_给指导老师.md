## 二、数仓分层与数据链路

**双链路并存**——这是目前项目的一个特点，也是我拿不准的地方之一（见第七章）。

```
【链路 A · 模拟数据】15 张表，全流程跑通
   → ECharts 大屏当前的数据源
   → 问题：指标是"假"的 —— ads_dau 每天恒为 1000、复购率恒定 0.99+，折线画出来是直线

【链路 B · 真实数据】12 张表，1063 万行
   ODS  ods_event_log_di                    31 分区 / 10,630,245 行
    ↓
   DWD  dwd_event_log_di       10,623,154 行（去重后）
        dwd_purchase_fact_di      186,059 行
   DIM  dim_product               140,665 行
    ↓
   DWS  dws_user_event_day      162 万行（用户 × 天）
        dws_product_event_day   127 万行（商品 × 天）
        dws_category_event_day    1,853 行（类目 × 天）
        dws_trade_day                31 行（交易日报）
    ↓
   ADS  ads_active_user_day / ads_funnel_day / ads_repurchase_day / ads_top_product_day
        （各 31 行；TopN 商品 1,550 行 = 31 天 × 50）
   → 已全部落表，但**大屏还没切到这条链路**
```

**自建调度**：DolphinScheduler 工作流 `gmall_dw_pipeline`（9 节点），按天定时跑数。

## 四、几个我认为有价值的发现

### 1. 真实数据推翻了教程里的"标准漏斗"

教材和模拟数据的假设都是「浏览 → 加购 → 购买」严格收窄。我在校验脚本里也这么写了，结果**31 天里 15 天违例**。

逐段拆开验证后，真实情况是：

| 检查 | 结果 |
|---|---|
| 浏览 < 加购 的天数 | **0** |
| 浏览 < 购买 的天数 | **0** |
| **购买 > 加购 的天数** | **15 / 31** |

全月：加购用户日 119,832 vs 购买用户日 **133,258**——**购买比加购多 11%**。

**原因是用户可以完全不进购物车直接购买**，所以加购是与购买**并行**的路径，不是必经中间态。用户级漏斗其实只有「浏览 → 购买」两环节。

> **模拟数据永远暴露不了这个**——生成脚本是按"先加购后下单"造的假数据，**它只会验证我的假设，不会挑战它**。这是我换真实数据集最大的收获。

### 2. 一次写入失败：三个 DataNode 全被"排除"

DWD 全量落表第一次失败（跑了 21 分钟，`HDFS Write: 0`）：

```
could only be written to 0 of the 1 minReplication nodes.
There are 3 datanode(s) running and 3 node(s) are excluded in this operation.
```

**关键判断**：`3 datanode(s) running` 说明节点**都健康**，但 `3 node(s) are excluded` 说明**这次写入一个都用不了**。

排查后确认是**并发写入把共享物理磁盘压垮**——6 个 reducer 同时往 31 个动态分区写、每文件 3 副本 ≈ 558 次写请求，而**三台虚拟机的磁盘最终排队到宿主机同一块物理盘**。

调整后（开启 `sort.dynamic.partition` 让 reducer 排序后**依次**写、reducer 6→3、写入期副本 3→2）：**1299 秒失败 → 481 秒成功**。

### 3. 同一个报错码，两种完全不同的根因

两次失败的表层报错**完全一样**（`return code 2 from MapRedTask`），但：

| | 第一次 | 第二次 |
|---|---|---|
| `HDFS Read` | 1.32 GB（正常） | **21.9 MB**（远小于输入 620MB） |
| 判读 | 读完了、**写不出去** | **读都读不动，死得极早** |
| 真因 | 磁盘写入并发 | 容器堆不够（`GC overhead limit exceeded`） |
| 修法 | **降并发** | **加内存** |

后来固定成一套判读方法：**看 Read / Write / CPU 三个数字的"量级是否符合预期"**，能把方向在 1 分钟内分开。

## 五、我踩过的坑（自查记录）

我用「假设 → 行动 → 实测 → 成立与否」的方式记录了每次实验，**共 7 份报告、约 40 个假设，其中 12 个被证伪**。

**三个我觉得最有价值的证伪**：

| 我原本的判断 | 实测结果 | 我错在哪 |
|---|---|---|
| 集群同步加了调优参数，所有作业都受益 | 写入型作业正常，**聚合型作业 637 秒后 GC 崩溃** | 判断依据应是「**这个作业有没有要同时装住大量数据的结构**」，而不是作业类型的名字。旧脚本头部本来就写着 `-Xmx768m` 并标注了"已调优"，是"统一配置"把这条信息抹掉了——**统一看起来整洁，实际是丢信息** |
| 服务 `active` 就可以开始跑批了 | HiveServer2 被标记 active 后**至少 50 秒**才真正监听端口 | 只看了"服务状态标志"，没验"外部可观测的判据"（端口在监听 + 真实请求成功） |
| 我写的日志检查脚本能判断作业是否在跑 | **判断反了**——作业一直在跑，是我的检查命令本身失效（非交互 SSH 里裸写 `yarn` 是 command not found，被 `2>/dev/null` 吞成了一片空白） | 「看起来合理的空答案」比报错更危险 |

## 六、我对项目现状的自我评估

**做得比较扎实的**：
- 真实数据集 + 完整分层链路 + 独立基线对账（不是"看起来对"，是"预测→实测吻合"）
- 每个结论都有实测输出支撑，失败和证伪都留存了记录
- 环境层（内存、调度、编码问题）的问题定位能力

**我自己看到的短板**：
1. **规模太小** —— 三节点伪集群，数据量 1000 万级。**没经历过真正的数据倾斜、大规模 shuffle、多租户资源竞争**
2. **只有离线** —— 没有实时链路（Kafka / Flink 经验为零）
3. **引擎单一** —— 全部走 MapReduce，`hive.exec.mode.local.auto` 之类的取舍都是在小数据量下的
4. **缺少数据治理的"规范面"** —— 对照阿里的《数仓建设七大规范》，我没有成文的命名规范、字段规范、生命周期管理
5. **大屏还是旧数据** —— 对外演示时讲的是真实数据链路，但画面是旧表（这一步还没做）
