# 组件详解 · 01 底座：虚拟机与 JVM

> **一句话定位**：虚拟化提供了"三台机器"，JVM 提供了"每个进程的运行容器"。这两样是所有大数据组件的地基——**没有它们，上面那十几个组件一个都跑不起来。**
>
> 涵盖：VMware Workstation、Ubuntu 虚拟机、JDK 8 与 JVM

---

## 〇、先建立直觉

| 名字 | 一句话类比 | 物理真相 |
|---|---|---|
| **虚拟机（VM）** | 一整台"电脑"，其实是宿主机上的一个大文件 | 三个 `.vmdk` 文件躺在宿主机 D 盘上 |
| **JVM** | 每个 Java 程序的"独立小房间" | 一个操作系统进程，有自己的内存上限、自己的端口 |

**最重要的那句话**：

> 你在架构图上看到的 `NameNode`、`DataNode`、`ResourceManager`……**全都是 JVM，全都是进程**，不是硬件、不是机器。
> "集群里有 9 个组件"这句话，物理上等于"lrh-1 上跑着 9 个 Java 进程"。

用一条命令你就能亲眼看到这件事：

```bash
jps -l
# 输出大致是：NameNode / SecondaryNameNode / DataNode / ResourceManager / NodeManager / QuorumPeerMain / HiveServer2 ...
# 每一个名字，对操作系统来说都只是一个 java 进程
```

## 一、为什么需要它们（没有会怎样）

**没有虚拟机**：你需要三台真实电脑，每台要装系统、连网线、占地方、费电。而且内存分配改起来得拆机箱。
有了虚拟机，**"给某台机器加 3GB 内存"只需要改一行配置**——本项目就真的这么干过（lrh-1 从 4096MB 改到 7168MB）。

**没有 JVM**：Hadoop 全家桶是 Java 写的。Java 的特点是"一次编写、到处运行"——同一份程序在 Windows 和 Linux 上都能跑，因为它不直接读机器指令，而是让 JVM 帮它转译。

**为什么每台机器上要跑这么多 JVM 而不是一个大程序？**
因为如果所有功能塞进一个进程，那么"NameNode 崩了"就等于"整个集群崩了"。**拆成多个 JVM，就是一个进程挂了不影响别人**——这也是分布式系统的基本思想：把大东西拆成能独立死活的小东西。

## 二、按 7 问框架拆解

### 问题 1：谁和谁说话？走网络还是本地？

| 通信 | 物理路径 |
|---|---|
| 三台虚拟机之间 | 走**虚拟网卡 + VMware NAT 网络**，网段 192.168.87.0/24 |
| 宿主机 ↔ 虚拟机 | 通过 VMware 提供的虚拟交换机；SSH 也是走这个 |
| JVM ↔ 操作系统 | 系统调用（`write()`、`read()`、socket） |
| 同一台机器上的两个 JVM | 走**本地回环网卡**（127.0.0.1），不经过真实网线 |

💡 **注意最后一条**：同一台机器上的 NameNode 和 DataNode 通信，也是"走网络"的（虽然不出去）。所以本项目的 `hive-site.xml` 里写 `jdbc:hive2://lrh-1:10000`——用的是主机名而不是 `localhost`，这样从任何一台机器都能用同一个配置连上。

### 问题 2：虚拟机的"数据"在哪？

- 三台虚拟机 = 宿主机 `D:\虚拟机\`、`D:\虚拟机2\`、`D:\虚拟机3\` 三个文件夹
- 每个文件夹里的 `.vmdk` 是"硬盘"，`.vmx` 是"主板配置"（内存多大、几核 CPU）
- **这三块"硬盘"最终都落在宿主机同一块物理盘上** → 这是本项目很多性能问题的根子

```
文件夹        .vmx 里的 memsize    实际节点
D:\虚拟机      7168             →  lrh-1 (192.168.87.131)
D:\虚拟机2     3392             →  lrh-2 (192.168.87.130)
D:\虚拟机3     4096             →  lrh-3 (192.168.87.132)
```

### 问题 3：谁负责"知道"？谁负责"存"？

| 角色 | 负责"知道" | 负责"存" |
|---|---|---|
| 虚拟化 | VMware 知道"虚拟内存地址怎么映射到宿主机物理内存" | `.vmdk` 文件存真正的数据 |
| JVM | JVM 知道"类在哪、对象在哪块堆内存" | 堆内存存对象；`.jar` 文件存代码 |

### 问题 4：一个动作分几步？哪步最贵？

**虚拟机开机**：

```
① VMware 读 .vmx 配置，按配置虚拟出 CPU/内存/网卡
② 加载引导程序 → Linux 内核启动
③ 内核挂载文件系统、启动第一个进程
④ systemd 接手，按依赖顺序启动所有服务  ← 这一步最慢，也是"启动顺序"真正发生的地方
```

**启动一个 Java 程序**：

```
① 操作系统创建进程、分配内存
② JVM 初始化：划出堆内存（-Xmx 决定上限）、加载核心类库
③ 加载你的程序类（从 .jar 里）
④ 调用 main 方法，程序真正开始跑   ← 前 3 步都算"启动开销"
```

**为什么第 3 步（JVM 初始化）值得关注**：它解释了一个常见现象——**跑一个 1 秒的小任务，却要等 10 秒**。因为等的是 JVM 启动，不是任务本身。本项目里"31 天分区用一条 SQL 一次装载，而不是调用 31 次 beeline"，省的就是这 31 次 JVM 启动的时间（省了七八分钟）。

### 问题 5：出错了谁发现？怎么补救？

**虚拟机的两种"停"状态，本项目踩过坑**：

| | 挂起（Suspend） | 关机（Powered Off） |
|---|---|---|
| 内存里的东西 | **写进了硬盘文件**（`.vmem`），下次恢复能接着跑 | 全丢了 |
| 判据 | `.vmss` 和 `.vmem` 文件**存在** | 两者**都不存在** |
| 能否改配置 | ❌ **不能**，会导致挂起状态被强制丢弃（等于硬断电） | ✅ 可以 |

> ⚠️ **本项目真实教训**：用户说"虚拟机已经关了"，我 ping 不通就准备改配置，幸好先查了文件——发现 `.vmss` 还在，**其实是挂起**。如果当时直接改 `memsize`，挂起状态会被丢弃。
>
> **更隐蔽的一点**：`.lck` 文件消失只说明 VMware 客户端不再占用它，**挂起状态仍躺在磁盘上**。
> **判断供电状态的唯一可靠依据是文件，不是 ping，也不是窗口是否关闭。**
>
> 顺带：本项目装了 VMware 的命令行工具 `vmrun.exe`（在 `D:\VMware\`，**不在 Program Files**，一开始漏查了），所以恢复、开机、关机都能自动化，不必手工点界面。

**JVM 出错**：Java 程序要的内存超过 `-Xmx` 上限 → 抛 `OutOfMemoryError`。如果这个进程是被 systemd 或 YARN 管的，可能还会被直接杀掉重试。

### 问题 6：换来了什么？代价是什么？

| 设计 | 换来了 | 代价 |
|---|---|---|
| 虚拟化 | 一台电脑当三台用；加内存只要改一行配置 | **三台机器共享同一块物理磁盘** → 磁盘 IO 压力被放大 |
| 多 JVM 拆进程 | 一个组件挂了不拖累其他 | 每个 JVM 都要吃一份基础内存（本项目给每个 512MB 上限，9 个进程就是 4.5GB） |
| 用 JDK 8 | 与 Hadoop 3.3.6 生态完全适配，稳定 | **组件版本被锁死**：Spark 4.x 要求 JDK 17+，所以本项目规划 Spark 时只能选 3.5.x |
| Ubuntu 桌面版 | 有图形界面，方便演示 | **白吃约 600MB 内存/台** → 本项目已关闭桌面，用一条命令随时开关 |

### 问题 7：规模放大 100 倍，先崩的是哪一环？

**虚拟化环境下先崩的是内存和磁盘**，而且有个反直觉的机制：

宿主机有 31.7GB 内存，三台虚拟机的配额加起来 12.3GB，看起来宽裕。但**宿主机的内存不是想给就给**——一旦给多了，宿主机会开始 swap（把内存挪到硬盘），**整个 Windows 都会变卡**。所以"往虚拟机上堆内存"这条路有硬天花板。

磁盘同理：三台 VM 的写入排队到同一块物理盘，**你给单个 VM 加内存并不会让磁盘变快**。

> 💡 **这正是本项目最重要的一课**：实验 01 把 lrh-1 可用内存从 601MB 提到 4123MB（6.9 倍），但后面跑批时真正卡住的**不是内存，是磁盘写入并发**（详见 `实验分析/实验03_全量ETL写入失败排查与调优.md`）。
> **扩容能解决"跑不起来"，但解决不了"跑得慢"——后者要去看 IO。**

## 三、本项目实况

### 3.1 安装位置

| 项 | 路径 |
|---|---|
| VMware Workstation | `D:\VMware\`（命令行工具 `vmrun.exe` 也在这里） |
| 三台虚拟机文件 | `D:\虚拟机\`、`D:\虚拟机2\`、`D:\虚拟机3\` |
| SSH 私钥（宿主机侧） | `D:\数据开发环境\VMware\sshkeys\cluster_ed25519` |
| JDK 8 | `/opt/jdk/jdk1.8.0_202`（三台一致） |

### 3.2 内存给谁多少（以及为什么）

| 节点 | 配额 | Java 进程数 | 说明 |
|---|---|---|---|
| lrh-1 | **7168 MB** | 9 个 | 从 4096 扩容而来，因为它要跑全部"大脑"角色 |
| lrh-2 | 3392 MB | 4 个 | 从 4392 **减配**而来（实测它最清闲，可用 2414MB） |
| lrh-3 | 4096 MB | 4 个 | 保持原样 |

### 3.3 JVM 堆上限（关键调优项）

原来所有守护进程都用默认的约 1000MB 堆上限，对 3~4GB 的机器是隐患（6 个 JVM 各自能长到 1GB）。现已统一限制：

| 配置项 | 值 | 位置 |
|---|---|---|
| `HADOOP_HEAPSIZE_MAX` | 512 | `hadoop-env.sh` |
| `YARN_RESOURCEMANAGER_HEAPSIZE` / `NODEMANAGER_HEAPSIZE` | 512 | `yarn-env.sh` |
| `ZK_SERVER_HEAP` | 512（原 1000） | `zkEnv.sh` |
| Hive MetaStore / HiveServer2 | 512 | 受 `HADOOP_HEAPSIZE_MAX` 影响 |
| DolphinScheduler | 512（**不要调大**） | `bin/env/` |

> ⚠️ **这里有个被证伪的预期，值得记住**：我原本以为"把堆上限从 1GB 调到 512MB 能释放 400~600MB 内存"，**实测只释放了约 60MB**。
> 原因：JVM 的实际内存占用（RSS）主要由**非堆部分**构成——metaspace、代码缓存、线程栈——它本来也没吃满 1GB 的堆。
> **调小 `-Xmx` 的真实价值不是"立刻省内存"，而是"限制上限、防止负载上来后膨胀"。** 详细复盘见 `实验分析/实验01_集群内存调优.md`。

### 3.4 常用操作

```bash
# 查看宿主机上有哪些虚拟机在运行
"D:\VMware\vmrun.exe" -T ws list

# 无界面启动 / 带界面启动（中文路径经 Git Bash 传递正常）
"D:\VMware\vmrun.exe" -T ws start 'D:\虚拟机\Ubuntu 64-bit.vmx' nogui
"D:\VMware\vmrun.exe" -T ws start 'D:\虚拟机\Ubuntu 64-bit.vmx' gui

# 判断是"挂起"还是"真关机"（唯一可靠依据）
ls "/d/虚拟机" | grep -E "\.vmss|\.vmem|\.lck"
```

## 四、我们踩过的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | **以为"关闭 VMware 窗口 = 关虚拟机"**，实际是挂起 | 判据只能是 `.vmss`/`.vmem` 文件，不能用 ping、不能用窗口状态 |
| 2 | **挂起状态下改 `.vmx` 内存配置** | 会导致挂起状态被强制丢弃（等于硬断电），必须恢复运行后优雅关机再改 |
| 3 | 三台虚拟机的名字**全叫 `Ubuntu 64-bit`**，无法从名字区分 | 只能靠**文件夹名**或 **MAC 地址**硬核对身份；改配置前必须先确认节点身份 |
| 4 | 集群装的是 **Ubuntu 桌面版**，GNOME 图形界面白吃约 600MB/台 | 已关闭（`desktop_switch.sh off`），可一条命令恢复；**关桌面不影响集群服务，实测服务 PID 完全不变** |
| 5 | 关机前没停 Hadoop，可能损坏 HDFS 元数据 | **改配置/关机前先 `sudo systemctl stop hadoop`** |
| 6 | 以为调小 JVM 堆能省下 400~600MB | **实测只省 60MB**（见 3.3 的复盘） |

## 五、面试高频追问

**Q1：同一台机器上的两个 Java 进程通信，算"网络通信"吗？**
A：算。走的是本地回环网卡（127.0.0.1），数据要经过操作系统的网络协议栈，只是不出物理网卡。所以本项目 `hive-site.xml` 里写主机名 `lrh-1` 而不是 `localhost`——这样三台机器能用同一份配置。

**Q2：为什么每台机器要跑这么多 JVM，不能合并成一个进程？**
A：核心是**故障隔离**。合并成一个进程的话，NameNode 出问题会连带 HDFS 数据服务一起挂。拆开之后一个进程崩了不影响别人。
代价是每个 JVM 都要吃一份基础内存——本项目给每个 512MB 上限，9 个进程就是 4.5GB，这是 lrh-1 需要 7GB 内存的直接原因。

**Q3：把 `-Xmx` 从 1GB 调到 512MB，为什么内存没省下来多少？**
A：因为 JVM 的实际内存占用（RSS）里，**堆只是其中一部分**，还有 metaspace（类元数据）、code cache（编译后的机器码）、线程栈、JVM 自身结构。
原来它也没真的吃满 1GB 堆，所以调小上限并不会释放等量内存（本项目实测只省约 60MB）。
**调小 `-Xmx` 的真实价值是"限制上限、防止负载上来后膨胀"**——原来 6 个 JVM 各自能长到 1GB，合计 6GB，对 3.8GB 的节点是明确的隐患。

**Q4：为什么这个项目选 JDK 8 而不是更新版本？**
A：因为 Hadoop 3.3.6 这一代生态对 JDK 17 支持不完善，而**生态兼容比版本新更重要**。
但这是个**有代价的选择**：JDK 8 锁死了组件上限——Spark 4.x 强制要求 JDK 17+，所以本项目规划 Spark 时只能选 **3.5.x**（2026-04 已 EOL）。这个取舍要能主动讲出来。

**Q5：三台虚拟机一共给了 12.3GB 内存，宿主机有 31.7GB，为什么不多给点？**
A：给多了宿主机会开始 swap，把内存挪到硬盘，**整个宿主机（包括你开的浏览器）都会变卡**。虚拟机的内存天花板是宿主机的**实际可用**内存，不是物理总量。
更关键的是：**磁盘是共享的**。给单个 VM 加内存不会让它写磁盘更快，所以在磁盘成为瓶颈时（本项目就是），加内存是无效优化。

## 附：本章名词速查

| 名词 | 一句话解释 |
|---|---|
| **虚拟机 / VM** | 用软件虚拟出的一台完整电脑，实际是宿主机上的一堆文件 |
| **宿主机** | 真正的那台物理电脑（本项目是 Windows） |
| **vCPU** | 分配给虚拟机的 CPU 核心数。本项目每台 2 个 |
| **`.vmx` / `.vmdk` / `.vmem` / `.vmss`** | 虚拟机配置 / 硬盘 / 挂起时的内存镜像 / 挂起状态标记 |
| **JVM** | Java 虚拟机，每个 Java 程序的运行容器，对操作系统来说就是一个进程 |
| **堆（Heap）** | JVM 里存放对象的内存区域，用 `-Xmx` 设上限 |
| **RSS** | 进程实际占用的物理内存，不等于堆大小 |
| **swap** | 内存不够时把数据临时挪到硬盘上，速度慢几十倍 |
| **OOM** | Out Of Memory，内存不够了 |
