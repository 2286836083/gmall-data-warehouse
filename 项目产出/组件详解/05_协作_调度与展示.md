# 第一部分：ZooKeeper —— 分布式系统的"裁判"

## 一、为什么需要它（没有会怎样）

分布式系统里有一类特别麻烦的问题：**多个进程要就"谁说了算"达成一致，但网络随时可能断，谁也分不清对方是"挂了"还是"只是慢"。**

具体到本项目，DolphinScheduler 的架构是"一主多从"：

```
DS master（多个）   ← 但如果同时有两个 master 都以为自己说了算，就会重复调度同一个任务
DS worker（多个）   ← 哪个 worker 有空、谁在干活？
```

**没有 ZooKeeper 会怎样**：两个 master 抢着调度同一个任务 → **任务被重复执行**（对数据仓库来说是灾难：同一天的数据被算两遍）。

> ⚠️ 这里有个前提要理解：**"两个 master 同时当领导"这种问题，靠"互相打个招呼"是解决不了的**——因为它们各自看到的网络状况不一样（有人看对方是死的，有人看对方是活的）。这类问题叫**分布式一致性问题**，必须有专门的算法来解。
> ZooKeeper 用的算法叫 **ZAB**，HDFS HA 用的是 **Paxos/Raft** 家族。**它们是同一个问题的不同解法。**

## 二、按 7 问框架拆解

### 问题 1：谁和谁说话？走网络还是本地？

所有客户端（DS master/worker、HDFS 的 Active NameNode 等）都连到 ZooKeeper 的 **2181** 端口，做两件事：

- **写**：创建/删除节点、抢锁、竞选领导
- **读**：查"现在谁是领导""有几个 worker 在线"

三台 ZooKeeper 之间还要互相通信（选主、同步数据）——**这部分走的是另一组端口（2888/3888），和客户端端口分开。**

### 问题 2：数据在哪？

ZooKeeper 存的是**极小的元信息**：谁是 leader、有哪些 worker 在、配置项。**它不存业务数据。**

它的数据模型是一棵树（叫 znode），很像文件系统：

```
/
├── dolphinscheduler/
│   ├── nodes/
│   │   ├── master/  ← 每个 master 在这下面挂一个临时节点
│   │   └── worker/  ← 每个 worker 在这下面挂一个临时节点
│   └── lock/        ← 选主用的锁
```

**判断"谁在线"的巧妙机制——临时节点（Ephemeral Node）**：

```
worker 启动 → 连上 ZooKeeper → 建一个临时节点 /nodes/worker/worker-1
worker 正常运行 → 它和 ZK 之间保持会话（类似心跳）
worker 挂了 / 网络断了 → 会话超时 → ZooKeeper 自动把这个临时节点删掉
运维人员看 ZK → 节点没了 → 知道 worker-1 挂了
```

> 💡 **这就是"心跳"的另一种实现**：不是"我主动来报到"，而是"我不报到了就自动被清掉"。
> **区别在于：清理动作是由 ZooKeeper 做的，不依赖挂掉的那个进程——这才能处理"进程已经死了、没法自己报告"的情况。**

### 问题 3：谁知道？谁存？

| 角色 | 干什么 |
|---|---|
| **Leader（ZK 自己选出来的）** | 处理所有**写**请求，并把变更同步给 Follower |
| **Follower** | 处理读请求；参与投票 |
| **客户端** | 只负责"用"，不参与一致性算法 |

**为什么写都要经过 Leader？** 因为要保证所有节点看到的数据顺序一致。如果随便哪个节点都能写，就冲突了。

### 问题 4：一个动作分几步？哪步最贵？

**写一个数据（比如抢锁当 leader）**：

```
① 客户端把请求发给任意一台 ZooKeeper（不一定是 Leader）
② 如果收到请求的是 Follower，它转发给 Leader
③ Leader 提出一个提案，发给所有 Follower
④ Follower 写进本地磁盘（事务日志），回一个"收到"
⑤ Leader 收到【过半】节点的确认 → 宣布这次写成功
⑥ 通知客户端成功
```

**最贵的是第 ④⑤ 步**——要等磁盘落地 + 网络往返。

> ⭐ **"过半"（quorum）这个设计极其重要**，它解释了 ZooKeeper 的两条铁律：
>
> | 集群规模 | 能容忍几台挂 | 说明 |
> |---|---|---|
> | 3 台 | **1 台** | 3 台里挂 2 台就没法工作了（剩下 1 台不过半） |
> | 5 台 | 2 台 | 容错能力翻倍，但要多两台机器 |
>
> **所以 ZooKeeper 集群是奇数台，最常见是 3 台。**本项目也是 3 台。
> **推论**：ZK 的可用性 = "过半可用"。3 台的集群里，**同时重启 2 台就会让整个 ZK 停止服务。**

### 问题 5：出错了谁发现？怎么补救？

- **Follower 挂了**：Leader 发现它不响应，集群继续工作（只要还过半）
- **Leader 挂了**：剩下的 Follower 重新投票选一个（这叫"选主"）
- **超过一半的节点挂了**：**整个 ZooKeeper 停止服务**（这是设计上的安全性选择——宁可停，也不给出一致性不可靠的答案）

### 问题 6：换来了什么？代价是什么？

| 设计 | 换来了 | 代价 |
|---|---|---|
| 过半写成功 | 强一致性：绝不会出现"两个 master 都以为自己是 leader" | **可用性下降**：3 台挂 2 台就全停 |
| 临时节点 | 进程挂了能自动被发现，不依赖挂掉者自报 | 依赖客户端与 ZK 的会话，**网络抖动会造成误判** |
| 数据放内存 | 读极快 | 数据量必须很小（不适合存业务数据） |
| 独立集群 | 不跟业务进程抢资源 | **多了一组要维护的进程**（本项目 3 个 JVM，各 512MB 上限） |

### 问题 7：规模放大 100 倍，先崩哪一环？

- **写入吞吐**：所有写都要过 Leader + 落盘 + 过半确认，**ZK 的写能力并不强**
- **会话数**：每个客户端一个会话，客户端多了 ZK 压力上升
- **典型误区**：把 ZooKeeper 当数据库用（存业务数据）→ 会很快爆掉

**排查命令**：

```bash
systemctl is-active zookeeper                    # 三台都应该是 active
echo ruok | nc lrh-1 2181                        # 应返回 imok
echo stat | nc lrh-1 2181                        # 看角色（leader/follower）与连接数
journalctl -u zookeeper -n 50 --no-pager
```

## 三、本项目实况

| 项 | 值 |
|---|---|
| 版本 | ZooKeeper 3.8.7 |
| 部署 | **三台都有**（lrh-1 / lrh-2 / lrh-3），构成 quorum |
| 客户端端口 | **2181** |
| 堆上限 | **512MB**（原为默认 1000MB，实验 01 里调小） |
| 服务名 | `zookeeper.service`（三台都注册成了 systemd 服务） |
| 实际用途 | DolphinScheduler 的 master/worker 注册与选主 |

### 本项目踩过的坑

**重启 ZooKeeper 必须逐台进行，保持多数派。** 实验 01 里调整 ZK 堆内存时的正确顺序是：

```
先重启 lrh-3 → 等它恢复并追上数据
再重启 lrh-2
最后重启 lrh-1
```

**为什么不能三台一起重启？** 因为同时停 2 台以上，剩余的节点不过半 → ZK 停止服务 → 所有依赖它的东西（包括 DS）全部报错。
**这条规则对其他集群组件也成立**：凡是"过半才对"的系统（ZK、HDFS HA 的 JournalNode），**重启必须一台一台来。**

# 第二部分：DolphinScheduler —— 值班排班表

## 一、为什么需要它（没有会怎样）

本项目的数据链路有 9 个步骤，**步骤之间有严格依赖**：

```
建库 → 建表 → 装载 ODS → 清洗到 DWD → 汇总 DWS（用户/商品/订单，三个可以并行）→ 计算 ADS → 校验
```

**没有调度器会怎样？** 你得每天半夜手动敲 9 条命令，而且必须**等前一条跑完再敲下一条**（跑早了数据还没准备好）。一天忘了敲，大屏第二天就是空的。

**DolphinScheduler 解决的正是这两件事：按时自动 + 依赖编排。**

## 二、按 7 问框架拆解

### 问题 1：谁和谁说话？

```
api（12345，给网页用）──► master（负责"什么时候该跑"）
                              │ 把任务分配给
                              ▼
                          worker（负责"真的去执行"）
                              │ 执行时调用的就是
                              ▼
                     beeline / shell 脚本 ──► Hive ──► YARN ──► HDFS
所有角色都要连 ZooKeeper（2181）来注册自己、选主
所有角色的元数据都存 MySQL（3306）
```

### 问题 2：数据在哪？

| 东西 | 在哪 |
|---|---|
| 工作流定义、任务依赖关系、执行历史 | **MySQL** 的 `dolphinscheduler` 库 |
| master / worker 的在线状态 | **ZooKeeper** |
| 任务真正处理的数据 | HDFS（它自己不碰数据，只是"发命令的") |

> 💡 **理解 DS 的定位**：它**不参与数据处理**，只是个"定时发命令的程序"。真正干活的还是 Hive + YARN + HDFS。所以 DS 出问题，**已经跑完的数据不会丢**，只是"下一批不会按时跑"。

### 问题 3：谁知道？谁存？

| 角色 | 职责 |
|---|---|
| **master** | 决定"工作流现在该执行哪一步了"，把任务分发给 worker |
| **worker** | 真正去执行任务（跑 shell、调 beeline） |
| **api** | 提供网页界面和接口 |
| **alert** | 发告警通知（邮件等）——本项目演示时不启动，省内存 |

**多 master 怎么分工？** 靠数据库行锁 + ZooKeeper 选主：每个工作流实例会被"分配"给某个 master，**用数据库锁保证同一个实例只有一个 master 在处理**。

### 问题 4：一个动作分几步？

```
① 到点了（定时触发）或手动点"执行"
② master 收到触发，检查依赖（前置任务都成功了吗）
③ master 把"可以执行的任务"分配给某个空闲 worker
④ worker 执行任务本身（本项目是 shell 节点，脚本里调 beeline 跑 SQL）
⑤ worker 上报执行结果（成功/失败）
⑥ master 根据结果决定：解锁下游任务，还是标记整个工作流失败
⑦ 全过程写进 MySQL（可在网页上看到每次执行的日志与耗时）
```

**并行的地方在第 ⑥ 步**：`dws_user` / `dws_sku` / `dws_order` 三个任务互不依赖，可以**同时**解锁、同时跑（前提是集群资源够——本项目只有 12 个容器，并行能力有限）。

### 问题 5：出错了谁发现？怎么补救？

| 出错 | 表现 | 处置 |
|---|---|---|
| 某个任务失败 | 工作流停在那一格，下游**不会**执行 | 网页上能看到失败日志；修完可以"从失败节点重跑" |
| worker 挂了 | master 检测到，把任务重新分配 | **但已经跑了一半的任务可能要重跑** |
| 整个 DS 没启动 | 网页打不开，任务不会自动跑 | **本项目特有**：DS 不自启，虚拟机重启后要手动拉起 |

### 问题 6：换来了什么？代价是什么？

| 设计 | 换来了 | 代价 |
|---|---|---|
| 依赖编排（DAG） | 不用人守着敲命令；失败会停下来不会跑出脏数据 | **依赖关系要维护**：加一个步骤要改工作流；依赖配错会导致该跑的没跑 |
| 多 master 多 worker | 高可用、能扩展 | 每个角色都是 JVM，**吃内存**。本项目 lrh-1 内存本来就紧，所以 alert-server 在演示时不启动 |
| 执行历史存 MySQL | 可追溯、可重跑 | 元数据库会越来越大，要定期清理 |

### 问题 7：规模放大 100 倍，先崩哪一环？

**先崩的是被调度任务的资源，不是 DS 自己。** 因为 DS 只是"发命令"的，它发出去 100 个任务，但集群只有 12 个容器 → **大量任务在 YARN 里排队**，看起来像"DS 卡住了"，实际是资源不够。

## 三、本项目实况

| 项 | 值 |
|---|---|
| 版本 | DolphinScheduler 3.1.8 |
| 安装位置 | `/home/lrh/dolphinscheduler/apache-dolphinscheduler-3.1.8-bin` |
| 角色分布 | lrh-1：master / api（alert 演示时不启动）；lrh-2、lrh-3：worker |
| 网页地址 | `http://lrh-1:12345/dolphinscheduler`（admin / dolphinscheduler123） |
| 元数据库 | MySQL 的 `dolphinscheduler` 库 |
| 堆上限 | **锁定 512MB，不随意调大**（调大会把 lrh-1 压垮） |

### 核心工作流：`gmall_dw_pipeline`（9 个节点）

```
create_db
   → ddl（建表）
      → ods_load（装载 ODS）
         → dwd_clean（清洗到 DWD）
            ├─ dws_user  ┐
            ├─ dws_sku   ├─ 三个并行
            ├─ dws_order ┘
            → ads_opt（算指标）
               → verify（校验）
```

### ⚠️ 本项目最重要的两个运维事实

**1. DS 不自启，虚拟机重启后必须手动拉起。**
这是设计选择（避免开机时内存不够导致 DS 启动失败），但意味着**重启虚拟机之后不拉起 DS，第二天大屏就是空的**。

```bash
# 在 lrh-1 上启动（顺序：master → worker → api）
cd /home/lrh/dolphinscheduler/apache-dolphinscheduler-3.1.8-bin
bash bin/dolphinscheduler-daemon.sh start master-server
bash bin/dolphinscheduler-daemon.sh start worker-server    # 在 lrh-2 / lrh-3 上执行
bash bin/dolphinscheduler-daemon.sh start api-server
```

**2. `alert-server` 演示时不要同时启动。**
本项目 lrh-1 实测内存 3868MB（扩到 6866MB 前），DS 的堆已锁 512MB，再开 alert-server 会显著挤占内存。**这是"功能完整性"和"内存现实"之间的取舍。**

## 一、为什么需要它（没有会怎样）

数据链路最后一步是"出指标"，但**面试官/老师不会看 `beeline` 里的一串数字**，他们要看到图。

**没有大屏会怎样**：整个项目止步于"命令行里能查到数"，看起来像个练习，不像一个交付物。

## 二、按 7 问框架拆解

### 问题 1：谁和谁说话？走网络还是本地？

**本项目的大屏是"零依赖"的**——没有后端、没有网络请求，全部文件都在本地：

```
dashboard.html  ──<script src>──►  echarts.min.js      （离线图表库，1MB）
                ──<script src>──►  dashboard_data.js    （数据文件）
```

> ⭐ **为什么不用 `fetch` 读本地 JSON？** 这是踩过的坑：
> 浏览器在 `file://` 协议下会以 **CORS 策略**拦截 `fetch('data.json')`，**双击打开页面会白屏**。
> 而 `<script src>` **不受 CORS 限制**，所以把数据写成 `dashboard_data.js`（内容是 `window.DASHBOARD_DATA = {...}`），用 `<script>` 标签加载就能正常工作。
>
> **这一步决定了"演示时能不能一键打开"，是整个方案的关键设计。**

### 问题 2：数据在哪？

数据来自 HDFS 上的 ADS 层表，经过一条导出链路变成页面能读的文件：

```
HDFS 的 ADS 表
  → beeline 导出 CSV（在 lrh-1 上执行 export_dashboard_data.sh）
    → Python 转成 JSON（csv2json.py）
      → 写成 dashboard_data.js
        → 拷到本机，和大屏页面放在同一个文件夹
```

### 问题 3：谁知道？谁存？

| 角色 | 职责 |
|---|---|
| `export_dashboard_data.sh` | 在集群上跑：查 5 张 ADS 表 → CSV |
| `csv2json.py` | CSV → `dashboard_data.js` |
| `dashboard.html` | 只管画图，不含数据 |

**这个分工的意义**：图表和数据分离，**换一批数据只要重新跑导出脚本，页面一行都不用改。**

### 问题 4：一个动作分几步？

```
① 在 lrh-1 上跑导出脚本 → 得到 CSV
② Python 转成 dashboard_data.js
③ 把 3 个文件放到同一个文件夹
④ 双击 dashboard.html → 浏览器读取本地 JS → ECharts 渲染
```

### 问题 5：出错了谁发现？

| 现象 | 原因 |
|---|---|
| **页面白屏** | 缺文件、或用了 `fetch` 读本地 JSON 被 CORS 拦 |
| **页面有坐标轴但没数据** | `dashboard_data.js` 是空的或格式不对 |
| **图表错位** | 窗口尺寸变化后没调用 `chart.resize()` |
| **换网络后打不开** | 用了 CDN 引 ECharts。本项目已改为**本地离线包**，断网也能开 |

**诊断手法**：浏览器按 F12 看 Console 的报错——**白屏这类问题，控制台一定有红字。**

### 问题 6：换来了什么？代价是什么？

| 设计 | 换来了 | 代价 |
|---|---|---|
| 纯静态、无后端 | 双击即开、断网可用、演示零风险 | 数据不是实时的，**要手动重新导出** |
| 数据写成 `.js` 而不是 `.json` | 绕开 `file://` 的 CORS 限制 | 数据文件不能用普通 JSON 工具直接读 |
| 离线打包 ECharts | 不依赖网络 | 多一个 1MB 的文件，**3 个文件必须始终放在同一目录** |

### 问题 7：规模放大 100 倍，先崩哪一环？

大屏本身不会崩（渲染几万个点没问题），**先崩的是"导出"这一环**：数据量大了，导出 CSV 会变慢、文件会很大。

**正确做法**：**不要把明细导出来**，只导聚合后的指标（本项目就是只导 ADS 层的汇总结果，每天几十行）。

## 三、本项目实况

| 文件 | 作用 |
|---|---|
| `dashboard.html` | 大屏页面，双击即开 |
| `dashboard_data.js` | 数据（由脚本生成，勿手改） |
| `echarts.min.js` | ECharts 5.5.1 离线包（1MB） |
| `export_dashboard_data.sh` | 在 lrh-1 上跑，导出 5 张表 |
| `csv2json.py` | CSV → JS 数据文件 |

> ⚠️ **这三个文件必须放在同一个文件夹**：`dashboard.html` 用相对路径 `<script src="./...">` 引用另外两个。搬走任何一个，页面就白屏。

### 本项目踩过的两个坑

**1. `beeline --outputformat=json` 实测不存在。**
合法取值只有 `table / vertical / csv2 / tsv2 / dsv / csv / tsv`。**必须改走 `csv2` + Python 转 JSON。**

**2. 模拟数据太"平"，画出来是一条直线。**
早期的模拟数据显示：`ads_dau` **每天恒为 1000**、复购率恒在 0.999~1.0。折线图画出来是直线，**演示说服力是负的**。

> 💡 **这条的普适价值**：**先看数据长什么样，再决定画什么图。**
> 当时的处理不是"硬把一条平线画成图"，而是**把数据源整个换掉**——改用真实的 REES46 电商行为数据集（1063 万行），现在每天的 DAU 有真实波动。
> **"数据不真实"是必须主动提出来的一类问题，它会同时影响演示效果和后续性能对比的结论。**

## 附：本章名词速查

| 名词 | 一句话解释 |
|---|---|
| **ZooKeeper** | 分布式协调服务，解决"谁在线、谁说了算"的一致性问题 |
| **Quorum（过半）** | 写操作要超过一半节点确认才算成功，保证不会出现两个领导 |
| **znode** | ZooKeeper 里的数据节点，组织成一棵树 |
| **临时节点（Ephemeral）** | 会话断开时自动删除的节点，用来表示"我还活着" |
| **选主（Leader Election）** | 从多个候选里选出一个负责写的节点 |
| **ZAB** | ZooKeeper 用的一致性算法 |
| **DAG** | 有向无环图，表示"任务谁先谁后、谁能并行" |
| **工作流 / 实例** | 定义"该怎么跑" / 某一次具体执行 |
| **DolphinScheduler** | 分布式任务调度系统，负责按时、按依赖自动跑任务 |
| **CORS** | 浏览器的跨域限制，`file://` 下会拦截 `fetch` 本地文件 |
| **CDN** | 内容分发网络，从网上加载公共库；演示场景应避免依赖 |
| **`.js` 数据文件 vs `.json`** | 前者用 `<script>` 加载不受 CORS 限制，后者用 `fetch` 会被拦 |
