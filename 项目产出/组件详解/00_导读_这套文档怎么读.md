## 一、这套系统到底在干什么

用一句话说：**把一堆零散的原始数据，经过几道工序，变成能画在图表上的指标。**

数据像小麦，不能直接吃，要经过脱壳、磨粉、筛分：

```
原始事件日志  →  清洗（去重、修时间、拆字段）  →  按主题汇总  →  指标  →  图表
    ODS               DWD                        DWS         ADS     大屏
```

但这套工序**一台电脑干不动**（数据太大、还要防止一台机器坏了全丢），所以要把工作拆到三台机器上。于是就需要一大堆"分工协作"的软件。

**关键认知：这十几个组件，本质上只在解决四个问题。**

| 要解决的问题 | 用什么软件 | 通俗说法 |
|---|---|---|
| 数据**存**在哪、存几份 | **HDFS** | 分散在三个仓库的图书馆 |
| 谁来**算** | **MapReduce**（将来是 Spark） | 一群工人分批处理 |
| 谁的机器上有**空闲资源**、派给谁 | **YARN** | 车间调度员 |
| 怎么用 **SQL** 来说话（不用写 Java） | **Hive** | 翻译官：把 SQL 翻成 MapReduce |

剩下的是配角：**MySQL** 存"表长什么样"、**ZooKeeper** 做"谁在线"的仲裁、**DolphinScheduler** 负责"每天几点按时跑"、**ECharts** 负责"给人看"、**JVM** 是上面这些都跑在里面的容器、**虚拟机**是这一切的物理底座。

## 二、启动顺序：为什么必须按这个次序

这是初学者最容易忽略、但面试官最爱问的一点：**这些组件之间有依赖，启动有严格的先后。**

```
① 虚拟机开机（物理底座）
        ↓
② ZooKeeper（三台）        ← 它不依赖任何人，所以最先起
        ↓
③ MySQL（lrh-1）           ← "账本"，Hive 和 DS 都要读它
        ↓
④ HDFS：先 NameNode，再 DataNode   ← DataNode 启动时要向 NameNode 报到
        ↓
⑤ YARN：先 ResourceManager，再 NodeManager   ← NM 启动时要向 RM 报到
        ↓
⑥ Hive：先 MetaStore，再 HiveServer2   ← HS2 启动时要连 MetaStore 和 MySQL
        ↓
⑦ DolphinScheduler：先 master，再 worker，最后 api/alert   ← 都要向 ZooKeeper 注册
        ↓
⑧ 作业真正跑起来
```

**为什么是这个顺序——一句话规律：**

> **一个组件启动时，会去连它的依赖。依赖没起来，它就起不来或起不健康。**

- ZooKeeper 不依赖任何人 → 第一个起
- DataNode 要向 NameNode 报道 → NameNode 必须先起
- HiveServer2 要读 MySQL 里的表结构 → MySQL 必须先起

**本项目踩过的真实坑**：三台虚拟机同时冷启动时，lrh-1 的 `hadoop.service` 会通过 SSH 去拉 lrh-2/3 的 worker 进程，但那一刻 worker 还没准备好接受 SSH → **静默失败，不报错**，结果是冷启动后只有 1 个 DataNode。
**修法**：改成每台机器各自启动自己的进程（worker 上新建 `hadoop-worker.service`），彻底消除启动时序依赖。**这就是"启动顺序"没处理好会出什么问题。**

## 四、哪台机器上跑着什么（本项目实况）

集群一共三台，每台 2 核，内存不均等：

| 节点 | IP | 内存 | 跑什么 |
|---|---|---|---|
| **lrh-1** | 192.168.87.131 | **7168 MB** | 全部"大脑"类角色：NameNode、SecondaryNameNode、DataNode、ResourceManager、NodeManager、ZooKeeper、MySQL、Hive MetaStore、HiveServer2、DS master/api |
| **lrh-2** | 192.168.87.130 | 3392 MB | DataNode、NodeManager、ZooKeeper、DS worker |
| **lrh-3** | 192.168.87.132 | 4096 MB | DataNode、NodeManager、ZooKeeper、DS worker |

**为什么 lrh-1 内存给到 7GB 而另外两台只有 3~4GB？**
因为它要跑 9 个 Java 进程，而另外两台只跑 4 个。最初的配置是"三台一样多"，结果最忙的 lrh-1 可用内存只剩 601MB 并开始用 swap（把内存挪到硬盘上，慢几十倍），而最清闲的机器还有 2GB 空着——**这就是"资源分配要按负载而不是按均分"的教科书案例**（详见 `实验分析/实验01_集群内存调优.md`）。

|---|---|---|
| JDK 8 | `/opt/jdk/jdk1.8.0_202` | — |
| Hadoop 3.3.6 | `/opt/hadoop/hadoop-3.3.6` | `etc/hadoop/`（hdfs-site.xml / yarn-site.xml / mapred-site.xml / hadoop-env.sh） |
| Hive 3.1.3 | `/opt/hive/apache-hive-3.1.3-bin` | `conf/hive-site.xml` |
| ZooKeeper 3.8.7 | `/opt/zookeeper/apache-zookeeper-3.8.7-bin` | `conf/zoo.cfg` |
| DolphinScheduler 3.1.8 | `/home/lrh/dolphinscheduler/apache-dolphinscheduler-3.1.8-bin` | `bin/env/` |
| Hive 数据仓库 | HDFS 上 `/user/hive/warehouse/gmall.db` | — |
| 数仓脚本 | `/home/lrh/workspace/` | — |
| 配置备份 | `/opt/backup/<日期>/` | — |

**看日志的万能命令**（本项目所有组件都注册成了 systemd 服务）：

```bash
journalctl -u hadoop -n 50 --no-pager          # HDFS + YARN
journalctl -u hive-server2 -n 50 --no-pager    # Hive 的 SQL 执行进度与报错
journalctl -u zookeeper -n 50 --no-pager
systemctl is-active hadoop zookeeper mysql hive-metastore hive-server2
```

> ⚠️ **注意**：`lrh-2` / `lrh-3` 上没有 `hadoop.service`，它们用的是 `hadoop-worker.service`。
> 这是本项目踩过的坑——旧文档 `虚拟机集群使用指南.md` 里写的"在 worker 上 `systemctl restart hadoop`"是**错的**，照做会报 Unit not found。**该文档尚未修正。**

## 七、学完这套文档你应该能回答的 6 个问题

如果你读完还答不上来，说明那一章要重读：

1. 我提交一条 SQL 之后，物理上依次发生了什么？（提示：Hive 编译 → YARN 分容器 → 读 HDFS → map → shuffle → reduce → 写回 HDFS）
2. 为什么 NameNode 的内存压力与"文件数"有关、与"数据大小"无关？
3. 为什么"服务是 active"不等于"能干活"？（提示：本项目有一次 `3 datanode(s) running` 但全部被踢出写入通道）
4. 三台机器上各跑着哪些进程？为什么 lrh-1 内存要配得更多？
5. 冷启动后为什么曾经只有 1 个 DataNode 在跑？
6. 为什么扩容内存后，跑批速度反而没变快？（提示：瓶颈可能不在内存，在磁盘并发）
