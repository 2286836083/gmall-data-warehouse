# 组件详解 · 03 调度与计算：YARN 与 MapReduce

> **一句话定位**：**YARN 是"派活的中介"**——它只管"谁的机器有空闲资源"，把资源切成块租出去；**MapReduce 是"干活的工人"**——它租到资源之后怎么算，YARN 并不关心。
>
> 涵盖：ResourceManager、NodeManager、Container、ApplicationMaster、MapReduce 的 map/reduce/shuffle，以及规划中的 Spark

---

## 〇、先建立直觉

| 名字 | 一句话类比 | 物理真相 |
|---|---|---|
| **YARN** | 车间的**调度员 + 工位管理** | 一组 JVM 进程，负责把机器的 CPU/内存切成"配额"租出去 |
| **Container（容器）** | 一块**租出去的工位**：一个 CPU 配额 + 一个内存配额 | 不是一个"盒子"，只是一份**资源账目 + 一个进程** |
| **MapReduce** | 一群**工人**：分头处理，再汇总 | map 和 reduce 任务，各自是一个 JVM 子进程 |
| **ApplicationMaster（AM）** | 这个作业的**现场监工** | 一个 JVM 进程，替作业向 YARN 要资源、盯着进度 |
| **Shuffle** | 把各工位做好的半成品**搬到一起** | 跨网络搬运，最贵的一步 |

**最重要的那句话**：

> **YARN 完全不知道你在算什么。** 它只认"我要 512MB 内存 + 1 个核，给我一个容器"。
>
> 所以 MapReduce、Spark、Flink 可以**共用同一套 YARN**——这叫做"计算与资源解耦"。本项目将来上 Spark，不需要改 YARN 一行配置，就是这个道理。

---

## 一、为什么需要它们（没有会怎样）

**没有 YARN 会怎样？** 你会退回到 Hadoop 1.x 的老办法：**每台机器固定跑固定数量的任务槽（slot），跑不满也占着，跑不过来也加不了**。而且 MapReduce 自己管资源，Spark 就没法复用同一批机器。

YARN 把这件事抽象成三层：

```
YARN 只管：机器上还有多少 CPU / 内存  →  切成容器租出去
谁来租：  MapReduce / Spark / Flink  →  "客户"
租了干什么：YARN 不管
```

**没有 MapReduce 会怎样？** 你得自己写"把一个 1.4GB 文件切成 11 份、分给 11 台机器算、再把结果汇总"的代码——每写一个统计需求都要重写一遍。MapReduce 把"切分 → 分发 → 并行算 → 汇总"封装成了一个固定模式。

> ⚠️ **但要理解 MapReduce 的时代局限**：它是 2004 年的设计，**每一步中间结果都要落盘**（map 写本地盘、shuffle 落盘、reduce 写 HDFS）。这让它**非常稳、但很慢**。所以在同一批数据上反复计算的场景（比如机器学习要迭代 100 轮），MapReduce 会慢到不可用——这就是 Spark 出现的原因。

## 二、按 7 问框架拆解

### 问题 1：谁和谁说话？走网络还是本地？

| 通信 | 走哪 |
|---|---|
| 客户端 → ResourceManager | 提交作业（网络） |
| RM → NodeManager | "在你这台起个容器"（网络） |
| 监工（AM）→ RM | 申请更多容器、汇报进度（网络） |
| 子进程 → HDFS | 读输入分片、写最终结果（网络） |
| 子进程 → 本地磁盘 | 写 map 的中间输出（**本地**，不走网络） |
| reduce ↔ 各机器的 map 输出 | **shuffle：全程走网络** |

### 问题 2：数据此刻在哪？什么时候只在内存？

| 阶段 | 数据位置 | 为什么 |
|---|---|---|
| 读输入 | 从 HDFS 的 DataNode 磁盘 → 子进程内存 | 尽量调度到**数据所在的那台机器**上跑（叫"数据本地性"），减少网络搬运 |
| map 输出 | **写本机磁盘** | 一次性中间数据，不值得付 3 副本的代价 |
| shuffle | 跨网络搬到 reduce 所在机器，**先落盘再读盘** | 因为要按 key 归并排序，内存装不下 |
| reduce 结果 | 写回 HDFS | 这是最终产物，要 3 副本保护 |

### 问题 3：谁负责"知道"？谁负责"存"？

| 角色 | "知道"什么 |
|---|---|
| **ResourceManager（RM）** | 整个集群**还剩多少资源**、每个作业要多少、队列怎么排队 |
| **NodeManager（NM）** | **本机**有多少资源、本机跑着哪些容器、容器超了配额就杀掉 |
| **ApplicationMaster（AM）** | **这个作业自己的**进度：哪些 map 完成了、还差多少 reduce |

> 这是一个**三层结构**：RM 看全局、NM 看本机、AM 看本作业。
> **好处**：某个作业的 AM 挂了只影响那个作业；RM 挂了影响全局但重启后能从日志恢复。
> **对应的代价**：RM 是**单点**（生产环境要配 HA）。

### 问题 4：一个动作分几步？哪一步最贵？

**一个 MapReduce 作业的 8 步**：

```
① 客户端把作业提交给 ResourceManager
② RM 挑一台机器，起容器跑「监工」ApplicationMaster
③ 监工向 RM 申请更多容器（要 CPU 配额 + 内存配额）
④ RM 联络各 NodeManager，在本机起一堆子进程
⑤ 每个子进程读 HDFS 上的一 个分片，执行 map 函数
⑥ map 的输出写进「自己那台机器」的本地磁盘        ← 不写 HDFS
⑦ reduce 通过网络把所有机器的 map 输出拉过来汇总   ← ★ shuffle，最贵
⑧ 结果写回 HDFS —— 走 HDFS 那套"问地址→写→转发"流程
```

**为什么第 ⑦ 步最贵，三个原因：**

1. **必须等所有 map 都完成**才能开始（木桶效应——最慢的那个决定开始时间）
2. **先落盘再被拉走**：map 输出落本地盘 → reduce 再从网络拉 → 又落盘
3. **纯搬运，没有计算产出**：数据在动，但没有产生任何新结果

> 💡 **一句可以背下来的判断**：**在小集群上，跑批的时间大头往往不是"算"，而是 shuffle + 写回。**
> 本项目实测印证了这一点：失败的作业 `Cumulative CPU` 只有 137 秒，但整个作业跑了 21 分钟——**时间全花在搬运和写盘上，不是在计算上**。

### 问题 5：出错了谁发现？怎么补救？

| 出错方 | 谁发现 | 怎么补救 |
|---|---|---|
| map/reduce 子进程挂了 | AM 通过心跳发现 | 换一台机器**重跑这个分片**（这是 MapReduce 容错的核心） |
| NodeManager 挂了 | RM 收不到心跳 | 把它上面的容器当作失败，任务在别的机器重跑 |
| ApplicationMaster 挂了 | RM 发现 | 整个作业重启一次 AM，已完成的 map 结果从磁盘恢复，不重算 |
| 某个任务算得特别慢（不是挂了） | AM 发现它拖后腿 | **推测执行**：在另一台机器同时跑一份，谁先完成用谁 |

> ⚠️ **本项目把这个机制关掉了**：`mapreduce.map.speculative=false` / `reduce.speculative=false`。
> 原因：集群只有 3 台 2 核机器，**同时跑两份反而抢资源**，适得其反。这是个典型的"教科书默认值不适合小集群"的例子。

### 问题 6：换来了什么？代价是什么？

| 设计 | 换来了 | 代价 |
|---|---|---|
| **容器化（配额制）** | 多作业能共存、互不干扰；资源能精确控制 | 配额给少了会 OOM 被杀；给多了会浪费。本项目设 512MB/容器，**调大调小都会出问题** |
| **计算与资源解耦** | Spark / Flink 都能复用 YARN | 每次启动都要"申请容器 → 起 JVM"，有固定启动开销 |
| **每步都落盘** | 极稳：挂了可以从上一个落盘点重来 | **慢**。这是 MapReduce 被 Spark 取代的根本原因 |
| **JVM 重用（`jvm.numtasks=10`）** | 一个 JVM 连着跑 10 个任务，省掉反复启动的开销 | JVM 里的内存泄漏会累积影响后续任务 |
| **关掉推测执行** | 小集群不抢资源 | 遇到"慢节点"没有兜底手段，只能等 |

**本项目的一套关键数字（值得理解背后的换算）**：

| 配置项 | 值 | 含义 |
|---|---|---|
| `yarn.nodemanager.resource.memory-mb` | **2048** | 每台机器愿意交给 YARN 的内存 = 2GB |
| `yarn.scheduler.minimum-allocation-mb` | 512 | 最小分配单位 |
| `yarn.scheduler.maximum-allocation-mb` | **2048** | 单个容器最大能要到 2GB（防超分） |
| `yarn.nodemanager.resource.cpu-vcores` | 2 | 每台机器交给 YARN 的 CPU 核数 |
| `mapreduce.map.memory.mb` / `reduce.memory.mb` | 512 | 一个 map/reduce 容器要 512MB |
| AM 容器 | 768 | 监工要多点内存 |

**算一下**：每台 2048MB ÷ 512MB = **4 个容器**；三台 = **12 个容器**。
本项目那次作业用了 6 个 map + 6 个 reduce = 刚好把 12 个容器占满 → **再提交别的作业就得排队**。
**这就是"为什么这个集群一次只能好好跑一个作业"的算术依据。**

### 问题 7：规模放大 100 倍，先崩的是哪一环？

**先崩 shuffle，然后崩磁盘。**

- **shuffle 数据量**：中间结果通常是输入的数倍。输入 1.4GB → 中间可能十几 GB 落盘
- **磁盘**：本地盘既要存 map 输出、又要存 shuffle 拉的临时数据。本项目三台 VM **共享宿主机同一块物理盘**，压力被放大
- **容器数上限**：12 个容器是硬天花板，数据量再大也只是让每个容器跑得更久，不会更快

**怎么验证瓶颈在哪**：

```bash
H=/opt/hadoop/hadoop-3.3.6/bin

# 看集群有多少资源可用（Total Nodes / 已用内存）
$H/yarn node -list

# 看一个作业的详细进度和每个阶段耗时
$H/mapred job -list all
$H/mapred job -status <application_id>

# 看一条 SQL 被拆成了几个作业（本项目实测：1 天规模 1 个，全量 1063 万行 11 个）
journalctl -u hive-server2 --since "-2h" --no-pager | grep -E "Total jobs|Launching Job [0-9]+ out of"
```

### 3.3 那次真实的失败与修复（本项目最有价值的一段经验）

**现象**：一条 INSERT 处理 1063 万行，跑 21 分 39 秒后失败。

**关键证据**：

```
Stage-Stage-1: Map: 6  Reduce: 6   Cumulative CPU: 137.54 sec
    HDFS Read: 1419781250  HDFS Write: 0   FAIL
```

**怎么读这一行**：
- `Cumulative CPU: 137.54 sec` → **只用了 137 秒 CPU，一点都不累**
- `HDFS Write: 0` → **算完了，一个字节都没写出去**
- 两条合起来 → **不是算不过来，是写不过来**

**根因**：这条 INSERT 被 Hive 拆成 **11 个 MR 作业**，6 个 reducer 同时向 31 个动态分区写文件、每个写 3 副本 ≈ **186 条并发写入流**，全压到宿主机同一块物理盘上 → DataNode 响应超时被逐个剔除 → 三个全被踢 → 0 副本写入。

**修复（4 条会话参数）**：

```sql
SET hive.optimize.sort.dynamic.partition = true;  -- 最关键：reducer 先排序再写，同一时刻只开一个分区文件
SET mapreduce.job.reduces = 3;                    -- 工人从 6 个减到 3 个
SET dfs.replication = 2;                          -- 写入期副本 3→2（跑完必须恢复 3）
SET hive.merge.mapfiles = false;                  -- 关掉合并作业，少起几个 MR
```

**结果**：失败（1299 秒）→ **成功（481 秒，快 63%）**，ORC 落盘 620MB、31 分区齐全。

> 📖 完整排查过程见 `实验分析/实验03_全量ETL写入失败排查与调优.md`（含 9 条假设的成立/证伪判定）。

### 3.4 一个我还没完全查清的问题（诚实记录）

**事实**：这一条 INSERT 被拆成了 **11 个 MR 作业**（日志里数十出来的）。1 天数据规模只需要 **1 个**。

**尚未查清**：这 11 个作业**各自具体在做什么**。可能涉及：`SELECT DISTINCT` 需要先做一轮去重、动态分区写入需要先把数据按分区排序、以及小文件合并作业。

**怎么补上这一课**（如果你感兴趣，这本身就是个不错的实验题目）：

```bash
journalctl -u hive-server2 --since "-5h" --no-pager \
  | grep -E "Total jobs|Launching Job|Ended Job|Stage-" | less
# 把每个作业的 Stage 名称和前后文归一次类，就能看出每个作业的职责
```

## 四、我们踩过的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | **一条 INSERT 被拆成 11 个作业**，但编译期只报告 `Total jobs = 2` | **不能用编译期的作业数估算耗时**，它会在执行中膨胀。估时要看数据规模 × 分区数 |
| 2 | 以为"YARN 里查不到作业"就是没提交 | 实际是非交互 SSH 下裸写 `yarn` 是 command not found，又被 `2>/dev/null` 吞掉报错 → **"命令不存在"和"结果为空"表现完全一样**。远程调 Hadoop 命令**一律用全路径** |
| 3 | 作业莫名失败后**留下 ACCEPTED 状态的残留应用**占着队列 | 失败后要主动 `yarn application -list` 检查并清掉 |
| 4 | 推测执行是默认开启的（教科书推荐） | 在 3 台 2 核的小集群上它**抢资源适得其反**，本项目已关闭 |
| 5 | 容器内存给 512MB 觉得"够用" | 容器超配额会被 NM **直接杀掉**。配额是硬约束，不是建议值 |

## 五、面试高频追问

**Q1：YARN 知道 MapReduce 在算什么吗？**
A：**不知道。** YARN 只认"给我 512MB 内存 + 1 核"这种资源请求，完全不关心业务逻辑。
这个设计叫**计算与资源解耦**，好处是同一套 YARN 能跑 MapReduce、Spark、Flink。本项目将来上 Spark，YARN 一行配置都不用改。

**Q2：MapReduce 为什么比 Spark 慢？慢在哪？**
A：慢在**每一步都要落盘**。map 输出写本地盘 → shuffle 落盘 → reduce 结果写 HDFS，而且**每个作业之间也要落盘**。
Spark 尽量把中间结果放在内存里（叫 RDD 缓存），**迭代场景下能快一个数量级**。
但要注意：**MapReduce 的落盘设计也带来了稳定性**——挂了可以从上一个落盘点重来。所以它没有"死"，只是适合的场景变了。
本项目之所以选 Spark **3.5.x 而不是最新的 4.x**，是因为集群是 JDK 8，而 Spark 4 强制要求 JDK 17+，且默认开启 ANSI SQL 模式会改变 NULL 语义、破坏现有 Hive SQL 的兼容性。

**Q3：这个集群最多能同时跑几个作业？**
A：按配置算：每台机器交给 YARN **2048MB**，容器标准大小 **512MB** → 每台 **4 个容器** → 三台共 **12 个容器**。
那次 ETL 用了 6 map + 6 reduce = 12 个容器，**刚好占满**。所以再提交别的作业只能排队。
这也解释了为什么"资源看起来够"却经常要等——**是容器数上限，不是内存总量的问题**。

**Q4：作业失败了，你怎么区分是"算不过来"还是"写不过来"？**
A：看作业收尾的统计行：

```
Cumulative CPU: 137.54 sec      ← 用了多少 CPU
HDFS Read: 1419781250  HDFS Write: 0   ← 读进去多少、写出去多少
```

- **CPU 很高但进度慢** → 算不过来（看并行度、数据倾斜）
- **CPU 不高但 Write 是 0 或很小** → **写不过来**（看并发写入流、副本数、磁盘 IO）
- **CPU 不高、Write 正常、但阶段之间卡很久** → 搬不过来（看 shuffle 数据量、网络）

本项目那次是第二类：CPU 只用 137 秒、Write 是 0。**这一条判断省掉了几十分钟的盲查。**

**Q5：为什么把推测执行关了？**
A：推测执行是"发现某个任务算得特别慢，就在另一台机器同时跑一份，谁先完成用谁"。
它的前提是**集群有富余资源**。本项目每台只有 2 核、总共 12 个容器，**同时跑两份只会互相抢资源，把快的也拖慢**。
所以这里选择关掉，接受"遇到慢节点就等着"。这是"教科书默认值不适用于小集群"的典型例子。

## 六、下一步：Spark 3.5.x（规划中）

本项目规划用 Spark 做同样一批 ETL，然后与 MapReduce 对比耗时。为什么强调"同一批数据、同样的 SQL"？因为**只有在相同输入下对比，加速比才有意义**。

已确定的技术选择与理由：

| 决策 | 选择 | 理由 |
|---|---|---|
| 版本 | **Spark 3.5.x**（不是 4.x） | 集群是 JDK 8；Spark 4 要求 JDK 17+ 且默认开 ANSI 模式会改 NULL 语义，有兼容风险 |
| 元数据 | `spark.sql.hive.metastore.version=3.1.3` | Hive 3.1.3 的元数据被 Spark 原生支持，无需重编译 |
| 输出位置 | 独立库 `gmall_spark` | 不覆盖 Hive 链路的结果，两条链路并存以便对比和回滚 |
| 已知坑 | 需把 Spark 自带的 `commons-collections-3.2.2.jar` 补进 Hive lib | 否则报 `ClassNotFoundException` |

> ⚠️ **一个前提提醒**：本项目原来只有 10 万行模拟数据，Spark 的**启动开销可能比它省下的计算时间还大**，做性能对比会得出"Spark 更慢"的误导结论。
> 后来数据源换成真实的 REES46 数据集（1063 万行），这个问题才自然解决——**数据量是 Spark 性能对比的前提，不是附带条件。**

| **MapReduce** | 分布式计算模型：分头处理（map）+ 汇总（reduce） |
| **map / reduce 任务** | 具体的计算子任务，各自是一个 JVM 子进程 |
| **Shuffle** | 把各机器上 map 的输出跨网络搬到 reduce 处，最贵的一步 |
| **数据本地性** | 尽量把计算任务调度到数据所在的机器上，减少网络搬运 |
| **推测执行** | 慢任务开副本同时跑，谁先完用谁；小集群通常关掉 |
| **虚拟内存检查（vmem-check）** | NM 检查容器是否超内存用量的机制，本项目关闭以避免误杀 |
| **数据倾斜** | 某个 key 的数据特别多，导致某个 reduce 特别慢，拖垮整个作业 |
