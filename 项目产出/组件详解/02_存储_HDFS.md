# 组件详解 · 02 存储：HDFS

> **一句话定位**：HDFS 把数据切成块，分散存到三台机器上，每块存 3 份——**任何一台机器坏了都不丢数据**。
>
> 涵盖：NameNode、SecondaryNameNode、DataNode，以及"块"和"副本"两个核心概念

---

## 〇、先建立直觉

| 名字 | 一句话类比 | 物理真相 |
|---|---|---|
| **NameNode** | 图书馆的**目录柜** | 一个 JVM 进程，内存里记着"哪个文件由哪些块组成、每块在三台机器的哪台上" |
| **DataNode** | 图书馆的**书架** | 一个 JVM 进程，把数据块写在自己的本地磁盘上 |
| **Block（块）** | 把一本厚书拆成若干册，分开存放 | 默认一个块 128MB，是存储和计算的基本单位 |

**最重要的那句话**：

> **NameNode 全程不碰数据。** 它只管"东西在哪"，真正的数据在 DataNode 的本地磁盘上。
>
> 这一条推出三个结论：
> 1. NameNode 的内存压力**与数据总量无关，只与文件数/块数有关** → 所以 HDFS 天生不适合存海量小文件（一个 1KB 文件和一个 1GB 文件，在目录柜里占的位置一样大）
> 2. NameNode 挂了**不会丢数据**（数据不在它那儿），但集群会"不知道数据在哪" → 整个 HDFS 用不了
> 3. 扩大数据量**不等于**要给 NameNode 加内存——这是初学者最常搞错的一点

---

## 一、为什么需要 HDFS（没有会怎样）

把 1063 万行事件日志（约 1.4GB 原始文本）放在**一台**机器上会怎样？

| 问题 | 一台机器 | HDFS 的做法 |
|---|---|---|
| 硬盘不够大 | 总会有更大的一天 | 切块分散到多台机器，容量随机器数增加 |
| 硬盘坏了 | 数据全丢 | 每块存 3 份，坏一台还有 2 份 |
| 读得太慢 | 只有一块盘的读带宽 | 三块盘并行读，理论带宽 ×3 |

所以 HDFS 的设计目标就三个：**能无限扩、坏了不丢、能并行读**。

> ⚠️ 但要清楚它的**不擅长**：它适合"写一次、读很多次"的大文件。**不适合**频繁修改的小文件——改一个字节也要重写整个块。所以它被用来做"数据仓库的底座"，而不是"数据库"。

## 二、按 7 问框架拆解

### 问题 1：谁和谁说话？走网络还是本地？

写一个文件时的**两条通道**（这是理解 HDFS 最关键的一张图）：

| 通道 | 参与者 | 传什么 | 大小 |
|---|---|---|---|
| **控制流** | 客户端 ⇄ NameNode | 只传位置信息（该写哪几台、写完了） | 几百字节 |
| **数据流** | 客户端 → DataNode1 → DataNode2 → DataNode3 | 真正的数据块，**逐级转发** | 几百 MB 起 |

> **数据流完全不经过 NameNode**，这就是"NameNode 不会被数据压垮"的原因。

### 问题 2：数据此刻在哪？什么时候只在内存？

**写文件的 6 个步骤**：

```
① 客户端问 NameNode：我要写 xxx，该写哪几台？        ← 控制消息，很小
② NameNode 回地址：DN1 / DN2 / DN3                  ← 只给位置，不碰数据
③ 客户端把数据发给 DN1
④ DN1 边写自己的磁盘、边转发给 DN2；DN2 同样转发给 DN3   ← 最贵的一步
⑤ 逐级回传"已收到"
⑥ 客户端通知 NameNode「写完」，NameNode 才记下元数据
```

**读文件的步骤**（比写简单，而且更聪明）：

```
① 客户端问 NameNode：这个文件的块在哪几台？
② NameNode 回一串地址（每个块都给多个可选位置）
③ 客户端**就近挑一台**直接读 → 读完一个块再读下一个
```

💡 读的时候**三个副本只读一个**，不像写的时候要三份都成功。所以"读性能"和"写性能"的瓶颈完全不同。

**"数据在哪"的完整答案**：

| 阶段 | 数据位置 |
|---|---|
| 写入过程中 | 客户端的网络缓冲 → 三个 DataNode 的本地磁盘 |
| 写完落定 | **三个 DataNode 的本地磁盘**（`/opt/hadoop/.../datanode/current/`） |
| NameNode 里 | 只有"目录条目"，没有数据 |

### 问题 3：谁负责"知道"？谁负责"存"？

| 角色 | 记什么 | 存在哪 |
|---|---|---|
| **NameNode** | 文件 → 块 → 块在哪些 DataNode 上；目录树；权限 | **内存里**（所以内存敏感），磁盘上有 `fsimage`（快照）+ `edits`（增量日志）两份备份 |
| **DataNode** | 自己磁盘上有哪些块 | 本地磁盘的块文件 |
| **SecondaryNameNode** | ⚠️ **它不是 NameNode 的备份！** | 见下 |

#### ⭐ SecondaryNameNode 到底干什么（初学者最容易误解的一个）

它的名字极具误导性。**它不提供高可用，NameNode 挂了它顶不上去。**

它干的事叫**检查点（checkpoint）**：

```
NameNode 运行时会不断写 edits 日志（记录"刚才又改了哪个文件"）
edits 越来越长 → 重启 NameNode 时要一条条重放，很慢

SecondaryNameNode 定期做：
  ① 把 fsimage 和 edits 拉过来
  ② 合并成一个新的 fsimage
  ③ 送回 NameNode
于是 NameNode 重启时不用重放一堆日志
```

**一句话**：它是个"定期帮你把账本合订成册的文书"，不是"备用馆长"。

> 面试如果问"NameNode 单点故障怎么办"，正确答案是 **HDFS HA（两个 NameNode 主备）+ JournalNode**，不是"用 SecondaryNameNode"。

### 问题 4：一个动作分几步？哪一步最贵？

写文件最贵的是**第 ④ 步**，因为：

```
一个大文件 = 3 次磁盘写入（三个 DataNode 各写一份）
           + 2 次网络转发（DN1→DN2→DN3）
```

**副本因子 3 意味着：写 1 份数据，物理上要付 3 倍的磁盘写入 + 2 倍的网络流量。**

> 所以本项目为了让跑批能成功，曾在**写入期临时把副本降到 2**（跑完立刻恢复 3）。这就是理解"副本是性能与可靠性的交易"后做出的取舍。

### 问题 5：出错了谁发现？怎么补救？

**常态探测**：DataNode 每隔几秒向 NameNode 发**心跳**。NameNode 一段时间收不到，就认为这个 DataNode 有问题。

**但本项目踩的是另一层——写入管线的临时剔除**：

```
could only be written to 0 of the 1 minReplication nodes.
There are 3 datanode(s) running and 3 node(s) are excluded in this operation.
```

翻译：**要求至少写成功 1 份，实际 0 份；三个 DataNode 全被踢出了这次写入。**

> ⭐ **关键区分**：原文写的是 `3 datanode(s) running` —— **节点是活着的**（心跳正常、没宕机），只是在这条**写入管线**上响应不过来，被逐个剔除了。
>
> **"running 但 excluded" = 忙不过来，不是坏了。** 这个区别决定了修复方向完全不同：前者要**降并发**，后者要**查服务**。
> 本项目就是靠这个判断，把方向定为"降写入并发"，而不是"去重启 DataNode"。

### 问题 6：换来了什么？代价是什么？

| 设计 | 换来了 | 代价 |
|---|---|---|
| **副本 3** | 坏一台不丢数据 | 3 倍磁盘写入 + 2 倍网络；**且三个副本都在同一条写入管线上，任一掉线整笔失败** |
| **文件切块（128MB）** | 可以并行读、单块损坏只影响一块 | 块太小 → 目录条目暴增、压垮 NameNode；块太大 → 并行度下降 |
| **NameNode 不碰数据** | 不会被数据量压垮 | 元数据全在内存 → **海量小文件场景内存先爆** |
| **适合一次写多次读** | 顺序读写性能极好 | 不适合频繁改小文件 |

> ⚠️ **本项目的一条重要认知**：3 副本在**只有 3 台 DataNode** 的集群上，容错度实际是**零**——因为三份数据必须落在三台机器上，**任何一台掉线，这次写入就失败**。
> 副本数 >= 节点数时，"高可用"是个假象。

### 问题 7：规模放大 100 倍，先崩的是哪一环？

**先崩 NameNode 的内存，然后崩写入带宽。**

- **元数据量**：文件数/块数 × 每条约 150 字节。1 亿个小文件 ≈ 15GB 内存 → NameNode 直接爆
- **写入带宽**：并发写入流 × 副本数。本项目就崩在这里（6 个 reducer × 31 个分区 × 3 副本 ≈ 186 条并发流）

**怎么提前发现**：

```bash
# 看 NameNode 内存压力（配合 jstat 或 HDFS UI 的 "Memory" 面板）
free -m                                    # 元数据在内存里，NameNode 所在机器最先吃紧
hdfs dfs -count -q /user/hive/warehouse     # 看文件数/目录数增长趋势
hdfs dfsadmin -report                       # 看容量与副本因子
```

**有没有办法提前避免小文件问题？** 有——**写入前做合并**。本项目里 `hive.merge.mapfiles` 就是干这个的（把多个小文件合并成大文件），代价是多了合并作业。

## 三、本项目实况

### 3.1 角色分布

| 角色 | 在哪台 | 端口 | 端口用途 |
|---|---|---|---|
| NameNode | lrh-1 | **8020** | 客户端与 DataNode 的 RPC 通信入口 |
| NameNode Web UI | lrh-1 | **9870** | `http://lrh-1:9870` 浏览文件、看 DataNode 状态 |
| SecondaryNameNode | lrh-1 | — | 做检查点合并（**不是热备**） |
| DataNode | **三台都有** | 9864 | 数据块管理 + Web UI |
| 副本因子 | — | — | **3** |
| 数据仓库目录 | — | — | `/user/hive/warehouse/gmall.db` |

### 3.2 当前数据规模（实测）

| 表 | 分区 | 行数 | 实际大小 |
|---|---|---|---|
| `ods_event_log_di`（原始事件） | 31 | 10,630,245 | 约 1.3 GB |
| `dwd_event_log_di`（清洗后） | 31 | 10,623,154 | 620.4 MB（ORC 压缩后） |
| `dwd_purchase_fact_di` | 31 | 186,059 | 9.1 MB |
| `dim_product` | 1（不分区） | 140,665 | 796 KB |

> 💡 **留意一个现象**：原始文本 1.3GB，清洗后变成 **620MB**——文件反而变小了。因为清洗后换成了 **ORC 列式存储 + SNAPPY 压缩**。这也是本项目"DWD 层改 ORC"的技术理由：查询只需读用到的列，且体积约是纯文本的 1/5~1/10。

### 3.3 常用命令

```bash
H=/opt/hadoop/hadoop-3.3.6/bin

$H/hdfs dfs -ls /user/hive/warehouse/gmall.db/            # 看有哪些表目录
$H/hdfs dfs -du -h /user/hive/warehouse/gmall.db/dwd_event_log_di   # 看表占用
$H/hdfs dfs -stat '%n %o %r' <文件路径>                    # 看文件名/块大小/副本数
$H/hdfs dfsadmin -report                                  # 集群总容量、剩余、各 DataNode 状态
$H/hdfs dfsadmin -report | grep -E "Live datanodes|Dead datanodes|Failed Volumes"

# 恢复副本数（写入期临时降过副本后必须执行）
$H/hdfs dfs -setrep -w 3 /user/hive/warehouse/gmall.db/dwd_event_log_di

# 排除"服务活着但写不进去"的情况（本项目吃过这个亏）
$H/hdfs dfs -touchz /tmp/health_check && echo "HDFS 可写" && $H/hdfs dfs -rm /tmp/health_check
```

### 3.4 一个容易搞混的数量级

HDFS 报告里的 **"Configured Capacity 28.87GB/node"** 是**分区总大小**，不是剩余空间。真正的剩余要看：

| 指标 | 看哪 |
|---|---|
| **HDFS 视角**的剩余 | `hdfs dfsadmin -report` 的 `DFS Remaining`（NameNode 缓存的、可能滞后） |
| **操作系统视角**的真实剩余 | `df -h /`（**这个才准**） |

> ⚠️ 本项目实测：NameNode 报 `DFS Remaining 10.11GB`，同时 `df -h /` 只显示 **8.9GB**。
> **NameNode 的值是滞后的，会高估**——因为它是上次扫描时的数字。排查空间问题要看 `df`。
>
> 另一个反直觉点：**跑批期间的最低余量才是真实瓶颈**。本项目运行中根分区一度只剩 6.7GB，跑完自动回收到 8.9GB。只看跑前的余量会误判。

## 四、我们踩过的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | **`0 of the 1 minReplication nodes ... 3 node(s) are excluded`** —— 三个 DataNode 全被踢出写入通道 | `running` 但 `excluded` ≠ 宕机，是**并发写入压力过大**。修法是降并发，不是重启服务（详见实验报告 03） |
| 2 | 以为"磁盘满"是 `HDFS Write: 0` 的原因 | 实测每节点还剩 30~35%、无 Failed Volumes、50MB 测试写入正常 → **都排除了**。`Write: 0` 只说"写失败了"，不说为什么 |
| 3 | 以为 NameNode 报的 `DFS Remaining` 就是真实剩余空间 | 它**滞后且高估**（报 10.11GB，实际 `df` 只有 8.9GB）。**排查空间一律看 `df`** |
| 4 | 写入期为成功把副本降到 2，**差点忘了恢复** | 这是"用可靠性换成功率"，必须在跑完立刻 `setrep -w 3` 恢复，并显式记录 |
| 5 | 误以为 SecondaryNameNode 是 NameNode 的备份 | **它不是**。NameNode 高可用要靠 HDFS HA（双 NameNode + JournalNode） |
| 6 | 关机前没停 Hadoop | 可能损坏 HDFS 元数据。**改配置/关机前先 `sudo systemctl stop hadoop`** |

## 五、面试高频追问

**Q1：NameNode 内存不够了，是数据太多了吗？**
A：**不是。** NameNode 只存元数据（文件→块→位置的映射），**不存数据**。所以它的内存压力与**文件数和块数**有关，与数据总量无关。
本项目 10,623,154 行数据放在 31 个分区文件里，NameNode 只需要记住这几十个文件的块位置。**但如果把同样数据拆成 1000 万个小文件，NameNode 立刻爆内存。**
所以正确说法是："NameNode 内存不够 = 小文件太多"。

**Q2：`0 of the 1 minReplication nodes` 这个报错，你怎么判断是磁盘满还是并发过高？**
A：看三个证据：
1. **报错原文**——磁盘满会明确写 `No space left on device` 或 `DiskOutOfSpaceException`；本次写的是 `3 node(s) are excluded`，是写入通道问题
2. **`running` 字样**——原文说 `3 datanode(s) running`，说明节点是活的，不是宕机
3. **实测量化**——`hdfs dfsadmin -report` 看剩余空间（本次 30~35%）、`df -i` 看 inode（本次 14%）、写个 50MB 测试文件（本次成功）
三个都排除了，才敢断定是并发。
**另外还有个便宜的分辨方法**：看 `Cumulative CPU` 和 `HDFS Write`——本次 CPU 只用 137 秒（不累）但 Write 是 0，**"算得动却写不出去"**，方向立刻明确。

**Q3：为什么 DWD 层的数据比 ODS 层还小？**
A：因为存储格式变了。ODS 是 **TEXTFILE**（纯文本，每行都要存字段名之外的原始字符），DWD 换成了 **ORC 列式存储 + SNAPPY 压缩**。
ORC 按列存储，查询时只需读用到的列；加上压缩，体积约是纯文本的 1/5~1/10。本项目实测：原始 1.3GB → 清洗后 620MB（而清洗还做了去重、拆字段，字段数反而变多了）。
**所以"列式存储比文本更省空间"这个结论要能讲出机制，不能死记。**

**Q4：副本数设成 3 就一定安全吗？**
A：**看集群有几台机器。** 本项目只有 3 台 DataNode，3 副本意味着"三份必须落在三台机器上"——**任何一台掉线，这次写入就整体失败，容错度实际为零**。
正确理解是：**副本数 >= 节点数时，"高可用"是假象**。要真正容错，节点数必须 > 副本数（比如 5 台机器 3 副本，容忍 2 台掉线）。
本项目因此在写入期把副本降到 2，换取"容忍一台掉线"。

**Q5：为什么 HDFS 不适合存大量小文件？**
A：两个层面：
1. **NameNode 内存**：每个文件/块在内存里约 150 字节，1 亿个小文件 ≈ 15GB 内存，直接爆
2. **IO 效率**：一次读操作要"问 NameNode 要地址 → 连 DataNode → 建立连接"，小文件读 1KB 也要走一遍这个流程，大部分时间花在通信而不是读数据上
**解法**：写入前合并（`hive.merge.mapfiles`）、或用专门格式（如 ORC/HAR）打包。

## 附：本章名词速查

| 名词 | 一句话解释 |
|---|---|
| **HDFS** | Hadoop 分布式文件系统，把数据切块分散存在多台机器上 |
| **NameNode** | 管目录的进程，只记"东西在哪"，不存数据 |
| **DataNode** | 存数据的进程，每个一块本地磁盘 |
| **SecondaryNameNode** | 定期合并元数据日志的文书，**不是热备** |
| **Block（块）** | 文件被切成的固定大小片段，默认 128MB |
| **副本 / replication** | 同一块数据存几份，本项目为 3 |
| **心跳** | DataNode 定期向 NameNode 报"我还活着" |
| **minReplication** | 一次写入最少要成功的份数，达不到就整笔失败 |
| **fsimage / edits** | NameNode 元数据的"快照"和"增量日志" |
| **检查点（checkpoint）** | 把增量日志合并进快照，减少重启时的重放时间 |
| **ORC** | 一种列式存储格式，查询只读用到的列，体积小、扫描快 |
| **机架感知** | 副本尽量放到不同机架上，防止整个机架断电全丢 |
| **DFS Remaining** | NameNode 认为的剩余空间，**滞后且会高估**，排查时以 `df` 为准 |
