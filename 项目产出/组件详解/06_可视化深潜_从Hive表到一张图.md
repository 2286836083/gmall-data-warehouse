## 一、先看全景：一条数据流水线

**类比**：把数仓想成一家**中央厨房**，大屏是**餐厅里给客人看的那块菜单屏**。
中央厨房（Hive）做菜很慢但量很大；菜单屏（浏览器）反应快但**只能拿一点点东西**。
两者之间不能直接连 —— 中间必须有人"**装盘**"。这条流水线就是装盘的过程：

```
①  Hive 数仓（ADS 指标层）
    gmall.ads_active_user_day / ads_funnel_day / ads_repurchase_day
    ads_top_product_day / dws_trade_day / dws_category_event_day
      │
      │  ② beeline 查询 + 导出
      ▼
    6 个 CSV 文件（纯文本，逗号分隔，**不带类型信息**）
    /home/lrh/workspace/new_chain/dashboard_real/raw/*.csv
      │
      │  ③ csv2json_real.py 转换（定义"数据契约"：哪列对应哪个字段）
      ▼
    dashboard_data_real.js  （内容是一句 JS：window.DASHBOARD_DATA = {...}）
      │
      │  ④ 拷到本机，和 html 放同一目录，双击打开
      ▼
    浏览器 dashboard_real.html
      │  读 <script src> 两个文件：echarts.min.js（画图引擎）+ dashboard_data_real.js（数据）
      │  执行 option 配置：把数据映射成坐标、颜色、宽度……
      ▼
    ⑤ 屏幕上的像素
```

**每一段的输入/输出/失败了会怎样**：

| 段 | 输入 | 输出 | 这一步失败会怎样 |
|---|---|---|---|
| ① Hive 表 | 1063 万行明细（ODS→DWD→DWS 算上来） | 4 张 ADS 指标表 + 2 张 DWS 表 | 图**没数据**（但页面还打得开，会显示提示） |
| ② 导出 | SQL | CSV（31 行/15 行/12 行…） | 某个 CSV 为空 → 对应那张图**空白**，其余正常 |
| ③ 转换 | CSV | `dashboard_data_real.js` | 字段对不上 → 图**画错但不报错**（最危险，见第六章） |
| ④ 加载 | 两个 .js | 内存里的一个对象 | 路径写错 → 页面白屏 + 提示"数据文件未加载" |
| ⑤ 渲染 | option 配置 | 像素 | JS 报错 → 图不出现，控制台（F12）有红字 |

> ⭐ **为什么要分成三段，而不是"一条 SQL 直接出图"**：
> **每一段都可以单独重跑、单独检查、单独替换。**
> 实测例子：我把导出跑完后发现**金额有浮点噪声**（`80952.47000000006`），
> 于是**只重跑了第 ③ 段**（CSV 已经在集群上），**3 秒**就修好了，不用重新查一遍 Hive（那要 3 分钟）。
> 这就是"分段"换来的好处：**改一处，不用重跑全部**。

## 二、为什么不能"页面直连数据库"（设计取舍）

初学者最容易想到的方案是：**让网页直接连 MySQL/Hive 查数据**。为什么不行？

**类比**：这相当于**把中央厨房的仓库钥匙复制一把给每位顾客**。三个问题：

| 问题 | 直连数据库的后果 |
|---|---|
| **安全** | 数据库账号密码必须写在前端 JS 里 —— 任何人按 F12 就能看到，等于把库公开 |
| **性能** | 浏览器每刷新一次就查一次 Hive。Hive 一条查询要跑 MapReduce **几分钟**，页面会一直转圈直到超时 |
| **演示稳定性** | 演示现场网络/集群一旦抖动，大屏就是一片空白 —— 而演示最怕的就是"当场打不开" |

**所以本项目选了"离线快照"**：数据**提前**导出成静态文件，页面**只读本地文件**。

> ⭐ **这个取舍的代价（要能说出来）**：
> **数据不是实时的**。ETL 跑完后必须**重新导出一次**，大屏才会更新。
> 本项目的数据文件里就明确写着 `generated_at`（生成时间）和 `range`（数据区间），
> 页面右上角也把它们显示出来 —— **让人一眼知道"这份图是什么时候的"**，避免把旧图当新数。

**什么时候该直连**：真正的生产 BI 系统会走"**后端 API + 数据库**"（浏览器只连后端，后端连库并做缓存），
或直接用 Superset / Metabase 这类 BI 工具。**面试时如果被问"为什么不做成实时的"，这就是标准答案**：
"演示优先选稳定性，实时性用后端 API 换，本项目规模下离线快照的性价比最高"。

## 三、第一段：为什么中间格式是 CSV

**类比**：CSV 就是**一张没有写类型的 Excel**。
它只记录"**值**"，不记录"这个值是数字还是文本"—— 这一点是后面好几个坑的根源。

**为什么用 CSV，而不是直接导 JSON？**
因为 **beeline 根本没有 JSON 输出格式**。这不是我懒，是工具的限制 ——
它的 `--outputformat` 只支持：`table` / `vertical` / `csv2` / `tsv2` / `dsv` / `csv` / `tsv`。

所以链条里**必然存在一次"格式转换"**（CSV → JSON），而这次转换就必须有人**定义类型**（第三章之后的主角）。

> 💡 **一个可以写进报告的小结论**：**"数据格式的转换点"就是"类型信息最容易丢失的地方"**。
> 每当你看到 CSV / 日志行 / 无 schema 的文本，就要多问一句：**"这里的数字，到了下一段还是数字吗？"**

## 四、第二段：转换脚本在干什么（**数据契约**）

### 4.1 什么是"数据契约"

**契约 = 双方约定好的字段清单**。

大屏 HTML 说："我要 `dau` 这个数组，每个元素要有 `dt` 和 `dau` 两个字段。"
导出+转换脚本说："我给你 31 行，每行有 `dt`、`dau`、`new_dau`、`active_dau`、`wakeup_dau`。"

**两边必须逐字对齐**，否则轻则图空白，重则**图画错但不报错**。

### 4.2 契约靠什么对齐：**列名 + 列序**

这条流水线里，对齐是**两处**做的（这是最容易出错的地方）：

```python
# 第 1 处：导出 SQL 里 SELECT 的列，顺序必须固定
run dau "SELECT dt, dau, new_dau, active_dau, wakeup_dau FROM gmall.ads_active_user_day ORDER BY dt"
#                └──────────── 这个顺序，就是 CSV 的列序 ────────────┘

# 第 2 处：转换脚本里按同样顺序声明列名
SPEC = { "dau": ["dt", "dau", "new_dau", "active_dau", "wakeup_dau"], ... }
#                └──── 一模一样，一个都不能换位 ────┘
```

> ⚠️ **为什么是"列序"而不是"列名"对齐？** 因为 **CSV 文件里只有"第一列、第二列"，没有列名绑定**。
> 转换脚本是靠**位置**去取值的。所以**如果你只是把 SQL 里两列换个位置、而没改脚本，数据就整体错位了 —— 而且不会报错**。
>
> 这是本项目反复强调的那类坑：**"静默跑错"比"报错"危险得多**。
> 所以两个脚本里都留了同一句注释：`顺序必须与 export_dashboard_real.sh 中的 SQL 保持一致`。

### 4.3 ★ 为什么**不能**沿用旧字段名（本次最重要的设计决定）

项目里原本有一版大屏（模拟数据版），字段叫 `sku_name`、`order_day`、`paid_orders`……
做真实数据版时，一个自然的想法是"**字段名不变，只换数据来源，这样 HTML 不用改**"。

**这个想法是错的，而且很危险。** 因为新链路里**有些字段根本不存在**：

| 旧字段 | 新链路有没有 | 如果硬套名字会怎样 |
|---|---|---|
| `sku_name`（商品名） | ❌ 真实数据只有 `product_id` / `brand` / `category_l1/l2` | 把品牌名塞进"商品名"，图上是**错的**但看不出来 |
| `order_uv` / `pay_uv`（下单/支付环节） | ❌ 只有 `view_uv` / `cart_uv` / `purchase_uv` | 把"购买"当成"支付"，指标口径**当场变质** |
| `paid_orders` / `cancelled_orders` / `refunded_orders`（订单状态） | ❌ **REES46 是行为事件流，没有订单状态这个概念** | 三个字段全填 0 或乱填 —— 图还在，但**在说谎** |
| `total_amount`（订单总额） | ❌ 只有成交金额 `gmv` | 把成交额当订单总额，GMV 口径错 |

**所以本次的决定是：字段名也一起改**（`top_product` 代替 `top_sku`、`purchase_uv` 代替 `order_uv`/`pay_uv`、
`trade_day` 代替 `order_day`），**宁可改 HTML，也不让名字说谎**。

> ⭐ **这一条可以单独拿去面试讲**：
> **"字段名是给人看的契约，不是给代码看的标识符。**
> 名字没变、含义变了，是数据工程里最难查的一类 bug —— 因为所有测试都会通过，
> 只有**懂业务的人盯着图**才会发现不对。"

### 4.4 契约被破坏时的三种失效模式

| 失效模式 | 现象 | 危险度 |
|---|---|---|
| **字段缺失** | 图是空的 / 显示 `undefined` | ⭐ 低（一眼看出来） |
| **列序错位** | 数字张冠李戴（把"加购数"画成"浏览数"） | ⭐⭐⭐ 高（图很好看，但是错的） |
| **类型错**（数字变成字符串） | 坐标轴排序乱、数值比较出错 | ⭐⭐ 中（见第六章第 3 坑） |

## 五、第三段：浏览器里真正画图的地方

### 5.1 ECharts 拿到数据后做了什么

ECharts 不会"自动懂数据"。你必须给它一个**配置对象**（`option`），
明确告诉它："这一列当 X 轴、那一列当柱子高度、这个颜色代表哪个系列"：

```js
series: [{ type: 'line', data: funnel.map(r => r.purchase_uv) }]
//                                └─ 你亲手把"数据的哪一列"映射到"图的哪个视觉通道"
```

**这就是"数据可视化"的实质**：把数据的某个维度，**映射**到图形的某个视觉通道（位置 / 长度 / 颜色 / 面积）。

### 5.2 从数据到图形，必经的 4 个动作（每个都可能出错）

| 动作 | 谁在做 | 出错会怎样 |
|---|---|---|
| **取值** | 你写的 `map(r => r.xxx)` | 字段名打错 → 全 `undefined` → 图空白 |
| **排序** | ECharts **默认行为**（！） | 这是第 2 个坑：**漏斗被按数值重排，顺序画反** |
| **定标**（算坐标轴范围/刻度） | ECharts | 数字被当字符串 → 刻度错乱（第 3 坑） |
| **取整/格式化** | 你的 `formatter` 函数 | 不处理 → 图上出现 `80952.47000000006`（第 1 坑） |

> ⭐ **一句话总结第五章**：
> **"图"是"数据 + 你写的映射规则 + ECharts 的默认行为"三者合成的结果。**
> 而**默认行为**是你最容易忽略的那一份输入 —— 第 2 个坑就完全由它造成。

## 六、这条流水线上的 6 个真实坑

> 这 6 个坑里，**4 个是本次真实踩到或提前抓到的**，2 个是本项目历史上的。
> 每个坑都给出「现象 → 根因 → 判据 → 解法」，并特别标注**怎么提前发现**。

### 坑 1：金额出现浮点噪声 `80952.47000000006`

| | |
|---|---|
| **现象** | 导出的 GMV 是 `80952.47000000006`，鼠标悬停的提示框里显示一长串小数 |
| **根因** | 计算机用**二进制浮点**（IEEE754）表示小数，而 `0.1` 这类十进制小数在二进制里**无法精确表示**，大量累加后误差就显现出来。**不是 Hive 的错，是所有浮点计算的通病** |
| **判据** | 一眼可见：小数位数异常多 |
| **解法** | 在**转换脚本**里按列统一取整：`ROUND = {"gmv": 2, "avg_order_amount": 2, "overall_rate": 4, ...}` |
| **怎么提前发现** | **别只看"脚本跑成功了"**，去**看生成的文件内容**。我是导出后 `head` 了一下 CSV 才发现的 |

> 💡 **原则**：**"归一化/取整"要放在"展示层之前的最近一层"**。
> 放在 Hive 里（`ROUND()`）会让 SQL 变啰嗦、且换一个口径就得改 SQL；
> 放在页面的 `formatter` 里则每张图都要写一遍。**放在中间层（转换脚本）最合适**。

### 坑 2 ★：ECharts 漏斗**默认按数值降序重排** → 顺序画反

| | |
|---|---|
| **现象** | 漏斗图本该是 浏览 → 加购 → 购买，实际画出来可能是 浏览 → 购买 → 加购 |
| **根因** | 真实数据里 **购买用户数(3612) > 加购用户数(2276)**（用户可以不进购物车直接买，实测 **31 天里有 15 天**如此）。而 **ECharts 漏斗默认 `sort: 'descending'`，会按数值把三档重排** —— 它以为你在画一个"标准的递减漏斗" |
| **判据** | 看图形顺序 vs 你的业务顺序是否一致；**数据上**看 `purchase_uv > cart_uv` 的天数 |
| **解法** | 显式写 `sort: 'none'`，让三档严格保持业务顺序 |
| **怎么提前发现** | ① 从数据里看"有没有非递减的情况"；② **最终还是要用眼睛看图** |

> ⭐ **这是全文最有价值的一个坑**，因为它同时教了三件事：
> 1. **库的"默认行为"是一种你没写、但生效了的输入**
> 2. **真实业务数据经常不满足"教科书形状"**（漏斗不一定逐级递减）
> 3. **"加购不是购买的必经环节"** 这个业务认知，决定了图该怎么画

### 坑 3：CSV 里的数字全是**字符串**

| | |
|---|---|
| **现象** | 坐标轴刻度错乱、排序不对（比如 `1000` 排在 `900` 前面） |
| **根因** | CSV 不带类型，读进来全是文本；JS 里 `"1000" < "900"` 是**真的**（按字符串逐位比较） |
| **判据** | 在浏览器控制台里 `typeof` 一下；或看排序是否"像字典序" |
| **解法** | 转换脚本里声明哪些列是数字并显式转换（`NUMERIC` 表） |
| **怎么提前发现** | **离线自检**：写个脚本检查"该是数字的字段，类型是不是 int/float"（见第八章第 2 条） |

### 坑 4：31 个 X 轴标签挤成一团

| | |
|---|---|
| **现象** | 31 天的日期全画在轴上，字叠字看不清 |
| **根因** | 数据从 5 天变成 31 天，**原来够用的标签密度不够用了** |
| **解法** | `axisLabel: { interval: 4 }` —— 每 5 个显示一个（`interval: n` 表示"跳 n 个"） |
| **注意** | 这是**假数据换真数据后才会暴露的问题**：旧版只有 5 天，怎么写都好看 |

### 坑 5：双 Y 轴的量纲陷阱

| | |
|---|---|
| **现象** | "成交金额（百万级）"和"客单价（百级）"画在同一个轴上 → 客单价被压成一条贴地直线 |
| **根因** | 两个指标**量纲差 1 万倍**，同一个坐标轴装不下 |
| **解法** | 用**双 Y 轴**（左轴金额、右轴客单价），并在图例/轴名上标清哪个对应哪个轴 |
| **判据** | 有一条线看起来"永远是 0"→ 多半是量纲问题 |
| **警告** | ⚠️ 双轴图**容易被误读**（两条线的交叉点没有意义）。所以**只有当两个指标确实需要一起看趋势时**才用 |

### 坑 6：`file://` 下的 CORS，`fetch` 读本地 JSON 会白屏

| | |
|---|---|
| **现象** | 双击打开 HTML，页面空白，控制台报 CORS/跨域错误 |
| **根因** | 浏览器对 `file://` 协议的 `fetch`/`XHR` 请求按跨域策略拦截 |
| **解法** | 把数据写成 `.js`（`window.DASHBOARD_DATA = {...}`），用 `<script src>` 加载 —— **`<script>` 不受 CORS 限制** |
| **详见** | `05_协作_调度与展示.md` 第三部分问题 1 |

> ⭐ **坑 6 顺带解释了一个初学者常问的问题**：
> **"为什么本地开发要起一个 HTTP 服务器（比如 `python -m http.server`）？"**
> 就是因为 `file://` 有很多限制。本项目为了让演示能"**双击即开**"，选择了绕开它（用 `.js`）。

## 七、业务口径：图上的数字到底是什么（**答辩/面试必问**）

**面试官最常问的一句话是："你这个 DAU 是怎么算的？"** 如果你答"就是表里查出来的"，基本就结束了。
所以这一章把每个指标的口径写清楚 —— **图是好看的，口径才是含金量**。

### 7.1 用户四分口径（本项目实测）

| 指标 | 定义 | 实测表现 |
|---|---|---|
| **DAU** | 当天产生过**任意行为**（浏览/加购/购买）的**去重用户数** | 日均 **52,349**，逐日波动 |
| **新增用户** `new_dau` | **首次出现日 = 当天**的用户 | **31/31 天 > 0** |
| **连续活跃** `active_dau` | 上一次活跃日 **= 昨天** | 有值 |
| **回流用户** `wakeup_dau` | 非首次，且上一次活跃日 **≠ 昨天** | **29/31 天 > 0** |

> ⭐ **这是"真实数据 vs 模拟数据"最有说服力的一条**：
> **模拟数据版的 `new_dau` 和 `wakeup_dau` 恒为 0**（因为模拟数据里每个用户每天都在，没有"首次"概念）。
> 真实数据能算出真值 —— **所以在图上把这三档堆叠起来，一眼就能看出"这不是模拟数据"**。

### 7.2 三环节漏斗，以及"为什么购买 > 加购"

| 环节 | 实测（2019-10-01） |
|---|---|
| 浏览 `view_uv` | 47,844 |
| 加购 `cart_uv` | 2,276 |
| 购买 `purchase_uv` | 3,612 |

**注意：购买(3612) > 加购(2276)** —— 这不是 bug。
**因为用户可以"不进购物车，直接购买"**，所以「加购」**不是**「购买」的必经环节。

> ⭐ **面试金句**：
> **"我一开始把漏斗写成『浏览≥加购 且 加购≥购买』，结果 31 天里有 15 天报"违例"。**
> **拆开查才发现：浏览≥加购 恒成立、浏览≥购买 恒成立，只有"加购≥购买"不成立。**
> **所以我修正后的结论是：真正的漏斗是「浏览→购买」两环节，加购是一条并行的独立路径。**
> **这提醒我：数据"报错"的时候，先怀疑自己的假设，再怀疑数据。"**
>
> （这段直接被本项目的三层校验脚本固化成了 SQL，见 `evt_verify.sql`。）

### 7.3 累计复购率：**不能取平均**

| | |
|---|---|
| 表字段 | `ads_repurchase_day(dt, total_buyers, repurchase_buyers, repurchase_rate)` |
| 口径 | **累计**：截止当日的购买用户里，买过 ≥2 次的占比 |
| 实测 | 0.2176 → 0.2897 → 0.3444 …（**随天数单调变化**，因为分母在累积） |
| ⚠️ 坑 | **对 31 天的 `repurchase_rate` 求平均是错的**（每天的"累计口径"含义不同，平均没有业务意义） |
| 正确做法 | 取**最后一天**的值（= 月末累计复购率），KPI 卡片上写清楚"月末累计" |

> 💡 **可迁移的教训**：**看到一个"率"字，先问它是"当日率"还是"累计率"。**
> 累计率只能取端点，当日率才能平均。

### 7.4 客单价：新链路能算、旧链路没有的指标

**客单价 = 成交金额 ÷ 成交笔数**，表里每天给了 `avg_order_amount`。

实测：**全月加权 309.45 元**（= 57,575,996.50 ÷ 186,059），**最高一天 328.53 元**。

> ⚠️ **2026-10-18 踩过的坑，正好是本节的活教材**：
> 大屏最初写成 `avg(每日客单价)` = **309.68**，与本节的 309.45 差了 0.23 元。
> **原因就是把 31 个日客单价又平均了一次**——那 31 天里有的天 7,714 单、有的天 4,970 单，
> 直接平均等于让"小单天"和"大单天"权重相同。
> **`AVG` 不可加**：日客单价可以平均，但**平均出来的东西不是"全月客单价"**，它只是个"日均客单价"，
> 两个名字听起来像、含义不同。已修正为 `sum(gmv)/sum(order_cnt)`。
>
> 这一条同时印证了 `零基础教程/07` 里那条警告（"不能对各城市的客单价再求平均"）——
> **文档里有警告，不等于代码里防住了。** 见 `手把手教程/大屏数据导出与切换实操.md`。

> 这个指标**旧链路给不了**（模拟数据的金额是随机生成的，客单价没有意义）。
> **"能算出一个有业务含义的客单价"，本身就是数据质量的证明。**

### 7.5 GMV 四路对账（本项目的招牌校验）

同一个月的 GMV，从**四条互相独立的计算路径**分别算出来，**必须完全相等**：

| 路径 | 来源表 | 实测 |
|---|---|---|
| 商品维度 | `dws_product_event_day` | 5.75759965E7 |
| 类目维度 | `dws_category_event_day` | 5.75759965E7 |
| 交易维度 | `dws_trade_day` | 5.75759965E7 |
| 明细事实 | `dwd_purchase_fact_di` | 5.75759965E7 |
| **大屏数据文件里重算** | `dashboard_data_real.js` 的 `trade_day` | **57,575,996.50** ✅ |

> ⭐ **为什么这条最有说服力**：四条路径**维度不同、算法不同、代码不同**，算的是同一批事件。
> **任何一条写错，这里立刻不相等。** 这比"我看了一下觉得对"强得多。

### 7.6 真实脏数据是**资产**，不是污点

类目 GMV 构成（全月累计）实测：

| 一级类目 | GMV | 占比 |
|---|---|---|
| electronics | 44,281,432.59 | 76.9% |
| **unknown** | **5,579,667.15** | **9.7%** |
| appliances | 3,481,396.04 | 6.0% |
| computers | 2,841,409.86 | 4.9% |
| furniture | 425,454.03 | 0.7% |

**`unknown` 占 9.7%** —— 这是源数据里**类目缺失**的真实情况（原始缺失率 31.9%，在 DWD 层归一为 `unknown`）。

> ⭐ **答辩时主动讲这个，比讲"我的数据很干净"加分得多**：
> **"我的数据里有 9.7% 的类目是缺失的，我没有丢掉它们，而是归一成未知类目单独展示 ——
> 因为丢掉会让 GMV 总额对不上，而保留能让业务方看到'有多少数据是没打标的'。"**

## 八、方法论：这次最值钱的 3 条可迁移经验

### 8.1 ★★「测试全绿 ≠ 做对了」—— 必须在最后一公里用**眼睛**验证

**同一天里我栽了两次，都是同一个原因。**

| 事件 | 自动化测试的结果 | 人眼的结果 |
|---|---|---|
| **DolphinScheduler 工作流"只有 1 个节点"** | **全绿**：16 个节点定义都在、16 条依赖边都在、16 个任务实例全部 SUCCESS、12 张表行数全对、GMV 四路收敛 | ❌ **画布上只画得出 1 个节点** |
| **本次大屏** | **全对**：字段齐全、类型正确、JS 语法通过、数据与 Hive 一分不差 | ❓ **我至今没亲眼看过它长什么样**（无头浏览器被沙箱挡住） |

**那个 DAG 事件的根因**：任务 code 用了 19 位（3.3e18），
超过浏览器 JS 能精确表示的整数上限 **2^53**（≈9.0e15）→ 16 个 code 在页面上**塌缩成同一个数** → 只剩 1 个节点。
但**数据库和 Java 侧是 64 位整数，执行完全正常** → 所有测试都绿。

> ⭐ **这条经验请记牢**：
> **"能自动验证的维度"之外，永远存在"看起来对不对"这一维。**
> 而这一维**只能靠人眼**。所以**做完任何面向人的产出（图、页面、画布、报告），
> 最后一件事必须是"自己打开看一眼"**，而不是"测试通过了所以应该没问题"。

**推论（跨技术栈的通用规律）**：
**当一个 ID / 数字从"执行链路"（Java/Python，64 位）跨到"显示链路"（浏览器，双精度浮点）时，
必须确认它没有超出对方能表示的范围** —— 要么传字符串，要么限制范围。

### 8.2 从**交付物**反向对账，而不是相信脚本说"成功"

导出脚本最后打印了"完成"，这**不算证据**。我的做法是：

```
从「最终交付的那个文件」dashboard_data_real.js 里重新算一遍：
   成交金额合计 = 57,575,996.50   ← 与 Hive 的 5.75759965E7 一致 ✅
   成交笔数合计 = 186,059         ← 与 dwd_purchase_fact_di 行数一致 ✅
   日均 DAU     = 52,349          ← 与 Hive 查出来一致 ✅
```

> ⭐ **为什么要"从交付物反算"**：因为**中间任何一步都可能悄悄改数据**
> （列错位、取整、类型转换、截断、LIMIT）。
> 只检查"脚本退出码是 0"，等于只检查了"它跑完了"，没检查"它跑对了"。
>
> **这也是数仓里"数据质量校验"的基本思路：从两端独立算，对不上就说明中间有问题。**

### 8.3 没有版本控制时，怎么保住回滚点

本项目**不是 git 仓库**。所以改大屏时的选择是 —— **一份都不覆盖，两版并存**：

| 旧版（模拟数据） | 新版（真实数据） |
|---|---|
| `dashboard.html` ✅ 原样保留 | `dashboard_real.html` |
| `dashboard_data.js` ✅ | `dashboard_data_real.js` |
| `export_dashboard_data.sh` ✅ | `export_dashboard_real.sh` |
| `csv2json.py` ✅ | `csv2json_real.py` |

> ⭐ **三个理由**（顺序就是重要性）：
> 1. **没有回滚点就不该动**：万一新版有 bug，旧版还能演示
> 2. **可以对照**：两个页面并排开，一眼看出"真实数据多了什么"
> 3. **符合项目原本的迁移习惯**：这个项目里"新表用新名字、与旧表并存"是既定做法
>    （`dwd_event_log_di` 与 `dwd_user_behavior_di` 并存、`ads_*_day` 与 `ads_*` 并存）
>
> **通用原则**：**动手前先想"如果搞砸了，我怎么退回去"。** 有版本控制就建分支，没有就并存。

## 九、FAQ（答辩/面试可能被追问的 8 个问题）

**Q1：你的大屏数据是怎么来的？**
A：三段式。① Hive 的 ADS 指标层（4 张指标表 + 2 张 DWS 表）→ ② beeline 导出成 6 个 CSV →
③ Python 转成一个 `window.DASHBOARD_DATA = {...}` 的 JS 文件 → 页面用 `<script src>` 加载。
**分成三段是为了每段能单独重跑和对账** —— 实测有一次只重跑第三段，3 秒修好了浮点精度问题，不用重新查 Hive。

**Q2：为什么不用 `fetch` 直接读 JSON？**
A：浏览器在 `file://` 协议下会按 CORS 策略拦截 `fetch` 读本地文件，**双击打开会白屏**。
而 `<script src>` 不受这个限制，所以把数据包成 `.js` 加载。**代价是要多一步转换，换来的是"演示时双击即开、不依赖网络和后端"。**

**Q3：为什么不做成实时的？**
A：显式取舍。实时需要后端 API + 缓存，本项目规模下性价比低；而**演示的第一需求是"点开就有"**。
代价是**数据不是实时的，ETL 后要重新导出**。为此我在数据文件里写了 `generated_at`，页面右上角也显示出来，
**避免有人把旧图当新数据看**。

**Q4：图上的 DAU 是怎么算的？**
A：当天产生过任意行为（浏览/加购/购买）的**去重**用户数。同一张表还一次算出了**新增**（首次出现日=当天）、
**连续活跃**（上次活跃=昨天）、**回流**（非首次且上次活跃≠昨天）三个口径 —— 一次扫表出四个指标。
**这里能讲出彩**：模拟数据版的"新增/回流"恒为 0，真实数据能算出真值。

**Q5：你的漏斗为什么只有三个环节？**
A：因为**源数据没有"订单状态"这个概念**。REES46 是**用户行为事件流**，只有 view/cart/purchase 三种事件。
旧版大屏的"下单/支付"两环节来自模拟数据的订单表，真实数据里不存在 ——
**所以我删掉了那两档，而不是拿别的字段硬凑**。（如果硬凑，图上会多出两个"在说谎"的环节。）

**Q6：漏斗里"购买 > 加购"是不是数据错了？**
A：不是，是**业务事实**。用户可以"不进购物车直接购买"，所以**加购不是购买的必经环节**（实测 31 天里 15 天如此）。
我最初把校验写成"浏览≥加购 且 加购≥购买"一条，结果 15 天报违例；
**拆开查才定位到：前两个关系恒成立，只有"加购≥购买"不成立。**
修正后的结论是：真正的漏斗是「浏览→购买」，加购是并行路径。
（这个坑也让我学到：**数据"报错"时，先怀疑自己的假设**。）

**Q7：你怎么保证图上的数是对的？**
A：**从交付物反向对账**。我不信"导出脚本说成功了"，而是从最终生成的 `dashboard_data_real.js` 里
重新算成交金额（57,575,996.50）、成交笔数（186,059）、日均 DAU（52,349），
去和 Hive 直接查的结果、以及**四条独立路径的 GMV**（商品/类目/交易/明细事实）比对 —— 全部一致。
`unknown` 类目占 9.7% 是真实缺失，我保留它而不是丢掉，因为**丢掉会让总额对不上**。

**Q8：你在这个过程中犯过什么错？**
A：（这题一定要准备，而且**要有具体的错**）
1. **把"真实数据"硬套进旧的字段名**的念头 —— 幸好及时否掉了，否则图表会在"说谎"（旧名 `order_uv`/`paid_orders` 在新链路没有对应物）。
2. **只看了"脚本跑成功"，没看生成的文件内容** —— 所以浮点噪声（`80952.47000000006`）第一版就漏进了交付物，是事后检查才发现的。
3. **最容易忽略的一类错**：同一个项目里我曾把工作流的节点 code 设成 19 位，导致浏览器里 16 个节点**塌缩成 1 个** ——
   而当时所有自动化测试都是绿的。**它教会我：面向人的产出，最后一公里必须用眼睛验证。**

## 十、名词速查

| 名词 | 一句话解释 |
|---|---|
| **ADS 层** | 数仓里"**面向指标**"的一层。它已经替你算好"每天一个值"，可视化直接拿它，不用自己聚合 |
| **数据契约** | 上下游约定好的**字段名 + 字段顺序 + 类型**。契约一破，图就画错 |
| **静默失败** | 不报错、但结果是错的。数据工程里最危险的一类问题（本项目的"错误的原因比错误的现象更危险"说的是同一件事） |
| **CORS** | 浏览器的跨域安全策略。`file://` 下会拦截 `fetch` 读本地文件，但**不管** `<script src>` |
| **`file://` 协议** | 双击打开本地 HTML 时的协议（区别于 `http://`）。限制较多，但**演示最省事** |
| **离线快照** | 数据提前导出成静态文件，页面只读本地。代价是**不实时** |
| **浮点噪声** | 二进制无法精确表示十进小数，累加后出现的 `...000000006` 这类尾巴 |
| **`sort: 'none'`** | 让 ECharts 漏斗**不许**按数值重排，严格保持你给的数据顺序 |
| **双 Y 轴** | 一张图里两套刻度。用于量纲差很大的两个指标；但**容易被误读**，能不用就不用 |
| **对账（reconciliation）** | 用**两条独立路径**算同一个数，对不上就说明中间有问题。本项目招牌是"GMV 四路收敛" |
| **累计率 vs 当日率** | 累计率的分子分母都在累积，**只能取端点、不能取平均** |
| **`generated_at`** | 数据文件里的"生成时间"。用来避免把旧图当新数据看 |
| **人眼验证** | 自动测试的**必要补充**。面向人的产出，最后必须自己打开看一眼 |
