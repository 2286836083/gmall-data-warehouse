# 开源同类项目调研

> **用途**：为「gmall 电商离线数仓」项目找参照物——看别人怎么做分层建模、怎么组织文档、踩过什么坑。
>
> 调研日期：2026-09-28
> 核实程度：标注 ✅ 的仓库已用 WebFetch 打开确认存在；标注 ⚠️ 的仅来自搜索结果，**未逐一核验**，引用前请自行确认。

## 〇、一个前提认知

**本项目的名字 `gmall` 源自尚硅谷的大数据数仓课程项目。** GitHub / Gitee 上有大量同名衍生仓库，绝大多数是 **Flink 实时数仓**方向。

所以：我们走的是一条**已经被很多人验证过的公开学习路径**，不是自己摸黑。好处是有大量作业可对照，坏处是容易"撞车"——**差异化要靠自己创造**（见文末第四章）。

## 一、最该看的（按与我们项目的相似度排序）

### ① `YangLv-Analyst/taobao-dw-project` ✅ —— 几乎是我们的"平行版本"

| 组件 | 它 | 我们 |
|---|---|---|
| Hadoop | **3.3.6** | **3.3.6** |
| Hive | **3.1.3**（MetaStore 后端 MySQL 8.0） | **3.1.3**（同） |
| Spark | **3.5.1** | 规划中，同为 **3.5.x** |
| 环境 | Windows 11 + WSL2 **单节点** 8GB | VMware **三节点**真集群 |

**它已经把我们规划中的事做完了**：

| 项 | 它的实测数据 |
|---|---|
| Hive(MR) 清洗 | 约 **7 分钟** |
| Spark 同逻辑清洗 | **1.5 秒**（约 **280 倍**） |
| 存储对比（9.9 万行） | csv 6.07MB → **ORC 1.39MB** |
| 数仓分层 | ODS → DWD → DWM → DWS → DM（对标阿里 ADS）+ dim，**5 层** |
| 维度建模 | 星型模型；`ROW_NUMBER()` 造代理键；`CASE WHEN` 派生年龄段 |

**它的 15 条踩坑记录里，有两条直接对应我们的问题**：

1. **#5** `return code 2 from MapRedTask`，起因是 `hive.exec.mode.local.auto=true` 把任务路由进了 HiveServer2 那个 256MB 的小堆导致 OOM。
   → **报错码和我们实验 03 那次一模一样，但根因完全不同**（我们是写入并发压垮 DataNode）。
   → **教训：同一个报错码背后可能有多种原因，别一看到就套经验。**
2. **#7** 「INSERT 执行中报 Connection reset，客户端断连导致任务被 KILL」
   → **正好解释了我们为什么必须用 `setsid nohup` 后台跑**，我们的做法是对的。

**它的核心经验沉淀也值得看**：「四种慢要分清」「聚合不可逆（`COUNT(DISTINCT)` 不能二次汇总）」「列式三件套（列裁剪 + 谓词下推 + 压缩存储）」「先探查后清洗」「直觉要验证」。

### ② `MrSuiChuan/data-warehouse-learning` ✅ —— 1.1k star

- 约 **1.1k star / 201 fork**，最后提交 2026-04-26（仍在维护）
- ⚠️ README 自述地址写的是 `Mrkuhuo/data-warehouse-learning`，但仓库现在的所有者显示为 `MrSuiChuan`（疑似改过名或转移），**两个地址都试一下**；Gitee 镜像 `wzylzjtn/data-warehouse-learning`
- **同一套分层、多种技术实现**：离线用 Doris，实时/数据湖用 Paimon / Hudi / Iceberg，配 DolphinScheduler + SeaTunnel + 数据生成器
- **看它主要是学"思路不变、换引擎实现"这件事怎么组织**——这正是我们接下来 Spark 双引擎要面对的问题

### ③ `CodeFuset/EComDWH-BatchDataProcessingPlatform` ✅ —— 规范性天花板

它有我们目前缺的东西：

- **数仓建模 SOP 文档**：命名规范、分层规范、字段命名规则、表生命周期管理规范
- Airflow 调度（DAG 在凌晨 2 点跑批）
- **Prometheus + Grafana 监控告警** + AlertManager 邮件
- GitHub Actions CI/CD 自动化起停集群
- **Spark 调优**：Salting 解决数据倾斜、Skew Join Hint、Broadcast Join、`reduceByKey` vs `groupByKey`
- **Hive 调优**：Z-Order 排序、Parquet + Snappy
- 每个优化都附**优化前后性能对比**

## 二、不是代码，但可能更该读

### 阿里巴巴《数仓建设七大规范》

网上多处转载，搜"数仓建设七大规范指南"即可。里面全是能**立刻拿来自查**的标准：

| 类别 | 要点 |
|---|---|
| **表命名** | 表名 = 类型 + 业务主题 + 子主题 + 表含义 + 存储格式 + 更新频率 |
| **分层调用** | 应用层优先调公共层；**ODS 不能被应用层直接引用**；任务深度建议不超过 10 层 |
| **数据类型** | 金额 `double`、字符串 `string`、ID 类 `bigint`、**时间用 `string`**、状态用 `string` |
| **NULL 处理** | **维度字段填 `-1`，指标字段填 `0`**（我们用 `unknown` 字符串，是另一种选择，值得对比） |
| **表生命周期** | 按"3 个月内最大访问跨度"决定保留天数（≤4 天→留 7 天，≤30 天→留 33 天…） |
| **事实表分类** | 事务型 / 周期快照型 / 累计快照型，各自的适用场景 |
| **冗余准则** | 冗余字段需有 3 个以上下游共用；重复率不超过 60% |

## 三、对照结论：我们缺什么、强在哪

### 3.1 我们缺的（可直接补）

| # | 缺什么 | 参考来源 |
|---|---|---|
| 1 | **建模规范类文档**（命名 / 字段 / 生命周期规范）—— 我们现在全靠习惯，没有成文标准 | 阿里七大规范、CodeFuset 的 SOP |
| 2 | **行数对账机制化** —— 我们做过一次（7,091 行重复差、140,665 商品数吻合），但没沉淀成可复用脚本 | taobao-dw 的"各层与 ODS 行数对账一致" |
| 3 | **Spark 双引擎对比** —— 已规划，未开工 | taobao-dw（7 分钟 → 1.5 秒） |
| 4 | **维度建模深度** —— 我们的 `dim_product` 还比较朴素，缺星型模型、代理键、派生维度 | taobao-dw 的星型双维表 |
| 5 | **监控告警** | CodeFuset 的 Prometheus + Grafana |
| 6 | **实时链路** | 尚硅谷 gmall 实时系列 |

### 3.2 我们强的（别妄自菲薄）

| # | 优势 | 为什么稀缺 |
|---|---|---|
| 1 | **真三节点集群** | 上面这些对标项目**大多是单节点 WSL2**（taobao-dw 就是 8GB 单机）。所以我们踩的坑——**副本写入、并发压垮 DataNode、心跳与剔除、worker 开机时序**——他们**根本踩不到**。这类经验在面试里更有说服力 |
| 2 | **真实公开数据集 1063 万行**（REES46，CC BY 4.0，有真实脏数据） | 对标项目多在 10 万行级、且多为干净数据 |
| 3 | **实验报告体系**（假设 → 行动 → 实测 → 证伪） | **这套方法论在公开项目里几乎见不到**——它证明的不是"我跑通了"，而是"我能定位自己的错误判断"。这是真正的差异化 |
| 4 | **可观测的进度机制** | 长任务分步执行 + 状态文件 + 实时进度看板，同类项目基本没有 |

## 四、怎么用这些项目（不要盲目抄）

**值得借鉴的**：文档结构、规范清单、**踩坑清单**、性能对比的表格形式、监控与调优的切入点。

**不建议直接抄的**：SQL 与配置。我们的集群拓扑（3 节点真集群）、数据源（真实脏数据 1063 万行）、内存约束（每节点 2 vCPU / 3~7GB、全集群 12 个容器）都与他们不同，抄过来大概率水土不服。

**特别提醒一点**：要注意区分定位——**教学项目**（尚硅谷系列）讲究"讲清楚 Step by Step"，**个人作品集**（taobao-dw、CodeFuset）讲究"展示能力密度"。两者的取舍逻辑不一样，学的时候要想清楚自己此刻需要哪一种。
