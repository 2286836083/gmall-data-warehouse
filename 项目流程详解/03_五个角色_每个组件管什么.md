# 03 · 五个角色：每个组件管什么

> **这一篇的目标**：搞清这套系统里"谁负责什么"。
> 三个大组件 + 两个配角，每个都只干一件事 —— **分清了就再也不会乱。**

---

## 一、先用一个类比建立全景（然后立刻讲物理上是什么）

把整个集群想象成**一家数据加工厂**：

```
┌────────────────────────────────────────────────────────────┐
│  ① HDFS      = 总仓库       东西放哪、放几份，坏一台不丢      │
│  ② YARN      = 调度员       哪台机器有空、活派给谁           │
│  ③ Hive      = 翻译官       把你的 SQL 翻译成干活的任务       │
│  ④ Spark     = 另一种工人   干同样的活，但方式不同（有时更快） │
│  ⑤ 调度系统  = 闹钟 + 班长   几点开工、先干哪个、失败了通知谁   │
└────────────────────────────────────────────────────────────┘
      配角：MySQL（账本）· ZooKeeper（仲裁"谁在线"）
```

> ⚠️ **类比之后必须讲物理上是什么**（这是本套文档的规矩）：
> 上面这 5 个，**每一个在机器上都是一个或几个正在运行的 Java 进程**。
> 它们通过**网络端口**互相通信。所以"组件"不是抽象概念，是**你能用 `ps` 命令看到的进程**。

---

## 二、① HDFS：总仓库

| 栏目 | 内容 |
|---|---|
| **目标** | 让一份大数据**存在多台机器上**，而且**坏一台机器不丢数据** |
| **它解决什么问题** | 一台机器硬盘就那么点大，而且会坏。1TB 数据放一台机器上，盘坏=数据全没 |
| **怎么做的** | 把文件**切成块**（默认每块 128MB）→ 每块**存 3 份**，放在不同机器上 |
| **物理上是什么** | · **NameNode（目录管理员）**：一个进程，**只在内存里记"哪个文件、哪块、在哪几台机器"**，**它自己不存数据**<br>· **DataNode（仓管）**：每台机器一个进程，**数据块就存在它所在机器的本地硬盘上** |
| **在本项目里** | 三台机器各一个 DataNode；数据放在 `/user/hive/warehouse/gmall.db/<表名>/dt=日期/` 这样的目录里 |
| **怎么知道它在正常工作** | `hdfs dfsadmin -report` 显示 **3 个 Live datanodes**、**0 个 Missing blocks**；而且能真的读写一次 |
| **不懂会怎样** | ⚠️ 往里塞**几百万个小文件** → NameNode 的内存会被压爆（它要为**每个文件**记一条） |

**一句话理解**：**HDFS 就是"横跨三台机器的一张大硬盘"，而且自动帮你存了三份。**

---

## 三、② YARN：调度员（它不干活！）

| 栏目 | 内容 |
|---|---|
| **目标** | 知道集群上**哪台机器还有空闲的内存和 CPU**，把任务派给合适的机器 |
| **它解决什么问题** | 三台机器上跑着很多任务，**得有人统一记账**，否则要么抢成一团、要么资源闲在那没人用 |
| **怎么做的** | 每台机器上报"我还有多少资源" → 来活了就挑一台划一块资源出去 |
| **物理上是什么** | · **ResourceManager（总调度）**：一个进程，**全集群只有一个**<br>· **NodeManager（每台机器的工头）**：每台机器一个<br>· **Container（容器）**：划出来的那块资源，本质是"**一个被限了内存和 CPU 的 Java 进程**" |
| **在本项目里** | **每台只给 YARN 2048MB / 2 个核** —— 这是本项目**最硬的一条约束**（后面所有参数都被它卡死） |
| **怎么知道它在正常工作** | `yarn node -list` 能看到 3 个节点；网页 `http://lrh-1:8088` 能看到正在跑的作业 |
| **不懂会怎样** | ⚠️ 给任务申请的内存**超过 2048MB** → YARN 直接拒绝，**任务起不来**（本项目就因为这个，参数配成了 1408m 这种怪数） |

> ⚠️ **最容易搞混的一点**：**YARN 不计算，也不存数据。**
> 它只做一件事：**决定"谁的资源分给谁"**。
> 干活的另有其人（Hive 翻译出来的任务、或者 Spark）。

---

## 四、③ Hive：翻译官

| 栏目 | 内容 |
|---|---|
| **目标** | 让你**用 SQL 说话**，而不用去写 Java 程序 |
| **它解决什么问题** | 集群上的计算很复杂（怎么切任务、怎么分发、怎么合并）。**如果每个需求都要写程序，那就没人用得动了** |
| **怎么做的** | 你写 SQL → 它**翻译成一批计算任务** → 交给 YARN 去跑 |
| **物理上是什么** | · **MetaStore（元数据服务）**：管"表长什么样"（表名、字段、分区在哪）——**它自己不存数据**<br>· **HiveServer2**：接收你 SQL 的服务，你连的是它<br>· **beeline**：你敲命令用的客户端工具 |
| **在本项目里** | 表结构存在 MySQL 里；你用 beeline 连 10000 端口提交 SQL |
| **怎么知道它在正常工作** | ★ **不能只看"进程还在"** —— 要**发一次真实查询并拿到结果**。（本项目实测：服务标记为"已启动"后，**还要等 50 秒**才真的能接受连接） |
| **不懂会怎样** | ⚠️ 以为"服务 active 就能用" → 前面的 50 秒里反复重启，把问题搞得更大 |

> **一个关键认知**：**Hive 不是一个计算引擎，它是"翻译官 + 目录柜"。**
> 真正算数据的是它翻译出来的任务（由 YARN 调度、在容器里执行）。
> 所以 Hive 的"执行引擎"是可以换的 —— 可以换成 Spark（这就是第 04 篇要讲的）。

---

## 五、④ Spark：另一种工人

| 栏目 | 内容 |
|---|---|
| **目标** | **换一种方式干活**，在某些场景下更快、更省事 |
| **它解决什么问题** | Hive 翻译出来的任务走的是"老工法"（MapReduce）：**每道工序之间的半成品都要搬回仓库（写磁盘）、每个小任务都要新起一个进程** —— 这两件事很慢 |
| **怎么做的** | ① 半成品**尽量留在内存里**，不搬仓库<br>② 工人（Executor）**雇一次一直用**，任务只是它内部的**线程**<br>③ 整条 SQL **一起排工期**（而不是一段一段分别排） |
| **物理上是什么** | · **Driver（驱动器）**：一个进程，负责排计划、派活、收结果 —— 是"大脑"<br>· **Executor（执行器）**：若干个常驻进程，跑在 YARN 的容器里 —— 是"手脚" |
| **在本项目里** | 装在 `/opt/spark-3.5.9-bin-hadoop3`，**通过 Hive 的元数据认识同一批表**（所以 Spark 里也能 `SELECT ... FROM gmall.xxx`） |
| **怎么知道它在正常工作** | ① 能看到 `gmall` 库的表<br>② 能读到真实数据且数值与 Hive 一致（本项目实测：1063 万行、GMV 逐位一致） |
| **不懂会怎样** | ⚠️ **以为"Spark 一定比 Hive 快"** → 实测发现轻作业反而更慢（见下） |

> ★ **本项目最重要的一个实测结论**（面试可以用）：
>
> ```
> 一个会话里连跑 8 段 SQL：  Spark 75 秒  vs  Hive 389 秒   → 快 5 倍
> 每段各起一个会话：         Spark 381 秒 vs  Hive 421 秒   → 只快 10%
> 轻量的作业：               Hive 反而更快
> ```
>
> **原因**：Spark **每次提交要花约 35 秒做准备**（启动进程、连接元数据、申请资源）。
> 8 次提交 = 280 秒，占它总耗时的 73%。
>
> **所以准确的说法不是"Spark 更快"，而是"Spark 把成本从『每次作业』挪到了『每次会话』"** ——
> 只有在"一次会话里连着干很多活"时才划算。

## 六、⑤ 调度系统（DolphinScheduler）：闹钟 + 班长

| 栏目 | 内容 |
|---|---|
| **目标** | **不用人盯着**：按时开工、按正确顺序干、失败了知道是谁 |
| **它解决什么问题** | 第 ③~⑦ 站有十几个步骤，**手工跑的话**：要按顺序敲、要凌晨爬起来、失败了不知道、要补 30 天数据就手动跑 30 遍 |
| **怎么做的** | 把步骤编排成一张**流程图（谁依赖谁）**，然后按图执行、记录每一次运行的结果 |
| **物理上是什么** | · **master（主任）**：解析流程图、拆任务、派活<br>· **worker（工人）**：真正执行任务的机器<br>· **api / alert**：提供网页、发送告警 |
| **在本项目里** | 3 个角色跑在三台机器上；网页 `http://lrh-1:12345/dolphinscheduler`（账号 admin） |
| **怎么知道它在正常工作** | ① 网页能开、worker 都注册上<br>② **有成功的运行实例**（本项目：16 个节点全部成功）<br>③ **连跑两次数据不翻倍**（证明每个步骤都能安全重跑） |
| **不懂会怎样** | ⚠️ ① 依赖没连对 → 上一步没跑完就开始下一步（**结果错，但不报错**）<br>⚠️ ② 步骤不能重跑 → 补一次数据，数字翻倍 |

> ⚠️ **本项目一个真实的坑（值得知道）**：
> 在调度界面上点"停止"，界面显示已停止，但**集群上那个任务其实还在跑**（跑了 3 天）。
> 原因：任务是通过远程登录启动的，**断开连接不会把它杀掉**。
>
> ★ **由此得到一条通用纪律**：**"界面上显示的状态"不等于"数据面的真实状态"。**
> 说"停了"，要自己去集群上确认（看进程、看作业列表）。

## 七、两个配角（顺便认识）

| 组件 | 目标 | 物理上是什么 | 在本项目里 |
|---|---|---|---|
| **MySQL** | 存**"表长什么样"**的账本（元数据） | 一个数据库进程，装在主节点 | Hive 的表结构、调度的运行记录都存在它里面 |
| **ZooKeeper** | 仲裁"**谁还在线**、谁是领导" | 三个进程（三台各一个），互相投票 | 调度系统用它来记录"有哪些工人上班了" |

> **为什么 MySQL 叫"账本"**：它存的是**描述**（表叫什么、有哪些字段），**不是数据本身**。
> 数据在 HDFS 上，账本在 MySQL 里 —— 这两个是分开的，**别搞混**。

## 八、它们怎么串起来（一张关系图）

```
        你（或者调度系统）
              │ 提交一条 SQL
              ▼
    ┌──────────────────┐
    │  ③ Hive（翻译官） │  把 SQL 翻译成一批任务
    └────────┬─────────┘
             │ "我需要资源"
             ▼
    ┌──────────────────┐
    │  ② YARN（调度员） │  决定派给哪台机器、给多大地方
    └────────┬─────────┘
             │ 在三台机器上划出容器，启动任务
             ▼
    ┌──────────────────┐
    │  任务实际执行      │  读数据 → 算 → 写结果
    └────────┬─────────┘
             │ 读写
             ▼
    ┌──────────────────┐
    │  ① HDFS（总仓库） │  数据就存在这三台机器的硬盘上（每份 3 个副本）
    └──────────────────┘

   ④ Spark：可以替换"翻译官+老工法"这一套（它自己排工期、自己派活给 Executor）
   ⑤ 调度系统：站在最外面，决定"什么时候提交哪些 SQL"
   MySQL：给 Hive 和调度系统提供"账本"
   ZooKeeper：给调度系统提供"谁在线"
```

**读这张图的顺序**：从下往上理解依赖 ——
**没有 HDFS 就没有数据；没有 YARN 就没资源；没有 Hive 就没法用 SQL；Spark 是可替换的工人；调度是外面的闹钟。**

## 九、常见混淆（这几组必须分清）

| 容易混 | 区别 |
|---|---|
| **HDFS vs MySQL** | HDFS 存**数据本身**（TB 级、文件）；MySQL 存**描述**（表结构、几千行） |
| **YARN vs Hive** | YARN **分资源**，不干活；Hive **翻译 SQL**，不存数据 |
| **Hive vs Spark** | Hive 是"**翻译官**"，Spark 是"**另一种工人**"。本项目里 Spark 用的是 Hive 的元数据（同一批表） |
| **HDFS 的分区 vs 表的分区** | 表的分区**就是** HDFS 上的目录（`dt=2019-10-01/`），其实是同一件事的两个说法 |
| **调度 vs 计算** | 调度只负责"**什么时候提交**"，它自己不算数据 |

> ⚠️ **最后一个坑（面试常问）**：**Hive 和 Spark 不是竞争关系。**
> Hive 管"表 + 把 SQL 翻译成任务"，Spark 管"把任务算出来"。
> 本项目里 Spark **通过 Hive 的元数据认识同一批表**，所以两个引擎能跑同一份 SQL、结果一致。

2. YARN 为什么叫"调度员"而不是"工人"？—— 对应 **§三**
3. Hive 的"翻译官"是翻译什么？它自己存数据吗？—— 对应 **§四**
4. Spark 快的原因有哪三条？为什么说"Spark 不一定比 Hive 快"？—— 对应 **§五**
5. 调度系统解决哪四个具体问题？—— 对应 **§六**
6. MySQL 和 HDFS 存的分别是什么？—— 对应 **§七、§九**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 三个大组件**
- **HDFS**：存数据（切块 + 每块 3 份副本，坏一台不丢）
- **YARN**：分资源（哪台机器有空闲、活派给谁）
- **Hive**：翻译 SQL（让你不用写 Java）

**2. 为什么 YARN 是调度员**
- 它**不计算、不存数据**，只决定"资源给谁、给多少"
- 物理上：ResourceManager（全集群 1 个）+ NodeManager（每台 1 个）+ 容器（一块被限了内存/CPU 的进程）
- 本项目硬约束：每节点 **2048MB**，超过就被拒绝

**3. Hive 翻译什么**
- 把**你写的 SQL** 翻译成**一批能在集群上跑的计算任务**
- **它自己不存数据**：元数据（表结构）在 MySQL 里，数据在 HDFS 上
- 两个进程：MetaStore（管表结构）+ HiveServer2（接收 SQL）

**4. Spark 快的原因 / 不一定快**
- 三条：① 半成品尽量留内存（不反复搬仓库）② Executor 常驻、任务用线程（不反复起进程）③ 整条 SQL 一起排工期
- 为什么不一定快：**每次提交约 35 秒固定开销** → 分段跑时 8×35=280 秒（占 73%）→ 轻作业反而更慢
- 准确说法："**成本从每次作业挪到每次会话**，只在会话复用时划算"

**5. 调度解决的四个问题**
- ① 按顺序（依赖）② 按时（凌晨自动跑）③ 失败知道（告警）④ 能补数/重跑
- 另：有运行记录可追溯

**6. MySQL vs HDFS**
- **HDFS = 数据本身**（TB 级、文件、切块存三份）
- **MySQL = 描述（元数据）**：表叫什么、有哪些字段、分区在哪（几千行）
- 一句话：**数据在 HDFS，账本在 MySQL**
</details>
