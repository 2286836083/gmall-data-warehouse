# 04 · 一次计算的物理过程：从 SQL 到结果

> **这一篇的目标**：让你能回答"我提交一条 SQL 之后，机器上到底发生了什么"。
>
> **为什么必须懂这个**：因为**所有"为什么慢""为什么挂"的答案都藏在这一篇里**。
> 不懂过程，遇到报错就只能靠重启和搜索。

---

## 一、先看一个最小的例子

**你的动作**：在命令行敲了一条最朴素的统计：

```sql
SELECT COUNT(1) FROM gmall.ods_event_log_di;
```

**机器上发生了什么**（一共 6 步）：

```
① 你敲回车
   ↓  连上 Hive 的服务，把 SQL 发过去
② Hive 把 SQL "翻译"成一批任务
   ↓  它发现"这个是统计行数"，可以分成几块算
③ Hive 去找 YARN："给我几台机器的资源"
   ↓  YARN 在三台机器上各划出一块资源（容器）
④ 每个容器里启动一个小程序，读自己分到的那部分数据
   ↓  lrh-1 读它上面的块、lrh-2 读它的、lrh-3 读它的
⑤ 各自数出自己那份有多少行
   ↓  把三个数报回来
⑥ 加起来 → 返回结果
```

**这个例子里最值得注意的一点**：**三台机器是"各数各的"，不需要通信。**
所以这种活儿天生适合拆开做，也就快。

---

## 二、但是——大部分 SQL 没这么简单

真正麻烦的是这种（本项目的主力 ETL 就是）：

```sql
SELECT dt, COUNT(DISTINCT user_id)
FROM gmall.dwd_event_log_di
GROUP BY dt;
```

**问题来了**：`COUNT(DISTINCT user_id)` 要求"**同一个人不能数两次**"。
但数据分散在三台机器上，**同一个人的行为可能出现在两台机器上**：

```
lrh-1 上的数据里有 用户A、用户B
lrh-2 上的数据里也有 用户A
      ↑ 如果各数各的：lrh-1 数出 2 个、lrh-2 数出 1 个 → 加起来 3 个
        实际只有 2 个人（A 和 B）          ← ❌ 错了
```

**所以必须先把"同一个人的数据"搬到同一台机器上，才能去重。**

这个"**把同类数据搬到一起**"的动作，术语叫 **shuffle（洗牌）**。

> **类比**：打牌时把同花色的牌归到一起。
>
> **物理上是什么**：**数据跨网络传输 + 两端各读写一次磁盘。**
> 这是整个计算过程中**唯一必须落盘、并且必须走网络**的地方，所以也是**最慢的一步**。

---

## 三、为什么 shuffle 这么贵（算一笔硬件账）

计算机各个部件的速度差了好几个数量级：

| 层级 | 速度 | 比内存慢多少 |
|---|---|---|
| 内存 | ~20 GB/s | 1× |
| 固态硬盘（NVMe） | ~3 GB/s | 7 倍 |
| 固态硬盘（SATA） | ~500 MB/s | 40 倍 |
| **机械硬盘** | **~150 MB/s** | **130 倍** |
| **千兆网络（机器之间）** | **~125 MB/s** | **160 倍** |

**shuffle 要同时走两样最慢的**：网络（把数据搬到别的机器）+ 磁盘（到了还要写下来）。

**再算量级**：这 1063 万行明细，光是搬一遍就是 GB 级的网络传输。

> ★ **记住这条结论（面试常问）**：
> **分布式计算慢，主要不是"算得慢"，而是"搬得慢"。**
> 所以优化一条 SQL 的核心思路永远是：**能不能少搬一点数据？**

---

## 四、为什么"一条 SQL"会变成"好几个作业"

**先说清楚**：Hive 不会把整条 SQL 一口气跑完。它会**切开**，每切一刀就是一个独立的作业。

**切在哪儿？就切在"必须搬数据"的地方（也就是 shuffle）。**

拿上面那条 SQL 举例：

```
【作业 1】三台机器各自读自己的数据 → 初步按 (dt, user_id) 去重
                ↓  ★ 到了这里必须搬数据（要让同一个用户落到一起）
          【shuffle】跨网络搬运
                ↓
【作业 2】收齐后 → 按 dt 汇总 → 写出结果
```

**所以要跑 2 个作业**（不是一个）。

**"几个作业"取决于 SQL 的写法**（这是很多人搞不清的点）：

| SQL 长什么样 | 要几个作业 | 为什么 |
|---|---|---|
| `SELECT COUNT(1) FROM t` | **1** | 各数各的，最后加一下，不用搬数据 |
| `GROUP BY 小基数` | **1** | 搬一次就够 |
| **`GROUP BY` + `COUNT(DISTINCT)`** | **2~3** | 去重没法在本地完成，要多搬一轮 |
| 大表关联大表 | 2~3 | 两边都要先按关联键搬一次 |
| `UNION ALL` 六段（本项目的校验 SQL） | **6** | 每段独立翻译成一个作业，**排队串行跑** |

> 📌 **本项目对照**：全链路里**最慢的节点不是 ETL，而是校验节点**（15 分 23 秒，占整链 28%）。
> 原因就是它的 `UNION ALL` 被翻译成了 **6 个作业排队跑**。
> ——**慢不一定在"算得多"，可能在"作业数量多、一个个排队"。**

### 4.1 ★ 怎么自己数（不靠别人说）

**Spark/Hive 每跑一个作业，都会在 YARN 上出现一条记录。**

```
网页看：http://lrh-1:8088    → 看应用列表里一条条冒出来
命令行：yarn application -list
```

**数一下就知道你这条 SQL 实际切成了几个作业。** 这比听任何人说都可靠。

## 五、为什么要给任务"留够内存"

**场景**：`GROUP BY` 的时候，机器要在内存里维护一张"**记账表**"：

```
dt=2019-10-01  →  已见过 47854 个人
dt=2019-10-02  →  已见过 46392 个人
...
```

如果分组特别多（比如按"商品 × 日期"分组，组合数达到 **430 万**），
这张"记账表"就很大 —— **内存装不下就会出问题**。

**装不下会怎样**：机器不会直接崩，而是开始**疯狂地做清理**（术语叫垃圾回收，GC），
**98% 的时间都花在清理上**，最后撑不住报错退出。

> 📌 **本项目对照（一次真实的调优）**：
> ```
> 作业：GROUP BY product_id, dt（430 万个组合）
> 配置 A：给 512MB 内存  → 跑 637 秒后失败（内存不够）
> 配置 B：给 1024MB 内存 → 63 秒成功
> ```
> **同一件事，只是把内存从小改成大，从"637 秒失败"变成"63 秒成功"。**
>
> ★ **判断法则（本项目最值钱的经验之一）**：
> 看这个作业**"囤不囤数据"**：
> - **不囤**（边读边写、清洗型）→ 内存可以给小
> - **囤**（大分组、去重、排序）→ **内存必须给大，给小必然失败**

## 六、一个"骗人"的现象：服务在跑 ≠ 能用

**这是本项目踩过的坑，也是通用纪律**：

```
Hive 的 SQL 服务被标记为"已启动"（active）之后，
还要再等约 50 秒，才真正能接受连接。
```

**如果你只看"服务状态是 active"就以为能用了** → 卡住 → 你会去重启服务 → 又把问题搞复杂。

> ★ **纪律**：说"服务好了"，必须给**外部判据**：
> - 端口在监听（`ss -lntp | grep 10000`）
> - **发一次真实查询，拿到真实结果**
>
> **"进程还在"和"能干活"是两件事。**

## 七、出了错怎么找线索（三个地方）

| 去哪看 | 看什么 |
|---|---|
| **网页 `http://lrh-1:8088`** | 作业是"排队中 / 运行中 / 失败"；**失败原因写在 Diagnostics 那一栏** |
| **命令行** | `yarn logs -applicationId <作业号>` —— 看完整日志 |
| **作业详情里的计数器** | ★ 最有用，见下 |

**计数器（Counters）怎么看**——只看四个就能定位大部分问题：

| 计数器 | 什么意思 | 怎么判断 |
|---|---|---|
| **读了多少数据** | 从 HDFS 读的量 | **比预期少很多** → 死在很前面 → **内存或初始化问题** |
| **写了多少数据** | 写出去了多少 | 读正常但**写是 0** → 算完了写不出去 → **写入的问题** |
| **CPU 时间** | 累计用了多少 CPU | 很小但耗时很长 → **它在等 IO/网络，不是在算** |
| **GC 时间** | 花在"内存清理"上的时间 | 占比很高 → **内存不够** |

**这套判断的价值**：不用看日志细节，**从数字的"量级"就能判断方向**。

## 八、还有两个"看起来像故障、其实是正常"的现象

### 8.1 退出码比日志更早告诉你真相

任务"失败"的时候，**先看退出码**：

| 退出码 | 含义 | 第一反应 |
|---|---|---|
| **143** | 被人**主动停止**（收到"请退出"信号） | **别找 bug，先想"是谁停的"** |
| **137** | 被**强制杀掉**（常见原因：内存超了被系统杀） | 查内存 |

> 📌 **本项目真实的教训**：有一次日志末尾看起来像 SQL 报错（有 `Error` 字样），
> 实际退出码是 **143** —— **是被人主动停掉的**。
> 如果一开始就盯着日志找语法错误，会往完全错误的方向排查。

### 8.2 日志里的"报错"不一定是故障

Spark 的日志里出现过"连接元数据服务失败"的异常，但**结果完全正确**。

**怎么判断它是不是真故障**（这套方法可以复用）：

| 判据 | 这次的情况 |
|---|---|
| 异常出现在哪一步 | 出现在**读元数据**，不在读数据的路径上 |
| 有没有自动恢复 | 系统**内置重试且成功了** |
| 结果对不对 | 和基线**逐位一致** |
| 重新跑是否复现 | 复现，结果仍正确 → **是稳定噪音，不是故障** |

> ★ **核心判断**：**"报错"不等于"数据错了"。**
> 但注意 —— **不是"忽略它"，而是"证明它不影响结果"**。
> 面试里被问"日志有异常你怎么办"，答这套证明过程，比答"我一般忽略 Warn"强得多。

## 九、把整篇串成一个故事（试着自己讲一遍）

```
我提交一条 SQL
   ↓
Hive 把它翻译成若干个"作业"（在需要搬数据的地方切开）
   ↓
每个作业去 YARN 申请资源，YARN 在几台机器上划出容器
   ↓
容器里：各读各的数据 → 算 → 如果需要，把数据搬到一起（shuffle，最贵）
   ↓
结果写回 HDFS
   ↓
如果某个任务挂了 → 自动重跑那一个（不重跑整个作业）
   ↓
我从 8088 网页 / 计数器 / 退出码 判断它是快是慢、是死是活
```

**能把这四句话流利地讲出来，这一篇就算过了。**

## 十、自测

**每题标了对应小节——答不出来就回去看那节。**

1. `SELECT COUNT(1)` 和 `COUNT(DISTINCT ...)` 有什么区别？为什么后者要慢？—— 对应 **§一、§二**
2. 什么叫 shuffle？它为什么是最贵的？—— 对应 **§二、§三**
3. 一条 SQL 会跑成几个作业？依据是什么？怎么自己数？—— 对应 **§四**
4. 什么样的作业"必须给大内存"？举一个本项目的实测例子。—— 对应 **§五**
5. 退出码 143 和 137 分别是什么意思？第一反应该是什么？—— 对应 **§8.1**
6. 日志里报异常，你怎么判断它是真故障还是噪音？—— 对应 **§8.2**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 两种 COUNT 的区别**
- `COUNT(1)`：各机器各数各的，**不用搬数据**，最后加一下 → 快
- `COUNT(DISTINCT)`：要保证"同一个人不数两次"，而**同一个人的数据可能分散在多台机器**上
  → 必须**先把同一个人的数据搬到一起**（shuffle）→ 慢

**2. shuffle**
- 定义：**把同类数据（同一个 key）搬到同一台机器上**
- 为什么贵：它**同时走两个最慢的通道** —— 网络（~125MB/s）+ 磁盘（两端各读写一次）
- 物理账：内存 20GB/s 是千兆网络的约 160 倍

**3. 几个作业 / 怎么数**
- 依据：**在需要 shuffle 的地方切一刀**，切几刀就几个作业
- 例：`COUNT(1)` = 1 个；`GROUP BY`+`COUNT(DISTINCT)` = 2~3 个；`UNION ALL` 六段 = 6 个
- 怎么数：打开 `http://lrh-1:8088` 看应用一条条冒出来，或 `yarn application -list`

**4. 什么作业必须给大内存**
- **"囤数据"的作业**：大基数 `GROUP BY`、`DISTINCT`、排序 —— 它们要在内存里维护一张很大的记账表
- 实测例子：`GROUP BY product_id, dt`（430 万组合）
  512MB → **637 秒后失败**；1024MB → **63 秒成功**

**5. 退出码**
- **143** = SIGTERM（**被人主动停止**）→ 第一反应："谁停的？"（不是找 bug）
- **137** = SIGKILL（**被强制杀掉**，常见是内存超限）→ 第一反应："查内存"

**6. 判断异常是真故障还是噪音**
- ① 异常发生在**哪条路径**（元数据 vs 数据）
- ② 有没有**自动恢复**（重试是否成功）
- ③ 结果是否与基线一致
- ④ 重跑是否复现
- 核心：**"报错"不等于"数据错了"，但要证明，不能默认忽略**
</details>
