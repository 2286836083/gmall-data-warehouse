# 01 · 全景图：一条数据的完整旅程

> **这一篇是整套文档的核心。** 读完它，你就有了"我有一条流水线"的整体感。
> 后面几篇都是在给这一篇的某一站做细节补充。

---

## 〇、先看这张图（记住 9 站就够）

```
  【数据是怎么一步步变成报表的】

  ① 用户在 App 上点击  ──────▶  产生一条日志
                                     │
  ② 日志攒成文件        ──────▶  31 个按天切的 CSV（约 1.3GB）
                                     │
  ③ 进仓库（ODS）       ──────▶  原样放进去，一行不改
                                     │        10,630,245 行 / 31 个分区
  ④ 清洗（DWD）         ──────▶  去重、解析时间、拆字段、空值统一
                                     │        10,623,154 行 / 成交 186,059 笔
  ⑤ 按主题汇总（DWS）   ──────▶  用户·商品·类目·交易 四个角度各一张表
                                     │
  ⑥ 算出指标（ADS）     ──────▶  一个业务问题一张表，共 6 张
                                     │
  ⑦ 导出                ──────▶  变成看图工具能读的文件
                                     │
  ⑧ 上墙（大屏）        ──────▶  双击打开就能看，6 张图
                                     │
  ⑨ 每天自动跑          ──────▶  上面 ③~⑦ 由调度系统按顺序自动执行
```

**这 9 站就是所有离线数仓的通用骨架。** 换一家公司、换一份数据，骨架都一样。

## 第一站：用户产生行为

| 栏目 | 内容 |
|---|---|
| **目标** | 产生"原始数据"——这是后面一切的原料 |
| **做什么** | 用户在电商 App 上浏览、加购、下单，程序把这些动作记成一条条日志 |
| **产物** | 一行一条事件，例如：<br>`2019-10-01 00:00:11 UTC, view, 商品44600062, ..., 用户541312140` |
| **谁在干** | 电商 App 自己（**不在这套集群里**，在业务方的服务器上） |
| **不懂会怎样** | 这是最容易被忽略的一站：**很多人以为"数据工程师负责造数据"，其实数据是业务系统产生的，我们只负责接过来** |

> 📌 **本项目对照**：本项目**没有自己的 App**，所以用的是公开数据集
> （REES46 电商行为数据，2019 年 10 月，做了 1/4 用户采样）。
> **也就是说，第 1、2 站是"别人已经做好的"，我们从第 3 站接手。**
> 面试时说清这点很重要 —— 不要含糊成"我采集了数据"。

---

## 第二站：日志攒成文件

| 栏目 | 内容 |
|---|---|
| **目标** | 把散落的日志变成**可以搬运的文件**（批量处理的前提是"攒够一批再算"） |
| **做什么** | 按天切割，生成一个日期一个文件 |
| **产物** | **31 个 CSV 文件**，命名就是日期（`2019-10-01.csv` … `2019-10-31.csv`），总共约 **1.3GB** |
| **谁在干** | 数据采集环节（本项目是数据集自带的） |
| **不懂会怎样** | 如果不按天切，后面就**没法"只重跑某一天"** —— 出问题只能全量重来 |

> **为什么按天切这么重要**：这是"**分批处理**"的基本单位。
> 后面每一层的表都按天分区，源头也是按天给文件 —— **两头对齐，才能做到"补某一天的数据"**。

---

## 第三站：数据进仓库（ODS 层）

| 栏目 | 内容 |
|---|---|
| **目标** | 把文件**原样**放进集群的总仓库，并且**按天摆放整齐**，让以后查某一天不用扫全表 |
| **做什么** | ① 把 31 个 CSV 传到 HDFS（集群的分布式仓库）<br>② 建一张表指向这些文件<br>③ 告诉 Hive"这一天对应这个目录" |
| **产物** | 一张表 `gmall.ods_event_log_di`：**31 个分区、10,630,245 行** |
| **谁在干** | **HDFS**（负责存）+ **Hive**（负责"登记表结构"、"按天分区"） |
| **怎么知道干对了** | ① 分区数 = **31**（一天一个）<br>② 总行数 = **10,630,245**<br>③ 事件类型只有三种：view / cart / purchase |
| **不懂会怎样** | ⚠️ **不建分区，直接把文件丢进目录** → 以后查一天的数据要把 **1TB 全读一遍**。分区不是"优化"，是**必需品** |

> **"ODS 层不加工"是什么意思**：原样存。**不做去重、不改格式、不把空值换成别的值。**
> 为什么这么死板？因为**原始形态是"证据"**。三个月后有人问"原始日志长什么样"，
> 你如果改过了就永远拿不回来。加工的事留给下一站。

> 📌 **本项目对照**：装载脚本做了个很实在的优化 —— 把 31 天的装载语句
> **合并成一个文件一次执行**。因为每调用一次工具都要冷启动一个 Java 进程（约 5 秒），
> 31 天分开跑要白等七八分钟。

---

## 第四站：清洗（DWD 层）

| 栏目 | 内容 |
|---|---|
| **目标** | 把"能看的原料"变成"能用的净菜" —— 让后面所有人**用同一套干净数据**，不用各自清洗 |
| **做什么** | 一条 SQL 干五件事：<br>① **整行去重**（实测有 7,091 行完全重复）<br>② 解析时间（把 `"2019-10-01 00:00:11 UTC"` 这种文本变成真正的时间）<br>③ 把类目路径 `electronics.smartphone` **拆成三级**<br>④ 空值统一成 `unknown`（不让它变成 NULL）<br>⑤ 价格 0 保留不删（是真实特征） |
| **产物** | ① `dwd_event_log_di`：**10,623,154 行**<br>② `dwd_purchase_fact_di`：**186,059 笔成交**<br>③ `dim_product`：**140,665 个商品**<br>④ `dim_date`：**365 天** |
| **谁在干** | **Hive**（把 SQL 翻译成一批计算任务）→ **YARN**（把任务分到三台机器） |
| **怎么知道干对了** | ★ **差额要对得上**：`10,630,245 − 10,623,154 = 7,091`，**正好等于去重掉的行数**。<br>算得出这个数，才说明清洗规则真的生效了 |
| **不懂会怎样** | ⚠️ 不去重 → **GMV（成交金额）虚高**，而且**不报错**，你可能几个月都发现不了 |

> **为什么清洗必须集中在一层做**：如果每个需求各自清洗，A 把空类目当 NULL、B 当成 `unknown`，
> **两张报表的数字就会对不上，而且谁也说服不了谁**。
> 全公司只有一份"洗过的数据"，口径才统一。

**这一层还有一个概念叫"粒度"**（整份数据里最重要的一个词）：

> **粒度 = 这张表的一行代表什么。**
> `dwd_event_log_di` 的粒度是"**一条事件**"，`dwd_purchase_fact_di` 是"**一笔成交**"，
> `dim_product` 是"**一个商品**"。
> **说不清粒度，这张表就没法用** —— 因为你不知道该拿它算什么。

## 第五站：按主题汇总（DWS 层）

| 栏目 | 内容 |
|---|---|
| **目标** | **预先**按几个常用角度把数据汇总好，让后面做报表时"直接拿来用"，不用每次都从 1000 万行明细重算 |
| **做什么** | 从明细里算出四个角度的日汇总：**用户 · 商品 · 类目 · 交易** |
| **产物** | 4 张表：<br>· `dws_user_event_day` → **用户 × 天**，1,622,820 行<br>· `dws_product_event_day` → **商品 × 天**，1,265,817 行<br>· `dws_category_event_day` → **类目 × 天**，1,853 行<br>· `dws_trade_day` → **天**，31 行 |
| **谁在干** | 还是 SQL，还是 Hive + YARN（或者换成 Spark，见第 03 篇） |
| **怎么知道干对了** | 每张表的**行数**和**粒度**都对得上；而且**同一个指标用不同路径算要收敛到同一个数** |
| **不懂会怎样** | ⚠️ **最容易犯的错：把"去重买家数"从上层加总。**<br>同一个用户买了两个商品，商品层各算 1 个买家，加总就变成 2 —— **数字虚高，不报错** |

> **名词**：**分区下推**（不用记，知道有这么回事就行）——
> 因为数据按天分区，算一天就只读一天的数据，这是"汇总层能很快算出来"的前提。

> 💡 **这一层的价值是"复用"**：做日活、做转化率、做复购，都要"用户一天的行为"，
> 那就**算一次 `dws_user_event_day`，大家共用**。省掉重复计算。

## 第六站：算出指标（ADS 层）

| 栏目 | 内容 |
|---|---|
| **目标** | 回答**具体的业务问题** —— **一个业务问题，一张表** |
| **做什么** | 从汇总层算出 6 个问题的答案 |
| **产物** | 6 张表，对应 6 个问题： |

| # | 业务问题 | 表 | 行数 |
|---|---|---|---|
| **Q1** | 每天有多少活跃用户？新增和回流各多少？ | `ads_active_user_day` | 31 |
| **Q2** | 从浏览到加购、到购买，转化如何？ | `ads_funnel_day` | 31 |
| **Q3** | 复购情况如何？ | `ads_repurchase_day` | 31 |
| **Q4** | 哪些商品卖得最好？ | `ads_top_product_day` | 1,550 |
| **Q5** | 各类目的销售结构与转化差异？ | `ads_category_day` | 434 |
| **Q6** | 交易大盘如何？客单价、环比？ | `ads_trade_day` | 31 |

| 栏目 | 内容 |
|---|---|
| **谁在干** | 同上一站（SQL + Hive/Spark + YARN） |
| **怎么知道干对了** | ★ **交叉对账**：GMV（成交金额）用**四条不同的路径**算，必须收敛到同一个数。<br>实测：四路全部 = **57,575,996.50** |
| **不懂会怎样** | ⚠️ **口径不定义清楚** → 图上是"下单数"、表里是"支付数"，**数字 quietly 不对** |

> **为什么"四路收敛"这么有说服力**：四条路径走了不同的表、不同的计算顺序。
> 它们能算出同一个数，说明**中间每一层都没算错**（重复、漏行、口径偏移都会导致对不上）。
> **这比"我看了一眼没报错"强太多。**

> 📌 **本项目对照（一个真实的坑）**：大屏最初**直接读 DWS 层**画图，跳过了 ADS。
> 表面能跑，但等于"把报表和中间层绑死"——中间层一改，报表就崩。
> 后来补了两张 ADS 表修正，**验证方式是新旧导出文件逐字节比对**（确认只是路径变了，数字没变）。

## 第七站：导出

| 栏目 | 内容 |
|---|---|
| **目标** | 把结果从集群里拿出来，变成**看图工具能读的格式** |
| **做什么** | 把 ADS 表导出成 CSV，再转成一份 `.js` 文件 |
| **产物** | `dashboard_data_real.js`（里面存着 6 组数据） |
| **谁在干** | 命令行工具（beeline）取数 + 一小段 Python 转换 |
| **怎么知道干对了** | ★ **导出的数字和集群里的数字一模一样**（实测：GMV 两边都是 57,575,996.50，成交 186,059 笔） |
| **不懂会怎样** | 中间环节悄悄丢了几行、或者把数字变成了文本 → **图上就画错了** |

> **为什么导出成 `.js` 而不是 JSON**：直接用网页读本地 JSON 会被浏览器的安全策略拦住（页面白屏）。
> 变成 `.js` 用**脚本标签**加载就能绕开 —— **为了做到"双击就能打开、不用联网"**。

## 第九站：每天自动跑（调度）

| 栏目 | 内容 |
|---|---|
| **目标** | 不用人盯着：**每天按时、按正确顺序自动跑一遍；失败了要知道** |
| **做什么** | 把 ③~⑦ 的步骤编排成一张"流程图"，让调度系统按依赖顺序执行 |
| **产物** | 一条工作流（本项目是 **16 个节点**）+ 每次运行的记录（成功/失败/耗时） |
| **谁在干** | **DolphinScheduler**（调度系统） |
| **怎么知道干对了** | ① 有**成功实例**的记录<br>② **连跑两次数据不翻倍**（说明每个步骤都能安全重跑）<br>③ 节点之间依赖连线正确（上一步没完不会开始下一步） |
| **不懂会怎样** | ⚠️ ① 依赖没连对 → 上一步没跑完就开始下一步，**结果错但不报错**<br>② 任务不能重跑 → 补一次数据，数字就翻倍 |

> **"能安全重跑"为什么是硬要求**：调度世界里**重跑是常态**（失败要重跑、补数要重跑、回溯要重跑）。
> 做法是每张表都用"**覆盖写**"而不是"追加写"。

## 十、本项目还有个特别之处：两条链路并存

**这一点面试时值得主动讲**：这个项目**故意保留了两条链路**。

| | 旧链路（对照组） | 新链路（正式） |
|---|---|---|
| 数据 | **模拟生成**，5 天 / 31.7 万行 | **真实数据**，31 天 / 1063 万行 |
| 为什么留着 | **当反面教材** | 正式用 |
| 它证明了什么 | 模拟数据**掩盖了所有问题**：日活恒为 1000、复购率恒在 0.99 以上 —— **画出来是一条直线** | 有波动、有脏数据、有真实业务形态 |

> **为什么"数字是平的"很致命**：报表上一条直线，说明**数据里没有任何真实变化** ——
> 用它根本看不出业务在发生什么。所以后来换成了真实数据。
>
> **一句话总结这件事**："我发现模拟数据掩盖了问题，所以换成了真实数据" ——
> 这句话本身就是一条很好的项目经历，而**旧链路就是它的物证**。

<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 九站**
① 产生行为 → ② 攒成文件 → ③ 进仓(ODS) → ④ 清洗(DWD) → ⑤ 汇总(DWS)
→ ⑥ 出指标(ADS) → ⑦ 导出 → ⑧ 上墙 → ⑨ 自动化调度

**2. 各站产物（③④⑥）**
- ③ ODS：`ods_event_log_di`，10,630,245 行、31 个分区
- ④ DWD：`dwd_event_log_di`（10,623,154 行）+ `dwd_purchase_fact_di`（186,059 笔）+ 商品维（140,665）+ 时间维（365）
- ⑥ ADS：6 张表对应 6 个业务问题

**3. 为什么 ODS 不改**
- **原始形态是"证据"**：改了以后，想看原始日志就永远拿不回来了
- 加工统一放到 DWD，才能保证**全公司只有一份口径**

**4. 7,091 的用处**
- 它就是"去重"这个动作的效果量：`10,630,245 − 10,623,154 = 7,091`
- 作用：**证明清洗规则真的生效了**（差额对得上 = 规则执行正确）

**5. 粒度**
- 定义：**这张表的一行代表什么**
- 例：`dwd_event_log_di` = 一条事件；`dws_user_event_day` = 一个用户一天；`dim_product` = 一个商品
- 为什么要说：**说不清粒度，就不知道该拿这张表算什么**（而且容易把不可加的数加起来）

**6. 四路对账为什么可信**
- 四条路径走了**不同的表、不同的计算顺序**
- 能收敛到同一个数（57,575,996.50），说明**中间每一层都没算错**
- 任何一层有重复/漏行/口径偏移，这个数就对不上

**7. 为什么留旧链路**
- 它是"**模拟数据掩盖问题**"这一判断的**物证**
- 模拟数据的日活恒为 1000、复购率恒 >0.99，**画出来是直线** ——
  删了它，"我发现模拟数据有问题所以换成真实数据"这句话就失去了支撑
