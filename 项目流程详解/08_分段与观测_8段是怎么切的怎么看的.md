# 08 · 分段与观测：8 段是怎么切的、怎么看

> **这一篇解决两个很具体的问题**：
> **① 那 8 段是按什么切的？② 切完之后，我去哪里看它跑到哪了、跑得怎么样？**
>
> 📌 本篇内容全部来自项目里的三个真实脚本：
> `项目产出/数据接入/evt_run.sh`（手工跑批）、`ds_prepare_steps.sh`（调度用）、
> `项目产出/进度看板/serve.py`（进度看板）。

---

## 〇、先把"8 段"的口径说准

**"8 段"指的是 8 个业务段**（DWS 4 张 + ADS 4 张）。

但**执行器实际跑的是 10 步** —— 因为前后还各加了一步：

| 步号 | 内容 | 文件的来源 |
|---|---|---|
| **1** | 建表（DWS/ADS 八张） | `evt_ddl.sql` |
| **2~9** | ★ **就是那"8 段"**：DWS 四张 + ADS 四张 | `evt_etl.sql` **切出来的 8 段** |
| **10** | 校验（行数 + 交叉对账 + 方向性） | `evt_verify.sql` |

```
你问的"8 段"  =  第 2~9 步
整个执行器跑的  =  10 步  =  建表 + 8 段业务 + 校验
```

> 💡 **为什么会多出这两步**：因为"建表"和"校验"**本来就不是** `evt_etl.sql` 的内容 ——
> 它们在另外两个文件里。执行器把它们和中间的 8 段拼在一起，组成完整的一轮跑批。

### 0.1 ⚠️ 三个最容易混的点（先说清楚，不然后面会绕）

#### 混淆 1：以为"每个 SQL 就是一段"

**不是。段是"人为划出的执行单元"，不是"SQL 的条数"。**

| 情况 | 允许吗 |
|---|---|
| 一段里放 3 条 SQL | ✅ 可以 |
| 一段里只放 1 条 SQL | ✅ 可以（本项目就是这样） |
| 把一条 SQL 从中间切开、放两段 | ✅ 也可以 |

**本项目恰好"一段 = 一条 INSERT"，纯属切法巧合** ——
因为 `evt_etl.sql` 本来就是"一张表一条 INSERT"写下来的，标记正好插在每条前面。

**反证**：DWD 那份 SQL（`etl_ods_to_dwd.sql`）切成 **4 段**，
而 DWS/ADS 这份切成 **8 段** —— 两份文件的段数不同，但都是"段"。
→ **段数由文件里的标记决定，不由 SQL 总数决定。**

#### 混淆 2：以为"Spark 负责了链路的一部分"

**不存在"前面 Hive 做、后面 Spark 做"这种分工。** 实际是这样：

```
【正式链路】DS 工作流 gmall_evt_pipeline（16 节点）
    ODS ──▶ DWD ──▶ DWS ──▶ ADS       ← ★ 全部由 Hive 跑，写进 gmall 库
                                         （这是项目的正式数据，从头到尾没变过）

【旁路实验】spark_bench（另外重算一遍，只为对比）
    DWD(只读) ──▶ DWS ──▶ ADS        ← 只有 Spark 跑，结果写进独立的 gmall_bench 库
                                         （完全不碰 gmall，用完可整库删掉）
```

**两句话记住**：
- **正式数据（`gmall` 库）从头到尾是 Hive 产的**，Spark 只是**在旁边做了个对照实验**
- **"把 Spark 接进调度"本身还是待办**（还没做），所以 Spark **目前不在正式链路里**

#### 混淆 3：以为"8 段是 Spark 的东西"

**8 段是"要跑的作业清单"，两个引擎共用同一份。**

对比实验的前提是"**同一份 SQL**"（不改业务逻辑），所以 Hive 和 Spark 跑的都是这 8 段：

| | Hive 侧 | Spark 侧 |
|---|---|---|
| 8 段怎么执行 | 8 次 `beeline` 调用 | 8 次 `spark-sql` 提交 |
| 会话数 | 8 个 | 8 个 |
| 每次会话的代价 | **参数不继承** → 每段要重拼 `setup.sql` | **约 35 秒**启动开销 |
| 所以 | —— | **8 × 35 = 280 秒** ← **这个账只在 Spark 侧** |

**"35 秒"是 Spark 每次会话的启动成本**，所以"8 × 35"只在"**Spark 分段跑**"这个场景成立。

#### 还有一个范围要说清：DWD 没被对比

**本次对比只覆盖 DWS/ADS 八段，不含 DWD。** 这不是能力限制（**Spark 当然能做清洗**），
而是实验范围的选择，理由三条：

1. DWS/ADS 八段**有现成的分段脚本**（已按标记切好），结构清晰
2. **DWS 四张都要扫 1063 万行明细** —— 最吃引擎性能，能测出真差异
3. ADS 四张是小表 —— 正好用来观察"**轻作业下两个引擎各自的固定开销**"

> ⏳ **DWD 段的对比列在待办里，还没做**（DWD 清洗是整链最慢的节点之一，值得补）。

## 一、怎么分：依据是 SQL 文件里的"注释标记"

### 1.1 切的依据不是"行数"也不是"时间"，是**写在 SQL 里的标记**

打开 `evt_etl.sql`，你会看到这样的注释行：

```sql
-- ===== STEP 1 / DWS·用户主题（dws_user_event_day）=====
INSERT OVERWRITE TABLE gmall.dws_user_event_day PARTITION (dt) SELECT ...;

-- ===== STEP 2 / DWS·商品主题（dws_product_event_day）=====
INSERT OVERWRITE TABLE gmall.dws_product_event_day PARTITION (dt) SELECT ...;

... 一直到 STEP 8
```

**这 8 个 `-- ===== STEP n` 标记，就是"8 段"的来源。**

切分逻辑（`evt_run.sh` 里真实的命令）：

```bash
awk -v d="$RUN" '
  /^-- ===== STEP /                       # 遇到以这个开头的行 → 段号 +1，转存到新文件
      { n++; print > (d"/step_" n ".sql"); next }
  n > 0 { print >> (d"/step_" n ".sql") } # 其余内容追加到当前段文件
' "$WS/evt_etl.sql"
```

**一句话理解这段 awk**：**从上往下扫，每遇到一个 STEP 标记就换一个新文件，后面的内容都写进当前这个文件。**

跑完你会得到：

```
$RUN/step_1.sql   ← STEP 1 的内容（DWS 用户主题）
$RUN/step_2.sql   ← STEP 2 的内容
...
$RUN/step_8.sql   ← STEP 8 的内容（ADS TopN）
```

> ★ **关键认知**：**分段这件事"定义在 SQL 里"，不是"定义在脚本里"。**
> 你想调整分段，改的是 `evt_etl.sql` 里的标记位置，脚本不用动。
> （这也解释了为什么标记里的名字要写清楚是"哪张表" —— 它同时是**切分点**和**步骤名**。）

### 1.2 ⚠️ 切完之后必须做一件事：把公共参数"拼"进每一段

这是本项目**踩过坑**的地方（踩了两次）：

```bash
# 每个分段前面拼上 setup.sql（公共参数），才生成真正要执行的 _run.sql
for f in "$RUN"/step_*.sql; do
  cat "$RUN/setup.sql" "$f" > "${f%.sql}_run.sql"
  rm -f "$f"
done
```

**为什么必须拼**：**每一次 `beeline` 调用都是一个全新的会话** ——
上一个会话里 `SET` 的参数，下一个会话**不继承**。

```sql
-- setup.sql 里的公共参数（每段都要有）
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;    -- ★ 少这行会报 Error 10096
SET mapreduce.job.reduces = 3;
SET mapreduce.map.memory.mb = 1024;                  -- ★ 调优参数
...
```

> ⚠️ **真实踩坑记录**（脚本注释里留着）：
> 有一次**只生成了 `setup.sql` 文件，却忘了拼进分段** ——
> 结果 `hive.exec.dynamic.partition.mode` 仍然是默认的 `strict`，
> 第 2 步写动态分区直接报 `Error 10096`。
>
> **教训**：**"参数文件生成了" ≠ "参数生效了"。**

**所以脚本里加了启动前自检**：

```bash
if ! grep -q "hive.exec.dynamic.partition.mode" "$RUN/step_1_run.sql"; then
  echo "!! 参数未拼接进分段文件，终止执行"; exit 1
fi
```

**在开跑之前就检查参数到没到位，查不到就直接终止** —— 而不是等跑到第 2 步才炸。

### 1.3 两个地方都需要分段，但切法不同

| 场景 | 谁在切 | 产物在哪 | 为什么 |
|---|---|---|---|
| **手工跑批** | `evt_run.sh` **自己切**（跑之前切一次） | `/home/lrh/workspace/new_chain/evt_run/` | 切完立刻执行，用完即弃 |
| **调度（DS）里跑** | `ds_prepare_steps.sh` **预先切好** | `/home/lrh/workspace/new_chain/ds_steps/` | DS 的每个节点只能执行**一个** SQL 文件，所以必须**事先**切好、每个节点对应一个文件 |

**`ds_prepare_steps.sh` 有个很讲究的设计**：

```
SQL 正文    → 直接从 evt_etl.sql 切（唯一事实来源，绝不复制粘贴）
公共参数    → 从 evt_run.sh 里"抽取"，而不是重抄一遍
```

**为什么**：如果参数在这里重抄一份，那么以后**改了 runner 的调优参数、忘了改这里**，
就会出现"两个地方参数不一致"，而且**很难发现**（本项目的老坑）。

**抽完也自检**：

```bash
for f in "$OUT"/dwd_step*.sql "$OUT"/evt_step*.sql; do
  grep -qF 'hive.exec.dynamic.partition.mode' "$f" || fail "...参数没拼上"
  grep -qF 'mapreduce.job.reduces'            "$f" || fail "...参数没拼上"
done
```

## 二、怎么看：三个地方，从细到粗

### 2.1 第一层：集群上的状态文件（最原始、最可靠）

执行器在集群上写三个文件：

| 文件 | 内容 | 用途 |
|---|---|---|
| **`status.tsv`** | 每段一行：**编号 │ 名称 │ 状态 │ 时刻 │ 用时** | ★ 主依据 |
| **`current`** | 当前正在跑的步骤（跑完即删） | 知道"现在在哪一段" |
| **`done`** | 全部完成的标志 + 完成时间 | 判断"整轮跑完了没" |

**`status.tsv` 长这样**（真实内容，制表符分隔）：

```
1     建表 DWS/ADS 八张        OK    2026-10-04 19:12:03   6s
2     DWS·用户主题（用户×天）   OK    2026-10-04 19:12:45   42s
3     DWS·商品主题（商品×天）   OK    2026-10-04 19:13:30   45s
...
10    校验（行数+交叉对账+方向性）OK   2026-10-04 19:56:27   18s
```

**怎么看它**（在集群上执行）：

```bash
cat /home/lrh/workspace/new_chain/evt_run/status.tsv        # 看所有已完成的段
cat /home/lrh/workspace/new_chain/evt_run/current           # 看现在跑到哪（文件不存在 = 没在跑）
cat /home/lrh/workspace/new_chain/evt_run/done              # 看整轮是否跑完
tail -f /home/lrh/workspace/new_chain/run_evt.log           # 看实时日志
```

**为什么用 `status.tsv` 而不是看日志**：日志是"流水"（要一行行找），
状态文件是"表格"（一眼看出**哪段成了、哪段失败了、各花了多久**）。

### 2.2 第二层：本机的进度看板（一条命令，有百分比）

在**你自己的电脑上**运行：

```bash
python "D:\数据开发\项目产出\进度看板\serve.py" 8765 evt_run
# 然后浏览器打开 http://localhost:8765/
```

**它是怎么工作的**（`serve.py` 的真实机制）：

```
你的电脑                                   集群（lrh-1）
┌────────────────────┐                    ┌──────────────────┐
│ serve.py 每 5 秒    │ ──ssh 执行探针────▶ │ dwd_progress.sh  │
│ 去集群拉一次状态     │ ◀──返回状态文本──── │ 读 status.tsv     │
│ ↓                   │                    └──────────────────┘
│ 算成百分比 → progress.json
│ ↓
│ 浏览器每 3 秒取一次 → 显示进度条
└────────────────────┘
```

**为什么要有这个东西**：一个 `Hive` 的 INSERT 一跑就是十几二十分钟，
**前台跑既看不到进度、SSH 单次调用还容易被超时打断**。
所以做成"远端写状态文件 + 本机轮询 + 网页展示"。

**它还能显示"还没开始的步骤的名字"** —— 因为脚本里维护了一份**步骤名清单**，
即使 `status.tsv` 里还没有那一行，页面上也能提前看到"接下来要跑什么"。

> 💡 **切换到 DWD 链路**：`python serve.py 8765 dwd_run`（另一条链路的步骤名不同）。

### 2.3 第三层：组件自带的界面（看"作业"层面的情况）

| 看什么 | 去哪 |
|---|---|
| **作业有没有在跑、成功还是失败、失败原因** | `http://lrh-1:8088`（YARN），或 `yarn application -list` |
| **调度里每个节点的状态、耗时、日志** | `http://lrh-1:12345/dolphinscheduler` |
| **Spark 作业的阶段与 shuffle 量** | `http://lrh-1:4040`（Spark 应用运行时才有） |

**分工**：状态文件/看板看的是"**我的业务跑到第几段了**"；
组件界面看的是"**底下那个作业怎么了**"。**出问题时要两个一起看。**

## 三、一串起来：一次跑批，你会看到什么

```
① 你在集群上启动（放后台，因为要跑几十分钟）
   setsid nohup bash evt_run.sh > run_evt.log 2>&1 < /dev/null &

② 脚本先切段 → 拼参数 → 自检通过 → 才开始跑
   （如果自检没过，它会直接终止，不会白跑）

③ 每跑一段：
   · status.tsv 追加一行（状态 START → OK/FAIL，含用时）
   · current 文件更新成"当前在跑哪段"
   · 日志里打印 ">>>>>> [时间] 步骤 N · 名称 → OK（用时 XXs）"

④ 你随时能看到进度（三个层次任选）
   · 集群上：cat status.tsv / cat current
   · 本机看板：http://localhost:8765/ ← 有百分比，最直观
   · 组件界面：8088 看作业

⑤ 全部跑完：写 done 文件，日志打印 ALL_DONE
```

**失败怎么办**：`status.tsv` 里那一段会标 `FAIL`，**后面的段不会继续跑**（脚本里 `|| exit`）。
修完问题之后，**断点续跑**：

```bash
bash evt_run.sh 3      # 从第 3 步接着跑（前面的段会被跳过，status.tsv 保留）
```

> ★ **这就是"分段"最大的价值**：不分段的话，第 6 段失败 = **前 5 段白跑，从头再来**。

## 五、★ 一个把前面几篇串起来的认知

**"分段"的代价，就是"会话"的代价 —— 两个引擎都一样。**

| | Hive 侧 | Spark 侧 |
|---|---|---|
| 一段 = 几次会话 | **1 次 `beeline` 调用 = 1 个会话** | 1 次提交 = 1 个会话 |
| 会话的代价 | **公共参数不继承** → 每段都得重新 `SET` 一遍（所以要拼 `setup.sql`） | **约 35 秒**启动开销（启动进程、连元数据、申请资源） |
| 8 段分开跑 | 8 次会话 | 8 次会话（实测比单会话慢 5 倍） |

### 5.1 ⚠️ 必须分清的三层：会话 ≠ 作业 ≠ 任务

**一个很常见的误解**：把"8 个会话"理解成"8 个 JVM"。**这是错的，而且错得很关键。**

真实的包含关系是三层：

```
① 会话（一次调用 / 一次提交）          ← 「8 段 = 8 个会话」说的是这一层，数量 = 8
     └─ ② 作业（SQL 被编译成的任务组）  ← 一条 SQL 可能变成 1~N 个作业（数 8088 就知道）
          └─ ③ 任务 / 容器              ← 每个容器一个 JVM，每个任务一个进程
                                        ★「反复起 JVM」说的是这一层，数量是几十上百
```

**两个引擎在 ②③ 层的做法完全不同**：

| 层级 | Hive / MapReduce | Spark |
|---|---|---|
| **② 作业** | 一条 SQL 编译成 **1~N 个 MR 作业**（本项目的校验 SQL 就变成 6 个） | 一条 SQL 是一个 **DAG** |
| **③ 进程** | **每个任务起一个新 JVM**，跑完就销毁 | **Executor 常驻**，任务只是它内部的**线程** |
| **"反复起 JVM"** | 说的是 **③ 层** —— 数量 = **任务数（几十上百）**，不是会话数（8） | 基本不发生（只有 Executor 启动那一次） |

**所以准确的说法是**：

- ❌ "MapReduce 要启动 8 个 JVM"
- ✅ "**两边都是 8 个会话**；但 Hive 侧每个会话内部还会产生若干作业，
  每个作业再起一批 JVM 容器（**几十上百个**）；而 Spark 侧的 Executor **只启动一次、之后一直复用**"

> 💡 **为什么这层区分重要**：它直接解释了"**为什么 MapReduce 慢**" ——
> **不是慢在"8 次会话"，是慢在"每个任务都要重新起一个 JVM"（第 ③ 层）。**
> Spark 的优化正是冲着这一层去的：**Executor 常驻，任务用线程跑。**

> ⚠️ **另外：两边的"会话代价"不能直接比大小**
> - Hive 侧 beeline 冷启约 **5 秒**（只是启动客户端进程）
> - Spark 侧约 **35 秒**（启动 Driver + 连元数据 + **向 YARN 申请 Executor 并等它就绪**）
>
> **35 秒里装的事情比 5 秒多得多** —— 这不是"Spark 慢 7 倍"，是口径不同。

**所以"分段"永远是一个权衡**：

```
分段多（细）  →  可观测性好、能断点续跑   ←→   但每次都要重新付"建会话"的成本
分段少（粗）  →  会话成本低、跑得快       ←→   但失败要从头来、看不到进度
```

> **面试可以这么讲**：
> "我把链路切成 8 段跑，为的是**可观测和断点续跑** ——
> 代价是每段都要重付一次会话建立成本（Hive 侧要重新 SET 参数，Spark 侧要付约 35 秒启动费）。
> 所以**分段是为了观测，合并会话是为了省成本**，
> 生产里我会用『分段开发 + 合并执行』的方式来兼顾。"

## 六、自测

**每题标了对应小节——答不出来就回去看那节。**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 口径**
- "8 段" = **8 个业务段**：DWS 四张 + ADS 四张
- 执行器实际跑 **10 步** = 建表(1) + **8 段业务(2~9)** + 校验(10)

**2. 切分依据**
- 依据是 **SQL 文件里的注释标记**：`-- ===== STEP n / 名称 =====`
- 工具：`awk`（遇到标记就新开一个文件）
- 想调整分段 → **改 `evt_etl.sql` 里标记的位置**，脚本不用动

**3. 为什么拼参数**
- 因为**每一次 `beeline` 调用都是一个全新会话**，`SET` 的参数**不跨会话继承**
- 不拼的后果：参数按默认值执行 → 动态分区未开 `nonstrict` → 报 **Error 10096**
- 所以脚本 `cat setup.sql step_n.sql > step_n_run.sql`，并在启动前 `grep` 自检

**4. 三个层次的看进度方式**
- ① **集群侧状态文件**：`cat status.tsv` / `cat current` / `cat done`
- ② **本机进度看板**：`python serve.py 8765 evt_run` → `http://localhost:8765/`（有百分比）
- ③ **组件界面**：`http://lrh-1:8088`（YARN 作业）、`http://lrh-1:12345`（调度节点状态）

**5. status.tsv**
- 五列：**编号 │ 名称 │ 状态 │ 时刻 │ 用时**
- 为什么不用日志代替：日志是**流水**（要一行行找），状态文件是**表格**（一眼看出哪段成了、哪段失败、各花多久）

**6. 断点续跑**
- `bash evt_run.sh 6`（传起始步号），前面的段会被跳过，`status.tsv` 保留

**7. 分段的代价**
- 每段都要重付一次"建会话"的成本
- **Hive 侧**：公共参数不继承 → 每段都得重新 SET
- **Spark 侧**：每次提交约 35 秒启动开销
- 所以分段是权衡：**细 = 可观测+能续跑但贵；粗 = 便宜但失败从头来**
