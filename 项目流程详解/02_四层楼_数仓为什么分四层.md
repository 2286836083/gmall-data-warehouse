# 02 · 四层楼：数仓为什么要分四层

> **这一篇的目标**：搞明白一件看起来"多此一举"的事 ——
> **为什么数据要搬四次（ODS→DWD→DWS→ADS），而不是一次算完？**

---

## 一、先看"不分层"会发生什么（这样你才知道分层在解决什么）

假设不分层，每个需求都**直接从原始数据算**：

```
需求1（每天多少活跃用户）  → 写一条 SQL，直接读原始日志
需求2（转化率多少）        → 再写一条 SQL，直接读原始日志
需求3（复购率多少）        → 又写一条 SQL，直接读原始日志
```

**三个麻烦立刻出现**：

| # | 麻烦 | 具体表现 |
|---|---|---|
| 1 | **重复劳动** | 三条 SQL 都要做同样的清洗：去重、解析时间、处理空值 —— **同样的活干三遍** |
| 2 | **口径打架** ⚠️ | A 同学把空的类目当"空值"，B 同学当成"未知" → **两张报表的数字对不上，而且谁也说不清谁对** |
| 3 | **改一次全崩** | 源数据的字段变了 → **三条 SQL 全要改**，而且你不知道还有多少条没发现 |

> **第 2 条最要命**：因为它**不报错**。两个数字不一样，但都"看起来合理"。
> 开会时两个人各拿一份报表，一个说"日活 4.7 万"，一个说"4.6 万" —— 一小时的会全耗在"谁对"上。

---

## 二、分层本质：把"清洗"和"算指标"拆开

```
ODS  原始层    把外面来的东西原样落地，一个字不改
  ↓
DWD  明细层    去重、解析时间、拆字段、统一空值  ← 全公司只有这一份口径
  ↓
DWS  汇总层    按主题（用户/商品/类目/交易）预先汇总  ← 算一次，大家共用
  ↓
ADS  应用层    一个业务问题一张表  ← 直接给报表/大屏用
```

> **类比**：像做菜。
> ODS = 采购回来的原料；DWD = 洗好切好的净菜；DWS = 炒好的半成品；ADS = 装盘上桌的成品。
>
> **物理上是什么**：**每一层都是 HDFS 上的一批文件 + 数据库里的一条"表结构"记录。**
> 层与层之间就是"读上一层的文件、算完写成下一层的文件" —— 一次搬运就是一批计算任务。

**分层换来的三样东西**：

| 换来什么 | 怎么来的 |
|---|---|
| **清洗只做一次** | 所有清洗都在 DWD 做，上层直接用 |
| **口径只有一个来源** | 空值怎么处理、怎么算去重、什么算"活跃"，**在 DWD 定死** |
| **改一处不影响全局** | 源数据变了只改 DWD；上层出问题只影响它自己 |

---

## 三、每层各自的目标（一句话）

| 层 | 目标（一句话） | 判断标准：**这层该不该做这件事** |
|---|---|---|
| **ODS** | **原样接住**外面来的数据，一个字不改 | ✅ 加分区、记来源<br>❌ 去重、改名、转格式、删行 |
| **DWD** | 产出一份**全公司共用的干净明细** | ✅ 去重、解析、拆字段、空值统一<br>❌ 做业务汇总（那是 DWS 的活） |
| **DWS** | 按主题**预先汇总**，供多方复用 | ✅ 按"用户×天"这类粒度聚合<br>❌ 做很专用的指标（那是 ADS） |
| **ADS** | **一个业务问题一张表**，直接能用 | ✅ 字段就是报表要显示的字段<br>❌ 给别的 ADS 当输入 |

**这套判断标准很重要**：以后你看到一张表做错了位置（比如在 ODS 里去了重），
**能用这张表指出它为什么错**，而不是凭感觉。

---

## 四、一条纪律：不许"跨层消费"（这是踩过坑才立的规矩）

**正确方向**：

```
大屏 / 报表  →  ADS  →  DWS / 维度表  →  DWD  →  ODS
（只读 ADS）    （只读 DWS/DWD）      （只读 DWD）   （只读 ODS）
```

**不允许**：

| ❌ 违规做法 | 后果 |
|---|---|
| 报表**直接读 DWS**（跳过 ADS） | 把报表和中间层**绑死** —— 中间层一改，报表就崩 |
| ADS 直接读 ODS | **绕过了全部清洗** —— 口径必然和别的报表打架 |
| ADS 读另一个 ADS | 链条变长，改一处影响一片 |

> 📌 **本项目对照（真实发生过）**：大屏最初有**两张图直接读 DWS 层**（类目图、交易图），
> 跳过了 ADS。表面能跑，但违反了"应用层只消费 ADS"这条规矩。
>
> **怎么修的**：补建两张 ADS 表，让大屏改读它们。
> **怎么证明没改坏数据**：把改前、改后的导出文件做**逐字节比对** ——
> 结果只差一个时间戳，说明"只是换了条路走过去，数字一个没变"。
>
> ★ **这件事本身就能当面试素材**：
> "我发现自己的项目违反了分层规范，补了表；并用逐字节比对证明改动是安全的。"
> —— **比"我的项目分层很规范"有说服力得多，因为它是真的。**

---

## 五、为什么"必须先定粒度"（这一篇的加分内容）

**名词**：**粒度 = 这张表的一行代表什么。** 这是整份数据里最重要的一个词。

| 表 | 粒度 |
|---|---|
| `ods_event_log_di` | 一行 = **一条事件** |
| `dwd_purchase_fact_di` | 一行 = **一笔成交** |
| `dws_user_event_day` | 一行 = **一个用户一天** |
| `dws_trade_day` | 一行 = **一天**（只有一行一天） |
| `dim_product` | 一行 = **一个商品** |
| `ads_top_product_day` | 一行 = **一天的某个排名位次** |

**为什么必须先定粒度**：因为**能不能把数字加起来，取决于粒度**。

```
同一个用户在类目下买了两个商品：
  商品层：商品A 有 1 个买家、商品B 有 1 个买家
  加总：1 + 1 = 2          ← ❌ 错！实际只有 1 个买家（都是同一个人）
```

**规律（记这一条就够）**：

| 这类数字 | 能不能跨层加总 |
|---|---|
| 金额、次数 | ✅ 能（加法） |
| **去重人数**（日活、买家数） | ❌ **绝对不能** |
| 比率（转化率、复购率） | ❌ **绝对不能** |
| 平均数（客单价） | ❌ 不能（要回原始数据重算） |

> 一句话：**"去重的数"和"比率"不能从上层的数加出来，必须回明细重算。**
>
> 📌 **本项目对照**：类目层的"买家数"就是**回明细重算**的，不是从商品层加的。
> 这条被单独列成"口径易错点 #1"，因为它**不报错、只出错**。

## 六、本项目的层数统计（可以背下来的数字）

`gmall` 库里现在一共 **30 张表**：

| | 旧链路（模拟数据，对照组） | 新链路（真实数据，正式用） |
|---|---|---|
| ODS | 3 张 | **1 张** |
| DWD | 2 张 | **2 张** |
| DIM（维度表） | 2 张 | **2 张** |
| DWS | 3 张 | **4 张** |
| ADS | 4 张 | **6 张** |
| 临时表 | 1 张 | —— |
| **合计** | **15 张** | **15 张** |

> ⚠️ **一个容易搞混的地方**：库里同时有**两套表**（旧链路 + 新链路），
> 名字很像但内容不同（比如 `dws_user_day` 是旧的、`dws_user_event_day` 是新的）。
> **正式用的是"新链路"那 15 张**，旧的那 15 张是**对照组**（用来证明"模拟数据会掩盖问题"）。

## 七、自测

**每题标了对应小节——答不出来就回去看那节。**

1. 不分层会产生哪三个麻烦？哪个最要命、为什么？—— 对应 **§一**
2. 四层各自的目标是什么？（一句话说清）—— 对应 **§三**
3. 什么叫"跨层消费"？本项目哪里违规过、怎么修的？—— 对应 **§四**
4. 什么叫粒度？"买家数"为什么不能跨层加总？—— 对应 **§五**
5. 库里一共多少张表？正式用的是哪一半？—— 对应 **§六**

<details>
<summary><b>参考答案要点</b>（先自己答一遍，再点开核对）</summary>

**1. 三个麻烦**
- ① **重复劳动**（同一套清洗写三遍）
- ② **口径打架**（空值处理不一致 → 两张报表数字对不上）← **最要命**
- ③ **改一次全崩**（源数据一变，所有 SQL 都要改，还找不全）
- 为什么 ② 最要命：**它不报错**，两个数字都"看起来合理"，扯不清谁对

**2. 四层目标**
- **ODS**：原样接住，一个字不改（证据保全）
- **DWD**：产出全公司共用的干净明细（唯一口径来源）
- **DWS**：按主题预先汇总，供多方复用
- **ADS**：一个业务问题一张表，直接给报表用

**3. 跨层消费**
- 定义：不按 `报表→ADS→DWS/DIM→DWD→ODS` 的顺序走，比如报表**直接读 DWS**
- 本项目：大屏的类目图/交易图原本直接读 DWS，跳过 ADS
- 修法：补建 `ads_category_day` / `ads_trade_day` 两张 ADS 表
- 验证：新旧导出文件**逐字节比对**，只差时间戳 → 证明只是换了路径、数字没变

**4. 粒度与不可加**
- 粒度 = **这张表的一行代表什么**
- "买家数"是**去重人数** → 同一用户买两件商品会被算两次 → **加总虚高**
- 规律：**去重数和比率不能跨层加；必须回能拿到明细的那一层重算**

**5. 表数**
- 一共 **30 张**：旧链路 15 张（模拟数据，对照组）+ 新链路 15 张（真实数据，正式用）
- 注意两套表名字很像，**别混**（`dws_user_day` 是旧的、`dws_user_event_day` 是新的）
</details>
