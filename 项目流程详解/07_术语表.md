## 一、数据与分层

| 术语 | 大白话解释 |
|---|---|
| **数仓（数据仓库）** | 把业务系统产生的数据，**经过加工后集中存放**的地方，专门用来做分析和报表 |
| **ODS（原始层）** | 数据进厂的第一站。**原样存，一个字不改** —— 因为原始形态是"证据" |
| **DWD（明细层）** | 清洗层：去重、解析时间、拆字段、统一空值。**全公司只有这一份口径** |
| **DWS（汇总层）** | 按主题（用户/商品/类目/交易）**预先算好**的中间结果，供大家复用 |
| **ADS（应用层）** | 最终报表用的表。**一个业务问题一张表** |
| **DIM（维度表）** | 描述"谁、什么、什么时候"的表（商品、时间…）。行数少、相对稳定 |
| **事实表** | 记录"**发生了什么**"的表（金额、次数）。行数大、只存编号 |
| **粒度** ★ | **这张表的一行代表什么。** 比如"一个用户一天"、"一笔成交"。**建模第一件事** |
| **分区** | 按某个字段把数据分目录存放（如 `dt=2019-10-01/`）。**作用是查一天不用扫全表** |
| **ETL** | 数据从一层搬到下一层的整个过程（抽取 → 转换 → 装载） |
| **T+1** | 今天算昨天的数据。**离线数仓的典型节奏** |
| **离线 / 批处理** | 攒一批再算，不追求秒级响应 |
| **幂等** ★ | **执行一次和执行多次结果一样。** 调度里重跑是常态，所以必须幂等 |
| **口径** | 一个指标的**确切定义**。比如"活跃用户"= 当天有任意事件的去重用户 |

## 二、计算与资源

| 术语 | 大白话解释 |
|---|---|
| **HDFS** | 分布式文件系统。**把数据切成块、每块存 3 份、放在三台机器上** |
| **块（Block）** | HDFS 存数据的最小单位，默认 **128MB** |
| **副本** | 一份数据存几份（本项目存 3 份）。坏一台机器不丢 |
| **NameNode** | HDFS 的"**目录管理员**"，只在内存里记"文件在哪、块在哪台机器"。**它自己不存数据** |
| **DataNode** | 真正**存数据块**的进程，每台机器一个 |
| **YARN** | 资源调度器。**决定"活派给谁、给多少资源"** —— 它不计算、不存数据 |
| **ResourceManager** | YARN 的总调度，**全集群只有一个** |
| **NodeManager** | 每台机器的"工头"，负责起容器、盯容器 |
| **容器（Container）** | 划出来的一块资源，**本质是一个被限了内存和 CPU 的进程** |
| **ApplicationMaster（AM）** | 一个作业的"项目经理"，向 YARN 要资源、盯着任务别死 |
| **MapReduce** | 老一代的计算方式：先各算各的（map），再合并（reduce） |
| **shuffle（洗牌）** ★ | **把同类数据搬到同一台机器上。** 最贵的操作（走网络 + 落磁盘） |
| **作业（Job）** | 一次计算的单位。**一条 SQL 可能被切成好几个作业** |
| **任务（Task）** | 作业内部并行的最小单位，处理一小片数据 |
| **JVM** | Java 虚拟机，跑 Java 程序的容器。**反复启动它很贵** |

## 三、组件

| 术语 | 大白话解释 |
|---|---|
| **Hive** | "**翻译官**"：把你写的 SQL 翻译成能在集群上跑的一批任务 |
| **MetaStore（元数据服务）** | Hive 里管"**表长什么样**"的服务（表名、字段、分区在哪） |
| **HiveServer2** | 接收你 SQL 请求的服务，你连的是它（端口 10000） |
| **beeline** | 你敲 SQL 用的命令行工具 |
| **MySQL** | 存"**账本**"的数据库 —— 表结构、调度记录存在这里，**不是数据本身** |
| **ZooKeeper** | 集群的"**仲裁员**"，记录"谁还在线" |
| **Spark** | "**另一种工人**"：半成品尽量留内存、工人常驻、整条 SQL 一起排工期 |
| **Driver（驱动器）** | Spark 应用的"**大脑**"：排计划、派活、收结果 |
| **Executor（执行器）** | Spark 的"**手脚**"：常驻进程，任务在它里面以**线程**方式跑 |
| **DolphinScheduler** | 调度系统："**闹钟 + 班长**"：按时、按顺序、失败能知道 |
| **ECharts** | 前端图表库，负责把数据画成图 |

## 四、调度

| 术语 | 大白话解释 |
|---|---|
| **工作流** | 一张"**谁依赖谁**"的流程图（模板，画一次） |
| **实例** | 工作流**跑起来的某一次**（一条运行记录，含成功/失败/耗时） |
| **依赖** | "上一步做完才能做下一步"。**调度的灵魂** |
| **定时** | "每天几点自动跑"的配置 |
| **补数** | 重算历史某几天的数据 |
| **上游 / 下游** | 上游 = 提供数据的（前一步）；下游 = 消费数据的（后一步） |
| **断点续跑** | 从失败的步骤接着跑，不用从头来 |
| **告警** | 出问题时发通知。**默认往往是不发的，要显式配** |

## 五、性能与排错

| 术语 | 大白话解释 |
|---|---|
| **性能瓶颈** | 拖慢整个任务的**那一个**环节（通常不是 CPU，而是搬数据/磁盘） |
| **数据倾斜** | 某个 key 的数据特别多 → **一个任务拖慢整个阶段** |
| **小文件问题** | 一堆很小的文件 → 每个都变一个任务，且压爆 NameNode 内存 |
| **GC（垃圾回收）** | 内存不够时，程序疯狂清理内存，**98% 时间都在清理** → 最后报错 |
| **内存溢出（OOM）** | 内存不够导致崩溃。分"堆内不够"和"容器超限"两种 |
| **退出码 143** | 收到"请退出"信号 → **被人主动停止的**（不是 bug） |
| **退出码 137** | 被强制杀掉 → **常见是内存超限** |
| **计数器（Counters）** | 作业的"体检表"：读了多少、写了多少、花了多少 CPU/GC 时间 |
| **基线** | 用来对比的标准值。**基线不可复现，对比就没意义** |
| **外部判据** ★ | 判断"好了没有"的硬证据。**"进程还在"不算，"发一次真实查询拿到结果"才算** |
| **控制面 / 数据面** ★ | 控制面 = 界面/系统显示的状态；数据面 = 数据与进程的**真实**状态。**两者可能不一致** |
| **执行计划（EXPLAIN）** | 让数据库告诉你"**它打算怎么跑**这条 SQL" |
