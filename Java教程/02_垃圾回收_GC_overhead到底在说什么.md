# 02 · 垃圾回收 —— `GC overhead limit exceeded` 到底是什么

> 本份解决一件事：**你那次报错到底在说什么？为什么"加内存就好了"？**
> 读完你应该能：把那个报错的**完整触发链条**讲出来，而不是只会说"内存不够"。

---

## 一、先看你那句报错的原文

```
java.lang.OutOfMemoryError: GC overhead limit exceeded
```

**它的意思不是"内存用完了"。**

| 如果是内存真用完 | 报错是 |
|---|---|
| `OutOfMemoryError: Java heap space` | 堆里放不下了 |
| `OutOfMemoryError: GC overhead limit exceeded` | **GC 在空转：花 98% 的时间回收，却只回收到不到 2%** |

后者是 JVM 的**一种保护性判断**：

> "我（JVM）已经在拼命回收了，但几乎什么都回收不回来。
> 照这个趋势跑下去永远不会成功，**与其让你卡死，不如我现在就报错退出**。"

所以它的本质是：**活对象太多，导致 GC 失效**，而不只是"空间小"。

---

## 二、机制一：JVM 怎么判断一个对象"死了"

### 2.1 两种方案

| 方案 | 做法 | 谁在用 | 致命缺陷 |
|---|---|---|---|
| **引用计数** | 每个对象记一个数字，有人引用就 +1，引用断开就 -1，归零即死 | **Python**、Objective-C | **循环引用**：a.b = b; b.a = a，两个都永远不会归零 |
| **可达性分析** | 从一批"根"出发，顺着引用链往下走，**走不到的就是死的** | **Java（JVM）** | 需要暂停应用线程（STW） |

> 你写 Python 时可能没注意过循环引用问题，因为 Python 额外有一套循环检测在补。
> **Java 从根上就不用引用计数**，所以压根没有这个问题。

### 2.2 什么是 GC Roots（可达性分析的起点）

```
GC Roots（一批一定"活着"的引用）
  ├─ 虚拟机栈里正在用的局部变量、参数
  ├─ 静态变量（static 字段）
  ├─ 常量（String 常量池）
  ├─ 本地方法栈里的 JNI 引用
  └─ 还在同步锁持有的对象
```

**顺序**：从这些根出发 → 顺着引用一层层往下走 → 走不到的对象标记为"死" → 回收。

### 2.3 一个关键细节：不是一次就死

对象被判定不可达后，还要经历**两次标记**才真正被回收（第一次标记 + 筛选是否需要执行 `finalize()`）。
> ⚠️ `finalize()` 机制在 **JDK 9 已被废弃**，实际开发中不该用。知道有这么回事即可。

## 三、机制二：三种回收算法（各自的代价）

| 算法 | 顺序 | 优点 | 代价 | 用在哪 |
|---|---|---|---|---|
| **标记-清除** | ① 扫一遍标记活的<br>② 再扫一遍清掉死的 | 不用搬对象，快 | **产生内存碎片**：空间够但放不下大对象 | 老年代（CMS 用过） |
| **标记-复制** | 把活的对象**复制**到另一块空间，剩下的整块清空 | 无碎片，分配时只要移动指针（快） | **浪费一半空间**（总有一半空着） | **新生代** |
| **标记-整理** | 标记后把活的**往一端挪**，挤掉空隙 | 无碎片、不浪费空间 | **要搬动对象**，慢，且要更新所有引用 | 老年代 |

**硬件映射**：

| 操作 | 物理消耗 |
|---|---|
| 标记 | **CPU** 遍历引用链（指针追逐，容易 cache miss） |
| 复制/整理 | **内存带宽**（把对象字节从一处搬到另一处） |
| 清除 | 几乎免费，只是把空间标记为空闲 |
| 搬完还要改引用 | 又一次 CPU + 内存写 |

## 四、机制三：为什么要分代（这是 GC 最重要的设计）

### 4.1 分代假说

> **弱分代假说**：绝大多数对象都是"朝生夕死"的。

实测支撑：一次普通的 Java 方法调用里 new 出来的临时对象，
**90% 以上活不过一次 Minor GC**。

### 4.2 所以设计成这样

```
新生代 (Young)                     老年代 (Old)
┌────────────┬────────┬────────┐  ┌──────────────┐
│   Eden     │  S0    │  S1    │  │  长期存活的   │
│   80%      │  10%   │  10%   │  │   对象        │
└────────────┴────────┴────────┘  └──────────────┘
   ↑ 新对象都在这     ↑ 复制的目标（总有一个是空的）

新生代用【标记-复制】：死的占 90%，只需要复制那 10% 活的 → 极快
老年代用【标记-整理】：对象都活得久，复制不划算，只能慢慢挪
```

**这就是 8:1:1 的由来**：Eden 80%，两个 Survivor 各 10%。
每次 Minor GC 把 Eden + 正在用的 Survivor 里**活着的对象**复制到另一个空的 Survivor。

## 五、三种 GC 的顺序与触发条件

| 名称 | 回收范围 | 触发条件 | 速度 |
|---|---|---|---|
| **Minor GC / Young GC** | 只回收新生代 | Eden 区放不下新对象时 | 快（ms 级） |
| **Major GC / Old GC** | 只回收老年代 | 老年代空间不足（通常先触发一次 Minor） | 慢 |
| **Mixed GC** | 新生代 + 部分老年代 | **G1 特有** | 中 |
| **Full GC** | 整个堆 + 元空间 | 老年代担保失败、元空间不足、显式 `System.gc()` | **最慢**，要尽量避免 |

### 5.1 对象晋升的三条路（顺序）

```
① 年龄达标：每熬过一次 Minor GC 年龄 +1，到阈值（默认 15）晋升老年代
② 大对象直通：超过 -XX:PretenureSizeThreshold 的对象直接进老年代
   （避免它在新生代里被反复复制，复制大对象很贵）
③ 动态年龄判定：Survivor 中某一年龄的对象总和 > Survivor 空间的一半
   → 该年龄及以上的对象直接晋升（不等到 15）
```

## 六、STW：为什么 GC 会"卡"

**Stop The World** = GC 期间**暂停所有应用线程**。

**为什么必须停**：你在遍历引用链的时候，应用线程还在不断改引用关系——
一边扫一边变，扫出来的结果就是错的。

**硬件映射**：

```
STW 期间：
  - CPU 在做 GC（不跑你的业务代码）
  - 你的程序对外表现是"完全卡住、无响应"
  - 内存带宽被 GC 的复制操作占满
```

**这直接解释了一个你熟悉的现象**：Hive/Spark 作业跑着跑着进度突然不动了——
如果容器内存吃紧，GC 频繁触发，**大量时间花在 GC 上而不是算数据**。
你那次 637 秒才失败，其中绝大部分时间就是在反复 GC。

## 七、★ 你的环境有个版本陷阱

| 环境 | JDK | 默认 GC | 特点 |
|---|---|---|---|
| **你的集群** | **JDK 8** | Parallel Scavenge + Parallel Old | **吞吐量优先**：允许较长 STW，但总吞吐最大 |
| **你的本机** | **JDK 13.0.1** | **G1 GC** | **低延迟优先**：把堆切成很多小 region，优先回收垃圾最多的 |

**这意味着：你在本机做 GC 实验，看到的现象和集群不一样。**

比如 G1 会有 `Mixed GC` 这个 JDK 8 默认收集器没有的阶段；
G1 的 `jstat` 输出列也和 Parallel 不同。别把本机的现象当成集群行为。

### 7.1 G1 简介（知道即可，不用深挖）

```
传统：堆是连续的一整块（新生代 / 老年代各占一段）
G1  ：把堆切成 ~2048 个等大的 Region，每个 Region 可以动态扮演
      Eden / Survivor / Old / Humongous（存大对象）

好处：可以只回收"垃圾最多"的几个 Region（Garbage First，名字由来）
      → 用较短的停顿换取较高的回收效率
```

## 八、★ 完整复盘你那次故障

### 8.1 触发链条（按这个顺序讲）

```
① SQL 是 GROUP BY product_id, dt
        ↓
② 需要在内存里维护一张聚合表：键 = (product_id, dt) 组合
        ↓
③ 实测组合数 = 430 万个
   → 这 430 万个键【必须全部活到聚合结束】，中途一个都不能回收
        ↓
④ 容器 512 MB，堆上限 -Xmx410m
        ↓
⑤ 堆被这 430 万个活对象占满，可用空间趋近于 0
        ↓
⑥ JVM 触发 GC → 扫一遍发现"全都活着"→ 回收率 ≈ 0%
        ↓
⑦ 于是反复 GC：花掉 98%+ 的时间，回收不到 2% 的空间
        ↓
⑧ JVM 判定：再跑也没意义 → 抛 GC overhead limit exceeded
        ↓
⑨ 整个过程耗时 637 秒后失败（时间基本都烧在 GC 上）
```

### 8.2 为什么加到 `-Xmx820m` 就好了

```
820m 能装下这 430 万个键 + 中间结果
→ GC 时仍然能回收出可观的空间
→ 回收率不再是 0%
→ 不再触发 overhead limit
→ 63 秒跑完
```

**注意**：不是"内存大了所以快"，而是**"内存够了所以 GC 不再空转"**。
这个区别在面试里很加分。

### 8.3 一个反直觉的点

```
-XX:-UseGCOverheadLimit   ← 关掉这个保护
```

关掉之后，同样的场景会变成 `OutOfMemoryError: Java heap space`。
**但这么做更糟**——因为 JVM 不再提前报警，而是真的把所有时间都耗在 GC 上直到彻底失败，
你可能要等更久才知道结果。**这个保护是有意义的，别关。**

## 九、可跑的验证（本机 JDK 13）

### 9.1 亲手造一次 `GC overhead limit exceeded`

```java
// GcOverhead.java —— 复现你集群上那个报错
import java.util.HashMap;

public class GcOverhead {
  public static void main(String[] args) {
    HashMap<Long, long[]> map = new HashMap<>();
    long i = 0;
    try {
      while (true) {
        // 每个 value 都是活对象，全都引用着 map，一个都回收不掉
        map.put(i++, new long[100]);
      }
    } catch (OutOfMemoryError e) {
      System.out.println("put 了 " + map.size() + " 条之后挂了");
      System.out.println("报错类型: " + e.getClass().getSimpleName());
      System.out.println("报错信息: " + e.getMessage());
    }
  }
}
```

```bash
javac GcOverhead.java && java -Xmx64m GcOverhead
```

**你会看到**：先是明显卡顿（GC 在空转），然后抛出 `GC overhead limit exceeded`。
**这个卡顿就是你在集群上感受到的 637 秒。**

### 9.2 对比：真正的"内存用完"

```java
// HeapSpace.java —— 一次分配一大块，不靠 GC 救场
public class HeapSpace {
  public static void main(String[] a) {
    try {
      byte[] big = new byte[200 * 1024 * 1024]; // 要 200MB，但只给了 64m
    } catch (OutOfMemoryError e) {
      System.out.println("报错: " + e.getMessage());
    }
  }
}
```

```bash
javac HeapSpace.java && java -Xmx64m HeapSpace
```

**你会看到**：`Java heap space`，而且是**立刻**报的，不卡顿。

> 把这两个对比跑一遍，你对这两种 OOM 的区别就有肌肉记忆了。

### 9.3 用 jstat 观察 GC 在空转

```bash
# 终端 1
java -Xmx64m GcOverhead

# 终端 2（先 jps -l 查 pid）
jstat -gcutil <pid> 500
```

**看什么**：某几列的百分比会一路顶到 100% 然后掉不下来，
同时 `FGCT`（Full GC 总耗时）快速增长 —— 这就是"GC 在空转"的可视化。

## 十、面试官会问（这一节的）

| 问题 | 答法要点 |
|---|---|
| 怎么判断对象可以回收？ | 可达性分析（从 GC Roots 出发遍历），不是引用计数 |
| GC Roots 有哪些？ | 栈上局部变量、静态变量、常量、JNI 引用 |
| 为什么要分代？ | 弱分代假说：多数对象朝生夕死 → 新生代用复制（只复制少量活对象），老年代用整理 |
| Minor GC 和 Full GC 区别？ | 范围不同（新生代 vs 全堆+元空间）、速度差一个量级 |
| 对象什么时候晋升老年代？ | 年龄到 15、大对象直通、Survivor 同龄过半 |
| **`GC overhead limit exceeded` 是什么？** | ★ 保护性报警，98% 时间 GC 却回收不到 2%；本质是活对象太多导致 GC 失效 |
| 它和 `Java heap space` 区别？ | 前者是"GC 救不回来"，后者是"真的放不下" |
| 怎么排查 OOM？ | `jstat` 看 GC 频率、`jmap -histo` 看谁占得多、`-XX:+HeapDumpOnOutOfMemoryError` 留现场 |

## 十一、术语卡

| 术语 | 一句话 |
|---|---|
| **可达性分析** | 从 GC Roots 出发走引用链，走不到的即死 |
| **GC Roots** | 一批确定活着的对象，是可达性分析的起点 |
| **Minor GC** | 只清新生代，靠复制存活对象完成 |
| **Full GC** | 清整个堆 + 元空间，最慢，要避免 |
| **STW** | GC 时暂停所有应用线程 |
| **晋升 (Promotion)** | 新生代对象活够久后搬到老年代 |
| **吞吐量** | 跑业务代码的时间 / 总时间；GC 时间占比越低吞吐越高 |
| **G1** | 把堆切成 region，优先回收垃圾最多的区域，JDK 9+ 默认 |
| **Humongous** | G1 里存放大对象的特殊 region |

## 十二、回到你的项目：怎么把这个讲成 30 秒

> "有一次全量 ETL 失败，报 `GC overhead limit exceeded`。
> 这个报错不是说内存用完了，而是 JVM 发现自己 98% 的时间都在做 GC，却回收不到 2% 的空间，
> 于是主动放弃。根因是那条 SQL 是 `GROUP BY product_id, dt`，实测有 430 万个组合，
> 这些键必须全部活到聚合结束，导致堆里几乎全是活对象，GC 扫一遍什么都回收不掉。
> 我把容器从 512 MB 加到 1024 MB、`-Xmx` 从 410m 加到 820m 之后，
> 哈希表装得下，GC 不再空转，从 637 秒失败变成 63 秒成功。
> 注意这里 `-Xmx` 只管堆，容器内存还要留给元空间和线程栈，
> 所以我没把 512 MB 全给堆——全给堆的话故障会变成 YARN 直接 kill 容器，那更难查。"

**这一整段用的是你自己的数据，但每一句都在讲机制。** 这就是"能讲"和"背下来"的区别。
