# 01 · JVM 内存模型 —— 你其实早就踩过它了

> 本份解决一件事：**`-Xmx410m` 到底在限制什么？为什么不能设成 512m？**
> 读完你应该能：把你在集群上那次调内存的经历，用 JVM 术语完整讲一遍。

---

## 一、从一个你已经做过的事开始

你做过的操作：

| 动作 | 结果 |
|---|---|
| 容器 512 MB / `-Xmx410m` | `GC overhead limit exceeded`，跑了 637 秒后失败 |
| 容器 1024 MB / `-Xmx820m` | 成功，63 秒 |

这两个数字背后是四个独立的 JVM 概念。我们一个一个来：

1. **容器 512 MB** → YARN 给这个 JVM 进程设的硬上限（操作系统层面的限制）
2. **`-Xmx410m`** → JVM **堆**的最大值（只是进程内存的一部分）
3. **`GC overhead limit exceeded`** → 垃圾回收失败的报警（不是"内存用完"）
4. **`GROUP BY product_id, dt` 430 万组合** → 堆里那张哈希表装不下

**先记住这个结论，后面全部围绕它展开：**
> `-Xmx` 管的是「堆」，而 JVM 进程要用的内存**远不止堆**。

## 二、机制：`java Main` 敲下去之后，按顺序发生了什么

```
① 操作系统创建一个进程（fork/exec）
        ↓
② 这个进程里跑的不是你的代码，是 JVM 自己
   —— JVM 本身是一个 C++ 写的程序（HotSpot）
        ↓
③ JVM 启动，向操作系统申请一大块内存（就是后面要分的堆、元空间…）
        ↓
④ 类加载：读 .class 字节码 → 把类的定义放进元空间
        ↓
⑤ 创建主线程，分配虚拟机栈，开始执行 main()
        ↓
⑥ 你的代码 new 对象 → 在「堆」里分配空间
        ↓
⑦ 堆不够了 → 触发 GC（暂停应用线程，扫描并回收）
        ↓
⑧ main 结束 → JVM 退出 → 进程内存全部还给操作系统
```

**硬件映射（物理上消耗了什么）**：

| 步骤 | 物理消耗 |
|---|---|
| ① 建进程 | 操作系统分配 PCB、内存空间；**进程是资源分配的最小单位** |
| ② JVM 启动 | 加载 JVM 的 C++ 代码到内存；CPU 执行 JVM 自身逻辑 |
| ③ 申请内存 | **向操作系统要虚拟内存**，此时只是"记账"，真正占用要等写入时才分配物理页 |
| ④ 类加载 | **读磁盘**（.class 文件）→ 写内存 |
| ⑥ new 对象 | 写内存（堆） |
| ⑦ GC | **吃 CPU**（扫描对象引用）+ **吃内存带宽**（搬移对象），期间应用线程暂停 |

第 ③ 步有个关键点：JVM 启动时申请的**虚拟内存**可以很大，但 YARN 容器限制的是**实际使用的物理内存**。这直接导致下一节的坑。

## 三、JVM 把内存分成六块

```
┌──────────────────────────────────────────────┐
│ 【线程私有】—— 每个线程各有一份                │
│  ├─ 程序计数器                                 │
│  ├─ 虚拟机栈                                   │
│  └─ 本地方法栈                                 │
├──────────────────────────────────────────────┤
│ 【线程共享】—— 所有线程共用                     │
│  ├─ 堆 Heap          ← -Xmx 只管这一块！       │
│  └─ 元空间 Metaspace                          │
├──────────────────────────────────────────────┤
│ 直接内存 DirectMemory（堆外）                   │
└──────────────────────────────────────────────┘
```

### 3.1 逐块详解

| 区域 | 放什么 | 大小怎么定 | 不够时报什么 | 硬件上是什么 |
|---|---|---|---|---|
| **程序计数器** | 当前线程执行到哪条字节码指令 | 固定，很小 | **不会溢出**（唯一规定的） | 一小块内存，近乎 CPU 寄存器的概念 |
| **虚拟机栈** | 一次方法调用 = 一个栈帧（局部变量、操作数栈、返回地址） | `-Xss`，默认约 1 MB/线程 | `StackOverflowError`（递归太深）<br>`OOM: unable to create native thread`（线程太多） | 线程私有的内存；**每开一个线程就多占一份** |
| **本地方法栈** | native 方法（C/C++ 写的） | 同 `-Xss` | 同上 | 同上 |
| **堆 Heap** | **所有对象实例、数组** | `-Xms`（初始）<br>`-Xmx`（最大） | `OutOfMemoryError: Java heap space` | JVM 进程向 OS 申请的一段内存 |
| **元空间 Metaspace** | 类的定义信息（类名、方法字节码、常量池） | `-XX:MaxMetaspaceSize`<br>**默认不限制**（用本地内存） | `OutOfMemoryError: Metaspace` | **本地内存（不是堆！）** |
| **直接内存** | NIO 的 `ByteBuffer.allocateDirect`，堆外缓冲 | `-XX:MaxDirectMemorySize`<br>默认≈`-Xmx` | `OOM: Direct buffer memory` | 本地内存，**不受 GC 管**（靠引用间接回收） |

### 3.2 一个容易记错的点

> **JDK 8 之后，"永久代（PermGen）"已经被移除，改成了元空间（Metaspace）。**
> 老资料里的 `-XX:PermSize` / `-XX:MaxPermSize` 在 JDK 8 及以后**已经无效**。
> 你的集群是 JDK 8，所以永远不会看到 `PermGen space` 这个报错——看到 `Metaspace` 才是对的。

## 四、★ 核心问题：为什么 512 MB 容器不能设 `-Xmx512m`

### 4.1 一个 JVM 进程的内存账本

```
YARN 容器上限 512 MB
  ├── 堆（-Xmx）                    ← 你能直接控制的
  ├── 元空间（类信息）
  ├── 线程栈 × 线程数（-Xss × N）    ← 线程多了很可观
  ├── 直接内存（NIO / 堆外缓冲）
  ├── JIT 编译后的代码缓存
  ├── GC 自己用的数据结构（Remembered Set、Card Table…）
  └── JVM 自身的 C++ 代码、栈
```

**除了第一行，后面几项都不受 `-Xmx` 限制。**

### 4.2 你那次的配置为什么是对的

```
容器 512 MB
  -Xmx410m   → 堆
  剩约 100 MB → 元空间 + 线程栈 + 直接内存 + GC 数据结构 + JVM 自身
              （约占 19.5%，是个合理的留出比例）
```

### 4.3 如果贪心设成 `-Xmx512m` 会怎样

失败方式会**完全变样**：

```
原来：OutOfMemoryError: GC overhead limit exceeded
      ↑ JVM 自己报的，至少还知道是内存问题

变成：Container killed by YARN for exceeding physical memory limits.
      Current usage: 511.3 MB of 512 MB physical memory used
      ↑ 操作系统/YARN 直接从外面杀掉进程
```

**为什么更难查**：第二种报错**完全不告诉你"堆设大了"**。
它只说"用了 511 MB 超过 512 MB"，你根本不知道多出来的那点在哪，
而 JVM 这边可能还没来得及自己 OOM 就被杀了——**连堆栈都没留下**。

> 面试可以直接讲这条：
> **"堆只是 JVM 内存的一部分，`-Xmx` 必须给堆外留出余量，否则故障会从『JVM 可控的 OOM』
> 变成『容器被 YARN 直接 kill』，而且后者的报错完全不指向真因。"**
> 能说清这个的人不多。

### 4.4 顺带解释另一个你见过的现象

`YARN 作业长时间 ACCEPTED` —— 这是**排队等资源**。
YARN 总容量只有 6144 MB / 6 vCores（3 节点 × 2048MB / 2 vCore），
每个作业要申请容器，申请不到就 ACCEPTED 等着。
**这和 JVM 无关，是调度层的排队**——但概念上和线程池的"任务进队列"是同一件事（见 04 分册）。

## 五、对象的一生：从 new 到被回收（顺序）

```
① 你写 Object o = new Object();
        ↓
② 【逃逸分析】JVM 判断：这个对象会不会逃出当前方法？
   —— 如果不会，可以做【标量替换】：不真的创建对象，
      把它拆成几个局部变量，直接在栈上用 → 省掉一次堆分配
      ⚠️ 严格说 HotSpot 不做真正的"栈上分配"，它做的是标量替换，效果接近
        ↓（如果需要真的分配）
③ 先尝试 TLAB（Thread Local Allocation Buffer）
   —— 每个线程在 Eden 里预先占一小块，避免多个线程抢同一块空间（加锁变慢）
        ↓
④ 分配在【堆的新生代 Eden 区】
        ↓
⑤ Eden 满了 → 触发 Minor GC
   —— 活着的对象复制到 Survivor 区，年龄 +1
   —— 死的对象直接清掉
        ↓
⑥ 反复几次后，年龄达到阈值（默认 15）→【晋升】到老年代
   另外两种情况也会提前晋升：
   - 大对象（超过 -XX:PretenureSizeThreshold）直接进老年代
   - Survivor 里同龄对象总和 > Survivor 空间一半 → 这些直接晋升
        ↓
⑦ 老年代也满了 → Major GC / Full GC（慢得多）
        ↓
⑧ 还是装不下 → OutOfMemoryError
```

**硬件映射**：

| 阶段 | 物理上发生什么 |
|---|---|
| ② 标量替换 | **不分配内存**，只用 CPU 寄存器/栈 → 最快 |
| ③ TLAB | 无锁分配（每个线程各用各的）→ 省掉锁竞争 |
| ⑤ Minor GC | **暂停应用线程（STW）**，CPU 扫描 Eden，把活对象**复制**到 Survivor（消耗内存带宽） |
| ⑦ Full GC | STW 时间**长得多**，扫整个堆 + 元空间 |

## 六、可跑的验证（本机 JDK 13.0.1 直接能跑）

### 6.1 看 JVM 的默认参数

```bash
java -XX:+PrintFlagsFinal -version 2>/dev/null | grep -iE "MaxHeapSize|MaxMetaspaceSize|ThreadStackSize"
```

你会看到 `MaxHeapSize` 大约是物理内存的 1/4——这是 JVM 的默认策略。

### 6.2 亲手看堆是怎么涨的

```java
// HeapWatch.java
public class HeapWatch {
  public static void main(String[] a) throws Exception {
    Runtime rt = Runtime.getRuntime();
    for (int i = 1; i <= 5; i++) {
      byte[] block = new byte[20 * 1024 * 1024]; // 每次申请 20MB
      System.out.printf("第%d次后: 已用=%dMB 最大=%dMB%n",
        i, (rt.totalMemory()-rt.freeMemory())>>20, rt.maxMemory()>>20);
      Thread.sleep(500);
    }
  }
}
```

```bash
javac HeapWatch.java && java -Xmx64m HeapWatch
```

**看什么**：`已用` 会一路涨到接近 64 MB，然后报错。
这就是"堆被吃光"的直观过程。

### 6.3 用 jstat 实时观察 GC（开两个终端）

```bash
# 终端 1：跑一个长任务
java -Xmx64m HeapWatch

# 终端 2：先查 pid，再观察（每 500ms 刷一次）
jps -l
jstat -gcutil <pid> 500
```

`jstat -gcutil` 输出各区的**使用百分比**。看到某列从 0 涨到 100 然后突然掉下来 ——
**那就是一次 GC 发生了**。

## 七、面试官会问（这一节的）

| 问题 | 答法要点 |
|---|---|
| JVM 内存分哪几块？ | 先说线程私有（计数器/虚拟机栈/本地方法栈）和线程共享（堆/元空间）两大类，再补直接内存 |
| 堆和栈的区别？ | 栈是线程私有、放方法调用和局部引用、自动回收；堆是共享、放对象、靠 GC |
| JDK 8 之后永久代去哪了？ | 被元空间取代，用的是本地内存而非堆 |
| `-Xmx` 和 `-Xms` 是什么？ | 堆的最大/初始值；生产上通常设成一样，避免运行时反复扩容 |
| 对象什么时候进入老年代？ | 年龄到阈值（默认15）、大对象直接进、Survivor 同龄对象过半 |
| **遇到过 OOM 吗？** | ★ 用你的 430 万组合案例答，见下一分册 |

## 八、术语卡

| 术语 | 一句话 |
|---|---|
| **堆 (Heap)** | 放对象实例的地方，GC 的主战场，`-Xmx` 管的就是它的最大值 |
| **栈 (Stack)** | 线程私有，一次方法调用 = 一个栈帧，方法结束自动弹出 |
| **元空间 (Metaspace)** | 类的定义信息，JDK 8+ 取代永久代，用本地内存 |
| **TLAB** | 每个线程在 Eden 里预占的小块，避免分配时加锁 |
| **逃逸分析 / 标量替换** | 对象不逃出方法时，JVM 干脆不创建对象，拆成局部变量 |
| **Minor GC** | 只回收新生代，快，但会 STW |
| **Full GC** | 回收整个堆 + 元空间，慢很多 |
| **STW (Stop The World)** | GC 时暂停所有应用线程 |
| **直接内存** | 堆外的 NIO 缓冲，不受 GC 直接管理 |
