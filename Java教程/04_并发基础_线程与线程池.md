# 04 · 并发基础 —— 线程、线程池，以及它们和 YARN 的关系

> 本份解决一件事：**"并行度 2" 到底是什么意思？为什么任务会排队？**
> 读完你应该能：说出线程池的完整工作顺序，并把它对应到 YARN 容器和 Spark executor 上。

---

## 一、先分清进程和线程

| | 进程 (Process) | 线程 (Thread) |
|---|---|---|
| 是什么 | 操作系统**分配资源**的基本单位 | CPU **调度执行**的基本单位 |
| 独有 | 独立的内存空间、文件句柄 | 自己的栈、程序计数器、寄存器 |
| 共享 | —— | **同一个进程内的线程共享堆内存** |
| 创建成本 | 高（要分配完整内存空间） | 低（只需栈和少量结构） |
| 切换成本 | 高（要换页表、刷新 TLB） | 较低（不用换内存空间） |

**硬件映射**：

```
一个 YARN 容器 = 一个（或几个）进程
   └─ JVM 进程
        ├─ 堆（所有线程共享）← 你的数据在这
        ├─ 主线程栈
        ├─ 工作线程栈 1
        ├─ 工作线程栈 2
        └─ ...
        
CPU 核数决定【真正能同时跑几个线程】
  → 你的集群 lrh-1/2/3 每个节点 2 vCore
  → 所以单节点最多真正并行 2 个线程
  → 线程数超过核数 → 靠操作系统时间片轮转"假装并行"，且要付【上下文切换】成本
```

> **上下文切换**的代价：保存当前线程的寄存器、加载下一个线程的、还可能让 CPU 缓存失效。
> 线程开太多，CPU 光切换不干活 —— 这就是"并行度不是越大越好"的物理原因。

## 二、机制：为什么需要线程池

**不用线程池**会怎样：

```
每来一个任务 → new Thread() → 跑完 → 销毁
```

代价：
- 创建/销毁线程要**系统调用**（从用户态切到内核态），不便宜
- 线程数不可控，来一万个任务就开一万条线程 → 内存爆（每条线程默认 1 MB 栈）
- 没有统一管理，出问题不知道是谁

**用线程池**：

```
提前建好 N 条线程，循环复用
新任务来了 → 丢进队列 → 空闲线程取走执行
```

> 和你在 01 分册看到的"YARN 容器复用"是**同一个思想**：
> 创建容器的成本很高，所以 Spark 要复用 executor —— 
> 只不过一个在 JVM 内（线程），一个在集群里（进程/容器）。

## 三、★ 线程池的七个参数与工作顺序（必考）

```java
new ThreadPoolExecutor(
  int corePoolSize,       // ① 核心线程数：即使空闲也保留
  int maximumPoolSize,    // ② 最大线程数：最多能扩到多少
  long keepAliveTime,     // ③ 非核心线程空闲多久后销毁
  TimeUnit unit,
  BlockingQueue<Runnable> workQueue,  // ④ 任务排队的地方
  ThreadFactory threadFactory,        // ⑤ 怎么创建线程（可以起名字）
  RejectedExecutionHandler handler    // ⑥ 满了怎么办（拒绝策略）
);
```

### 3.1 一个任务进来，按顺序发生什么

```
任务提交
   ↓
① 当前线程数 < corePoolSize ?
   ├─ 是 → 【新建一条核心线程】直接跑，结束
   └─ 否 → 继续
   ↓
② 工作队列没满 ?
   ├─ 是 → 【进队列等着】，结束
   └─ 否 → 继续
   ↓
③ 当前线程数 < maximumPoolSize ?
   ├─ 是 → 【新建一条非核心（临时）线程】来救急，结束
   └─ 否 → 继续
   ↓
④ 执行【拒绝策略】
```

> ⚠️ **最容易记错的地方**：
> 很多人以为"核心线程满了就扩到最大线程数"，**错了**。
> 正确顺序是：**核心线程 → 队列 → 才扩到最大线程**。
> 也就是说，即使你有 100 的 maxPoolSize，只要队列没满，就永远只会用 corePoolSize 条线程。

### 3.2 四种拒绝策略

| 策略 | 行为 | 适用场景 |
|---|---|---|
| `AbortPolicy`（默认） | 直接抛 `RejectedExecutionException` | 要立刻知道出问题 |
| `CallerRunsPolicy` | **让提交任务的那个线程自己去跑** | ★ 天然的"反压"：提交方变忙就不会再猛提交 |
| `DiscardPolicy` | 默默丢掉，不通知 | 允许丢任务（很少用） |
| `DiscardOldestPolicy` | 丢掉队列里最老的那个，然后重试提交 | 允许丢旧任务 |

## 四、线程安全：三个层次

### 4.1 `volatile` —— 只解决"看得见"

```java
volatile boolean running = true;
```

两个作用：
1. **可见性**：一个线程改了，其他线程**立刻能看到**（不会一直用自己缓存的旧值）
2. **禁止指令重排序**

**但不保证原子性**：
```java
volatile int count = 0;
count++;   // 这一句实际是 读 → 加1 → 写 三步，多线程下仍然会错
```

### 4.2 `synchronized` —— 加锁

```java
synchronized (lockObj) {
  count++;   // 同一时刻只有一个线程能进来
}
```

**机制**：基于对象的 monitor（监视器锁）。JDK 6 之后有**锁升级**优化：

```
无锁 → 偏向锁（只有一个线程用过）
     → 轻量级锁（有轻微竞争，用 CAS 自旋）
     → 重量级锁（竞争激烈，向操作系统申请互斥量，线程会阻塞）
```

**设计意图**：大多数锁其实根本没竞争，所以先用便宜的方案，竞争真来了才升级。

### 4.3 CAS —— 无锁

```java
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();   // 内部用 CAS，不加锁
```

**机制**：Compare And Swap，CPU 提供的一条指令：

```
我认为当前值是 A → 如果是，就改成 B；如果不是，说明别人改过了，我重试
```

**代价**：
- 竞争剧烈时**自旋重试**会白烧 CPU
- **ABA 问题**：值从 A 变成 B 又变回 A，CAS 以为没变过
  → 解决：用 `AtomicStampedReference` 带上版本号

## 五、把线程池对应到你的集群

这是本份最有用的部分 —— **它们是同一套逻辑的不同层级**。

| 线程池概念 | 对应到你的集群 |
|---|---|
| `corePoolSize` | YARN 里常驻的容器 |
| `workQueue` | **作业排队等资源**（你见过 `ACCEPTED` 卡住） |
| `maximumPoolSize` | YARN 集群总容量 **6144 MB / 6 vCores** |
| 拒绝策略 | 资源实在不够 → 排队或失败 |
| 上下文切换 | 并行度超过 CPU 核数时的损耗 |

### 5.1 你实测过的两个现象，现在能解释了

| 你见过的 | 用这套概念解释 |
|---|---|
| **YARN 作业长时间 ACCEPTED** | 申请不到容器 → 相当于"任务进了队列但没线程来取" |
| **Spark 单会话 75s、分段 381s** | 分段跑 = 每次都新建"线程池"（会话）再销毁；单会话 = 复用已有的 |

> 所以你在 02 分册里学到的"Spark 把成本从每次作业挪到每次会话"，
> 本质和这里"线程池避免反复创建线程"是**同一个模式**。
> **复用 vs 重建**，是贯穿整个大数据调优的一条主线。

## 六、可跑的验证

### 6.1 亲眼看线程池的工作顺序

```java
// PoolOrder.java —— 验证「核心 → 队列 → 最大 → 拒绝」
import java.util.concurrent.*;

public class PoolOrder {
  public static void main(String[] a) {
    ThreadPoolExecutor pool = new ThreadPoolExecutor(
      2,                                  // corePoolSize = 2
      4,                                  // maximumPoolSize = 4
      10, TimeUnit.SECONDS,
      new ArrayBlockingQueue<>(2),        // 队列只能放 2 个
      Executors.defaultThreadFactory(),
      new ThreadPoolExecutor.AbortPolicy()
    );

    for (int i = 1; i <= 7; i++) {
      final int id = i;
      try {
        pool.execute(() -> {
          System.out.println("任务" + id + " 在跑，线程数=" + pool.getPoolSize());
          try { Thread.sleep(3000); } catch (Exception e) {}
        });
        System.out.println("任务" + id + " 提交成功，队列=" + pool.getQueue().size());
      } catch (RejectedExecutionException e) {
        System.out.println("任务" + id + " ★被拒绝了");
      }
    }
    pool.shutdown();
  }
}
```

```bash
javac PoolOrder.java && java PoolOrder
```

**看什么**：
- 任务 1、2 → 立刻建核心线程（线程数变 2）
- 任务 3、4 → **进队列**（线程数还是 2！这就是最容易记错的地方）
- 任务 5、6 → 队列满了，才扩到 3、4
- 任务 7 → **被拒绝**

**亲手看到一次，这个顺序就再也忘不掉了。**

### 6.2 看线程不安全的后果

```java
// NotSafe.java —— 看看 count++ 为什么会错
public class NotSafe {
  static int count = 0;
  public static void main(String[] a) throws Exception {
    Runnable r = () -> { for (int i = 0; i < 100000; i++) count++; };
    Thread t1 = new Thread(r), t2 = new Thread(r);
    t1.start(); t2.start(); t1.join(); t2.join();
    System.out.println("期望 200000，实际 " + count);
  }
}
```

```bash
javac NotSafe.java && java NotSafe
```

**看什么**：实际值**小于** 200000（两个线程互相覆盖写入）。
然后试试把 `count` 改成 `AtomicInteger`，或者给循环加 `synchronized`，结果就对了。

## 七、面试官会问（这一节的）

| 问题 | 答法要点 |
|---|---|
| 线程池的工作顺序？ | ★ **核心线程 → 队列 → 最大线程 → 拒绝**，不是"核心满了就扩最大" |
| 队列满了会怎样？ | 先扩到 maxPoolSize，还不行才执行拒绝策略 |
| 有哪些拒绝策略？ | Abort（抛异常）/ CallerRuns（提交者自己跑）/ Discard / DiscardOldest |
| `volatile` 能保证线程安全吗？ | **不能**，只保证可见性和禁止重排序，**不保证原子性** |
| `volatile` 和 `synchronized` 区别？ | volatile 轻量、无锁、只管可见性；synchronized 互斥、保证原子性和可见性 |
| CAS 有什么问题？ | ABA 问题（加版本号解决）；竞争激烈时自旋烧 CPU |
| `synchronized` 的锁升级？ | 无锁 → 偏向锁 → 轻量级锁 → 重量级锁（JDK 6+） |
| 线程数开多少合适？ | CPU 密集型 ≈ 核数；IO 密集型可以更多。**没有银弹，要压测** |

## 八、术语卡

| 术语 | 一句话 |
|---|---|
| **上下文切换** | CPU 从一个线程切到另一个，要保存/恢复现场，有成本 |
| **核心线程** | 线程池里即使空闲也保留的线程 |
| **阻塞队列** | 任务排队的地方，满了才触发扩容 |
| **偏向锁** | 只有一个线程用过锁时，连 CAS 都省了 |
| **自旋** | 抢不到锁时不阻塞，而是循环重试（省上下文切换，但烧 CPU） |
| **CAS** | Compare And Swap，一条 CPU 指令实现的无锁原子操作 |
| **ABA** | 值从 A→B→A，CAS 误以为没变过 |
| **反压 (backpressure)** | 让上游慢下来，而不是无限堆积 |

## 九、一条主线（把前四份串起来）

你会发现整份教程在反复出现**同一个模式**：

| 场景 | 复用了什么 | 省掉了什么 |
|---|---|---|
| 线程池 | 线程 | 反复 `new Thread()` 的系统调用 |
| Spark 单会话 | executor + metastore 连接 | 每次 ~35 秒的启动开销 |
| YARN 容器复用 | 容器 | 反复申请容器的排队时间 |
| Spark executor | JVM 进程 | 反复启动 JVM 的成本 |

> **"复用 vs 重建"是大数据性能调优的第一主线。**
> 以后遇到任何性能问题，都可以先问一句：
> **"这里有没有什么东西在反复创建又销毁？"**
