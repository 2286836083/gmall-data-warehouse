# 05 · IO 与序列化 —— 数据怎么落盘、怎么跨网络

> 本份解决一件事：**shuffle 为什么慢？为什么 Spark 推荐换序列化器？**
> 读完你应该能：说出"一次磁盘读取"物理上发生了什么，以及序列化在 shuffle 里占什么位置。

---

## 一、先搞清楚一次"读文件"物理上发生了什么

你写 `file.read()` 时，背后是这样的：

```
① 你的 Java 代码调用 read()
        ↓
② 【系统调用】从用户态切换到内核态
   —— CPU 要保存现场、切换权限级别，这一步【不便宜】
        ↓
③ 操作系统向磁盘控制器发指令
        ↓
④ 磁盘按【块】读取（通常是 4 KB）
   —— 就算你只要 1 个字节，也得把整块读上来
        ↓
⑤ 数据先从磁盘进【内核缓冲区】，再从内核缓冲区【拷贝】到你的 Java 程序
   —— 这里有一次内存拷贝
        ↓
⑥ 切换回用户态，read() 返回
```

### 1.1 关键结论：缓冲为什么能快一个量级

| 不缓冲 | 用缓冲 (`BufferedInputStream`) |
|---|---|
| 读 1 字节 → 一次系统调用 | 一次性读 8 KB 到内存缓冲区，之后 8000 次"读"都在内存里完成 |
| 100 万字节 = **100 万次系统调用** | 100 万字节 ≈ **123 次系统调用** |

**硬件映射**：省掉的正是第 ② 步（用户态/内核态切换）和第 ④ 步（磁盘按块读）。

> 你项目里读 CSV 时如果没用缓冲，慢是必然的。这是最容易拿到的性能优化。

## 二、BIO 与 NIO

| | BIO（Blocking IO，阻塞式） | NIO（Non-blocking IO） |
|---|---|---|
| 模型 | **一个连接配一个线程**，`read()` 时线程干等 | 一个线程管多个连接，用 selector 轮询"谁有数据了" |
| 线程数 | 连接多 → 线程多 → 上下文切换爆炸 | 少量线程即可 |
| 适用场景 | 连接少、逻辑简单 | **高并发**（网络服务、shuffle 传输） |

**机制对比（顺序）**：

```
BIO:
  while (true) {
    Socket s = server.accept();        // 阻塞：没人来就一直等
    new Thread(() -> handle(s)).start(); // 来一个开一条线程
  }

NIO:
  Selector selector = ...;              // 一个"监视器"
  while (true) {
    selector.select();                  // 阻塞，但只阻塞这一个线程
    for (key : selector.selectedKeys()) // 谁有数据就处理谁
      handle(key);
  }
```

> **不用深挖 NIO 的 API**。大数据岗位考的是"为什么需要它"：
> 连接数上万时，BIO 的线程模型撑不住，所以要 NIO。
> Netty（Spark/Flink 的网络传输底层）就是基于 NIO 的。

## 三、序列化：把对象变成字节流

### 3.1 为什么需要它

```
内存里的对象（有引用、有结构）
        ↓ 【序列化】
字节流（一串 0 和 1）
        ↓
可以：写进磁盘 / 通过网络发给另一台机器
        ↓ 【反序列化】
另一台机器上重建出对象
```

### 3.2 ★ 为什么 shuffle 一定要序列化

Shuffle 是什么：**把数据按 key 重新分发到不同节点**。

```
节点 A 的数据  ──网络──►  节点 B
```

网络只能传**字节**，不能传"Java 对象"。所以：

```
① map 端把处理完的 (key, value) 对象【序列化】成字节
② 先【落盘】（防止内存放不下）
③ 通过网络传给对应的 reduce 节点
④ reduce 端读进来【反序列化】成对象
⑤ 才开始聚合计算
```

**硬件映射**：

| 步骤 | 物理消耗 |
|---|---|
| 序列化 | **CPU**（遍历对象、编码成字节） |
| 落盘 | **磁盘 IO** |
| 网络传输 | **网络带宽**（数据量越大越慢） |
| 反序列化 | **CPU** |

> 这就是为什么 shuffle 是 Spark 里最贵的操作之一：
> CPU + 磁盘 + 网络 **三样全占了**。

### 3.3 两种序列化器对比

| | Java 原生 `Serializable` | **Kryo** |
|---|---|---|
| 用法 | 实现 `Serializable` 接口即可 | 需注册类（也可不注册） |
| 速度 | 慢 | **快 10 倍量级** |
| 体积 | 大（带完整类名、字段信息） | **小很多** |
| 缺点 | —— | 不是所有类都能序列化；字段增删的兼容性弱 |

**Spark 里的对应配置**：

```scala
// Spark 默认是 Java 序列化器，生产上通常换成 Kryo
spark.serializer = org.apache.spark.serializer.KryoSerializer
spark.kryo.registrationRequired = true      // 强制注册，未注册会报错（更安全）
```

> ⚠️ **诚实说明**：你现在的 Spark 环境**没有启用 Kryo**（用的是默认的 Java 序列化器）。
> 这是可以马上做的一个优化实验 —— 改一个配置，测一下 shuffle 耗时变化。
> **这就是 P1 的一个现成题目。**

## 四、NIO 的零拷贝（了解即可）

传统读文件再发网络，数据要**拷贝 4 次**、切换 4 次上下文：

```
磁盘 → 内核缓冲区 → 用户缓冲区 → Socket 缓冲区 → 网卡
```

`FileChannel.transferTo()`（零拷贝）可以省掉中间步骤：

```
磁盘 → 内核缓冲区 → 网卡
```

> Kafka 之所以快，零拷贝是重要原因之一。
> 面试被问"Kafka 为什么快"时，这是一条标准答案。

## 五、可跑的验证

### 5.1 亲眼看缓冲差多少

```java
// BufferCost.java —— 对比缓冲 vs 不缓冲
import java.io.*;

public class BufferCost {
  public static void main(String[] a) throws Exception {
    // 先造一个 20MB 的测试文件
    File f = new File("test.bin");
    try (OutputStream o = new FileOutputStream(f)) {
      byte[] chunk = new byte[8192];
      for (int i = 0; i < 2560; i++) o.write(chunk);
    }
    System.out.println("测试文件: " + (f.length() >> 20) + " MB");

    // ① 不缓冲：一次读 1 字节
    long t0 = System.currentTimeMillis();
    long sum1 = 0;
    try (InputStream in = new FileInputStream(f)) {
      int b;
      while ((b = in.read()) != -1) sum1 += b;
    }
    long t1 = System.currentTimeMillis();

    // ② 缓冲：一次读 8KB
    try (InputStream in = new BufferedInputStream(new FileInputStream(f))) {
      byte[] buf = new byte[8192];
      int n;
      while ((n = in.read(buf)) != -1) { /* 处理 */ }
    }
    long t2 = System.currentTimeMillis();

    System.out.println("不缓冲: " + (t1 - t0) + " ms");
    System.out.println("带缓冲: " + (t2 - t1) + " ms");
    System.out.println("相差约 " + ((t1 - t0) / Math.max(1, (t2 - t1))) + " 倍");
    f.delete();
  }
}
```

```bash
javac BufferCost.java && java BufferCost
```

**看什么**：差距通常有**几十倍**。这就是"缓冲"的价值，看得见摸得着。

### 5.2 看序列化后的体积差多少

```java
// SerSize.java —— 看看对象序列化后有多大
import java.io.*;
import java.util.ArrayList;

public class SerSize {
  static class Evt implements Serializable {
    String userId, productId, dt;
    double price;
    Evt(String u, String p, String d, double pr) {
      userId = u; productId = p; dt = d; price = pr;
    }
  }

  public static void main(String[] a) throws Exception {
    ArrayList<Evt> list = new ArrayList<>();
    for (int i = 0; i < 100_000; i++)
      list.add(new Evt("user_" + i, "prod_" + i, "2019-10-01", 99.9));

    ByteArrayOutputStream bos = new ByteArrayOutputStream();
    try (ObjectOutputStream oos = new ObjectOutputStream(bos)) {
      oos.writeObject(list);
    }
    System.out.println("10 万条事件序列化后: " + (bos.size() >> 10) + " KB");
    System.out.println("平均每条: " + bos.size() / 100_000 + " 字节");
    System.out.println("→ 你的 ODS 有 1063 万行，按此比例约 " + (bos.size() * 106L >> 20) + " MB");
  }
}
```

```bash
javac SerSize.java && java SerSize
```

**看什么**：每条对象序列化后通常要**上百字节**，而原始 CSV 一行才几十字节。
**对象比文本膨胀很多** —— 这就是为什么大数据要用紧凑的二进制格式（Parquet/ORC）而不是存对象。

> 这条也能解释你的项目：ODS 是 1.3 GB 文本，
> 如果在内存里全变成 Java 对象，会膨胀好几倍。

## 六、面试官会问（这一节的）

| 问题 | 答法要点 |
|---|---|
| BIO / NIO / AIO 区别？ | BIO 阻塞+一个连接一线程；NIO 非阻塞+selector 多路复用 |
| 为什么需要缓冲？ | 减少系统调用次数和磁盘按块读的次数 |
| 什么是序列化？为什么需要？ | 对象 ↔ 字节流；网络传输和落盘只能处理字节 |
| Java 序列化和 Kryo 区别？ | 后者快 10 倍、体积小，但要注册类 |
| **shuffle 为什么慢？** | ★ CPU（序列化）+ 磁盘（落盘）+ 网络（传输）三样全占 |
| 零拷贝是什么？ | 减少内核态/用户态之间的数据拷贝；Kafka 快的其中一个原因 |
| Spark 怎么优化序列化？ | 配 `KryoSerializer` 并注册类 |

## 七、术语卡

| 术语 | 一句话 |
|---|---|
| **系统调用** | 用户程序请求操作系统做事，要切换权限级别，有成本 |
| **用户态 / 内核态** | CPU 的两种权限级别，切换要保存现场 |
| **缓冲区** | 内存里的一块中转区，把多次小 IO 合并成一次大 IO |
| **块 (block)** | 磁盘读写的物理最小单位（通常 4 KB） |
| **Selector** | NIO 的多路复用器，一个线程监视多个连接 |
| **零拷贝** | 跳过用户态中转，数据直接从内核缓冲区到网卡 |
| **序列化 / 反序列化** | 对象 ↔ 字节流 |
| **Shuffle** | 按 key 把数据重新分发到不同节点，最贵的操作之一 |
