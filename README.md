# gmall 电商数仓 · 离线数据仓库全链路

> 基于 REES46 真实电商行为数据（**1,063 万行 / 31 天 / 15 张源表**）的离线数仓，
> 从 ODS 到 ADS 全链路自建，含 **16 节点 DolphinScheduler 编排** 与
> **Spark / Hive 双引擎 A/B 对比**。

本项目的目的不是"跑通一个 demo"，而是**在一套资源受限的三节点集群上，把每个结论都跑到能拿数据说话**。
所以你会在这里看到失败、看到被证伪的假设、看到"改了参数之后反而更慢"的实测结果。

---

## 一、一眼看结果

| 维度 | 实测值 |
|---|---|
| 源数据 | 42,448,764 行读入 → 按用户 1/4 可复现采样 → **10,630,245 行**（25.04%） |
| 时间跨度 | 2019-10-01 ~ 2019-10-31，**31 个分区** |
| ODS 体积 | **1.3 GB** / 31 个 HDFS 文件 / 1 张表 |
| 表规模 | **30 张**（新链路 15 + 旧链路 15 对照组） |
| 全月 GMV | **57,575,996.50**（8 条计算路径收敛到同一值） |
| 成交笔数 | **186,059** |
| 端到端耗时 | Hive 链 **54 分 10 秒**（16/16 SUCCESS）；Spark 链 **14 分 46 秒**（11/11 SUCCESS） |
| 性能结论 | 单会话 Spark 比 Hive 快 **5.0×**，但每段独立起会话只快 **1.10×** |

## 二、架构

```
   REES46 原始 CSV（2019-10 电商行为）
            │
            ▼
   ┌─────────────────┐
   │ ODS  贴源层      │  ods_event_log_di          1,063 万行 / 31 分区
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ DWD  明细层      │  dwd_event_log_di          10,623,154（去重/解析/拆类目/归一空值）
   │ DIM  维度层      │  dwd_purchase_fact_di         186,059（一行一笔成交）
   │                 │  dim_product 140,665 ｜ dim_date 365
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ DWS  汇总层      │  dws_user_event_day      1,622,820（用户×天）
   │                 │  dws_product_event_day   1,265,817（商品×天）
   │                 │  dws_category_event_day      1,853（类目×天）
   │                 │  dws_trade_day                  31（天）
   └────────┬────────┘
            ▼
   ┌─────────────────┐
   │ ADS  应用层      │  6 张表，一表一业务问题（Q1~Q6）
   └────────┬────────┘
            ▼
   DolphinScheduler 工作流  │  ECharts 离线大屏（双击即开）
```

**分层是单向的**，有强制规范：应用层只消费 ADS，ADS 只读 DWS/DWD，DWS 只读 DWD/DIM，禁止跨层。
这条规范曾经被违反过（大屏直接读 DWS），后来补建 ADS 表修正，并用导出文件逐字节比对验证。

## 三、三个值得看的技术点

### 1. 一次"看着像内存不足、其实是结构不对"的调优

| 阶段 | 配置 | 结果 |
|---|---|---|
| 初次 | 容器 512 MB / `-Xmx410m` | **失败**，`GC overhead limit exceeded`，跑了 **637 秒** |
| 调整后 | 容器 1024 MB / `-Xmx820m` | **成功**，**63 秒** |

关键不是"加内存就好了"，而是判断依据：**这个作业有没有需要同时装住大量数据的结构**。
`GROUP BY product_id, dt` 产生 **430 万组合**，聚合过程要驻留内存做 hash——这类"囤数据"的作业必须放大容器；
而写入型作业边读边写，压小反而更省资源。

> 衍生教训：一套配置统一压到最小看起来整洁，实际是把"按作业类型分层"的设计抹掉了。

### 2. 双引擎对比：Spark 的收益来自会话复用，不是单条 SQL 更快

同一份 SQL、同一套资源、同一时间窗口：

| 对比方式 | Hive | Spark | 倍数 |
|---|---|---|---|
| 单会话连跑八段 | 389 s | **75 s** | **5.0×** |
| 每段各起一个会话 | 421 s | 381 s | **1.10×** |
| 同期基线复跑（B 组） | 1,099 s | **677 s** | **1.62×** |

而且**八段里有四段 Spark 反而更慢**（轻作业）。原因是会话启动开销约 **35 秒/次**。

→ 结论：Spark 把成本从"每次作业"挪到了"每次会话"。**只有作业足够重、且能复用会话时，它才划算。**

### 3. 一个"跑得对、显示全错"的生产级 bug

DolphinScheduler 画布上 16 个节点只剩 1 个，但**工作流执行完全正常**（16/16 SUCCESS、行数全对）。

根因：DS 把 `task code` 当 **JSON 数字**返回，浏览器用 JS 双精度浮点解析，只能精确到 `2^53`。
超过之后多个不同的 code 塌缩成同一个数 → DAG 只剩 1 个节点。

这个 bug 的特点是**所有自动化测试都发现不了**——数据库是 64 位整数，执行链路完全正确，只有人眼看画布才能发现。

## 四、数据里发现的三件事（不是"跑通了"，是"看出了什么"）

1. **漏斗不是三段递进，"加购"不是购买的前置环节。**
   实测 31 天里有 **15 天"购买用户数 > 加购用户数"**。第一反应是数据错了，查下去发现：
   **用户可以完全不进购物车直接下单**。所以 `cart_rate` 与 `cart_to_purchase_rate` 是两个独立指标，**不能相乘当漏斗**。

2. **空值是空串，不是 NULL。**
   `category_code` 空串占 **32.2%**，而 `IS NULL` 查出 **0 条**。用 `IS NULL` 判空会得出"数据很干净"的错误结论。

3. **类目确实有脏数据。** `category_l1` 里 `unknown` 占 **9.7%**（GMV 占比 10.9%），做类目分析必须单列或排除。

## 六、怎么确认这些数字不是编的

三个可独立验证的判据：

```sql
-- 1. ODS 行数与分区数
SELECT COUNT(*) FROM ods_event_log_di;                    -- 10,630,245
SELECT COUNT(DISTINCT dt) FROM ods_event_log_di;          -- 31

-- 2. 交易大盘（Q6）
SELECT SUM(gmv), SUM(order_cnt) FROM ads_trade_day;       -- 57,575,996.50 / 186,059

-- 3. 购买事实（DWD 一行一笔成交）
SELECT COUNT(*) FROM dwd_purchase_fact_di;                -- 186,059
```

> 注：第 3 条只陈述事实，不宣称它与 `dws_product_event_day` 的 `purchase_cnt` 严格相等——
> 两者一个是去重后的成交明细、一个是商品维度聚合，是否逐笔对齐**尚未实测验证**，故不作断言。

另有对账证据：**8 条独立计算路径的 GMV 全部收敛到同一值**；Hive 与 Spark 双引擎的 8 张表行数逐项一致、分区数 31 = 31。

## 七、已知局限（不是没做，是明确知道边界在哪）

| 局限 | 现状 | 影响 |
|---|---|---|
| **全量覆盖写入** | 每天全量重写，端到端约 54 分钟 | 数据量再涨就会顶不住；增量写入是下一步 |
| **无实时链路** | 只有 T+1 离线 | 不覆盖流式场景 |
| **数据只覆盖 31 天** | 2019-10 单月 | 做不了同环比、季节性分析 |
| **集群资源受限** | 三节点 VM，YARN 单容器上限 **2048 MB / 2 vCore** | 无法做大规模压测；很多调优实验被这个上限卡死 |
| **无订单状态** | 源数据只有 `view` / `cart` / `purchase` 三类事件 | "已支付/已取消/已退款"这类分析无法做 |
